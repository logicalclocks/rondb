RonSQL Subquery Support

RONDB-733 — Phase 7: Subquery support in the RonSQL query engine

Overview

RonSQL now supports subqueries in the WHERE clause through a multi-phase execution architecture. Inner subqueries are executed first as standalone RonSQL queries; their results are then substituted as constants or filter expressions into the outer query. Correlated subqueries are decorrelated at preparation time so they can also run as standalone queries.

Five types of subquery are currently supported:

Architecture

1. Uncorrelated Scalar Subquery

How it works

The inner SELECT returns a single value (e.g., MIN, MAX, COUNT, SUM). It is executed as a standalone query, and the result is substituted as a literal constant into the outer WHERE clause. 

-- Query as written:
SELECT l_orderkey, SUM(l_quantity), COUNT(*)
FROM lineitem
WHERE l_quantity > (SELECT MIN(l_quantity) FROM lineitem)
GROUP BY l_orderkey;

-- Inner returns: 5
-- Outer becomes:
SELECT l_orderkey, SUM(l_quantity), COUNT(*)
FROM lineitem
WHERE l_quantity > 5
GROUP BY l_orderkey;

Supported comparison operators: =, !=, >, >=, <, <=. Multiple subqueries can appear in the same WHERE clause connected by AND.

2. Uncorrelated IN Subquery

How it works

The inner query returns multiple rows. Each value is collected into a list, then substituted as an OR-chain of equality comparisons. The inner query must return a single column. A GROUP BY with an aggregate wrapper like MIN(col) can be used to produce distinct values. 

-- Query as written:
SELECT l_orderkey, SUM(l_price)
FROM lineitem
WHERE l_orderkey IN (SELECT MIN(l_orderkey)
                       FROM lineitem
                       WHERE l_quantity > 20
                       GROUP BY l_orderkey)
GROUP BY l_orderkey;

-- Inner returns: {3, 5}
-- Outer becomes:
WHERE l_orderkey = 3 OR l_orderkey = 5

A safety limit of 1000 values prevents excessive OR-chain expansion.

3. Correlated EXISTS / NOT EXISTS

How it works

Correlated EXISTS and NOT EXISTS are decorrelated at preparation time. The correlation predicate (inner.col = outer.col) is removed from the inner WHERE, and the correlation column is added to the inner SELECT and GROUP BY. The result is transformed into an IN subquery. 

-- Original EXISTS:
WHERE EXISTS (SELECT l_id FROM lineitem
              WHERE l_orderkey = o_id AND l_quantity > 20)

-- Decorrelated inner SQL:
SELECT MIN(l_orderkey) FROM lineitem
WHERE l_quantity > 20
GROUP BY l_orderkey

-- Outer becomes:
WHERE o_id IN (3, 5)

For NOT EXISTS, the same decorrelation applies but the resulting IN subquery is wrapped in T_NOT, producing a not-in filter: outer rows matching none of the inner values pass the filter.

4. Correlated Scalar Subquery with Aggregation

How it works

A correlated scalar subquery references an outer column inside the inner WHERE clause. RonSQL decorrelates it by:

1
Detect Find comparison conjuncts where one side is a subquery with a correlated inner WHERE.
2
Decorrelate Remove the correlation predicate, add the correlation column to SELECT + GROUP BY.
3
Execute Run the decorrelated inner query — produces (key, value) pairs.
4
Substitute Replace the comparison with an OR-chain of AND-pairs in the outer filter. 
-- Original query:
SELECT o_id, SUM(o_total) FROM orders
WHERE o_total > (SELECT SUM(l_price)
                  FROM lineitem
                  WHERE l_orderkey = o_id)
GROUP BY o_id;

-- Decorrelated inner (2 columns):
SELECT l_orderkey, SUM(l_price)
FROM lineitem
GROUP BY l_orderkey
-- Returns: (1,300), (2,200), (3,550), (4,200), (5,750)

-- Outer WHERE becomes:
WHERE (o_id=1 AND o_total>300)
   OR (o_id=2 AND o_total>200)
   OR (o_id=3 AND o_total>550)
   OR (o_id=4 AND o_total>200)
   OR (o_id=5 AND o_total>750)

All six comparison operators are supported. When the subquery appears on the left side of the comparison (e.g., (SELECT ...) < col), the operator is automatically flipped.

Limitations

Current constraints

  • Subqueries must appear as top-level AND conjuncts in WHERE (not inside OR).
  • Correlated subqueries support only a single correlation predicate (inner.col = outer.col).
  • IN subqueries and correlated scalar subqueries are limited to 1000 result rows.
  • Subquery inner queries must be single-table (no inner joins).
  • Inner queries currently require an aggregate function (e.g., MIN, SUM) — plain projection queries are not yet supported (Step 45).
  • NULL values in subquery results are skipped (comparison with NULL is always false).
  • Subqueries in HAVING clause are parsed but follow the same execution pipeline.
