2. Change 1: process startup

Two calls in a new file, process_setup.cc, invoked as the first statement of main() after the signal handlers and before start_fs_cache() creates the first thread (today that happens at main.cc:263, before the config is even parsed), plus one allocation change in the JSON parser. The startup code lives in its own file because main.cc differs heavily between 26.02 and 26.10 and a one-line call merges cleanly.

3. Change 4: a limit on operations per batch

This is listed before the buffer design because it is independent of it and small.

Today nothing bounds the number of operations in a batch. The request body is capped at 1 MiB, which still allows about 17 000 minimal operations. BatchMaxSize, which reads like a cap, is the number of operations sent to NDB per execution loop at pkr_operation.cpp:1295, and the request is parsed and buffered in full before that loop runs. The Go server rejected batches above BatchMaxSize; rdrs2 lost that check.

4. Change 2: buffers

This section is the complete buffer design. It explains how buffers are used today, the proposal with one rule per subsection and an example each, how large a buffer must be and why that differs between 26.02 and 26.10, what it saves, and the code changes.

4.1 The problem in one example

A batch read of three rows, each 200 bytes, arrives at rdrs2. The server takes one request buffer and one response buffer from its pools. With the default configuration those are 2 MiB and 10 MiB. The batch uses about 1 KB of the request buffer and about 1 KB of the response buffer, holds both until the JSON has been sent, and returns them. For the lifetime of that HTTP request, 12 MiB of memory was reserved to carry 2 KB of data.

With 64 worker threads, 64 such HTTP requests in flight hold 768 MiB. The pool never frees buffers, so the peak stays allocated. On a 500 MiB pod this is the single largest reason traffic can push rdrs2 past its limit.

The buffers are this large for one reason: rdrs2 does not know in advance how big a row will be, and a row can contain a blob. So every operation is promised the whole configured size, and the configured size is set to the largest row anyone wants to return, 5 MiB by default.

The fix is to let a value that does not fit continue into the next buffer. Then the buffer only has to be large enough for the part of a row that is bounded, and blobs can be any size.

4.2 How buffers are used today

4.2.1 One operation

A single primary key read writes one operation request into a request buffer and gets one response back in a response buffer. Each response starts with a 36-byte header of nine 4-byte words. Every address inside a response is an offset from the start of that response, not from the start of the buffer. That is what lets many responses be packed into one buffer.

4.2.2 A batch

A batch takes one request buffer and one response buffer and packs the operation requests and the responses one after another. The controller keeps a heap-side array with one entry per operation that records where that operation's response starts. Nothing about the batch is written inside the buffers.

Operations are only started in the lower half of a buffer. Once the write position passes the halfway mark, the next operation goes into a fresh buffer from the pool, and the buffer that filled up records which operation opened the new one. That link is the chain. When the HTTP request finishes, release walks the chain from entry 0 and returns every buffer.

4.2.3 Why a response buffer is 10 MiB

When an operation starts, it is told how much it may write: the space left in its buffer, which the halfway rule keeps at 5 MiB or more. Every value is appended with a capacity check, and a blob is checked against the whole remaining space before the first byte is read. If a value does not fit, the batch fails with "Response buffer overflow". Nothing ever continues into another buffer.

So the configured RespBufferSize is the largest row rdrs2 can return, and the buffer is twice that so the promise survives packing. The number 5 MiB has no documented origin; it came from the first Go server in 2024 and was carried over. Request buffers follow the same rule with ReqBufferSize, 1 MiB doubled to 2 MiB.

Example, today

A batch of 2 000 reads of 200-byte rows needs about 800 KB of response space. It takes one response buffer, fills it to about 800 KB, and holds 10 MiB. A second batch with one 6 MiB blob fails, because 6 MiB is more than the 5 MiB promise, even though 10 MiB are allocated.

4.3 The proposal

Make buffers small. Keep each response's fixed header and fixed data part in one buffer, exactly as today. Let the blob part continue into the next buffer of the chain. Five rules, each with an example.

4.3.1 Rule 1: a response's fixed part stays in one buffer

An operation's header, column table and every bounded value are written into one buffer, its home. The reader resolves them from one base pointer, exactly as today. Nothing changes for integers, dates, decimals, strings, or binary columns.

Example

A feature store row with 40 columns and 30 KB of data has a fixed part of about 31 KB: 36 bytes of header, 644 bytes of column table, and the values as text with terminators. It lands in one buffer, whole.

4.3.2 Rule 2: a start reserve instead of the halfway mark

Before placing an operation, the writer checks how much of the current buffer is free. If less than the start reserve is free, the operation starts in a fresh buffer. The reserve is the largest fixed part any operation can have, a compile-time constant explained in section 4.4. With that, rule 1 (4.3.1) holds without doubling the buffer.

Example, 26.02 limits

Response buffer 512 KiB, reserve 185 KiB. Operations may start while less than 327 KiB are used. A batch of 200-byte rows starts about 800 operations in one buffer before moving to the next. A batch of 30 KB rows starts 11. The worst possible row, 185 KiB of fixed part, starts at 0 and a second one starts right after it at 185 KiB.

On the request side the writer knows more than the reserve: the encoder computes each operation's upper bound before writing (section 4.6, create_native_request), and the chain is handed that bound. An operation starts in a fresh buffer when less than the larger of the reserve and its own bound is free. This is what keeps a lowered StartReserveOverride harmless for requests, where there is no rule 5 retry: the pool test's 4 KiB reserve would otherwise let a third column-less operation (106 KiB of name reservation) be placed in the 48 KiB left behind two others and be refused with 400.

4.3.3 Rule 3: blob and text values spill

A blob is read from NDB in 32 KiB chunks and copied into the response, as today. When a chunk does not fit, the writer copies the part that fits, fills the buffer to its last byte, takes the next buffer from the pool, links it to the chain, and continues at offset 0. Continuation buffers have no header. The blob's column table entry is the same four words as today: its length, and an address. The address is an offset in the response's virtual stream: the home buffer's bytes first, then that response's continuation buffers in chain order. A first blob therefore has a home-buffer offset as today; a second blob in the same row, which starts inside a continuation buffer, has an offset past the home buffer's end. Values written before the blobs keep plain home offsets, so nothing changes for them.

TEXT columns take the same path with one difference. Today the Text branch stages the raw bytes in the response buffer and then converts them to utf8mb4, trims and JSON-escapes them into a new string before appending. The conversion works on whole characters, so the escaped output, not the raw bytes, is what spills. The implementation stages the raw TEXT in the request's arena, runs the existing conversion and escaping, and writes the escaped result through the same write-with-spill primitive the Blob branch uses. The transient cost is the TEXT length in the arena plus the three temporary copies the conversion already makes today, about five times the value for a few milliseconds; a streaming converter that avoids the staging copy is a later refinement.

The reader is handed the buffer chain and the operation index. It notices that address plus length runs past the end of the home buffer and builds a segment list: the tail of the home buffer, then whole buffers along the chain, until the length is consumed. Base64 encoding of a segmented value is a loop with one encoder state, and the bundled libbase64 already has that streaming API.

Example

Figure 3: a 10 MiB blob with 512 KiB buffers. 502 KiB fit behind the fixed part in buffer 1. Nineteen full buffers follow. The last 10 KiB land in buffer 21. The chain holds 21 buffers for the lifetime of the HTTP request and returns them together.

4.3.4 Rule 4: blobs are written last

Today the writer walks the read columns in request order and writes each value inline. If a blob sat in the middle of the row and spilled, every column after it would land in a continuation buffer and rule 1 (4.3.1) would break. Writing blobs first is worse: the fixed part would then follow the blob into whatever buffer it ended in, so the header would be in one buffer and the values in another.

Writing blobs last costs almost nothing. The column table stores an address per value, so physical order and table order are independent. The writer makes two passes over the read columns, bounded columns first, then blob and text columns. Table entries are filled by column index instead of by write count, so entry i still matches request column i and the reader is untouched.

4.3.5 Rule 5: a retry, so the start reserve is a heuristic and not a promise

The start reserve is computed from limits and code paths. If it is ever wrong, the result must still be right. So if an operation overflows its buffer and did not start at offset 0, the writer takes a fresh buffer and writes that operation again from offset 0, where it has the whole buffer. The row is already in the NDB record; this is a second formatting pass, not a second read. The writer records an overflow flag whenever a capacity check fails, so the retry decision does not depend on matching error text. Only an operation whose fixed part is larger than a whole buffer fails, with the same error as today. Since the buffer size is computed from the same limits, that can only mean the expansion constant is wrong, which is a code fix and not a configuration change.

Example

Suppose a future column type expands text eight times instead of six, and a row's fixed part is 240 KiB where the start reserve expected at most 185 KiB. The operation starts at offset 300 KiB of a 512 KiB buffer, overflows at 512 KiB, is retried at offset 0 of a fresh buffer, and succeeds. Packing lost one partly used buffer. Correctness lost nothing.

4.4 How large must a buffer be? The home buffer question

Rule 1 only works if the largest possible fixed part fits in a buffer with room to spare. This section computes that largest fixed part from the limits in the code, shows that it changes between 26.02 and 26.10, and makes the code derive it rather than carry a number.

4.4.1 What is in a fixed part, and how much it can grow

The response stores every value as text with a terminator. Numbers, dates and decimals expand a little. Character columns expand a lot, in two steps that both happen inside the response buffer: CHAR and VARCHAR values are converted to utf8mb4, then JSON-escaped. Binary values are copied raw; their base64 happens later, outside the pool.

So the worst row is one made entirely of control characters in single-byte VARCHAR columns, which expands six times. Nobody stores that, but the writer must not corrupt memory if someone does, and the retry in rule 5 (4.3.5) covers the case where even this estimate is wrong.

4.4.4 Derive every size from the limits at compile time

rdrs_const.h computes the minimum buffer, the start reserve and the default buffer from the same kernel limits the data node uses. The code never contains a byte count.

constexpr Uint32 MAX_ROW_BYTES      = MAX_TUPLE_SIZE_IN_WORDS * 4;
constexpr Uint32 MAX_TEXT_EXPANSION = 6;   // utf8mb4 conversion, then \u00xx escaping

constexpr Uint32 MIN_RESP_BUFFER =
    PK_RESP_HEADER_END + 4 + MAX_ATTRIBUTES_IN_TABLE * 16
  + MAX_ROW_BYTES * MAX_TEXT_EXPANSION + MAX_ATTRIBUTES_IN_TABLE;

constexpr Uint32 MIN_REQ_BUFFER =
    PK_REQ_HEADER_END + 2 * (MAX_ATTR_NAME_SIZE + 1) + 256
  + MAX_ATTRIBUTES_IN_INDEX * (8 + MAX_ATTR_NAME_SIZE + 1) + MAX_KEY_SIZE_IN_WORDS * 4
  + 17 + MAX_ATTRIBUTES_IN_TABLE * (1 + MAX_ATTR_NAME_SIZE + 2);

constexpr Uint32 RESP_START_RESERVE      = MIN_RESP_BUFFER;
constexpr Uint32 REQ_START_RESERVE       = MIN_REQ_BUFFER;
constexpr Uint32 DEFAULT_RESP_BUFFER = next_pow2(2 * MIN_RESP_BUFFER);  // the buffer size; not a setting
constexpr Uint32 DEFAULT_REQ_BUFFER  = next_pow2(2 * MIN_REQ_BUFFER);

static_assert(DEFAULT_RESP_BUFFER >= 2 * MIN_RESP_BUFFER);
static_assert(DEFAULT_REQ_BUFFER  >= 2 * MIN_REQ_BUFFER);

The implementation adds two terms the formulas above leave out, the status message (256 bytes) and the operation id, which is a config value bounded by a new PROBLEM check, and uses the corrected column-name reservation from section 4.6. The minimums then evaluate to about 193 KiB and 116 KiB on 26.02; the defaults are unchanged at 512 KiB and 256 KiB.

Neither size is user configurable. RespBufferSize today is the only knob that sets the largest row rdrs2 can return, which is the one reason anyone touches it; with spilling that reason is gone, and every other value a user could choose is worse than the computed one. The same holds for ReqBufferSize: an operation request has no blobs and its maximum follows from the limits. So both keys are removed, the server uses DEFAULT_RESP_BUFFER and DEFAULT_REQ_BUFFER, and a new --print-limits flag prints the computed values (print-config is generated from the settings and cannot print a non-setting). Because rdrs2 rejects unknown config keys at startup, the two old keys are still accepted and ignored with a warning for one release so a hand-written config keeps working, then dropped. 5. Change 3: pool ceiling, idle shrink, stats

Change 2 makes each buffer small. This change bounds how many there are and gives surplus back. All of it lives in buffer_manager.hpp plus one timer.

itemdecision
initialisation and allocationThe pool's global gets a trivial constructor and an explicit init() called from main() once the config is loaded (today it is built before main() from compiled-in defaults). Buffers are allocated with mmap and freed with munmap, so shrink returns pages to the kernel without depending on glibc's mmap threshold.
Internal.BufferPoolSharePercentDefault 50. At startup rdrs2 reads the memory limit it runs under, cgroup v2 memory.max, else cgroup v1 memory.limit_in_bytes, else physical RAM, and sets the pool budget to this share of it. The buffer cap is then budget divided by the computed size of one pair, applied to each pool. A 500 MiB pod gets about 330 pairs on 26.02 sizes, a 10 GiB pod about 6 800, with nothing to configure. The other half of the pod is left for the parse buffers, the per-request arenas, the NDB API and the process itself.
Internal.MaxBuffersOverride. Default 0, meaning use the derived cap. A non-zero value replaces it for operators who want an explicit count. get_req_buffer and get_resp_buffer return failure once buffersCount reaches the cap; the two getNext functions in encoding.cpp propagate that and the controller answers HTTP 503 with "buffer pool exhausted". --print-limits shows the cap in effect and the limit it was derived from.
Internal.BufferShrinkAfterSDefault 60. Each pool records the last time its free list was empty or below PreAllocatedBuffers. A shrink call runs from the probe server's existing timer loop (probe_server.cpp:379), and from a one-second Drogon loop timer when probes are disabled, since the probe server only exists when ProbeEnable is true: if the free count exceeds PreAllocatedBuffers and the quiet period has passed, the surplus is taken off the free list under the pool mutex and munmap'ed outside it, down to PreAllocatedBuffers. In-flight buffers are not in the free vector and are never touched.
statsget_req_buffers_stats returns the response stats today (copy-paste at buffer_manager.hpp:152) and nothing calls either. Fixed, and exported through metrics.cpp as new metric families only, names to be agreed in section 10.4: per pool in_use, free, peak, allocated, and counters for rejected, retry (change 2 rule 5) and shrunk. A third family, rdrs_limits, exposes the computed numbers (max columns, max row bytes, request and response buffer bytes, operations per batch, buffer cap, memory limit, start reserve) so the test suite reads the limits from /metrics on whichever branch it runs. No existing metric changes.
never freed beforeBuffers were only ever returned to the free vector. Shrink is the first code that deletes one, so the destructor logic and the stats must agree; the pool accounting test in section 8 checks that.

  • rdrs.disableTransparentHugePages, default true: the perl prctl wrapper in front of rdrs2. Already drafted as an uncommitted change on top of chart 26.2.21. Stays harmless once rdrs2 makes the call itself.
  • rdrs.internal with the rdrs2 names, each rendered only when set so older images do not reject the key: PreAllocatedBuffers, MaxBuffers, BufferShrinkAfterS, MaxOperationsPerBatch, NumThreads. No buffer size keys, because change 2 computes them.

7.1 Pod-level worst case: 64 batches of 512 operations at once

The operation limit bounds one batch; the pod is bounded by the cap, not by the thread count. With 64 HTTP requests in flight, each a 512-operation batch, request buffers alone are:

64 batches of 512 operations26.0226.10
typical, columns named, about 300 B per operation10 MiB10 MiB
worst, no columns named, column-name reservation per operation3.1 GiB24 GiB
responses on top, if every read returns a widest row+ 5.8 GiB+ 15 GiB

No pod holds the worst case and the design does not try to. The first batches take buffers up to the pool budget and the rest get 503 until buffers return: a 503 storm under abuse, no OOM kill, and full service for the typical case, which a 500 MiB pod holds many times over. On 26.10 the worst case is dominated by the 780 KiB column-name reservation per operation; that is the deferred refinement in section 10.1 and this is the scenario where it would pay off.

The idle figures after the change are derived from the measured breakdown (parse buffers, arenas, stacks, pool) and need the measurement in section 8 to confirm them.

8. Tests

rdrs2 has three test layers and all three are used: C++ unit tests in server/test on gtest, the Go integration suite in server/test_go, which the MTR test rdrs2-golang_gotest runs against the suite's servers (every Go package is discovered automatically), and MTR tests in the rdrs2-golang suite that start rdrs2 with their own config where a test needs a small pool or a lowered start reserve. Every new line of code is reached by at least one test below, and every test that depends on a limit reads it from the rdrs_limits family on /metrics. That is what makes the same test file exercise 512 columns on 26.02 and 4 096 columns on 26.10 without edits.

9. Branch plan

9.1 Implement on 26.02

One pull request from branch RONDB-1144 against 26.02-main, built as four commits in this order so review can follow one change at a time and the rdrs2-golang suite is green after each: startup (change 1), batch limit (change 4), pool (change 3, with the constants header), buffers (change 2). The chart change is a separate pull request in rondb-helm, paired with the release that carries this one.

9.2 Merge to 26.10

The intent is that no size and no test needs retyping, and that every place where 26.10 needs an edit fails to compile rather than silently keeping the old behaviour. What makes that true:

  • No size literal in the code. Every buffer size, reserve and minimum is a constexpr over MAX_ATTRIBUTES_IN_TABLE, MAX_TUPLE_SIZE_IN_WORDS, MAX_ATTR_NAME_SIZE, MAX_ATTRIBUTES_IN_INDEX and MAX_KEY_SIZE_IN_WORDS. On 26.10 they evaluate to 1 MiB response and 2 MiB request buffers without anyone typing them.
  • No size literal in the tests. The Go and MTR tests build their widest tables from rdrs_limits, so widest_row_fits_home_buffer runs 4 095 columns on 26.10 by itself.
  • The static_asserts fail the build if a future limit outgrows what the pool can allocate, so a limit increase is caught at compile time and not at the first wide read.
  • The stale MAX_TUPLE_SIZE_IN_BYTES on 26.10, which today rejects legal rows above 30 004 bytes, is replaced by the derived expression and disappears in the merge.
  • 26.10 has code paths that do not exist on 26.02: batch write and delete controllers, pk_batch_base_operation.cpp with its own halfway rule, and a batch_parse_impl shared by read, write and delete. They call functions this change removes or re-signs (the getNext buffer helpers, release_array_buffers, create_native_request, process_pkread_response, pk_batch_read, the PKRResponse constructor), so the merge fails to compile at exactly those spots and they get the same rule. The operation-limit check moves into batch_parse_impl at the merge.
  • No config file can carry a stale size across the merge, because sizes are not settings.

What should be verified on 26.10 after the merge: the listed spots compile again with the new rule, the build passes the static_asserts, --print-limits shows 4096, 72000, 1 MiB and 2 MiB, and the full suite is green with no test edited. The only planned 26.10-specific follow-up is the column-name reservation from the dictionary, which lowers the request buffer there from 2 MiB to about 512 KiB; it is a refinement and not a requirement.

10. What is left

10.1 Deliberately out of scope for this round

  • Column-name reservation from the dictionary. Would cut the 26.10 request buffer from 2 MiB to about 512 KiB, but it moves the reservation from create_native_request to create_response and complicates the request encoder. Not needed for correctness on either branch. Deferred.
  • NumThreads derived from the CPU limit. Not doing it. The chart exposes NumThreads so it can be set per deployment; the default stays 64.
  • A cap on the JSON arena per HTTP request. The arena grows with the response and is released per request. It is bounded indirectly by MaxBuffers and MaxOperationsPerBatch. Out of scope; too many changes already.

10.2 Correction: scan reads do not use the pool

An earlier draft listed scans as sharing the pool design. They do not. scan_read_ctrl.cpp builds its response in a RapidJSON string buffer reserved at ScanRespBufferSize, 256 KiB, per request (scan_read_ctrl.cpp:220) plus an arena, and never calls the buffer manager. Nothing in this document touches scans, and ScanRespBufferSize stays a setting.

10.3 Decided: the buffer cap follows the pod's memory

A fixed count is wrong for one of the two pod sizes we run: 256 pairs is generous on a 500 MiB pod and far too small for a 10 GiB pod serving a high workload. So the default cap is derived from the memory limit at startup, as change 3 describes: half of the pod for the pools, divided by the size of one pair. The pool grows on a bigger pod without anyone touching a setting, and MaxBuffers remains as an explicit override.

pod limitpool budget at 50%pairs, 26.02 sizes (768 KiB)pairs, 26.10 sizes (3 MiB)
500 MiB250 MiB≈ 330≈ 83
2 GiB1 GiB≈ 1 360≈ 340
10 GiB5 GiB≈ 6 800≈ 1 700

What this is not: it is not a runtime watchdog that reads memory usage on every request. That was part of the earlier broad design and stays in the backlog. One read of the limit at startup is about twenty lines, has no per-request cost, and gives the scaling that matters. If a pod is resized, rdrs2 restarts anyway.

Tests: a unit test for the derivation with injected limit values and both cgroup layouts, and the MTR check that --print-limits shows the cap and the limit it came from. The pool_cap_returns_503 test sets MaxBuffers explicitly so it does not depend on the test host's memory.

10.4 To be discussed before PR 3: metric names

No existing metric is renamed, relabelled or removed. The customer's HPA reads rdrs_endpoints_response_status_count and rdrs_endpoints_response_time_summary, and dashboards read the other three existing families, http_request_duration_seconds, rdrs_http_connection_count, rdrs_rondb_connection_state and rdrs_rondb_total_ndb_objects. All stay exactly as they are. The pool metrics are new families only, proposed as one gauge family rdrs_buffer_pool with labels pool=request|response and state=in_use|free|peak|allocated, and one counter family rdrs_buffer_pool_events with labels pool and event=rejected|retry|shrunk. The names are a proposal for discussion; whatever is chosen, additive only.
