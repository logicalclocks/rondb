Multi-Leaf Aggregation & Continuation Queries

Exploring the next evolution of pushdown join aggregation in RonDB

1. Current Architecture: Single Aggregate Leaf

Today, RonDB pushdown join aggregation uses a linear chain query tree with exactly one aggregate leaf. The scan root produces rows, intermediate lookup/scan nodes join related tables, and the leaf node runs the AggInterpreter to compute GROUP BY, COUNT, SUM, etc.

Current: Single aggregate leaf — linear chain

  ┌─────────────┐     ┌─────────────┐     ┌─────────────────────┐
  │ dept (scan)  │────▶│ emp (lookup)│────▶│ task (lookup)       │
  │ root        │     │ LEFT JOIN   │     │ LEFT JOIN           │
  │             │     │             │     │ T_AGGREGATE_LEAF    │
  │             │     │             │     │ AggInterpreter:     │
  │             │     │             │     │  GROUP BY dept.name │
  │             │     │             │     │  COUNT(*), SUM(hrs) │
  └─────────────┘     └─────────────┘     └─────────────────────┘

  Signal flow:
  SCAN_FRAGREQ ──▶ LQHKEYREQ ──▶ LQHKEYREQ ──▶ AggInterpreter
                                                       │
  JOIN_AGG_COMPLETE_REQ ◀──────────────────────────────┘
       │
       ▼
  TRANSID_AI (aggregated results) ──▶ NDB API ──▶ Application
Figure 1: Single-leaf aggregation — all results flow through one AggInterpreter

The JOIN_AGG_COMPLETE_REQ signal triggers DblqhProxy to merge per-thread results, finalize (compute AVG from SUM/COUNT, etc.), and send aggregated rows via TRANSID_AI back to the DBTC/DBSPJ coordinator, which forwards them to the NDB API.

2. Query 1: Sibling Aggregations (Independent Tables)

SQL E-commerce: Revenue and Shipping Cost per Store

SELECT s.store_name,
       SUM(o.revenue)   AS total_revenue,     -- aggregate over orders
       SUM(sh.cost)     AS shipping_cost       -- aggregate over shipments
FROM store s
LEFT JOIN orders o    ON o.store_id = s.id
LEFT JOIN shipment sh ON sh.store_id = s.id
GROUP BY s.store_name

Why This Needs Multiple Leaves

Orders and shipments are independent siblings — a store's shipments are not children of its orders. With a single aggregate leaf, you'd have to pick one table as the leaf and somehow fold the other table's aggregation into it. This creates a cross-product problem: if a store has 10 orders and 5 shipments, a naive join produces 50 rows, inflating both SUM(revenue) and SUM(cost) by the other table's fan-out.

Multi-leaf: two independent aggregations on sibling branches

                   ┌──────────────────────────┐
                   │ store (scan, root)       │
                   │                          │
                   └────────┬─────────────────┘
                      ┌─────┴──────┐
                      ▼            ▼
         ┌──────────────────┐  ┌──────────────────┐
         │ orders (lookup)   │  │ shipment (lookup) │
         │ LEFT JOIN        │  │ LEFT JOIN         │
         │ AGG LEAF 1       │  │ AGG LEAF 2        │
         │ SUM(revenue)     │  │ SUM(cost)         │
         └──────────────────┘  └──────────────────┘
Figure 2: Sibling aggregate leaves — each independently aggregates against the root

Real-World Value

This pattern is extremely common in reporting and analytics:

  • Financial dashboards: Revenue vs. expenses per department (different source tables)
  • Inventory systems: Units received vs. units shipped per warehouse
  • SaaS metrics: Active users vs. support tickets per account
  • IoT/monitoring: Sensor readings vs. alert counts per device

Today these require two separate queries or a UNION ALL with post-processing. With multi-leaf aggregation, the data nodes compute both sums in a single scan pass over the root table.

3. Query 2: Multi-Level Aggregation (Different Granularity)

SQL HR Report: Headcount and Total Task Hours per Department

SELECT d.dept_name,
       COUNT(DISTINCT e.id)  AS headcount,      -- aggregate at emp level
       SUM(t.hours)           AS total_hours     -- aggregate at task level
FROM department d
LEFT JOIN employee e ON e.dept_id = d.id
LEFT JOIN task t     ON t.emp_id = e.id
GROUP BY d.dept_name

The Fan-Out Problem

With the current single leaf at the task level, each employee appears once per task. An employee with 5 tasks is counted 5 times in COUNT(e.id). COUNT(DISTINCT) solves this in SQL, but the AggInterpreter doesn't currently support DISTINCT — it would need to maintain a per-group set of seen values, which is expensive.

Multi-level: aggregation at two different depths in the join chain

  ┌─────────────────┐     ┌─────────────────────┐     ┌──────────────────┐
  │ department      │────▶│ employee            │────▶│ task             │
  │ (scan, root)    │     │ (lookup, LEFT JOIN)  │     │ (lookup, LEFT)   │
  │                 │     │ AGG LEAF 1           │     │ AGG LEAF 2       │
  │                 │     │ COUNT(e.id)          │     │ SUM(t.hours)     │
  └─────────────────┘     └─────────────────────┘     └──────────────────┘

  Leaf 1 aggregates at the employee level (no fan-out from tasks).
  Leaf 2 aggregates at the task level (full fan-out, but only SUM).
  Results are combined per GROUP BY key at finalization.
Figure 3: Multi-level aggregation — COUNT at employee level, SUM at task level

Real-World Value

Multi-level aggregation at different granularity is a fundamental SQL pattern:

  • Order analytics: COUNT(DISTINCT customers) + SUM(line_item_total) — customer count at order level, revenue at line-item level
  • Content platforms: COUNT(DISTINCT authors) + SUM(view_count) — author count at article level, views at page-view level
  • Supply chain: COUNT(DISTINCT suppliers) + SUM(part_quantity) — supplier count at purchase-order level, quantities at line-item level

By aggregating at the natural level of each metric, the data node avoids the cross-product inflation entirely — no DISTINCT tracking needed.

4. Query 3: Correlated Subqueries with Independent Aggregation

SQL Product Catalog: Rating and Sales Summary

SELECT p.product_name,
       (SELECT AVG(r.score) FROM review r WHERE r.product_id = p.id)   AS avg_rating,
       (SELECT SUM(s.qty)   FROM sale s   WHERE s.product_id = p.id)   AS total_sold,
       (SELECT COUNT(*)     FROM returns t WHERE t.product_id = p.id)  AS return_count
FROM product p
WHERE p.category = 'Electronics'

Decorrelation into Multi-Leaf

RonSQL currently decorrelates correlated subqueries into separate pushdown queries. Each subquery runs independently, and the results are joined client-side. With multi-leaf aggregation, all three subqueries could be decorrelated into sibling branches of a single query tree:

Three correlated subqueries → three aggregate leaves in one tree

                        ┌───────────────────────┐
                        │ product (scan, root)  │
                        │ WHERE category =      │
                        │   'Electronics'        │
                        └────────┬──────────────┘
                   ┌─────────────┼─────────────┐
                   ▼             ▼             ▼
         ┌──────────────┐ ┌──────────────┐ ┌──────────────┐
         │ review       │ │ sale         │ │ returns      │
         │ LEFT JOIN    │ │ LEFT JOIN    │ │ LEFT JOIN    │
         │ AGG LEAF 1   │ │ AGG LEAF 2   │ │ AGG LEAF 3   │
         │ AVG(score)   │ │ SUM(qty)     │ │ COUNT(*)     │
         └──────────────┘ └──────────────┘ └──────────────┘
Figure 4: Three correlated subqueries as sibling aggregate leaves

Real-World Value

Correlated scalar subqueries with aggregation are pervasive in application queries:

  • Product pages: Average rating + review count + sales count in one query
  • User profiles: Post count + follower count + total likes
  • Account summaries: Balance + transaction count + pending transfer sum

Today each subquery is a separate round-trip. Multi-leaf aggregation reduces this to one scan pass over the driving table, with sibling lookups fanning out to each related table independently.

5. Continuation Queries: Feeding Results Back Into the Data Nodes

A more ambitious idea: instead of sending aggregated results back to the NDB API for consumption or further processing, feed the results directly into another query stage within the data nodes. This is the concept of a continuation query.

The Problem with Current Result Flow

Current: results always exit to the NDB API

  ┌─────────┐   JOIN_AGG_COMPLETE_REQ   ┌──────────┐
  │  DBSPJ  │ ─────────────────────────▶│ DblqhProxy│
  │         │                           │ (merge)  │
  └─────────┘                           └────┬─────┘
                                              │ TRANSID_AI
                                              ▼
  ┌─────────┐   TRANSID_AI              ┌──────────┐
  │ NDB API │ ◀─────────────────────────│  DBTC    │
  │ (client)│                           │          │
  └────┬────┘                           └──────────┘
       │
       ▼   Round-trip to API
  Application processes results
  (possibly sends another query)
Figure 5: Current flow — results always leave the data nodes

For multi-stage analytics (e.g., "aggregate, then join with another table, then aggregate again"), this means:

  1. First aggregation runs inside data nodes
  2. Results travel to the API over the network
  3. API sends a new query with the results as input
  4. Second aggregation runs inside data nodes
  5. Results travel back to the API again

Each round-trip adds latency and network overhead. For analytical workloads with chained aggregations, this can dominate execution time.

The Continuation Query Concept

Instead of sending TRANSID_AI results to the API, the JOIN_AGG_COMPLETE_REQ handler could redirect results into a new query stage that runs within the same data node:

Continuation: results feed into the next query stage

  ┌─────────┐  JOIN_AGG_COMPLETE_REQ  ┌──────────────┐
  │  DBSPJ  │ ──────────────────────▶ │  DblqhProxy  │
  │ (stage 1│                         │  (merge)     │
  │  query) │                         └──────┬───────┘
  └─────────┘                                │
                                             │  Instead of TRANSID_AI to API:
                                             │  Feed rows into stage 2
                                             ▼
                                    ┌──────────────────┐
                                    │ Continuation      │
                                    │ Stage 2 query:   │
                                    │ JOIN / SCAN /    │
                                    │ AGGREGATE        │
                                    └────────┬─────────┘
                                             │
                                             ▼
                                    Results to API (or stage 3...)
Figure 6: Continuation query — results stay inside the data nodes

Concrete Example: TPC-H Q11 Pattern

SQL Aggregate, then filter by aggregate threshold

-- TPC-H Q11 pattern: "important stock identification"
SELECT ps.partkey, SUM(ps.supplycost * ps.availqty) AS value
FROM partsupp ps
JOIN supplier s ON s.suppkey = ps.suppkey
JOIN nation n   ON n.nationkey = s.nationkey
WHERE n.name = 'GERMANY'
GROUP BY ps.partkey
HAVING SUM(ps.supplycost * ps.availqty) >
       (SELECT SUM(ps2.supplycost * ps2.availqty) * 0.0001
        FROM partsupp ps2
        JOIN supplier s2 ON s2.suppkey = ps2.suppkey
        JOIN nation n2   ON n2.nationkey = s2.nationkey
        WHERE n2.name = 'GERMANY')
ORDER BY value DESC

This query has two stages:

  1. Stage 1: Aggregate SUM(supplycost * availqty) grouped by partkey
  2. Stage 2: Filter results where value exceeds the threshold (which is itself an aggregate)
TPC-H Q11: Two-stage query with HAVING threshold from a second aggregation

Stage 1a — Per-part value aggregation:

  ┌─────────────────┐     ┌─────────────────┐     ┌─────────────────┐
  │ partsupp        │────▶│ supplier        │────▶│ nation          │
  │ (scan, root)    │     │ (lookup, INNER)  │     │ (lookup, INNER) │
  │                 │     │                  │     │ WHERE name =    │
  │                 │     │                  │     │   'GERMANY'     │
  │                 │     │                  │     │ AGG LEAF        │
  │                 │     │                  │     │ GROUP BY partkey│
  │                 │     │                  │     │ SUM(cost*qty)   │
  └─────────────────┘     └─────────────────┘     └─────────────────┘

  Results: {partkey, value}
        │
        │  Continuation (no API round-trip)
        ▼

Stage 1b — Total value (for threshold computation):

  Same tree structure, but GROUP BY is empty (scalar aggregate):
  SUM(supplycost * availqty) → single row: {total_value}

Stage 2 — Filter + sort:

  "virtual scan" over Stage 1a results
    WHERE value > total_value * 0.0001
    ORDER BY value DESC

  Final results → API
Figure 5b: TPC-H Q11 — two aggregation stages feeding into a filter

With continuation queries, stage 1's aggregated results could feed directly into a stage 2 filter/scan without leaving the data nodes.

6. Implementation Architecture for Continuation Queries

Option A: TRANSID_AI Redirect

SIGNAL FLOW Redirect TRANSID_AI to another DBSPJ query

The simplest approach: modify continueJoinAggSend() in DblqhMain.cpp to send TRANSID_AI to a continuation DBSPJ instance instead of the original DBTC coordinator.

// Current: send to DBTC/API
sendSignal(state->m_resultRef, GSN_TRANSID_AI, ...);

// Continuation: send to a pre-registered stage 2 DBSPJ
if (state->m_continuationRef != RNIL) {
    sendSignal(state->m_continuationRef, GSN_TRANSID_AI, ...);
} else {
    sendSignal(state->m_resultRef, GSN_TRANSID_AI, ...);
}

Pros: Minimal protocol changes. Reuses existing TRANSID_AI handling.
Cons: Stage 2 DBSPJ must be set up before stage 1 completes. Requires careful transaction coordination.

Detailed Signal Flow (Option A)

1. DBTC sets up both stages:
   JOIN_AGG_SETUP_REQ (stage 1, aggStateKey=1)
   JOIN_AGG_SETUP_REQ (stage 2, aggStateKey=2)

2. DBSPJ executes stage 1 query tree:
   SCAN_FRAGREQ → LQHKEYREQ chain → AggInterpreter (key=1)

3. Stage 1 completes:
   JOIN_AGG_COMPLETE_REQ (aggStateKey=1, continuationRef=stage2_spj)
     → DblqhProxy merges per-thread results
     → continueJoinAggSend() sends TRANSID_AI to stage 2 DBSPJ
       (instead of DBTC/API)

4. Stage 2 DBSPJ receives TRANSID_AI as "scan rows":
   Treats incoming rows as if they came from a scan root
     → triggers child lookups for each row
     → feeds results to stage 2 AggInterpreter (key=2)

5. Stage 2 completes normally:
   JOIN_AGG_COMPLETE_REQ (aggStateKey=2, continuationRef=RNIL)
     → Results sent to API via normal path

Option B: Materialized Intermediate Table

SIGNAL FLOW Write results to a transient NDB table, then scan it

After JOIN_AGG_COMPLETE, write aggregated rows into a temporary NDB table within the data node. Stage 2 then scans this table as its root.

Stage 1 completes:
  JOIN_AGG_COMPLETE_REQ → merge → finalize
    → INSERT rows into temp_agg_results table
    → JOIN_AGG_COMPLETE_CONF (with temp table reference)

Stage 2 begins:
  SCAN_TABREQ on temp_agg_results
    → JOIN with other tables
    → AGGREGATE (optional)
    → Results to API

Cleanup:
  DROP temp_agg_results (or auto-expire after transaction)

Pros: Clean separation between stages. Stage 2 is a normal query — no special coordination. Temp table can be scanned by multiple stage 2 queries.
Cons: Write amplification (results written to disk/memory, then re-read). Temporary table management overhead. Data distribution — aggregated results from different data nodes need to be accessible.

Detailed Signal Flow (Option B)

1. DBTC sets up stage 1 + temp table metadata:
   JOIN_AGG_SETUP_REQ (stage 1, aggStateKey=1)
   CREATE temp_agg_t1 (PK = GROUP BY cols, VALUE = agg results)

2. Stage 1 executes and completes:
   JOIN_AGG_COMPLETE_REQ (aggStateKey=1)
     → DblqhProxy merges → finalize
     → INSERT each group into temp_agg_t1
       (N inserts for N groups — uses LQHKEYREQ internally)

3. Stage 2 is a completely standard SPJ query:
   SCAN_TABREQ on temp_agg_t1 (or another table with temp as child)
     → SCAN_FRAGREQ → LQHKEYREQ chain → AggInterpreter
     → No awareness that data came from a previous aggregation

4. Cleanup:
   DROP temp_agg_t1 (or auto-expire with transaction)

Option C: In-Memory Pipeline (Zero-Copy)

DESIGN Direct memory handoff between query stages

The most efficient but most complex approach: the AggInterpreter's finalized result buffer is passed directly as the input row source for a stage 2 scan/lookup operation, without serializing to TRANSID_AI or writing to a table.

Stage 1 AggInterpreter completes:
  gb_map contains: {group_key → [agg_result_1, agg_result_2, ...]}

Stage 2 receives a "virtual scan" over the gb_map:
  for each (key, value) in gb_map:
      construct RowPtr from key + value columns
      → feed to stage 2 lookup_parent_row / scanFrag_parent_row
      → stage 2 join + aggregate as normal

Result: zero network hops, zero serialization between stages

Pros: Maximum performance — no serialization, no network, no temporary storage. Results stay in L1/L2 cache.
Cons: Requires new "virtual scan" abstraction in DBSPJ. Tightly couples the AggInterpreter's output format with DBSPJ's input format. Complex lifecycle management (stage 1 state must be kept alive until stage 2 completes).

Detailed Signal Flow (Option C)

1. DBTC sets up both stages as a pipeline:
   JOIN_AGG_PIPELINE_SETUP_REQ:
     stage 1: aggStateKey=1, query tree = [partsupp→supplier→nation]
     stage 2: aggStateKey=2, query tree = [virtual_scan→part lookup]
     pipeline: stage1.output → stage2.root_input

2. Stage 1 executes and completes:
   JOIN_AGG_COMPLETE_REQ (aggStateKey=1, pipeline_mode=true)
     → DblqhProxy merges → finalize
     → gb_map is NOT deallocated — kept alive for stage 2

3. Stage 2 begins — "virtual scan" over gb_map:
   for each (key, value) in stage1.gb_map:
     construct RowPtr {partkey, total_value}
       → feed to stage 2 DBSPJ as if from SCAN_FRAGREQ
       → stage 2 child lookups execute normally
       → results → stage 2 AggInterpreter (key=2)

4. Stage 2 completes:
   JOIN_AGG_COMPLETE_REQ (aggStateKey=2)
     → Results to API
     → Release stage 1 gb_map memory

7. Signal Protocol for Continuation

Regardless of which implementation option is chosen, the signal protocol needs extension to express "this query's output feeds into another query."

New Signals

Signal Direction Purpose
JOIN_AGG_CONTINUE_REQ DBSPJ → DblqhProxy After COMPLETE, instead of sending results to API, feed them into a continuation query identified by a stage 2 aggStateKey or query reference
JOIN_AGG_CONTINUE_CONF DblqhProxy → DBSPJ Stage 2 has received all rows from stage 1 and has begun execution
JOIN_AGG_PIPELINE_SETUP_REQ DBTC → DblqhProxy Set up a multi-stage pipeline: allocate all stages' AggInterpreters and wire their output→input connections

Modified JOIN_AGG_COMPLETE_REQ

The existing JOIN_AGG_COMPLETE_REQ could be extended with a continuationRef field:

// JoinAggCompleteReq — extended for continuation
struct JoinAggCompleteReq {
    Uint32 senderRef;
    Uint32 senderData;
    Uint32 requestId;
    Uint32 aggStateKey;
    Uint32 maxBatchRows;
    Uint32 continuationRef;    // RNIL = send to API (current behavior)
    Uint32 continuationData;   // stage 2 query identifier
};

When continuationRef != RNIL, continueJoinAggSend() sends TRANSID_AI to the continuation target instead of the original result receiver. The continuation target (a DBSPJ instance or a direct DBLQH scan) processes the rows as if they came from a normal scan.

8. Comparison of Approaches

Aspect Option A: Redirect Option B: Temp Table Option C: Pipeline
Complexity Low Medium High
Network hops 0 (same node) 0 (same node) 0 (same node)
Serialization TRANSID_AI format NDB row format (write+read) None (zero-copy)
Storage overhead None Temp table on disk/memory None
Multi-stage (3+) Chain redirects Chain temp tables Chain pipelines
Cross-node results Needs routing Table handles distribution Node-local only
Error handling Abort stage 2 Drop temp table Complex lifecycle
Reuse of results Single consumer Multiple consumers Single consumer

Recommendation

Option A (TRANSID_AI redirect) is the pragmatic first step. It reuses the existing signal infrastructure, requires minimal protocol changes, and delivers the core benefit (no API round-trip). Option C is the long-term ideal but requires significant new abstractions. Option B is useful when the intermediate results need to be accessed by multiple subsequent queries (e.g., self-join on aggregated data).

A reasonable evolution path:

  1. Implement Option A for single-consumer continuations
  2. Add Option B for multi-consumer scenarios (temp tables already partially supported in NDB)
  3. Investigate Option C for performance-critical analytical pipelines

9. Putting It Together: Multi-Stage Analytical Query

Combining multi-leaf aggregation with continuation queries enables complex analytical patterns in a single data-node execution:

Example: "Top departments by profit margin, with headcount"

Stage 1 — Multi-leaf aggregation:

  department (scan)
    ├── employee (LEFT, leaf 1: COUNT → headcount)
    └── transaction (LEFT, leaf 2: SUM(revenue) - SUM(cost) → profit)

  Results: {dept_id, headcount, profit}
        │
        │  Continuation (no API round-trip)
        ▼

Stage 2 — Filter + sort:

  "virtual scan" over stage 1 results
    WHERE profit > 0
    ORDER BY profit / headcount DESC
    LIMIT 10

  Final results → API: top 10 departments by profit-per-employee
Figure 7: Multi-stage pipeline — two aggregate leaves feeding into a continuation filter
Detailed query tree for the multi-stage example:

Stage 1 — Multi-leaf aggregation (two leaves, one scan root):

                   ┌──────────────────────────┐
                   │ department (scan, root)  │
                   │ T_AGGREGATE_ANCESTOR     │
                   └────────┬─────────────────┘
                      ┌─────┴──────┐
                      ▼            ▼
         ┌──────────────────┐  ┌──────────────────────┐
         │ employee (lookup) │  │ transaction (lookup)  │
         │ LEFT JOIN        │  │ LEFT JOIN             │
         │ AGG LEAF 1       │  │ AGG LEAF 2            │
         │ GROUP BY dept_id │  │ GROUP BY dept_id      │
         │ COUNT(e.id)      │  │ SUM(revenue)          │
         │  → headcount     │  │ SUM(cost) → profit    │
         └──────────────────┘  └──────────────────────┘

  Merged results: {dept_id, headcount, profit}
         │
         │  Continuation → Stage 2
         ▼

Stage 2 — Filter, compute, sort (no table access needed):

  ┌──────────────────────────────────────────────┐
  │ "virtual scan" over Stage 1 merged results   │
  │                                              │
  │  WHERE profit > 0                            │
  │  Compute: profit_per_head = profit/headcount │
  │  ORDER BY profit_per_head DESC               │
  │  LIMIT 10                                    │
  └──────────────────────────────────────────────┘

  Final: top 10 depts by profit-per-employee → API
Figure 8: Detailed query tree — multi-leaf stage 1 feeds into continuation stage 2

Without these features, this query requires:

  1. Query 1: COUNT employees per department → API
  2. Query 2: SUM revenue and cost per department → API
  3. Client-side join of results
  4. Client-side computation of profit margin
  5. Client-side sort and LIMIT

With multi-leaf + continuation: one query, zero round-trips, all computation inside the data nodes.

10. Non-Root Continuation: Aggregated Results as a Child Node

The examples so far assume stage 1 results become the scan root of stage 2. But a more powerful (and common) pattern is when the aggregated results feed into stage 2 as a child lookup node — the root of stage 2 is a different table.

Motivating Query: Supplier Cost Analysis with Part Details

SQL Enrich aggregated results by joining with a master table

-- Stage 1: Aggregate supplier costs per part (for German suppliers)
SELECT ps.partkey, SUM(ps.supplycost * ps.availqty) AS total_value
FROM partsupp ps
JOIN supplier s ON s.suppkey = ps.suppkey
JOIN nation n   ON n.nationkey = s.nationkey
WHERE n.name = 'GERMANY'
GROUP BY ps.partkey

-- Stage 2: Join with part master table for enrichment + second aggregation
SELECT p.type,
       COUNT(*)              AS part_count,
       SUM(agg.total_value)  AS type_total_value,
       AVG(p.retailprice)    AS avg_retail
FROM part p
JOIN [stage1_results] agg ON agg.partkey = p.partkey
GROUP BY p.type
ORDER BY type_total_value DESC

Stage 2 scans the part table as its root and joins with stage 1's aggregated results as a child lookup node. This is fundamentally different from the root-continuation case: stage 2's root drives the iteration, and stage 1 results are looked up on demand.

Stage 1 — Aggregation query:

  ┌─────────────────┐     ┌─────────────────┐     ┌─────────────────┐
  │ partsupp        │────▶│ supplier        │────▶│ nation          │
  │ (scan, root)    │     │ (lookup, INNER)  │     │ (lookup, INNER) │
  │                 │     │                  │     │ WHERE name =    │
  │                 │     │                  │     │   'GERMANY'     │
  │                 │     │                  │     │ AGG LEAF        │
  │                 │     │                  │     │ GROUP BY partkey│
  │                 │     │                  │     │ SUM(cost*qty)   │
  └─────────────────┘     └─────────────────┘     └─────────────────┘

  Results: {partkey, total_value}  ──────────────────────┐
                                                        │
                                                        │ Continuation
                                                        │ (non-root child)
                                                        ▼
Stage 2 — Enrichment + re-aggregation:

  ┌──────────────────┐     ┌──────────────────────────┐
  │ part (scan, root) │────▶│ [stage1 results]        │
  │ T_AGG_ANCESTOR   │     │ (lookup by partkey)      │
  │                  │     │ INNER JOIN               │
  │                  │     │ AGG LEAF                 │
  │                  │     │ GROUP BY p.type           │
  │                  │     │ COUNT(*), SUM(total_value)│
  │                  │     │ AVG(p.retailprice)        │
  └──────────────────┘     └──────────────────────────┘

  Final: {type, part_count, type_total_value, avg_retail} → API
Figure 9: Non-root continuation — stage 1 results used as a child lookup in stage 2

Why Non-Root Position Is Harder

When stage 1 results feed in at the root, stage 2 simply iterates them sequentially (like a scan). When they feed in as a child, stage 2's root performs a scan of a real table, and for each root row, stage 2 needs to look up a matching row in the stage 1 results by key. This is a fundamentally different access pattern.

  • Root position: sequential iteration over results (scan-like)
  • Child position: random-access lookup by key into results (hash-like)

How Each Option Handles Non-Root Continuation

Option A: TRANSID_AI Redirect — Challenging at Non-Root

SIGNAL FLOW Redirect doesn't naturally support child-position access

TRANSID_AI redirect works well when stage 2's root consumes the stream sequentially. But when stage 1 results are a child node, stage 2 needs to look up specific keys in stage 1's output as each root row arrives. TRANSID_AI is a push-based stream — there's no way for stage 2 to "pull" a specific row by key.

Possible workaround: Buffer all stage 1 TRANSID_AI rows into a hash map indexed by partkey on the receiving side. When stage 2's root row arrives, look up the hash map. This effectively becomes a materialized hash join:

// Stage 2's DBSPJ receives stage 1 results via TRANSID_AI redirect
// Buffer into hash map keyed by partkey
HashMap<Uint32, AggRow> stage1_results;

// Stage 2 root (part scan) drives iteration
for each part_row from SCAN_FRAGREQ:
    lookup key = part_row.partkey
    if (stage1_results.contains(key)):
        // Join and feed to stage 2's AggInterpreter
        combined = merge(part_row, stage1_results[key])
        handleJoinAggRow(combined)

Pros: Reuses TRANSID_AI infrastructure.
Cons: Stage 1 must complete before stage 2's scan begins (blocking). Requires allocating a hash map in DBSPJ for buffering, which may be large. Essentially reimplements hash join inside DBSPJ.

Option B: Materialized Temp Table — Natural Fit

SIGNAL FLOW Temp table makes child-position access trivial

This is where temp tables shine. Stage 1 results are written to a temporary NDB table with partkey as the primary key. Stage 2's child node simply does a normal LQHKEYREQ lookup into this table — no special handling needed at all.

Stage 1 completes:
  JOIN_AGG_COMPLETE_REQ → merge → finalize
    → INSERT INTO temp_stage1(partkey, total_value) VALUES (...)
    → temp table has partkey as primary key

Stage 2 query tree (normal SPJ query):
  Node 0: SCAN part (root)
  Node 1: LOOKUP temp_stage1 ON partkey = part.partkey  ← normal lookup!
           (INNER JOIN, AGG LEAF)

→ No special DBSPJ changes for the child node — it's just a table lookup

Pros: Stage 2 is a completely standard SPJ query. No new abstractions needed. Works with any tree topology — the temp table can appear at any position (root, child, grandchild). NDB's existing distribution handles multi-node cases.
Cons: Write amplification. Temp table DDL overhead. Need to ensure the temp table is on the same data node for locality.

Option C: In-Memory Pipeline — Virtual Lookup

DESIGN Direct lookup into the AggInterpreter's group-by hash map

The most elegant solution: stage 2's child node performs a virtual lookup directly into stage 1's gb_map. The gb_map is already a hash map keyed by GROUP BY columns — the lookup is essentially free.

Stage 1 AggInterpreter's internal state after finalization:
  gb_map = {
    partkey=17  → {total_value: 45230},
    partkey=42  → {total_value: 89100},
    partkey=99  → {total_value: 12500},
    ...
  }

Stage 2 child node "virtual lookup":
for each part_row from root scan:
    key = part_row.partkey
    result = gb_map.lookup(key)     // O(1) hash lookup
    if (result != nullptr):
        // INNER JOIN: combine and continue
        combined = merge(part_row, result)
        handleJoinAggRow(combined)  // → Stage 2 AggInterpreter
    else:
        // No match — INNER JOIN filters this row out
        // (or inject null for LEFT JOIN)

Pros: Zero-copy, zero-serialization. The gb_map is already a hash table — no new data structure needed. Cache-friendly: both stage 1 results and the lookup are in the same L1/L2 cache context. O(1) per lookup.
Cons: Requires a "virtual lookup" abstraction in DBSPJ that replaces LQHKEYREQ with an in-memory hash probe. Stage 1's gb_map lifetime must extend until stage 2 completes. Only works when stage 1 and stage 2 run on the same LDM thread (node-local only).

Non-Root Continuation: Comparison

Aspect Option A: Redirect Option B: Temp Table Option C: Pipeline
Child-position access Requires hash buffer Normal LQHKEYREQ gb_map.lookup()
Stage ordering Stage 1 must finish first Stage 1 must finish first Can overlap (probe on demand)
Memory overhead Hash buffer in DBSPJ Temp table storage None (reuse gb_map)
Multi-node support Complex routing NDB distribution Node-local only
Code complexity Medium (hash buffer) Low (standard query) High (virtual lookup)

Key insight for non-root continuation: Option B (temp table) is the strongest choice because the child node becomes a standard table lookup requiring zero changes to DBSPJ's query execution. Option C is optimal for single-node deployments where the gb_map is already in cache. Option A is the weakest fit because it must buffer and index the entire stage 1 result set before stage 2 can begin — effectively recreating what Option B does with less infrastructure support.

Real-World Queries at Non-Root Position

Non-root continuation is actually the more common pattern in practice, because most analytical queries aggregate first and then enrich:

  • Sales dashboard: Aggregate daily sales per product → JOIN with product catalog for names, categories, images
  • User analytics: Aggregate events per user → JOIN with user profile for demographics, region, tier
  • Financial reporting: Aggregate transactions per account → JOIN with account master for account type, branch, manager
  • Log analysis: Aggregate error counts per service → JOIN with service registry for team owner, SLA tier

In all these cases, the aggregation produces a smaller result set (grouped keys) that then gets enriched by joining with a master/dimension table. The aggregated results naturally appear as a child lookup in the enrichment query, not as the scan root.
