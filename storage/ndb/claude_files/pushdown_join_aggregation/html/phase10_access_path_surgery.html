RONDB-733 Phase 10: AccessPath Surgery for Pushed Join Aggregation

This document explains how MySQL's query optimizer builds AccessPath trees for aggregate queries, and how RonDB's aggregation pushdown modifies those trees to route aggregate computation to NDB data nodes instead of the MySQL server.

1. Background: What Is Aggregation Pushdown?

In a standard MySQL query like: 

SELECT t1.grp, SUM(t3.amount), COUNT(*)
FROM t1 JOIN t2 ON t2.pk = t1.pk
         JOIN t3 ON t3.pk = t2.pk
GROUP BY t1.grp;

MySQL normally fetches every matching row from the storage engine, then computes SUM and COUNT itself using its aggregate iterators. With aggregation pushdown, the NDB data nodes compute the aggregates directly, returning only the grouped summary rows (e.g., 3 rows for groups A/B/C instead of all 8 individual rows). This dramatically reduces network traffic and CPU work at the MySQL server.

RonDB implements this via the NdbAggregator program, which is attached to a pushed join query. The data node's DBLQH block runs the aggregation engine (AggInterpreter) on the leaf rows of the join, and DBSPJ coordinates sending grouped results back to the API.

Phase 10 extended this to 3+ way joins (e.g., t1 → t2 → t3). The NDB data node side already worked for multi-table joins. The challenge was entirely in the MySQL server's AccessPath tree surgery.

2. How the MySQL Query Optimizer Builds Aggregate AccessPaths

MySQL's optimizer represents the physical execution plan as a tree of AccessPath nodes. Each node corresponds to an iterator that produces rows. For our 3-way join aggregate query, the optimizer produces one of two tree shapes depending on whether ORDER BY / LIMIT is present:

Simple GROUP BY (no ORDER BY)

AGGREGATE
  ├─ NESTED_LOOP_JOIN
  ├   ├─ NESTED_LOOP_JOIN
  ├   ├   ├─ TABLE_SCAN (t1)
  ├   ├   └─ EQ_REF (t2)
  ├   └─ EQ_REF (t3)

GROUP BY + ORDER BY + LIMIT

SORT
  ├─ LIMIT_OFFSET
  ├   ├─ TEMPTABLE_AGGREGATE
  ├   ├   ├─ TABLE_SCAN (temp table)
  ├   ├   └─ subquery: AGGREGATE
  ├   ├       └─ NESTED_LOOP_JOIN
  ├   ├           ├─ NESTED_LOOP_JOIN
  ├   ├           ├   ├─ TABLE_SCAN (t1)
  ├   ├           ├   └─ EQ_REF (t2)
  ├   ├           └─ EQ_REF (t3)

The optimizer chooses TEMPTABLE_AGGREGATE when it needs to materialize aggregate results into a temporary table so that upstream operators (SORT, LIMIT, HAVING) can operate on concrete stored rows.

3. The AGGREGATE Iterator

The AGGREGATE AccessPath creates an AggregateIterator that implements the standard aggregation algorithm: 

// Pseudocode for AggregateIterator::Read()
while (child->Read() == 0) {
    // For each input row, accumulate into Item_sum objects
    for (each Item_sum *func) {
        func->add();  // reads from the record buffer
    }
    if (group_changed) {
        return 0;  // Emit the completed group
    }
}
Key point: Item_sum::add() reads column values from MySQL's record buffer (the TABLE::record[0] memory area). It assumes the storage engine has placed individual row data there via setResultRowRef().

4. The TEMPTABLE_AGGREGATE Iterator

TEMPTABLE_AGGREGATE wraps an AGGREGATE subquery and materializes its results into a temporary table. This is needed when the result set must be sorted, limited, or re-scanned. Its execution flow is: 

// Pseudocode for TemptableAggregateIterator::Init()
while (subquery->Read() == 0) {     // Read rows from the AGGREGATE child
    if (new_group) {
        init_tmptable_sum_functions();   // calls reset_field() on each Item_sum
        INSERT into temp table;
    } else {
        update_tmptable_sum_functions(); // calls update_field() on each Item_sum
        UPDATE temp table row;
    }
}

// TemptableAggregateIterator::Read() then scans the temp table
return table_scan->Read();  // returns materialized aggregate rows

The critical methods involved:

Method Called When Purpose
reset_field() First row of a new group Store the initial aggregate value into result_field (temp table column)
update_field() Subsequent rows of same group Accumulate the value into the existing result_field

5. The Problem: Why Surgery Is Needed

When aggregation is pushed to NDB, each row returned by the storage engine is already a complete aggregate result for one group. The data node has already computed SUM, COUNT, MIN, MAX — the MySQL server just needs to pass them through.

However, the AccessPath tree still contains the standard aggregate iterators. Without modification, here's what goes wrong:

Problem 1 — AGGREGATE re-aggregates: The AGGREGATE iterator calls Item_sum::add(), which tries to read individual column values from TABLE::record[0]. But with pushed aggregation, no individual field values exist in the record buffer — each row IS the aggregate result, delivered via set_pushed_value_int() on the Item_sum objects. The add() calls produce garbage.
Problem 2 — TEMPTABLE_AGGREGATE must stay: Simply removing TEMPTABLE_AGGREGATE (as was tried during development) breaks ORDER BY and LIMIT queries. The SORT iterator above it needs materialized rows in a temp table to sort. Without the temp table, Sort uses "addon fields" that read from the record buffer, but pushed aggregate values live on Item_sum objects, not in any record buffer. This caused ORDER BY queries to show duplicate rows with the last group's values.

6. The AccessPath Surgery

The solution, implemented in fixup_pushed_access_paths() (ha_ndbcluster.cc), handles the two AccessPath types differently:

Case 1: Standalone AGGREGATE

When AGGREGATE appears without a wrapping TEMPTABLE_AGGREGATE (simple GROUP BY, no ORDER BY/LIMIT), we remove it entirely, replacing it with the root table scan:

Before Surgery

AGGREGATE
  └─ NESTED_LOOP_JOIN
      ├─ NESTED_LOOP_JOIN
      ├   ├─ TABLE_SCAN (t1)
      ├   └─ EQ_REF (t2)  ← pushed child
      └─ EQ_REF (t3)  ← pushed child

After Surgery

TABLE_SCAN (t1)

  AGGREGATE removed — would re-aggregate.
  NLJs removed — pushed children don't
  produce individual rows at MySQL level.
  Only the root table scan remains.

case AccessPath::AGGREGATE: {
  if (has_pushed_aggregation) {
    // Remove AGGREGATE — it would re-aggregate from record buffer.
    // Replace with the NLJ-stripped child (root table scan).
    AccessPath *child =
        strip_pushed_child_nljs(subpath->aggregate().child);
    *subpath = *child;
    return false;  // Re-walk the replaced node
  }
  break;
}

Returning false tells the walker to re-visit the node (which is now the TABLE_SCAN) so that any TABLE-level fixups still apply.

Case 2: TEMPTABLE_AGGREGATE

When TEMPTABLE_AGGREGATE wraps an AGGREGATE (queries with ORDER BY / LIMIT), we keep TEMPTABLE_AGGREGATE but gut its subquery, removing the inner AGGREGATE and the NLJs:

Before Surgery

SORT
  └─ TEMPTABLE_AGGREGATE
      ├─ TABLE_SCAN (temp)
      └─ subquery: AGGREGATE
          └─ NESTED_LOOP_JOIN
              ├─ NESTED_LOOP_JOIN
              ├   ├─ TABLE_SCAN (t1)
              ├   └─ EQ_REF (t2)
              └─ EQ_REF (t3)

After Surgery

SORT
  └─ TEMPTABLE_AGGREGATE
      ├─ TABLE_SCAN (temp)
      └─ subquery: TABLE_SCAN (t1)

  TEMPTABLE_AGGREGATE stays — Sort needs it.
  Inner AGGREGATE removed — no re-aggregation.
  NLJs removed — pushed children handled by NDB.
  reset_field() stores pushed values into temp table.

case AccessPath::TEMPTABLE_AGGREGATE: {
  if (has_pushed_aggregation) {
    // Keep TEMPTABLE_AGGREGATE — materializes results for SORT/LIMIT.
    // Remove the inner AGGREGATE and strip pushed-join-child NLJs.
    AccessPath *sub = subpath->temptable_aggregate().subquery_path;
    if (sub->type == AccessPath::AGGREGATE) {
      sub = sub->aggregate().child;
    }
    sub = strip_pushed_child_nljs(sub);
    subpath->temptable_aggregate().subquery_path = sub;
    return true;  // Don't walk children — we handled the subquery
  }
  break;
}

Returning true stops the walker from descending further — we've already rewritten the subquery path ourselves.

7. strip_pushed_child_nljs(): Removing Pushed Join Children

In a pushed join, tables t2 and t3 are "pushed children" — their rows are fetched by the NDB data node as part of the pushed join, not by MySQL iterators. The NESTED_LOOP_JOIN nodes for these children must be stripped because their inner side produces no rows at the MySQL level. 

// ha_ndbcluster_push_agg.cc
AccessPath *strip_pushed_child_nljs(AccessPath *path) {
  while (path->type == AccessPath::NESTED_LOOP_JOIN) {
    const TABLE *inner_table =
        GetBasicTable(path->nested_loop_join().inner);
    if (inner_table != nullptr &&
        inner_table->file->member_of_pushed_join() != nullptr &&
        inner_table->file->member_of_pushed_join() != inner_table) {
      // Inner side is a pushed-join child (not the root) — strip this NLJ
      path = path->nested_loop_join().outer;
    } else {
      break;
    }
  }
  return path;
}

The function walks iteratively (not recursively) because NLJs nest linearly for PK-lookup chains. Each iteration peels one pushed child from the outermost NLJ, following the outer pointer until it reaches the root TABLE_SCAN:

NLJ (inner=t3, pushed child) ➡ follow outer └─ outer: NLJ (inner=t2, pushed child) ➡ follow outer └─ outer: TABLE_SCAN (t1, root) ➡ return this

The check member_of_pushed_join() != inner_table distinguishes pushed children from the pushed join root. The root table's member_of_pushed_join() returns a pointer to its own table, while children return a pointer to the root.

8. Item_sum Modifications: Bridging Pushed Values to Temp Tables

After surgery, the TEMPTABLE_AGGREGATE's subquery is a bare TABLE_SCAN. When this scan reads a row, the pushed aggregate values are available on the Item_sum objects via m_pushed_value_int / m_pushed_value_double, set by the handler's ndb_fetch_next_aggregate_row().

TEMPTABLE_AGGREGATE calls reset_field() to store these values into the temp table. But the original reset_field() implementations try to read from the record buffer or call val_*() on child expressions — which don't have the right data. We need to intercept and store the pushed values directly:

Item_sum_sum::reset_field()

void Item_sum_sum::reset_field() {
  if (m_pushed_aggregate) {
    if (m_pushed_null) {
      result_field->set_null();
    } else {
      result_field->set_notnull();
      if (hybrid_type == DECIMAL_RESULT) {
        my_decimal dec;
        int2my_decimal(E_DEC_FATAL_ERROR, m_pushed_value_int, false, &dec);
        result_field->store_decimal(&dec);
      } else {
        float8store(result_field->field_ptr(), m_pushed_value_double);
      }
    }
    return;
  }
  // ... original code for non-pushed path ...
}

Item_sum_count::reset_field()

void Item_sum_count::reset_field() {
  if (m_pushed_aggregate) {
    int8store(result_field->field_ptr(), m_pushed_value_int);
    return;
  }
  // ... original code ...
}

Item_sum_hybrid::reset_field() (MIN/MAX)

void Item_sum_hybrid::reset_field() {
  if (m_pushed_aggregate) {
    if (m_pushed_null) {
      result_field->set_null();
    } else {
      result_field->set_notnull();
      result_field->store(m_pushed_value_int, unsigned_flag);
    }
    return;
  }
  // ... original switch on hybrid_type ...
}

update_field() — No-Op Guards

Each pushed row is a complete, distinct aggregate group. The TEMPTABLE_AGGREGATE iterator should never encounter a duplicate group key, so update_field() should not be called. A defensive guard is added anyway: 

void Item_sum_sum::update_field() {
  if (m_pushed_aggregate) return;  // Already the correct aggregate result
  // ... original code ...
}

The same guard is added to Item_sum_count::update_field() and Item_sum_hybrid::update_field().

9. The val_decimal() Fix: Why SUM Returned Zero

During development, all tests passed except SUM always returned 0. The root cause was subtle:

For SUM on INT columns, MySQL internally uses hybrid_type == DECIMAL_RESULT. When the output pipeline formats the result, it calls Item_sum_sum::val_decimal(), not val_int().

The pushed aggregate check had been added to val_int() and val_real(), but val_decimal() was missed. It fell through to the original code which read from uninitialised decimal buffers, producing zero: 

my_decimal *Item_sum_sum::val_decimal(my_decimal *val) {
  // THIS CHECK WAS MISSING — causing SUM to return 0
  if (m_pushed_aggregate) {
    null_value = m_pushed_null;
    if (null_value) return nullptr;
    int2my_decimal(E_DEC_FATAL_ERROR, m_pushed_value_int, false, val);
    return val;
  }
  // ... original decimal/real handling ...
}

The fix converts the pushed integer value to a my_decimal via int2my_decimal(), matching how MySQL stores SUM results internally.

The complete data flow with pushed aggregation:

1. NDB data nodes compute aggregates (SUM, COUNT, MIN, MAX per group) 2. Simple GROUP BY (AGGREGATE removed): TABLE_SCAN → handler returns pushed rows directly Item_sum::val_int() / val_decimal() reads m_pushed_value_int 4b.
