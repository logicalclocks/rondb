1. High-Level Overview

Pushdown Join Aggregation allows queries like SELECT region, SUM(amount) FROM orders JOIN customers ON ... GROUP BY region to execute the aggregation inside the NDB data nodes rather than transferring millions of intermediate join rows back to the MySQL server or API application for aggregation.

Before this feature, NDB could push down multi-table joins (SPJ — Select-Project-Join) so that child-table lookups happen inside the data nodes. But the final aggregation (GROUP BY + SUM/COUNT/MIN/MAX) always happened at the API, requiring all intermediate rows to be transferred over the network. For analytical queries over large datasets, this network transfer dominated query time.

Key Insight: By aggregating at the leaf table's LDM thread — where the join rows are already assembled — we send only the aggregated group results (typically a few rows) instead of millions of intermediate rows. For TPC-H Q12 on a 1GB dataset, this reduces network transfer from ~600K rows to just 2 group rows.

The feature spans four major subsystems:

  • DBLQH/DBTUP — The aggregation engine: receives rows, groups them, computes aggregates, manages memory
  • DBTC/DBSPJ — The coordinator: orchestrates setup, routes aggregation programs, triggers completion
  • NDB API — Client-side: builds aggregation programs, sends them with queries, receives results
  • MySQL Handler — SQL integration: detects pushable aggregations, builds programs, replaces AccessPath nodes

3. Implementation Phases

The feature was built bottom-up across 14 phases, starting from the data node kernel and working up through the coordinator, NDB API, and finally the MySQL handler layer.

Figure 3: Implementation timeline — bottom-up from kernel to SQL layer.

Phases 1-6: DBLQH Kernel Engine

Phase 1: Signal Infrastructure COMPLETE

Defined 8 new GSN signals (944-951) for the JOIN_AGG protocol: SETUP_REQ/CONF/REF, COMPLETE_REQ/CONF/REF, RELEASE_REQ/CONF. Created JoinAgg.hpp signal definitions and registered handlers in DBLQH, DBTC, and DBSPJ.

Phase 2: State Management COMPLETE

Added JoinAggregationState struct with TransientPool-based allocation in SimulatedBlock. Node-level pool shared across all LDM threads. State machine: IDLE → SETUP_COMPLETE → FINALIZING → SENDING_RESULTS → COMPLETED.

Phase 3: Signal Flags & Routing COMPLETE

Added JoinAggFlag to LQHKEYREQ (bit 7 of attrLenFlags) and SCAN_FRAGREQ (SF_JOIN_AGG_SHIFT = 25). DblqhProxy routes SETUP and RELEASE to main thread; COMPLETE routed to V_QUERY workers for merge.

Phase 4: Row Processing Integration COMPLETE

Added handleJoinAggRow() interception in DBTUP at three paths: non-interpreted, interpreted scan, and interpreted non-scan. Rows are fed to AggInterpreter just before sendReadAttrinfo. Linked parent attributes passed via cinBuffer section 4.

Phase 5: Completion & Result Sending COMPLETE

Implemented execJOIN_AGG_COMPLETE_REQ: merges per-thread interpreters (MUTEX_FREE) or finalizes shared interpreter (MUTEX_BASED), then sends groups in batches of 16 via TRANSID_AI with CONTINUEB yielding (signal 45) to prevent thread starvation.

Phase 6: Memory & Concurrency COMPLETE

Four sub-phases:

  • 6a: JoinAggInterpreter with chunk-based memory allocator (32KB pages, 25% of RG_QUERY_MEMORY budget)
  • 6b: Group eviction under memory pressure — oldest group serialized to TRANSID_AI, sent to API
  • 6c: MUTEX_BASED strategy with std::mutex for low-cardinality GROUP BY
  • 6d: MUTEX_FREE strategy with per-thread interpreters and bucket-level merge at completion

Phase 7: DBTC/DBSPJ Coordinator

Phase 7: Three-Phase Orchestration COMPLETE

SETUP: DBTC extracts agg program from Section 2, sends JOIN_AGG_SETUP_REQ to each data node, collects aggStateKeys into a section attached to SCAN_FRAGREQ.

RUN: DBSPJ routes aggStateKey in LQHKEYREQ variableData for child lookups. Suppresses T_EXPECT_TRANSID_AI for aggregate leaf nodes — no per-row results sent.

COMPLETE: After all SCAN_FRAGCONFs received, DBTC sends JOIN_AGG_COMPLETE_REQ to all nodes. Data nodes merge, finalize, and send remaining groups via TRANSID_AI.

RELEASE: Final cleanup of JoinAggregationState pools.

Phase 8: NDB API

Phase 8: NDB API Integration COMPLETE

Extended NdbQueryOptions with setAggregation() and addLinkedProjection(). Added DABits NI_AGGREGATE (0x2000) and NI_AGGREGATE_LEAF (0x4000) for serialization. New receiver type NDB_AGG_RECEIVER (5) for dedicated result dispatch. Section 2 combined format: [boundsLen, bounds..., aggReceiverId, aggProgram...].

Phases 9-14: MySQL Handler Integration

Phases 9-10: Detection & Program Building COMPLETE

Feature-gated by ndb_join_pushdown_aggregate session variable. ndb_can_push_aggregation() validates: entire join must be pushed, only COUNT/SUM/MIN/MAX (no DISTINCT/ROLLUP). ndb_build_aggregation_program() maps MySQL Item_sum objects to NdbAggregator instructions, including linked projections for multi-table GROUP BY.

Phase 10: AccessPath Surgery COMPLETE

Removes AGGREGATE/TEMPTABLE_AGGREGATE node from AccessPath tree entirely, replacing it with the pushed join child. Adds m_pushed_aggregate, m_pushed_value_int/double, m_pushed_null to Item_sum base class with early-return in val_int()/val_real() for 4 subclasses.

Phase 11: EXPLAIN Support COMPLETE

Added "Pushed aggregate" annotation to EXPLAIN output when join aggregation is pushed down.

Phase 12: SQL-Level MTR Tests COMPLETE

Comprehensive SQL test suite in mysql-test/suite/ndb_push_agg/: 2-way and 3-way joins, GROUP BY on root/child/both, all aggregate functions, NULL handling, HAVING, ORDER BY, LIMIT.

Phase 13: Eviction Testing COMPLETE

ERROR_INSERT 5090 forces maxGroups=3 to trigger eviction at SQL level. ERROR_INSERT 4040 for intermittent eviction testing. Verifies correct results even when groups are evicted mid-scan and merged at the API.

Phase 14: COUNT(column) & Outer Join Restriction COMPLETE

Added support for COUNT(column) (excludes NULLs, unlike COUNT(*)). Added restriction to reject pushdown for outer joins where NULL padding would affect aggregate correctness.

Chunk-Based Memory Allocator

Figure 5: Chunk-based memory allocator. Each 32KB chunk holds multiple groups. When live_groups reaches 0, chunk is freed.

Group Eviction Under Memory Pressure

When the aggregation hash table cannot accommodate a new group (budget exhausted), the oldest group is evicted:

  1. evictOneGroup() serializes the oldest group to a TRANSID_AI signal buffer
  2. The evicted group is sent directly to the API receiver (bypassing DBSPJ)
  3. Group memory is freed from the chunk allocator
  4. The new group is inserted into the freed space
  5. The API's NdbAggregator merges evicted groups with final results
Correctness guarantee: Evicted groups are partial aggregates. The API uses NdbAggregator::ProcessRes() to merge partial results from the same group (keyed by GROUP BY values) using the same accumulator logic. This works because all aggregate operations (SUM, COUNT, MIN, MAX) are associative and commutative.

Concurrency Strategies

Figure 6: Two concurrency strategies. MUTEX_FREE is the default, chosen for high-cardinality GROUP BY scenarios.

DBTC ScanRecord Extensions

Uint32 m_aggStateKeys[];     // Per-node state keys from SETUP_CONF

Section 2 Combined Format

The aggregation program shares Section 2 with index bounds in SCAN_TABREQ:

Word 0:                boundsLen (0 if no bounds)
Words 1..boundsLen:    bounds data (for index scans)
Word boundsLen+1:      aggReceiverId (API receiver ID for result routing)
Remaining words:       aggregation program (NdbAggregator bytecode)

DBTC splits this in execSCAN_TABREQ:

  • Bounds → scanKeyInfoPtr
  • Receiver ID → m_aggReceiverId
  • Program → m_aggProgramPtrI (kept as section for forwarding to DBLQH)

aggStateKeys Section in SCAN_FRAGREQ

After SETUP completes, DBTC builds a section of (nodeId, aggStateKey) pairs and attaches it to SCAN_FRAGREQ for DBSPJ. DBSPJ extracts the key for each node and appends it to LQHKEYREQ variableData when sending child lookups to leaf tables.

DBSPJ Optimizations

  • T_EXPECT_TRANSID_AI suppression: Aggregate leaf nodes don't send per-row results. DBSPJ skips waiting for TRANSID_AI, only expecting LQHKEYCONF.
  • RT_AGGREGATE flag: Marks the Request as containing aggregation, changing routing behavior.
  • JoinAgg bypass: For large result sets, DBSPJ can bypass DBTC/API round-trip for batch flow control, sending heartbeats (SCAN_HBREP) to keep the connection alive.

Linked Column Resolution (Bit-15 Encoding)

Columns from parent tables in a multi-table GROUP BY use a special encoding:

// Column ID encoding in aggregation program:
// Bit 15 (0x8000) = 0  → local column (from leaf table)
// Bit 15 (0x8000) = 1  → linked column (from parent table)
// Bits 0-14            → position index in linked attribute buffer

Example: GroupByLinked(position=2, col_id) → stored as 0x8002
AggInterpreter resolves by scanning AttributeHeader chain to position 2

Result Routing

Each data node sends aggregated results directly to the API via TRANSID_AI. For GROUP BY queries, the receiver is selected by hashing the GROUP BY key:

receiverData = selectReceiverData(key, key_len)
             = receiverIds[hash(key, key_len) % numReceiverIds]

This ensures the same group from different data nodes arrives at the same API receiver, where NdbAggregator merges partial results.

7. MySQL Handler Integration Details

Detection and Validation

ndb_can_push_aggregation() checks:

  • Feature gate: SET ndb_join_pushdown_aggregate = ON
  • Entire join must already be pushed (SPJ)
  • Only COUNT(*), COUNT(col), SUM, MIN, MAX supported
  • No DISTINCT, ROLLUP, or window functions
  • All GROUP BY columns must come from pushed tables
  • No outer joins (NULL padding would corrupt aggregates)

9. Key Design Decisions

Bottom-Up Development Order

Decision: Build from kernel (DBLQH) up to SQL handler, not top-down.
Rationale: The aggregation engine at the data node is the most complex and performance-critical component. Building it first with direct signal tests enabled rapid iteration without the overhead of full SQL roundtrips. Each layer was tested independently before integration.

Per-Thread vs Shared Interpreter

Decision: Default to MUTEX_FREE (per-thread interpreters).
Rationale: NDB data nodes use multiple LDM threads for parallel scan processing. A shared interpreter with mutex creates contention at high cardinalities. Per-thread interpreters eliminate all contention; the merge at COMPLETE phase is O(N_threads × N_groups) but happens only once. MUTEX_BASED remains available for low-cardinality cases.

AccessPath Surgery vs Pass-Through

Decision: Remove AGGREGATE node from AccessPath tree entirely.
Rationale: Making AGGREGATE a pass-through would still require MySQL's group-change detection, sorting, and expression evaluation overhead. Removing the node entirely lets the root handler return pre-aggregated rows directly, eliminating all MySQL-side aggregation cost. The Item_sum early-return mechanism provides the bridge.

Direct API Sending for Evicted Groups

Decision: Evicted groups bypass DBSPJ and send directly to the API receiver.
Rationale: DBSPJ is designed for row-level flow control. Routing evicted aggregate groups through DBSPJ would add complexity for no benefit. The API receiver can merge partial aggregates regardless of arrival order thanks to the commutative/associative property of the supported aggregate operations.

Section 2 Multiplexing

Decision: Share Section 2 between bounds and aggregation program.
Rationale: Adding a new section would require changes to all signal handling code. The combined format with a bounds length prefix allows zero-copy splitting in DBTC and is backward compatible (non-aggregate queries have no extra data after bounds).
