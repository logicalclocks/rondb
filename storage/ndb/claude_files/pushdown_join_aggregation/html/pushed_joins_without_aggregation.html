1. Overview: What is a Pushed Join?

In NDB Cluster, a pushed join (or SPJ join) pushes multi-table join execution down to the data nodes. Instead of the MySQL server fetching rows from one table and then issuing separate requests for each matching row in the next table, the entire join tree is sent as a single query plan to DBSPJ (the Select-Project-Join block), which orchestrates all the child lookups and scans from within the data node cluster — child operations can target any data node, not just the node where DBSPJ runs.

The core idea: for each row produced by the root scan, DBSPJ automatically performs the child lookups (or child scans) using column values from the parent row as join keys. These column values are called linked columns. DBLQH sends result rows from all tables directly to the NDB API via TRANSID_AI signals, each tagged with correlation IDs that allow the API to reconstruct the join result by matching child rows to their parent rows.

Key Benefit: Without pushed joins, a 2-table join with 10,000 root rows would require 10,000 separate network round-trips from the API to the data nodes for child lookups. With pushed joins, DBSPJ orchestrates all child lookups internally within the cluster (sending LQHKEYREQ or SCAN_FRAGREQ to any data node holding the relevant fragment) — saving those round-trips. The API still receives all rows (root and child) directly from DBLQH via TRANSID_AI signals, and uses correlation IDs to assemble the final join result. The savings come from eliminated round-trips, not reduced data volume.

2. End-to-End Signal Flow

The following diagram shows the complete signal flow for a pushed join query (root table scan + child PK lookup). A key architectural detail: DBLQH sends two separate TRANSID_AI signals for each row — one directly to the NDB API (the result row with correlation ID) and one to DBSPJ (linked column values for dispatching child operations). The API thus receives all row data directly from DBLQH, not via DBSPJ.

Figure 1: Complete signal flow for a 2-table pushed join (root scan + child PK lookup). DBLQH sends two separate TRANSID_AI signals per row: one directly to the NDB API (result row + corrId) and one to DBSPJ (linked columns for child dispatch). Steps 4–7 repeat for every root row in the batch. Step 8 (SCAN_FRAGCONF from root LQH) signals the root batch is complete; DBSPJ waits for all child LQHKEYCONFs before sending its own SCAN_FRAGCONF to DBTC (step 9).

Scan-Scan Join Variant (Multi-Fragment)

When the child operation is a scan (not a PK lookup), the signal flow changes significantly. As each parent row arrives via TRANSID_AI, scanFrag_parent_row() expands the key pattern into a range bound and appends it to the fragment's m_rangePtrI section — with the parent's correlation ID embedded in bound word 0 via scanFrag_fixupBound(). After all parent rows in the batch have been processed, each SCAN_FRAGREQ sent to child LQH carries all accumulated range bounds (one per parent row), so a single child scan processes multiple parent-derived ranges simultaneously.

DBSPJ dispatches these SCAN_FRAGREQs to multiple child fragments in parallel, where each fragment may reside on any data node in the cluster. The number of fragments started simultaneously is controlled by scanFrag_parallelism(), which adapts based on runtime fanout statistics. Each child fragment independently returns rows via dual TRANSID_AI and signals completion via SCAN_FRAGCONF. DBSPJ tracks m_frags_outstanding and waits for all fragments before reporting batch complete.

Figure 1b: Signal flow for a 2-table pushed join (root scan + child scan) with 3 child fragments. DBSPJ uses adaptive parallelism: Wave 1 starts Frag 0 and Frag 1 in parallel while Frag 2 waits (SFH_NOT_STARTED). When both SCAN_FRAGCONFs arrive, DBSPJ sends SCAN_NEXTREQ to Frag 1 (which has more data) and starts Frag 2 (Wave 2). Once all fragments report done, DBSPJ sends SCAN_FRAGCONF to DBTC. Each corrIdStart is incremented by bs_rows per fragment to ensure unique correlation ID ranges.
Scan-Scan vs Scan-Lookup — Key Differences:
  • Timing: Lookups are dispatched immediately per parent row; child scans are deferred until the parent batch is complete (parent_batch_complete() triggers scanFrag_send())
  • Bounds accumulation: scanFrag_parent_row() appends range bounds to fragPtr.m_rangePtrI with correlation IDs embedded in bound word 0 via scanFrag_fixupBound()
  • Fanout: Each parent row can produce 0 or many child rows (range scan), vs exactly 0 or 1 for PK lookups
  • Multi-fragment parallelism: scanFrag_parallelism() determines how many fragments to start simultaneously, adapting based on m_recsPrKeyStat (95th percentile fanout). Remaining fragments start as earlier ones complete
  • Pruning: If T_PRUNE_PATTERN is set, each parent row's bounds go to a specific fragment based on computePartitionHash(); otherwise all fragments scan the same bounds
  • Fragment state machine: Each ScanFragHandle transitions: SFH_NOT_STARTED → SFH_SCANNING → SFH_WAIT_NEXTREQ → SFH_SCANNING → ... → SFH_COMPLETE
  • corrIdStart partitioning: Each fragment gets a unique corrIdStart range (incremented by bs_rows per fragment) so correlation IDs don't collide across fragments

3. DBTC–DBSPJ Interaction and Parallelism

DBTC's role is to receive the query from the API and distribute work across multiple DBSPJ instances for parallel execution.

Fragment Distribution

An NDB table is partitioned into fragments, each stored on a data node. DBTC determines which fragments to scan and maps each to a DBSPJ instance:

Figure 2: DBTC distributes root table fragments across DBSPJ instances using round-robin. Each DBSPJ instance scans its assigned root fragments locally, but child lookups and scans can target DBLQH on any data node where the child table fragment resides.

MultiFragFlag Optimization

When MultiFragFlag is set in SCAN_TABREQ (default for SPJ queries), DBTC bundles multiple fragments destined for the same data node into a single SCAN_FRAGREQ. Fragment locations are sorted by primaryBlockRef so adjacent fragments on the same node are grouped together. The fragment IDs are appended to a list section in the signal.

This reduces signal overhead but decreases cross-thread parallelism, since all bundled fragments share one DBSPJ instance. The trade-off favors reduced overhead for typical OLTP workloads where fragment count is moderate.

Without MultiFragFlag

Each fragment gets a different DBSPJ instance (via round-robin cspjInstanceRR++ % 120), maximizing parallelism across TC threads. This is used when maximum throughput is needed, such as with aggregation queries.

4. Query Tree Format (High Level)

The query plan is serialized as a QueryTree and sent as the AttrInfo section of SCAN_FRAGREQ. It contains two interleaved sequences: node definitions and node parameters.

Figure 3: QueryTree layout in the AttrInfo section. Node definitions are followed by per-node parameters.

Each QueryNode contains: operation type (scan, lookup, unique index lookup), table/index ID, schema version, parent node reference, and RequestInfo flags indicating what linked data is needed. The QueryNodeParameters contain the actual patterns for constructing keys and attribute projections from parent row data.

5. DBSPJ Internal Data Structures

Request

A Request represents a complete pushed join query being executed by one DBSPJ instance. It tracks the overall state and coordinates all tree nodes.

TreeNode

ScanFragHandle

struct ScanFragHandle {

Row Buffers

DBSPJ uses a page-based row buffer system. When a parent row arrives (TRANSID_AI), it is stored in the TreeNode's RowBuffer so that children can later extract linked column values from it.

6. Linked Columns: Moving Data Between Tables

Linked columns are the mechanism by which DBSPJ passes column values from parent rows to child operations. They serve two purposes:

  1. Join key construction: The child's primary key is built from parent column values (e.g., WHERE child.id = parent.child_id)
  2. Linked attribute passing: Parent columns needed by grandchild operations are forwarded through intermediate nodes

Pattern System

Linked columns are defined using a pattern language stored in the QueryTree. When DBSPJ receives a parent row, it expands these patterns using the actual row data to produce concrete key values and attribute parameters.

Figure 7: The pattern language for linked columns, illustrated with a 3-table join. P_PARENT(0) navigates to the immediate parent, while P_PARENT(1) skips one level to reach the grandparent — enabling the child (Parts) to access columns from Orders that were not available in the intermediate LineItems row.

Expansion Process

When a parent row arrives in DBSPJ (via TRANSID_AI from DBLQH), the expand() method is called to build concrete key/attribute sections from patterns:

// In lookup_parent_row():
// 1. Expand key pattern → build child's primary key from parent columns
expand(keyPtrI, m_keyPattern, parentRowRef, keyIsNull);

// 2. Expand attr param pattern → build linked attributes for child's params
expand(attrPtrI, m_attrParamPattern, parentRowRef, hasNull, addTableMeta=true);

// The expand() function walks the pattern:
for each pattern entry:
  switch (type):
    P_PARENT:  navigate up 'levels' to target ancestor row
    P_COL:     extract column value from target row, append to section
    P_ATTRINFO: extract column with AttributeHeader, append to section
    P_DATA:    copy inline constant data to section

7. Correlation IDs: Parent–Child Row Matching

Every row returned from DBLQH via TRANSID_AI includes a correlation data suffix. This allows the API to match child rows to their parent rows and reconstruct the join result.

Correlation Data Format

// Appended as the last 3 words of every TRANSID_AI row:
Word 0: AttributeHeader (CORR_FACTOR64 = 0xFFE8, size=2)
Word 1: [parentTupleId : 16 bits | tupleId : 16 bits]
Word 2: rootReceiverId (identifies which SPJ worker produced this row)

How It Works

Figure 9: Correlation IDs link child rows back to their parent rows. The API uses TupleCorrelation to reconstruct join pairs from the interleaved TRANSID_AI stream.
12-bit Correlation ID Limit: Tuple IDs are 12 bits (max 4096 = MaxCorrelationId). This limits the maximum batch size for parent operations that have children. The batch size is capped at 4096 / fragsPerWorker rows to ensure unique correlation IDs within a batch.

8. Batch Size Calculation

Batch sizes are calculated at two levels: the NDB API sets the overall budget, and DBSPJ adaptively distributes it across fragments based on runtime statistics.

API-Side Batch Size

// NdbQueryOperationImpl::calculateBatchedRows()

// Step 1: Start with configured max batch rows for root scan
Uint32 maxBatchRows = myClosestScan->m_maxBatchRows;

// Step 2: Apply NdbReceiver limits (considers parallelism)
NdbReceiver::calculate_batch_size(
    parallelism,          // number of fragments in parallel
    maxBatchRows,         // in/out: capped by transport limits
    batchByteSize,        // in/out: byte budget
    MAX_PARALLEL_OP_PER_SCAN_SPJ);  // hard limit: 4000 rows

// Step 3: Apply 12-bit correlation ID constraint (parents only)
if (has_children) {
    maxBatchRows = MIN(maxBatchRows, 4096 / fragsPerWorker);
}

// Step 4: Reconcile with all child operations recursively
for each child:
    childMax = child->calculateBatchedRows(myClosestScan);
    maxBatchRows = MIN(maxBatchRows, childMax);

The API sends the root scan's limits in SCAN_TABREQ:

FieldDescriptionTypical Value
batch_size_rowsMax rows per batch256–4000
batch_size_bytesMax bytes per batch64KB–1MB
first_batch_sizeInitial batch (may differ)Same as batch_size_rows
scanParallelismFragments to scan in parallel= workerCount × fragsPerWorker

Child Scan Buffer Sizing: API → QueryTree → DBSPJ

The root scan's batch limits travel in SCAN_TABREQ. But child scan operations have their own independent batch sizes, which are serialized into the QueryTree that the API sends alongside SCAN_TABREQ. Understanding this propagation chain is key to understanding the "budget" that estmMaxKeys() tries to stay within.

Step 1: API calculates per-operation batch sizes

Each scan operation in the query tree calls calculateBatchedRows() independently. The critical concept is myClosestScan — each operation tracks its closest scan ancestor:

// NdbQueryOperationImpl::calculateBatchedRows(closestScan)

if (isScanOperation()) {
    myClosestScan = this;                    // I am a scan — use my own batch
} else {
    myClosestScan = closestScan;             // Lookup — inherit parent scan's batch
}

// For this scan: calculate batch from NdbReceiver defaults
maxBatchRows = myClosestScan->m_maxBatchRows;   // 0 = use cluster config default
NdbReceiver::calculate_batch_size(parallelism, maxBatchRows, batchByteSize, ...);

// Parent scans: cap by 12-bit correlation ID
if (has_children)
    maxBatchRows = MIN(maxBatchRows, 4096 / fragsPerWorker);

// Recursively constrain children
for each child:
    childMax = child->calculateBatchedRows(myClosestScan);
    maxBatchRows = MIN(maxBatchRows, childMax);

if (isScanOperation()) {
    m_maxBatchRows = maxBatchRows;           // Store final batch for this scan
    return 0xFFFFFFFF;                       // Don't constrain parent scan
} else {
    return maxBatchRows;                     // Lookup: constrain parent scan
}
Scan operations return 0xFFFFFFFF: When a child scan calls calculateBatchedRows(), it stores its own m_maxBatchRows but returns 0xFFFFFFFF (no constraint) to its parent. This is because child scans have their own independent batch buffers — they don't consume the parent's buffer. Only child lookups constrain the parent scan, since lookup responses share the parent scan's batch buffer. This means each scan in the tree gets its own budget, calculated independently from cluster config defaults.

Step 2: API serializes child batch sizes into QueryTree

After calculateBatchedRows() runs for the whole tree, each scan operation's m_maxBatchRows and m_maxBatchBytes are serialized into the QueryTree as QN_ScanFragParameters. This is the data structure that DBSPJ will parse at build time:

// NdbQueryOperationImpl::prepareAttrInfo() — for each child scan

QN_ScanFragParameters *param = ...;

// CRITICAL: multiply by fragsPerWorker for multi-fragment bundling
const Uint32 batchRows  = getMaxBatchRows()  * fragsPerWorker;
const Uint32 batchBytes = getMaxBatchBytes() * fragsPerWorker;

param->batch_size_rows  = batchRows;     // Stored in QueryTree
param->batch_size_bytes = batchBytes;    // Stored in QueryTree

Step 3: DBSPJ extracts child batch sizes at build time

When DBSPJ receives the QueryTree in SCAN_TABREQ, it calls scanFrag_build() for each scan node. For child scans, the batch sizes come from the QueryTree parameters (not from SCAN_TABREQ — that only contains the root's batch):

// Dbspj::scanFrag_build() — for CHILD scans

const QN_ScanFragParameters *param = ...;   // From QueryTree

// Extract child's independent batch size
dst->batch_size_rows  = param->batch_size_rows;    // Child's own row budget
dst->batch_size_bytes = param->batch_size_bytes;    // Child's own byte budget

// Stored in TreeNode's m_scanFragReq template — used for all SCAN_FRAGREQs

These stored values become the org->batch_size_rows and org->batch_size_bytes that scanFrag_getBatchSize() reads at runtime.

Figure 10c: Child batch sizes originate in the API's calculateBatchedRows(), travel through the QueryTree as QN_ScanFragParameters, are extracted by DBSPJ at build time, and are refined at runtime by scanFrag_getBatchSize().

Lookup children: no independent buffer

Unlike child scans, child lookups (LQHKEYREQ operations) do not have their own batch_size_rows — each lookup returns exactly one row. Instead, the parent scan's batch buffer must have room for all lookup responses. This is why lookup children do constrain their parent scan in calculateBatchedRows(): if the parent generates 1000 rows and each spawns a lookup, the parent scan's batch must accommodate 1000 lookup responses. The constraint flows upward: a lookup child returns its myClosestScan's maxBatchRows, ensuring the ancestor scan doesn't generate more lookups than it has buffer for.

DBSPJ-Side Runtime Adjustment

At runtime, DBSPJ further refines the child's configured batch size in scanFrag_getBatchSize(), accounting for rows already received and runtime statistics:

// Dbspj::scanFrag_getBatchSize()
// How many rows can we still fetch into the available batch buffers?

// Available rows = configured batch size − already received rows
availableBatchRows = org->batch_size_rows − data.m_totalRows;

// For parent nodes: also limited by remaining correlation IDs (12-bit)
if (!isLeaf())
    availableBatchRows = MIN(availableBatchRows, MaxCorrelationId − m_corrIdStart);

// Available bytes = configured batch bytes − already received bytes
availableBatchBytes = org->batch_size_bytes − data.m_totalBytes;

// Use record size statistics to estimate rows that fit in available bytes
if (m_recSizeStat.isValid()) {
    batchLimitedByBytes = availableBatchBytes / estmRecSize;
    batchSizeRows = MIN(batchSizeRows, batchLimitedByBytes);
}

Adaptive Parallelism in DBSPJ

DBSPJ dynamically calculates how many fragments to scan in parallel using scanFrag_parallelism(). It uses runtime fanout statistics from previous batches to estimate optimal parallelism:

// Dbspj::scanFrag_parallelism()

maxParallelism = MIN(batchSizeRows, frags_not_complete);
minParallelism = MIN(rootFragCount, maxParallelism);

if (T_SCAN_PARALLEL flag set)
    return maxParallelism;  // Full parallel: all fragments at once

if (no statistics yet)
    return minParallelism;  // Conservative: start with rootFragCount

// Use 95th percentile of records-per-key fanout
estmRecsPrKey = m_recsPrKeyStat.getUpperEstimate();
estmRowsSelected = keysToSend × estmRecsPrKey;

// Parallelism = how many fragments we can afford given batch budget
parallelism = (batchSizeRows × frags_not_started) / estmRowsSelected;
parallelism = CLAMP(parallelism, minParallelism, maxParallelism);
Figure 10: Batch budget flows from total → per-fragment → child branch estimation. The system adapts based on observed fanout from previous batches.

Fanout Statistics: IncrementalStatistics

DBSPJ uses an adaptive statistical estimator (IncrementalStatistics, based on NdbStatistics in stat_utils.hpp) to track runtime fanout. The estimator uses a hybrid approach: simple moving average for the first 5 samples, then exponentially weighted moving average (EWMA) afterwards so that recent batches carry more weight than old ones.

// NdbStatistics — Welford's online algorithm with EWMA transition

void update(double sample) {
  if (m_noOfSamples == 0) {
    m_mean = sample;
    m_sumSquare = 0;
    m_noOfSamples = 1;
  } else {
    const double delta = sample - m_mean;

    if (m_noOfSamples == m_maxSamples) {   // Window full (5 samples)
      m_sumSquare -= (m_sumSquare / m_noOfSamples);  // Expire oldest contribution
      m_noOfSamples--;                                // Make room for new sample
    }

    m_noOfSamples++;
    m_mean += (delta / m_noOfSamples);                // Updated mean
    m_sumSquare += fabs(delta * (sample - m_mean));   // Updated variance
  }
}

double getStdDev() const {
  return (m_noOfSamples > 1) ? sqrt(m_sumSquare / (m_noOfSamples - 1)) : 0;
}

Two key statistics are tracked per ScanFragData:

Statistic Measures Sampled When
m_recsPrKeyStat Rows returned per key/bound sent per fragment (fanout) Fragment completes: completedRows / completedKeys
m_recSizeStat Bytes consumed per row (record size) Batch completes: totalBytes / totalRows

How m_recsPrKeyStat Is Collected

Each ScanFragHandle tracks m_keysSent (the number of range bounds dispatched to that fragment) and m_totalRows (rows returned). When a fragment completes scanning (all ranges exhausted), these are accumulated into the shared ScanFragData:

// DbspjMain.cpp — scanFrag_execSCAN_FRAGCONF(), after fragment completes

data.m_completedKeys += fragPtr.p->m_keysSent;   // Keys sent to this fragment
data.m_completedRows += fragPtr.p->m_totalRows;   // Rows received back

// When all fragments in this wave complete:
if (data.m_completedKeys > 0) {
    const double recsPrKey = double(data.m_completedRows)
                           / data.m_completedKeys;
    data.m_recsPrKeyStat.sample(recsPrKey);        // Feed into estimator

    data.m_completedKeys = 0;   // Reset for next wave
    data.m_completedRows = 0;
}

Upper Estimate: 95th Percentile

When DBSPJ needs a conservative (high) fanout estimate — to avoid overshooting batch buffers — it uses the 95th percentile:

// IncrementalStatistics::getUpperEstimate()

double getUpperEstimate() const {
  return (m_noOfSamples >= 2)
    ? getMean() + (2 * getStdDev())   // ≈ 95th percentile (normal approx.)
    : getMean() * 1.20;               // Only 1 sample: add 20% safety margin
}
Why 95th percentile? If the actual fanout exceeds the estimate, rows overflow the batch buffer, causing DBSPJ to request SCAN_NEXTREQ round-trips. Using the mean would underestimate half the time. The 95th percentile (mean + 2σ) provides a conservative bound that overestimates only ~5% of the time, at the cost of slightly underutilizing batch buffers on average.

Recursive Fanout Estimation: estmMaxKeys()

estmMaxKeys() walks the query tree top-down, accumulating the compound fanout through each level, and returns the maximum number of root keys that can be processed without overflowing any child's batch buffer. It is used for sorted-order optimization: if estmMaxKeys() ≥ 2.0, DBSPJ can safely request more root rows.

// Dbspj::estmMaxKeys() — recursive fanout accumulation

double estmMaxKeys(requestPtr, treeNodePtr, fanout) {
  double maxKeys = 99999.99;    // No constraint unless this is a scan

  if (treeNodePtr is a scan) {
    // Multiply accumulated fanout by this node's records-per-key
    if (statistics available) {
      if (isLeaf)
        fanout *= m_recsPrKeyStat.getUpperEstimate();   // Conservative (95th pct)
      else
        fanout *= m_recsPrKeyStat.getMean();             // Mean for intermediates
    }

    // Non-pruned scans hit ALL fragments — multiply by fragment count
    if (!pruned)
      fanout *= fragCount;

    // How many keys fit in the available batch buffer?
    batchRows = scanFrag_getBatchSize(treeNodePtr, ...);
    maxKeys = batchRows / fanout;
  }

  // Recurse into every child — take the MINIMUM (bottleneck)
  for each child of treeNodePtr:
    childMaxKeys = estmMaxKeys(requestPtr, child, fanout);
    maxKeys = MIN(maxKeys, childMaxKeys);

  return maxKeys;
}
Leaf vs. non-leaf distinction: Leaf scans use getUpperEstimate() (95th percentile) because overestimating at the leaf is the safest — it avoids buffer overflow at the terminal node. Non-leaf (intermediate) scans use getMean() because the accumulated fanout already compounds conservatively through the tree, and using upper estimates at every level would make the estimate excessively pessimistic.

Worked Example: 3-Table Join

Consider Orders → LineItems → Parts where Orders has 8 unpruned fragments:

The bottleneck is the LineItems scan: with a mean fanout of 3.2 rows per key across 4 fragments, each root key generates 12.8 LineItem rows on average. Given a 500-row batch buffer, only 39 root keys can be processed before the child buffer fills up. Lookups (Parts, Supplier) impose no scan-level constraint because they don't accumulate rows in batch buffers the same way.

Pruned vs. non-pruned scans: If the LineItems scan were pruned (e.g., partition key known from parent), the query hits only 1 fragment instead of all 4. The fanout would be 1.0 × 3.2 × 1 = 3.2, allowing 500 / 3.2 = 156 root keys per batch — a 4× improvement. Pruned scans are indicated by T_PRUNE_PATTERN or T_CONST_PRUNE flags on the TreeNode.

9. Congestion Control and Deferred Operations

When join fanout is high, a single parent batch can spawn thousands of child operations. Without throttling, this would exhaust memory and signal buffers. DBSPJ uses a hysteresis-based congestion control mechanism that defers child dispatch when outstanding operations are too high, then resumes in controlled bursts when capacity frees up.

9.1 Threshold Constants

Three constants in DbspjMain.cpp govern congestion behavior:

Constant Value Purpose
HighlyCongestedLimit 256 When m_outstanding ≥ 256, new child operations are deferred
MildlyCongestedLimit 128 When m_outstanding < 128, deferred operations begin resuming
ResumeCongestedQuota 32 Maximum operations resumed per RT-break cycle

The gap between 256 (defer) and 128 (resume) creates hysteresis — preventing rapid oscillation between deferring and resuming. The system only starts resuming once outstanding operations have dropped significantly below the defer threshold.

9.2 Congestion Check: When to Defer

The congestion check occurs in the row-processing path. When DBSPJ processes a parent row and is about to dispatch child operations (lookups or scans), it checks:

// DbspjMain.cpp — inside row processing for child dispatch
if (treeNodePtr.p->m_bits & TreeNode::T_CHK_CONGESTION)
{
  if (requestPtr.p->m_outstanding >= HighlyCongestedLimit)
  {
    // Don't dispatch — defer this parent row's correlation ID
    jam();
    registerActiveCursor(requestPtr, treeNodePtr);
    handleTreeNodeComplete(signal, requestPtr, treeNodePtr);

    // Queue the correlation ID for later replay
    treeNodePtr.p->m_deferred.m_correlations.append(corrVal);

    // Mark this node as suspended
    requestPtr.p->m_suspended_tree_nodes |= (1 << treeNodePtr.p->m_node_no);
    return;
  }
}

9.3 DeferredParentOps: What Gets Stored

The DeferredParentOps structure is deliberately lightweight — it stores only correlation IDs (4 bytes each), not full row copies:

struct DeferredParentOps {
  Uint32 m_corrIdStart;                        // First correlation ID in this batch
  SLFifoRowList m_correlations;                // Queue of deferred corrIds
};

The actual parent row data remains in the scan ancestor's m_rows RowCollection, indexed by correlation ID. When replay occurs, m_parent_batch_repeat() looks up each deferred corrId to retrieve the original row. This avoids duplicating row storage.

9.4 Resume Mechanism

Resumption is triggered by lookup_countSignal(), called when an LQHKEYCONF or LQHKEYREF arrives (i.e., a child lookup completes). Each completed lookup decrements m_outstanding. When it drops below MildlyCongestedLimit (128):

// DbspjMain.cpp — lookup_countSignal()
requestPtr.p->m_outstanding--;

if (requestPtr.p->m_outstanding < MildlyCongestedLimit &&
    requestPtr.p->m_suspended_tree_nodes != 0)
{
  jam();
  resumeCongestedNode(signal, requestPtr);
}

resumeCongestedNode() iterates through m_suspended_tree_nodes, finding each suspended TreeNode and calling its m_parent_batch_repeat() handler. This replays deferred correlation IDs, dispatching the child operations that were originally held back.

9.5 RT-Break Quota

To prevent resumeCongestedNode() from running too long in a single real-time break, it processes at most ResumeCongestedQuota (32) operations before yielding. If more deferred operations remain, the TreeNode stays in m_suspended_tree_nodes and will be resumed again when the next lookup_countSignal() fires.

This ensures the data node thread remains responsive to other signals even during large resume bursts.

9.7 Interaction with checkBatchComplete()

When all parent rows in a batch have been processed but some TreeNodes are suspended (have deferred correlation IDs), checkBatchComplete() will not complete the batch. The request remains active until all deferred operations have been replayed and their child responses received. Only when m_suspended_tree_nodes == 0 and m_outstanding == 0 and m_active_tree_nodes == 0 can the batch truly complete.

Why only correlation IDs? Storing full parent rows in DeferredParentOps would double memory usage under congestion — exactly when memory pressure is highest. Instead, only 4-byte corrIds are stored. The actual row data lives in the scan ancestor's m_rows RowCollection (already allocated), and m_parent_batch_repeat() looks up each row by its corrId during replay. This means congestion deferral adds only ~4 bytes per deferred parent row.

10. Tuning Parallelism and Batch Sizes

There are several levers available for increasing parallelism in pushed joins. Configuration can be applied at three levels: NDB Cluster config (config.ini, affects all connections), MySQL session variables (per-connection), and NDB API methods (per-query-operation).

10.1 Configuration Levels Overview

10.2 NDB Cluster Configuration (config.ini)

These parameters are set in config.ini under the [api] section and serve as defaults for all API connections (including all MySQL Server connections). They are read at connection time via ndb_cluster_connection.cpp and stored in the per-connection m_ndbapiconfig struct.

Parameter Default Range Effect
BatchSize 384 1 – MAX_PARALLEL_OP Default batch size in rows per fragment
BatchByteSize 32 KB 1 KB – 1 MB Default batch size in bytes per fragment
MaxScanBatchSize 32 KB 1 KB – 16 MB Maximum collective batch size across all fragments of one scan

These flow into the batch calculation as follows:

// ndb_cluster_connection.cpp — read from config at connect time
m_ndbapiconfig.m_scan_batch_size  = CFG_MAX_SCAN_BATCH_SIZE;   // MaxScanBatchSize
m_ndbapiconfig.m_batch_byte_size  = CFG_BATCH_BYTE_SIZE;       // BatchByteSize
m_ndbapiconfig.m_batch_size       = CFG_BATCH_SIZE;            // BatchSize

// NdbReceiver::calculate_batch_size() — uses these as caps:
//   maxBatchRows = MIN(user_requested, m_batch_size)
//   batchByteSize = MIN(maxBatchRows * m_batch_byte_size, m_scan_batch_size)
config.ini example: 
[api]
BatchSize=1000              # More rows per fragment (default 384)
BatchByteSize=131072        # 128 KB per fragment (default 32 KB)
MaxScanBatchSize=524288     # 512 KB total across all fragments (default 32 KB)
Requires a rolling restart of API nodes (MySQL Servers) to take effect. Data nodes do not need to restart.

10.3 MySQL Session Variables

MySQL exposes several thread-local variables via SET SESSION that override or complement the cluster-level defaults. These are defined as MYSQL_THDVAR in ha_ndbcluster.cc.

ndb_batch_size (bytes)

-- Override the byte budget for this session
SET SESSION ndb_batch_size = 65536;   -- 64 KB (default: 0 = use cluster config)

When set to a non-zero value, this overrides BatchByteSize from config.ini for this connection. It is applied in ha_ndbcluster::transaction_checks() at the start of each transaction:

// ha_ndbcluster.cc — transaction_checks()
m_batch_size = THDVAR(thd, batch_size);   // ndb_batch_size session variable

This controls the byte budget for all NDB scans in this session, including both standalone scans and pushed join scans.

ndb_join_pushdown (boolean)

-- Disable pushed joins for this session (debug/comparison)
SET SESSION ndb_join_pushdown = OFF;

-- Re-enable (default)
SET SESSION ndb_join_pushdown = ON;

When OFF, the MySQL optimizer will not attempt to push multi-table joins down to data nodes. Each table is scanned independently and joined at the MySQL Server. This is useful for performance comparisons or when pushed joins produce suboptimal plans.

ndb_optimized_node_selection

-- Control how transactions select data nodes
SET SESSION ndb_optimized_node_selection = 3;   -- Default: 0

Influences which data node is chosen as the transaction coordinator. Higher values enable more sophisticated locality-based selection, which can reduce network hops for pushed joins when the root table's primary fragment is on a specific node.

ndb_use_exact_count

-- Use exact row counts for query planning (slower but more accurate plans)
SET SESSION ndb_use_exact_count = ON;   -- Default: OFF

When enabled, the MySQL optimizer gets accurate row count estimates from NDB, which can lead to better join ordering decisions and more appropriate batch size choices for pushed joins.

ndb_force_send

-- Disable adaptive send (force immediate send of all signals)
SET SESSION ndb_force_send = ON;   -- Default: ON

When ON, signal buffers are flushed to data nodes immediately without waiting for additional operations to batch. For pushed joins with high parallelism, this ensures SCAN_FRAGREQs are dispatched without delay.

Viewing current settings

-- Show all NDB-related session variables
SHOW SESSION VARIABLES LIKE 'ndb%';

-- Key ones for pushed join tuning:
SELECT @@ndb_batch_size, @@ndb_join_pushdown, @@ndb_use_exact_count;

10.4 NDB API Methods (Per-Operation)

When using the NDB API directly (not through MySQL), the NdbQueryOperation class provides fine-grained control over batch sizes and parallelism for each scan operation in a pushed join query tree.

setBatchSize(Uint32 batchSize)

// Set maximum rows per batch for this scan operation
NdbQueryOperation *rootScan = query->getQueryOperation(0u);
rootScan->setBatchSize(2000);   // 0 = use default from cluster config

// Constraint: for non-root scans, batchSize >= fragmentCount
// (each fragment must be able to return at least 1 row)

Sets m_maxBatchRows which flows into calculateBatchedRows(). For parent operations (those with children), the effective batch size is further capped at 4096 / fragsPerWorker to respect the 12-bit correlation ID limit.

setParallelism(Uint32 parallelism)

// Fix the number of fragments scanned in parallel
rootScan->setParallelism(8);   // Scan 8 fragments simultaneously

// Constraints:
//   - Only for root scan operations
//   - Cannot be used with ordered (sorted) index scans
//   - 0 = max parallelism (all fragments at once)

Overrides DBSPJ's adaptive parallelism for the root scan. The value is sent as scanParallelism in SCAN_TABREQ, and DBTC allocates that many ScanFragRec handles. Child scan parallelism is always adaptive and cannot be directly overridden from the API.

setMaxParallelism()

// Scan all fragments in parallel from the start
rootScan->setMaxParallelism();

// Equivalent to setParallelism(rootFragments)
// Maximizes throughput at the cost of higher memory usage

setAdaptiveParallelism()

// Let DBSPJ dynamically choose parallelism (default for child scans)
childScan->setAdaptiveParallelism();

// DBSPJ starts conservatively (rootFragCount fragments) then adjusts
// based on m_recsPrKeyStat fanout statistics from previous batches

This is the default for non-root scan operations. Root scans default to max parallelism. Adaptive parallelism uses scanFrag_parallelism() which was described in Section 8.

Complete NDB API Example

// Building a pushed join query with tuned batch sizes
NdbQueryBuilder builder(ndb);

// Define query tree: Orders → LineItems (scan-scan join)
const NdbQueryTableScanOperationDef *ordersScan =
    builder.scanTable(ordersTable);
const NdbQueryIndexScanOperationDef *lineitemsScan =
    builder.scanIndex(lineitemsIndex, ordersScan, ...);

NdbQuery *query = transaction->createQuery(&builder.prepare(), ...);

// Tune root scan: large batches, full parallelism
NdbQueryOperation *root = query->getQueryOperation(0u);
root->setBatchSize(4000);          // Max rows per batch
root->setMaxParallelism();         // All fragments in parallel

// Child scan: let DBSPJ adapt
NdbQueryOperation *child = query->getQueryOperation(1u);
child->setBatchSize(2000);         // Allow large child batches
// child parallelism is always adaptive — controlled by DBSPJ

transaction->execute(NoCommit);

10.5 How MySQL Server Uses These Settings

When the MySQL optimizer decides to push a join, the handler in ha_ndbcluster_push.cc builds an NdbQuery and applies configuration from the session variables. The flow is:

// ha_ndbcluster_push.cc — simplified flow

1. MySQL optimizer calls handler->make_pushed_join()
   → Checks: THDVAR(thd, join_pushdown) == true?

2. Build NdbQueryDef from the join plan
   → Each table becomes an NdbQueryOperationDef

3. At execution time, create NdbQuery from NdbQueryDef
   → Root scan gets batch size from:
      a. ndb_batch_size session variable (if non-zero)
      b. Else cluster config BatchByteSize / BatchSize
   → Parallelism: root always max, children adaptive

4. NdbQueryOperation::calculateBatchedRows() runs:
   → Applies correlation ID cap (4096 / fragsPerWorker)
   → Recursively reduces to min acceptable across children
   → Byte limit from ndb_batch_size or BatchByteSize

5. SCAN_TABREQ sent to DBTC with:
   batch_size_rows, batch_size_bytes, scanParallelism
MySQL Server has no direct control over child scan parallelism. The MySQL handler sets the root scan's batch size and parallelism. Child operations (both lookups and scans) have their batch sizes derived from the root's budget via calculateBatchedRows(), and child scan parallelism is always adaptive (managed by DBSPJ's scanFrag_parallelism() using runtime fanout statistics). The only way to influence child behavior from MySQL is by increasing the root batch budget, which gives children more room to work with.

10.6 Table Partitioning

The number of table fragments (partitions) directly determines the maximum parallelism for scans on that table. More fragments means more independent scan units that can be distributed across DBSPJ instances.

-- Default: NDB auto-partitions based on data node count and LDM threads
-- Typically: fragments = dataNodes × LDM_threads_per_node

-- Explicit partitioning for higher parallelism:
CREATE TABLE orders (
  order_id INT PRIMARY KEY,
  customer_id INT,
  order_date DATE
) ENGINE=NDB
  PARTITION BY KEY(order_id)
  PARTITIONS 32;             -- 32 fragments instead of default

-- MAX_ROWS hint (alternative — NDB infers partition count):
CREATE TABLE lineitems (
  ...
) ENGINE=NDB
  MAX_ROWS=100000000;        -- Hint: expect 100M rows → more partitions
Impact on pushed joins: With 32 partitions across 4 data nodes (8 per node) and MultiFragFlag OFF, each DBTC distributes fragments across TC threads using round-robin DBSPJ instance assignment. With 4 TC threads per node, this gives 4×4 = 16 DBSPJ instances working in parallel. Increasing partitions beyond the number of TC threads × data nodes doesn't add more DBSPJ parallelism, but does allow finer-grained work distribution within each DBSPJ instance's adaptive parallelism.

10.7 MultiFragFlag (Automatic)

MultiFragFlag controls whether multiple fragments are bundled into a single SCAN_FRAGREQ to one DBSPJ instance (reducing signal overhead) or each fragment gets its own SCAN_FRAGREQ to a different DBSPJ instance (maximizing TC-thread parallelism). This is not user-configurable — it is automatically determined by the query structure:

Condition fragsPerWorker MultiFragFlag DBSPJ Parallelism
Standard (unordered) scan rootFrags / dataNodes ON 1 instance per data node
Ordered (sorted) scan 1 OFF 1 instance per fragment
Aggregation query (RONDB-733) 1 OFF 1 instance per fragment
Pruned scan (single fragment) 1 OFF 1 instance 
// NdbQueryOperation.cpp — fragsPerWorker determination (simplified)
if (pruned)
    m_fragsPerWorker = 1;
else if (orderedScan)
    m_fragsPerWorker = 1;     // Merge-sort needs per-fragment streams
else if (m_hasAggregation)
    m_fragsPerWorker = 1;     // Maximize TC-thread parallelism
else
    m_fragsPerWorker = rootFragments / dataNodeCount;  // Bundle for efficiency

if (m_fragsPerWorker > 1)
    ScanTabReq::setMultiFragFlag(reqInfo, 1);

10.8 Practical Tuning Guide

The following table summarizes common tuning scenarios for pushed joins:

Symptom Likely Cause Configuration Fix
Many SCAN_NEXTREQ round-trips Batch too small for fanout SET ndb_batch_size = 131072; or increase BatchSize/BatchByteSize in config.ini
Only 1 TC thread active MultiFragFlag ON, all fragments bundled Use ordered index scan (forces fragsPerWorker=1) or use aggregation query
Child scans start slowly Adaptive parallelism conservative start NDB API: setMaxParallelism() on root; or increase partitions so minParallelism is higher
Byte limit hit before row limit Large rows exhaust byte budget SET ndb_batch_size = 262144; or BatchByteSize=262144 and MaxScanBatchSize=1048576
Pushed join slower than non-pushed Bad join order or excessive fanout SET ndb_join_pushdown = OFF; to compare; SET ndb_use_exact_count = ON; for better plans
Low parallelism across nodes Too few partitions ALTER TABLE t REORGANIZE PARTITION; or recreate with more PARTITIONS

Theoretical Maximum Parallelism

Total parallelism = dataNodes × partitionsPerNode × (1 if MultiFrag, else TC_threads)

Example with MultiFrag OFF (ordered/aggregation scans):
  4 data nodes × 8 partitions/node × 4 TC threads = 128 parallel DBSPJ instances
  batch_size_rows per fragment = total_batch / 128

With MultiFrag ON (default unordered scans):
  4 data nodes × 1 DBSPJ instance per node = 4 parallel instances
  Each instance handles 8 fragments sequentially within one thread
  batch_size_rows per fragment = total_batch / (8 fragments bundled)
Key insight: The batch size budget (batch_size_rows and batch_size_bytes) is divided by the parallelism to get per-fragment limits: bs_rows = availableRows / parallelism. If the total budget is too small relative to the parallelism, each fragment gets very few rows per batch, causing excessive NEXTREQ round-trips. When increasing parallelism (more partitions, MultiFragFlag OFF), also increase BatchSize and BatchByteSize proportionally so per-fragment batches remain adequately sized.
