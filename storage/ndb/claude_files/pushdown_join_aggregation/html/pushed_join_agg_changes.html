Pushdown Join Aggregation

How RONDB-733 extends the pushed join architecture to execute aggregation inside data nodes — new signals, changed data paths, concurrency strategies, and implications for batch sizing, fanout, and buffer management.

This document is a companion to NDB Pushed Joins (Without Aggregation), which describes the baseline DBSPJ architecture. Here we focus on what changes when aggregation is pushed down alongside the join.

1. Architectural Overview: What Changes

In a regular pushed join, DBLQH processes each row from the NDB interpreter and sends it directly to the NDB API via TRANSID_AI. With pushdown join aggregation, the row is intercepted before it reaches the API: instead of being forwarded, it is fed into a JoinAggInterpreter that maintains a GROUP BY hash map and accumulates aggregate values (SUM, COUNT, MIN, MAX, etc.). Only the final aggregated groups are sent to the API.

This requires three major architectural additions that don't exist in the regular pushed join path:

  1. A signal lifecycle (SETUP / COMPLETE / RELEASE) managed by DBTC, separate from the normal SCAN_FRAGREQ flow, to create and destroy aggregation state on each data node
  2. Shared state across LDM threads (JoinAggregationState), coordinated by DblqhProxy, because aggregation must combine results from multiple fragments processed by different threads
  3. A new interpreter engine (JoinAggInterpreter) with its own chunk allocator, hash map, group eviction, and flow-controlled result delivery
Companion document: The baseline pushed join architecture (signal flow, DBSPJ data structures, linked columns, batch sizing, congestion control) is documented in NDB Pushed Joins (Without Aggregation). This document assumes familiarity with that material and focuses only on the delta.

2. New Signal Lifecycle: SETUP / COMPLETE / RELEASE

Regular pushed joins need only SCAN_FRAGREQ/CONF to drive the query. Aggregation adds a three-phase signal protocol managed by DBTC that brackets the scan execution:

Figure 1: The four-phase aggregation lifecycle. SETUP creates shared state, RUNNING accumulates rows into GROUP BY hash maps (with optional eviction), COMPLETE finalizes and streams batched results, RELEASE frees all resources.

Signal Definitions (JoinAgg.hpp)

SignalDirectionKey Payload
JOIN_AGG_SETUP_REQ DBTC → DblqhProxy transid, tableId, concurrencyStrategy, resultRef/Data, Section 0: aggProgram, Section 1: receiverIds
JOIN_AGG_SETUP_CONF DblqhProxy → DBTC aggStateKey — pool index for O(1) lookup by all worker threads
JOIN_AGG_COMPLETE_REQ DBTC → DBLQH worker aggStateKey, maxBatchRows (controls result batch size)
JOIN_AGG_COMPLETE_CONF DBLQH worker → DBTC numResultRows, resultBytes (final statistics)
JOIN_AGG_SEND_REQ DBLQH → DBTC "I've batched N rows, pausing (receiver not ready)"
JOIN_AGG_SEND_CONF DBTC → DBLQH "Continue, new maxBatchRows = M"
JOIN_AGG_RELEASE_REQ DBTC → DblqhProxy aggStateKey
JOIN_AGG_RELEASE_CONF DblqhProxy → DBTC (acknowledgement)
SETUP and RELEASE go to DblqhProxy (single-threaded, manages pool), while COMPLETE goes to a DBLQH worker (which performs the merge and result serialization). This is because SETUP/RELEASE need coordinated pool management, while COMPLETE needs access to the LDM execution environment for sending TRANSID_AI signals.

3. Changed Data Path: Row Interception and Aggregation

In a regular pushed join, the NDB interpreter processes each row (WHERE clause), and if it passes, the row is sent via TRANSID_AI — one signal for the API (result data) and one for DBSPJ (linked columns for child dispatch). With aggregation, the leaf table's data path is fundamentally different:

Figure 2: In regular joins, every matching row generates a TRANSID_AI to the API. With aggregation, handleJoinAggRow() consumes rows into the GROUP BY hash map. Only aggregated groups are eventually sent.

Intermediate Tables: No Result Rows

In a regular pushed join, all tables in the join tree send their result rows to the API (each with a FLUSH_AI marker in the AttrInfo). With aggregation, only the leaf table (marked with NI_AGGREGATE_LEAF in the QueryTree) produces result data. Intermediate tables pass data only through linked attributes for child dispatch — they never send TRANSID_AI result rows to the API. This makes sense: the API doesn't need the intermediate rows, only the final aggregated result.

4. Shared State: JoinAggregationState and Cross-LDM Coordination

In regular pushed joins, each SCAN_FRAGREQ is completely independent — each LDM thread processes its fragment(s) with no shared state. Aggregation changes this fundamentally: all LDM threads on a data node must contribute to the same aggregation result. This requires shared state managed by DblqhProxy.

JoinAggregationState Structure

Created by DblqhProxy during JOIN_AGG_SETUP_REQ, one per data node per query:

struct JoinAggregationState {
  // Immutable after SETUP (no synchronization needed)
  Uint32 m_transid[2];
  Uint32 m_senderRef, m_senderData, m_requestId;
  Uint32 m_resultRef, m_resultData, m_routeRef;     // API routing
  Uint32 *m_agg_program;                             // Aggregation bytecode (ndbd_malloc'd)
  Uint32  m_agg_program_len;
  Uint32 *m_receiverIds;                             // Hash-partitioned result routing
  Uint32  m_numReceiverIds;
  Uint32  m_strategy;                                // MUTEX_BASED or MUTEX_FREE

  // Interpreter(s) — depends on strategy
  JoinAggInterpreter *m_agg_interpreter;             // MUTEX_BASED: single shared
  JoinAggInterpreter **m_per_thread_interpreters;    // MUTEX_FREE: one per LDM thread
  Uint32 m_num_threads;

  // Atomic operation tracking
  std::atomic<Uint32> m_outstanding_ops;
  std::atomic<Uint32> m_completed_ops;
  std::atomic<Uint32> m_failed_ops;
  Uint32 m_total_ops_expected;

  // Result streaming state
  Uint32 m_agg_curr_batch_size_rows;
  Uint32 m_agg_curr_batch_size_bytes;
  Uint32 m_rows_sent;
  Uint32 m_max_batch_rows;                           // Flow control limit

  // State machine (atomic)
  // IDLE → SETUP_COMPLETE → ACCUMULATING → FINALIZING → SENDING_RESULTS → COMPLETED
};

DblqhProxy: The Coordinator

DblqhProxy is the single-threaded proxy block that runs outside of any LDM thread. It handles SETUP and RELEASE because these require coordinated pool management. Its responsibilities:

  • SETUP: Seize pool record, calculate initial memory budget (1% of available RG_QUERY_MEMORY pages, min 4 pages = 128KB — grows dynamically as needed), ndbd_malloc the aggregation program and receiver IDs, create interpreter(s), initialize chunk allocators
  • RELEASE: Free interpreter chunks, free program buffer, free receiver IDs array, release pool record back to TransientPool
aggStateKey for O(1) lookup: SETUP_CONF returns an aggStateKey (a TransientPool index) that is embedded in subsequent SCAN_FRAGREQs. Each DBLQH worker can look up the shared JoinAggregationState in O(1) without any search — critical for performance since every row processed must access this state.

5. Concurrency Strategies: Mutex-Based vs. Mutex-Free

Multiple LDM threads on the same data node process different fragments of the same table concurrently. They all need to accumulate into the same GROUP BY hash map. Two strategies are supported:

Figure 3: Mutex-based shares one interpreter (high contention, shared budget); mutex-free gives each thread its own interpreter (zero contention, merge at completion). Both strategies grow memory dynamically via chunk allocation.

The strategy is specified in JOIN_AGG_SETUP_REQ and cannot be changed during execution. For mutex-free, the merge phase at COMPLETE iterates through each per-thread interpreter's hash map, combining groups with matching keys by merging their accumulator values (e.g., adding SUM values, taking MAX of MAX values).

5.1 Chunk-Based Memory Allocator

Each JoinAggInterpreter uses a chunk-based allocator for GROUP BY data. The interpreter object itself is placed in an initial 32KB page (MEM_CHUNK_SIZE = 32768), but group data is allocated in additional 32KB chunks that are acquired dynamically from lc_ndbd_pool_malloc() as needed. There is no fixed 32KB-per-thread limit — memory grows on demand up to the available system memory in the RG_QUERY_MEMORY resource group.

// JoinAggInterpreter — chunk-based memory growth

struct MemChunk {
  char     *data;          // Usable data (after MemChunk header)
  Uint32    capacity;      // MEM_CHUNK_SIZE - sizeof(MemChunk)
  Uint32    used;          // Current allocation offset
  Uint32    live_groups;   // Active groups in this chunk
  MemChunk *next, *prev;   // Doubly-linked list
};

// Fields tracking memory state:
MemChunk *m_chunks;              // Head of chunk list
MemChunk *m_current_chunk;       // Active chunk for new allocations
Uint32    m_total_chunk_bytes;   // Sum of all allocated chunks
Uint32    m_memory_budget;       // Current budget (grows dynamically)
Uint32    m_budget_increment;    // How much to grow budget each time
Uint32    m_total_available;     // System-wide limit (RG_QUERY_MEMORY)

Budget Calculation at SETUP

// DblqhProxy.cpp — execJOIN_AGG_SETUP_REQ

// Query available memory in the RG_QUERY_MEMORY resource group
Resource_limit rl;
m_ctx.m_mm.get_resource_limit_nolock(RG_QUERY_MEMORY, rl);
available_pages = MIN(rl.m_max - rl.m_curr, free_shared_pages);

// Initial budget: 1% of available, minimum 4 pages (128 KB)
budget_pages = MAX(available_pages / 100, 4);

// For mutex-free: divide budget across threads
per_thread_budget = MAX(budget_pages / num_threads, 4);

// Each interpreter gets:
interp->initChunkAllocator(thread_id, per_thread_budget, available_pages);
//   m_memory_budget  = per_thread_budget × MEM_CHUNK_SIZE  (e.g., 128 KB)
//   m_budget_increment = m_memory_budget                    (doubles each growth)
//   m_total_available  = available_pages × MEM_CHUNK_SIZE   (system limit)

Dynamic Growth: bookMoreMemory()

When a new group needs memory and the current chunk is full, allocNewChunk() is called. If allocating another 32KB chunk would exceed the current budget, bookMoreMemory() extends the budget:

// JoinAggInterpreter::allocNewChunk()

if (m_total_chunk_bytes + MEM_CHUNK_SIZE > m_memory_budget) {
    if (!bookMoreMemory())      // Try to grow budget
        return nullptr;         // System memory exhausted
}
void *page = lc_ndbd_pool_malloc(MEM_CHUNK_SIZE, RG_QUERY_MEMORY,
                                 m_thread_id, false);
m_total_chunk_bytes += MEM_CHUNK_SIZE;
// ... initialize MemChunk, append to linked list ...

// bookMoreMemory():
bool bookMoreMemory() {
    Uint32 new_budget = m_memory_budget + m_budget_increment;
    if (new_budget > m_total_available)
        return false;           // No more system memory
    m_memory_budget = new_budget;
    return true;                // Budget extended
}
Figure 3b: Memory grows in 32KB chunks. The budget starts small (1% of available, min 128KB) and extends on demand via bookMoreMemory() until system memory is exhausted.
Contrast with AggInterpreter: The regular (non-join) AggInterpreter used for single-table scan aggregation fits entirely in one 32KB page with inline buffers and a std::map. The JoinAggInterpreter was separated specifically to support dynamic chunk growth, the 1024-bucket hash table, linked attribute processing, and group eviction — none of which the simpler AggInterpreter needs.

6. Group Eviction: When Memory Runs Out

In production, m_max_groups is 0 (unlimited) — the hash map can hold as many groups as memory allows. Eviction is triggered when the chunk allocator can no longer allocate memory for a new group, i.e., when allocGroupData() returns nullptr because allocNewChunk() failed (system memory exhausted after repeated bookMoreMemory() attempts). This is the real-world eviction trigger.

The code returns AGG_EVICT_NEEDED in two cases:

// JoinAggInterpreter::processRecWithLinkedAttrs() — two eviction triggers

// 1. m_max_groups limit hit (only non-zero in ERROR_INSERT testing)
if (m_max_groups > 0 && m_n_groups >= m_max_groups) {
    return AGG_EVICT_NEEDED;
}

// 2. Memory allocation failure (the real production trigger)
char *agg_rec = allocGroupData(rec_len, key_len);
if (agg_rec == nullptr) {
    return AGG_EVICT_NEEDED;   // No memory for new group
}

The caller in handleJoinAggRow() handles both cases identically — evict one existing group and retry:

// DbtupExecQuery.cpp — handleJoinAggRow() eviction loop

retry:
  Int32 ret = interp->processRecWithLinkedAttrs(row, linked_data, linked_len);

  if (ret == AGG_EVICT_NEEDED) {
      // Evict one group to free memory (or free a group count slot)
      Int32 evict_ret = interp->evictOneGroup(buf, buf_size, &words_written);

      // Send evicted group as a partial result via TRANSID_AI
      // Hash-route to correct receiver: receiverIds[hash(key) % numReceiverIds]
      Uint32 receiverId = state->selectReceiverData(evicted_key, key_len);
      sendSignal(state->m_resultRef, GSN_TRANSID_AI, signal, ...);
      state->m_rows_sent++;

      goto retry;   // Now there's room — insert the new group
  }

Evicted groups are partial results — they contain the accumulated aggregates for that group so far. The NDB API's aggregator must merge partial results for the same group key from multiple evictions and multiple data nodes. This is why the receiver routing uses a hash of the group key: all partial results for the same group always arrive at the same API receiver, enabling local merge without cross-receiver coordination.

In practice, eviction is rare. Since the chunk allocator grows dynamically (Section 5.1) up to the full RG_QUERY_MEMORY capacity, eviction only occurs when the data node's query memory resource group is genuinely exhausted — typically only for queries with extremely high GROUP BY cardinality or when multiple concurrent aggregation queries compete for memory.
Testing eviction: Since eviction is rare in production, two ERROR_INSERT codes exist to force it during testing:
  • ERROR_INSERT 5090: Forces setMaxGroups(3) during SETUP, so the 4th distinct group triggers eviction regardless of available memory
  • ERROR_INSERT 4040: Randomly evicts every 7th row when the map has more than 2 groups, stressing the eviction and partial-result merge paths

7. Result Flow Control: JOIN_AGG_SEND_REQ/CONF

In regular pushed joins, DBLQH sends individual rows via TRANSID_AI as they are processed, with no explicit flow control between DBLQH and the API (batch size limits the output implicitly). With aggregation, the result volume can be large (many groups) and is produced in a burst during the COMPLETE phase. Explicit flow control prevents overwhelming the API:

// DBLQH — continueJoinAggSend() result streaming loop

while (groups remaining in hash map) {
    serialize next group → TRANSID_AI buffer
    m_agg_curr_batch_size_rows++;
    m_agg_curr_batch_size_bytes += group_bytes;

    if (m_agg_curr_batch_size_rows >= m_max_batch_rows) {
        // Batch full — send what we have, then pause
        flush TRANSID_AI signals to API;

        // Ask DBTC for permission to continue
        send JOIN_AGG_SEND_REQ(rows_sent, bytes_sent);
        return;  // Will resume when SEND_CONF arrives
    }
}

// All groups sent — finalize
send JOIN_AGG_COMPLETE_CONF(numResultRows, resultBytes);

When DBTC receives JOIN_AGG_SEND_REQ, it checks whether the API has consumed the previous batch (receiver ready). If so, it replies with JOIN_AGG_SEND_CONF containing a new maxBatchRows limit (typically 256). DBLQH resumes serialization from where it paused.

8. Impact on Fanout, Batch Sizing, and Parallelism

Aggregation changes several assumptions that the regular pushed join batch sizing relies on. This section describes those differences and their implications.

8.1 MultiFragFlag Disabled: Maximum TC-Thread Parallelism

For regular (unordered) pushed joins, the API bundles multiple fragments per worker (fragsPerWorker = rootFragments / dataNodes) using MultiFragFlag. This sends one SCAN_FRAGREQ per data node, with all that node's fragments bundled into a single DBSPJ instance.

Aggregation forces fragsPerWorker = 1, disabling MultiFragFlag. Each fragment gets its own SCAN_FRAGREQ to a separate DBSPJ instance on a different TC thread:

// NdbQueryOperation.cpp — fragsPerWorker for aggregation

if (m_hasAggregation) {
    // Each fragment gets its own SCAN_FRAGREQ to a separate DBSPJ instance
    // for maximum parallelism across TC threads. Multi-fragment bundling would
    // serialize all fragments on a node into one DBSPJ instance.
    m_fragsPerWorker = 1;
}
Why this makes sense for aggregation: Multi-fragment bundling saves API round-trips by reducing the number of SCAN_FRAGREQs. But aggregation results are per-node (not per-fragment) — the savings from bundling don't apply. Meanwhile, distributing fragments across DBSPJ instances gives parallelism across TC threads, which is more valuable for the compute-intensive aggregation workload.

8.2 scanParallelism: Explicit vs. Implicit

For regular queries, DBTC derives scanParallelism from the number of receiver IDs in Section 0 of SCAN_TABREQ. With aggregation, Section 0 carries aggregation receiver IDs (hash-partitioned result routing), not scan worker handles. The actual scan parallelism must be communicated separately:

// NdbQueryOperation.cpp — explicit scanParallelism for aggregation

if (m_hasAggregation) {
    ScanTabReq::setJoinAggFlag(reqInfo, 1);
    scanTabReq->scanParallelism = m_workerCount * m_fragsPerWorker;
    // Stored in DATA word 15 of SCAN_TABREQ (extended format)
}

// DbtcMain.cpp — reading scanParallelism
if (ScanTabReq::getJoinAggFlag(ri))
    scanParallel = scanTabReq->scanParallelism;   // Explicit
else
    scanParallel = numReceiverIds;                 // Implicit from Section 0

8.3 Batch Byte Size: Different Semantics

For regular pushed joins, batch_size_bytes controls the amount of data received at the API — directly tied to API receive buffer capacity. For aggregation, the root scan's batch_size_bytes controls DBLQH → DBSPJ throughput (raw scan rows flowing through the join), not API buffer size (the API receives only aggregated groups, which are much smaller).

// NdbQueryOperation.cpp — restore batch_byte_size for aggregation root

if (getQuery().m_hasAggregation && getParentOperation() == nullptr) {
    // For aggregate root scans, batch_byte_size controls DBLQH→DBSPJ
    // throughput, not API receive buffer. result_bufsize() caps it to
    // the tiny API buffer (no getValue columns). Restore to the value
    // from calculate_batch_size() so config BatchByteSize takes effect.
    m_maxBatchBytes = batchByteSize;
}
Result size reduction: A join that produces 100,000 rows with aggregation might yield only 50 aggregated groups. The API receive buffer only needs to hold these 50 groups, not the 100,000 intermediate rows. The intermediate rows are consumed entirely within the data nodes by the JoinAggInterpreter.

8.4 Fanout and estmMaxKeys()

The fanout estimation machinery (estmMaxKeys(), m_recsPrKeyStat, scanFrag_parallelism()) described in the companion document still operates normally for the join portion of the query. The root scan and child operations still use batch buffers with the same sizing logic. What changes is the leaf table's output:

  • In a regular join, the leaf table's rows flow to the API, and its batch buffer capacity is the binding constraint in estmMaxKeys()
  • With aggregation, the leaf table's rows are consumed by JoinAggInterpreter — they never reach the API. The binding constraint shifts to the JoinAggInterpreter's hash map capacity (m_max_groups) and chunk allocator budget instead of the scan batch buffer
  • If the hash map fills, eviction handles the overflow (partial results sent to API), so the scan never stalls — it just produces more partial groups that need merging

This means aggregation queries are less sensitive to batch size tuning for the leaf table — the critical resource is the aggregation memory budget, not the batch buffer. However, the join tables above the leaf still use normal batch sizing, so tuning those remains relevant.

9. NDB API Changes: Receivers, Programs, and Result Merging

9.1 Aggregation Receivers

The NDB API allocates a set of NdbReceiver objects specifically for aggregation results, separate from the regular scan receivers. The count equals the number of workers (m_workerCount), providing hash-partitioned result routing:

// NdbQueryOperation.cpp — prepareSend()

m_numAggReceivers = m_workerCount;
m_aggReceivers = new NdbReceiver *[m_numAggReceivers];

for (Uint32 i = 0; i < m_numAggReceivers; i++) {
    NdbReceiver *rec = ndb->getNdbScanRec();
    rec->init(NdbReceiver::NDB_AGG_RECEIVER, this);
    m_aggReceivers[i] = rec;
}

Each receiver gets a disjoint subset of group keys (via hash routing at the data node). Because the same group key from different data nodes always maps to the same receiver, merging partial results happens locally within each receiver — no cross-receiver coordination needed.

9.2 Aggregation Program Transmission

The aggregation bytecode (the program that tells JoinAggInterpreter which columns to GROUP BY and which aggregates to compute) is packed into Section 2 of SCAN_TABREQ alongside any bounds data:

Section 2 layout for aggregation:
  [boundsLen]                    // Uint32: length of bounds data (0 if none)
  [bounds data...]               // boundsLen words
  [aggReceiverId]                // Uint32: object map ID for result routing
  [aggregation program...]       // Variable-length bytecode

DBTC extracts the bounds and forwards the remaining data (receiver ID + program) to DblqhProxy via JOIN_AGG_SETUP_REQ sections.

9.3 Result Collection and Merging

Aggregated results arrive as TRANSID_AI signals at the aggregation receivers. The API accumulates these in m_aggResultData with offset tracking per batch. After all scan batches complete (EndOfData), the API processes all accumulated batches:

// NdbQueryImpl::processAggResults()

for each batch received on aggregation receivers:
    skip AttributeHeader (1 word)
    feed remaining data to m_aggregator->ProcessRes()

m_aggregator->PrepareResults()
// User calls query->getAggregator()->FetchResultRecord() to iterate

ProcessRes() merges partial aggregates from multiple data nodes and from eviction: if two partial results share the same group key, their SUM values are added, COUNT values are added, MAX values take the larger, etc.

10. Potential Optimizations Not Yet Exploited

The current implementation prioritizes correctness and simplicity. Several optimizations are architecturally possible but not yet implemented:

10.1 Larger Batch Budgets for Aggregation

Opportunity: Since aggregated results are much smaller than raw join rows (50 groups vs. 100,000 rows), the API receive buffer is underutilized. The root scan's batch_size_bytes could be increased specifically for aggregation queries to allow more raw rows to flow through the join pipeline per batch, reducing SCAN_NEXTREQ round-trips.

Current state: The API already restores batchByteSize for aggregation root scans (not capping to the tiny API buffer), but the cluster-level BatchByteSize config still applies uniformly. A per-query override for aggregation could yield significant throughput gains for large joins.

10.2 Adaptive Congestion Thresholds

Opportunity: DBSPJ's congestion control (Section 9 of the companion document) uses fixed thresholds: defer at 256 outstanding, resume at 128. For aggregation queries, the child operations feed rows into a hash map (not into API buffers), so the "congestion" semantics differ. The hash map can absorb rows much faster than API network delivery, so higher thresholds could be used, reducing the frequency of defer/resume cycles.

Current state: The same HighlyCongestedLimit (256) and MildlyCongestedLimit (128) apply regardless of whether aggregation is active.

10.3 Pipelined Result Delivery

Opportunity: Currently, aggregation follows a strict sequence:
  1. SETUP (blocking)
  2. RUNNING — all scans complete, all rows accumulated
  3. COMPLETE — finalize, merge per-thread interpreters, stream all results
Results are not delivered until all scans have finished. For queries with many fragments, some fragments complete long before others. Partial results from completed fragments could be streamed to the API while other fragments are still scanning, reducing latency to first result.

Challenge: Partial results would need to be clearly marked as non-final, and the API aggregator would need to handle streaming merge. The JOIN_AGG_SEND_REQ/CONF flow control already exists and could be extended to support this.

10.4 Adaptive Receiver Count

Opportunity: Currently, m_numAggReceivers = m_workerCount (fixed). For queries with very few distinct groups (e.g., GROUP BY country with ~200 countries), fewer receivers would suffice and reduce overhead. For queries with millions of distinct groups, more receivers could improve parallelism.

Challenge: Receiver count must be known before execution (at SETUP time), but the number of distinct groups is often unknown. Could use optimizer estimates or hints from the query definition.

10.5 Memory-Adaptive Concurrency Strategy

Opportunity: The concurrency strategy (mutex-based vs. mutex-free) is currently chosen by the query builder. An adaptive approach could:
  • Start with mutex-free if memory budget allows (budget / num_threads ≥ min_chunk_size)
  • Fall back to mutex-based if memory is tight
  • Consider the expected GROUP BY cardinality: few groups favor mutex-based (less memory waste), many groups favor mutex-free (less contention per insert)
Current state: Strategy is fixed at query definition time and cannot adapt to runtime conditions.

10.6 Aggregation-Aware estmMaxKeys()

Opportunity: The estmMaxKeys() function estimates how many root keys can fit in child batch buffers based on fanout statistics. For aggregation queries, the leaf table's "output" is not rows but aggregated groups — a dramatic reduction. An aggregation-aware version could use the hash map capacity and expected group count instead of the scan batch buffer to estimate the leaf's constraint, potentially allowing larger root batches.

Current state: estmMaxKeys() treats the aggregation leaf identically to a regular leaf scan, using batch_size_rows / fanout as the constraint. Since the hash map handles overflow via eviction, this underestimates the actual capacity.
