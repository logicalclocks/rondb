RONDB-1051 — read-path micro-optimisations from execLQHKEYREQ through sendReadAttrinfo

This document summarises the 47 commits on the RONDB-1051-execLQHKEYREQ branch since RONDB-1051-baseline. The optimisation target is the entire committed-read signal chain as it flows through an NDB data node — from the LQHKEYREQ signal entry in DBLQH to the final TRANSID_AI signal sent back by DBTUP.

An earlier document (rondb_1051_performance.html) described the first 17 commits, which focused on the PK read, TUX ordered-index key-attribute read, and interpreter single-column read paths (hot inside DBTUP/DBTUX — particularly the tuxReadPk, tuxReadAttrsOpt, and readSingleAttribute functions). This document covers those and the subsequent 30 commits, which extended the work across the full signal chain on the primary-key read critical path.

Context: every committed-read request coming into an LDM thread as an LQHKEYREQ signal traverses the chain below. On busy clusters this is hundreds of thousands of calls per LDM thread per second, so code-size and instruction-count savings multiply up quickly.

4. Impact on the L1 instruction cache

Modern CPUs typically have 32–64 KB of L1 instruction cache per core. The committed-read chain, on a single request, touches every function listed above plus the sub-functions they invoke (setup_read, readAttributes, NdbMutex_Lock/Unlock, jam ring, etc.).

Three classes of change contribute to better I-cache behaviour:

Fewer bytes in the hot region

Every byte of code that is moved to the cold-text region leaves the hot working set and does not compete for L1-I ways. The cumulative hot reduction on the PK read chain is ~4.2 KB. A single L1-I miss costs ~10–20 cycles on modern ARM64 cores; even a modest reduction in miss rate across the full read chain saves real latency at scale.

Straightened hot paths (fewer branches + better branch-target locality)

Before the work, several functions had the hot path woven between cold branches, forcing forward-then-backward jumps across multiple cache lines even on the fast case. Examples:

  • execLQHKEYREQ: the TakeOver / disk-flag / op-dispatch pattern is now linearly arranged.
  • handleReadReq: the old zigzag (cbz ttl_ignore → jump, cmp ttl_only_expired → jump, 2× RNIL → back-jump, tbz interpreted_exec → jump) is reduced to a single ldrb + cbz on the cached TTL bit followed by straight-line fall-through to the readAttributes call.
  • sendReadAttrinfo: cross-node API and EXECUTE_DIRECT paths are now the first two dispatches; long-signal and routing paths are out-of-line.

Cold paths moved to a far-away cold-text region

Multiple handlers — handleTakeOver, continueACCKEYCONF_zwrite_slow, handleReadReqOnlyExpiredOnNonTtlTable, sendReadAttrinfoLong, sendReadAttrinfoRouted, prepareContinueAfterBlockedLabSlow — were marked __attribute__((noinline, cold)). The linker groups cold functions into a dedicated region ~3 MB away from the hot text. Cold helpers never compete with hot code for L1-I way residency, and when they do fire (rare), a missed I-cache line on a cold path has no follow-on effect on steady-state hot execution.

5. Stack-issue fixes

Two fixes eliminated serious per-call stack overhead.

5.1 getElement: 8 KB stack array → Dbacc member

The function had Uint32 keys[2048] (8 KB) on its stack as a scratch buffer for table-key compares. Since 8 KB exceeds the 4 KB stack guard-page size, the compiler was forced to emit, on every call:

  • A bl __chkstk_darwin function call to probe the new stack pages (stack probing is required by the ABI to avoid guard-page overrun corruption).
  • 8288 bytes of sub sp, sp, #… on entry and matching add on exit (4 instructions).
  • A stack-canary load + write on entry (4 insns) and a canary check on each of 7 return paths (4 insns each) plus one cold ___stack_chk_fail trampoline.

The fix moved m_get_element_keys[2048] to a per-Dbacc-instance member. getElement is not reentrant on a single instance (signal-driven, one ACCKEYREQ at a time per LDM/QT thread), so this is safe. Stack frame dropped from 8480 B to 176 B, and all of the __chkstk_darwin and canary cost went away. Memory cost is +8 KB per Dbacc instance (~16 instances per process = +128 KB static — trivial).

5.2 sendReadAttrinfo: three LinearSectionPtr[3] stack locals → cold helpers

Any local array triggers clang's stack protector. sendReadAttrinfo had three LinearSectionPtr ptr[3] declarations (one per long-signal path), which forced a canary load on entry and a canary check on each of its six return paths — about 15 instructions of pure overhead on the cross-node hot path that never actually uses a LinearSectionPtr.

The fix split the function: the hot path (API reply, cross-node short signal, same-node EXECUTE_DIRECT) stays inline with no LinearSectionPtr locals; the three long-signal and routing paths were moved to sendReadAttrinfoLong (cold) and sendReadAttrinfoRouted (cold). Frame dropped from 144 B to 64 B; canary eliminated entirely from the hot function.

5.3 Earlier KeyReqStruct shrink (Phase 1)

Mentioned for completeness: the KeyReqStruct local in execTUPKEYREQ was shrunk from ~33 KB to ~880 B, eliminating another __chkstk_darwin call and a ~33 KB stack adjustment on every TUP key operation. (Details in the earlier Phase 1 doc.)

7. Performance estimate for a committed read

Assumptions: modern ARM64 CPU (Neoverse-N1, Apple M1-class, AWS Graviton), ~3 GHz, IPC on mixed integer/memory code of ~2.0–2.5.

Purely from instruction-count reduction

  • ~850 insns saved / 2.25 IPC ≈ 380 cycles saved per read.
  • At 3 GHz ≈ ~125 ns saved per committed read.

From reduced I-cache pressure

~4.2 KB of hot code removed from the committed-read working set. Independent measurements on OLTP workloads typically show ~1–3 L1-I misses per request in busy-cluster conditions; removing ~27% of hot text reduces that proportionally. At ~15 cycles per miss avoided:

  • If baseline hit 1 L1-I miss per request: expect ~0.3 fewer misses → ~4–5 ns saved.
  • If baseline hit 3 L1-I misses per request (dense hot path): expect ~0.8 fewer misses → ~12 ns saved.

From stack-pressure relief

  • __chkstk_darwin eliminated: saves the probe's page-walk + function-call overhead, roughly 20–30 cycles on every read. At 3 GHz: ~8–10 ns saved.
  • Stack canary elimination (getElement and sendReadAttrinfo): saves ~2 canary loads + 2 checks per call, ~8–10 cycles → ~3 ns saved.
  • Smaller stack frames (+540–8000 B stack reclaimed per frame): reduces data-cache pressure on the spill/fill path. Hard to quantify precisely; worth ~1–3 ns on dense spills.

Aggregate estimate

Per committed-read call: ∼140–160 ns saved on a modern ARM64 core, assuming a warm L1-D, code cache not fully dirty.

On throughput:

  • If baseline committed-read latency into execLQHKEYREQ (excluding network, excluding API client work) is ~1.0–1.5 µs per request in hot LDM conditions, saving ~150 ns is a ~10–15% speedup on the LDM-thread-bound portion of a PK read.
  • For a workload limited by LDM-thread CPU (i.e. hitting saturation on LDM at ~1M–1.5M qps per thread), this translates to a comparable ~10–15% throughput increase on committed reads.
  • In wall-clock end-to-end latency (which includes network and TC scheduling that this work does not touch), the reduction is smaller: ~3–6% latency decrease on a typical Rondis GET or REST PK-read at moderate load.

The ranges are widest at high concurrency. When LDM threads are saturated and I-cache is thrashing, the I-cache savings matter more than the insn count (each avoided miss is worth ~15 cycles where each avoided insn is ~0.5 cycles) — in that regime the upper bound of ~15% is realistic. At low concurrency with warm caches the ~10% lower bound applies.

8. Reverts and lessons

Two optimisations were reverted during the work; their lessons are saved in the project memory system for future sessions:

Item 11 — specialised release_frag_prepare_key_access

The specialisation assumed the fragment-lock mode stayed in {READ_KEY, RK_WK, RK_REFRESH} from acquire to release, but the lock can be upgraded mid-operation (for write triggers, refresh) to WRITE_KEY or EXCLUSIVE. The specialised release would silently call the wrong sub-function, corrupting the concurrent-read counters. Debug builds fired an ndbassert during recovery; release builds would have drifted into deadlock. Reverted in 0707d650d; original 6-arm dispatch via handle_release_frag_access restored.

Item P — outline ZREFRESH path in execTUPKEYREQ

The ZREFRESH block was already at the lexical tail of the function, past the ZREAD hot region. Outlining it to a cold helper only added argument marshalling and a separate function frame while providing no I-cache benefit to the hot ZREAD path (which never reaches the tail region anyway). Net __TEXT grew by ~490 B for zero hot-path gain. The change was discarded before commit. Lesson saved: only outline cold blocks that actually sit inside the function's hot I-cache window.

9. Reproducing the measurements

The prod-build binary for size measurements is at prod_build/bin/ndbmtd. To reproduce individual function sizes, extract symbol boundaries: 

nm prod_build/bin/ndbmtd | grep -E "^[0-9a-f]+ T " | sort > /tmp/syms.txt
grep -n "function_name" /tmp/syms.txt
# Size = (next_address - this_address)

# Disassemble a function:
otool -tv prod_build/bin/ndbmtd | awk '
  /^__ZN.*function_symbol:/ { capture=1; next }
  capture && /^__ZN.*:/ { exit }
  capture { print }'

Each commit was verified against ndb_basic (MTR suite). Several commits were also verified against the specific crash scenario that revealed the Item 11 regression (recovery after error_insert 2342).
