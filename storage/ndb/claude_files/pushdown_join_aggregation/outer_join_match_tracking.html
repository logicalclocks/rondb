Outer Join Match Tracking for Pushdown Join Aggregation

1. Problem Statement

In pushdown join aggregation, DBLQH routes child scan rows through the aggregation engine and sends aggregated results directly to the API node. The flag T_EXPECT_TRANSID_AI is not set on aggregate leaf nodes, so DBSPJ never sees per-row child results.

For outer joins, DBSPJ must identify which parent rows had no matching child row so it can inject null-extended rows into the aggregate. In normal (non-aggregate) outer joins DBSPJ tracks matches via the m_matched bitmask updated in execTRANSID_AI — but that path is unavailable here because TRANSID_AI signals are suppressed.

Core tension: aggregate leaves bypass DBSPJ for efficiency, but outer join semantics require DBSPJ-level knowledge of which parent rows were matched.

2. Implemented Approach: Bitmask Exchange Protocol

2.1 Overview

Each DBLQH worker atomically marks matched scan ranges in a shared bitmask during scan processing. After the child scan completes, DBSPJ sends a single JOIN_AGG_MATCH_REQ signal per data node. DBLQH instance 1 reads the bitmask, returns it in a JOIN_AGG_MATCH_CONF long section, and resets it for the next batch. DBSPJ ORs the per-node bitmasks and injects null rows for unmatched parent rows.

2.2 Signal Definitions

// GSN 963 — DBSPJ → DBLQH instance 1
struct JoinAggMatchReq {
  static constexpr Uint32 SignalLength = 6;
  Uint32 senderRef;      // DBSPJ block reference
  Uint32 aggStateKey;    // Pool index for JoinAggregationState
  Uint32 transId[2];     // Transaction ID
  Uint32 requestPtrI;    // DBSPJ Request pool pointer
  Uint32 treeNodePtrI;   // DBSPJ TreeNode pool pointer
};

// GSN 964 — DBLQH instance 1 → DBSPJ
struct JoinAggMatchConf {
  static constexpr Uint32 SignalLength = 5;
  Uint32 senderRef;        // DBLQH instance 1 reference
  Uint32 aggStateKey;      // Echo
  Uint32 requestPtrI;      // Echo
  Uint32 treeNodePtrI;     // Echo
  Uint32 numBitmaskWords;  // Words in long section 0
  // Long section 0: matched_ranges bitmask
};

2.3 Shared State

struct JoinAggregationState {
  static const Uint32 MAX_SCAN_RANGES = 4096;
  bool m_outer_join_agg_scan;
  std::atomic<Uint32> m_num_scan_ranges;
  std::atomic<Uint32> m_matched_ranges[MAX_SCAN_RANGES / 32]; // 128 words

  void setMatchedRange(Uint32 range_no) {
    if (range_no < MAX_SCAN_RANGES) {
      Uint32 word = range_no / 32;
      Uint32 bit  = 1u << (range_no % 32);
      m_matched_ranges[word].fetch_or(bit, std::memory_order_relaxed);
    }
  }
};

2.6 Step-by-Step Protocol

  1. ScanFragReq setup — DBSPJ sets OuterJoinAggFlag (bit 29) and passes aggStateKey in variableData. DBLQH stores it on the scan record and sets m_outer_join_agg_scan = 1.
  2. During scan — Each DBLQH worker processes child rows through the aggregation engine. When a row matches (i.e. read_len > 0), the worker calls setMatchedRange(range_no), which performs an atomic fetch_or on the shared m_matched_ranges array. It also updates m_num_scan_ranges via compare-exchange to track the highest range number seen.
  3. All fragments complete — DBSPJ detects the child scan is done. It allocates a zeroed bitmask (m_agg_match_bitmask) via ndbd_malloc and sends JOIN_AGG_MATCH_REQ to DBLQH instance 1 on every data node that has aggregation state (m_aggNodes bitmask). Tracks outstanding count in m_agg_match_outstanding.
  4. DBLQH instance 1 responds — Loads the atomic m_matched_ranges into a stack buffer, resets the bitmask and m_num_scan_ranges to zero (isolating the next batch), then sends JOIN_AGG_MATCH_CONF with the bitmask as long section 0.
  5. DBSPJ ORs bitmasks — As each CONF arrives, DBSPJ ORs the incoming bitmask into its combined m_agg_match_bitmask. A parent range is "matched" if any data node reported a match.
  6. Null row injection — When the last CONF arrives (m_agg_match_outstanding == 0), DBSPJ iterates parent rows in the scan ancestor. For each row whose bit is not set, it calls sendJoinAggNullRow, which expands linked attributes from the parent row and sends a JOIN_AGG_NULL_ROW_REQ to DBLQH. The aggregation engine processes the null-extended row, producing the correct outer join aggregate result.

2.7 Key Implementation Details

  • Thread safety: std::atomic<Uint32> with memory_order_relaxed. No locks needed — each worker ORs independently, and the bitmask is only read after all workers finish.
  • Capacity: 4096 scan ranges (128 × 32 bits). Matches the maximum batch size for pushed scan-scan joins.
  • Batch isolation: Instance 1 resets the bitmask on read, ensuring the next SCAN_NEXTREQ batch starts clean.
  • Memory: 512 bytes on the data node (shared state), plus a small ndbd_malloc allocation on DBSPJ (freed after null row processing).

3. Alternative Approach: TRANSID_AI Notification

3.1 Overview

Instead of suppressing TRANSID_AI for aggregate leaf nodes, have DBLQH send a lightweight TRANSID_AI to DBSPJ for each matching child row (in addition to routing the row through the aggregation engine). DBSPJ would then use its existing m_matched per-row tracking, identical to the non-aggregate outer join path.

3.2 Required Changes

  • Set T_EXPECT_TRANSID_AI on aggregate leaf nodes that are outer joins.
  • Add T_BUFFER_MATCH on the scan ancestor to buffer match state per parent row.
  • DBLQH: after routing a child row through the aggregation engine, also send a TRANSID_AI to DBSPJ with (at minimum) the range_no.
  • DBSPJ: execTRANSID_AI would mark the parent row as matched via existing m_matched logic.

3.3 Signal Flow

Figure 3: TRANSID_AI notification — per-row signals from DBLQH to DBSPJ

3.4 Advantages

  • Reuses existing DBSPJ m_matched infrastructure — no new signal types needed.
  • No atomic bitmask machinery on the data node.
  • Immediate per-row tracking; DBSPJ knows match status in real time.

3.5 Drawbacks

  • Sends M TRANSID_AI signals per batch (one per matching child row), instead of N signals (one per data node). For typical OLAP workloads, M >> N.
  • TRANSID_AI carries row data, not just a match flag — unnecessary bandwidth even if we strip it to a minimal payload.
  • High fan-out risk: large child result sets can cause signal congestion on the DBSPJ node, increasing latency for all concurrent queries.
  • Re-introduces the overhead that pushdown aggregation was designed to eliminate (per-row signaling to the coordinator).

4.1 Latency Analysis

The comparison table above shows the bitmask exchange is more efficient in throughput and signal count. But what about end-to-end query latency, particularly for small queries where the scan itself is fast?

The bitmask round-trip penalty

The bitmask exchange adds a synchronous round-trip after the child scan completes. DBSPJ cannot inject null rows (and thus cannot finish the query) until all JOIN_AGG_MATCH_CONF responses arrive. The timeline looks like:

Figure 4: Latency timeline comparison for a small query

The key latency components:

  • Intra-node signal (same host, via job buffer): ~10–50 μs
  • Cross-node signal (network round-trip): ~50–200 μs
  • MATCH_REQ/CONF round-trip: one cross-node signal per data node, sent in parallel — latency is the slowest response, typically ~100–400 μs

Small queries (single batch): the bitmask penalty matters

Consider a small outer join query that scans 10 child rows across 4 data nodes. The scan itself completes in perhaps 100–500 μs. The post-scan MATCH_REQ/CONF round-trip then adds another ~100–400 μs — potentially doubling the query latency.

With the TRANSID_AI approach, the same query would send 10 extra per-row signals during the scan (negligible overhead for 10 rows), and DBSPJ would already know the match state when the scan completes — null row injection begins immediately with zero post-scan delay.

Example: A lookup-style outer join that touches 5 parent rows with 3 matching children. Bitmask exchange: ~200 μs scan + ~200 μs round-trip = ~400 μs. TRANSID_AI: ~200 μs scan + 3 inline signals = ~210 μs. The bitmask approach is ~2× slower here.

Multi-batch queries: the round-trip accumulates

The single-batch analysis above understates the cost. A scan-scan pushed join processes parent rows in batches (up to MAX_SCAN_RANGES = 4096 per batch). For a query with B batches, DBSPJ sends JOIN_AGG_MATCH_REQ once per batch, because the bitmask must be read and reset before the next batch can start. The MATCH_REQ/CONF round-trip sits on the critical path between batches:

Figure 5: Multi-batch latency — MATCH_REQ/CONF round-trip repeats on every batch

The total added latency from bitmask exchange is B × RT, where B is the number of batches and RT is the MATCH_REQ/CONF round-trip time (~100–400 μs). This is a serial cost — each batch must complete its match exchange before the next parent batch can be requested via SCAN_NEXTREQ.

With TRANSID_AI, there is no per-batch synchronization overhead for match tracking. Match state is known inline as the scan runs. The only post-batch work is iterating the parent rows to inject null rows, which is purely local on DBSPJ.

Example: A medium-sized outer join aggregate query with 1000 parent rows batched at 128 per batch (B = 8), with an average of 200 matching child rows per batch across 4 data nodes. Bitmask adds 8 × 200 μs = 1.6 ms of serial round-trip latency. If each batch scan takes ~2 ms, the total scan time is ~16 ms, and the match exchange adds ~10% overhead. Over the same query, TRANSID_AI would send 1600 extra signals total (200 × 8), costing ~5–8 ms in signal processing. The two approaches are comparable here.

Large queries: both costs grow, but differently

For larger queries the picture depends on how batch count and rows-per-batch scale:

Scenario Batches (B) Rows/batch Bitmask added latency TRANSID_AI signal cost
Small OLTP-ish 1 10 ~200 μs ~30 μs
Medium analytical 8 200 ~1.6 ms ~5 ms
TPC-H style 50 2000 ~10 ms ~300 ms + congestion
Large analytical 200 4000 ~40 ms ~2.4 s + severe congestion

The bitmask cost grows as O(B × N) signals (B batches × N data nodes), adding O(B × RT) latency. The TRANSID_AI cost grows as O(B × M) signals where M is matching rows per batch. Since M typically grows much faster than N (hundreds or thousands vs. 2–8), the bitmask approach wins decisively as queries get larger, despite the per-batch penalty.

The crossover point (per batch)

Within a single batch, the two approaches cross over when the per-row signal cost of TRANSID_AI equals the fixed round-trip cost of the bitmask exchange:

  • MATCH_REQ/CONF fixed cost per batch: ~200 μs (one network round-trip)
  • TRANSID_AI marginal cost per row: ~2–5 μs (signal scheduling + execTRANSID_AI processing on DBSPJ)
  • Crossover: ~40–100 matching child rows per batch

For multi-batch queries, the total crossover is at the same ratio — the per-batch costs simply multiply by B on both sides. Queries below ~50 matching rows per batch favor TRANSID_AI; above ~100, the bitmask wins.

Why the penalty is acceptable

Pushdown join aggregation targets OLAP workloads — queries that aggregate large result sets (GROUP BY over joins). These queries typically have hundreds to thousands of matching child rows per batch, well above the ~50-row crossover. A query with only 10 matching rows per batch is unlikely to benefit from pushdown aggregation at all (the aggregation engine setup cost exceeds any savings from avoiding API round-trips).

Even in the worst case for the bitmask approach (many batches, few matching rows each), the accumulated round-trip cost stays modest in absolute terms: 10 batches adds ~2 ms, 50 batches adds ~10 ms. For the queries where this matters, the total query time is dominated by scan processing, not by the match exchange.

The bitmask round-trip is also fully parallelized across data nodes within each batch. DBSPJ sends all MATCH_REQ signals at once and waits for the slowest response. The per-batch latency does not grow with the number of data nodes — it stays at one round-trip regardless of cluster size.

5. Analysis & Conclusion

The two approaches represent fundamentally different trade-offs between implementation simplicity and runtime efficiency:

  • The bitmask exchange sends O(N) signals where N = number of data nodes (typically 2–8). The payload is a compact bitmask of at most 128 words (512 bytes for 4096 ranges).
  • The TRANSID_AI approach sends O(M) signals where M = number of matching child rows. For typical OLAP aggregation workloads, M can range from thousands to millions.
The bitmask exchange approach is the correct choice for pushdown join aggregation. The entire purpose of pushing aggregation to the data nodes is to avoid per-row signaling between DBLQH and the coordinator. Introducing per-row TRANSID_AI signals for match tracking would negate much of that benefit. The additional implementation complexity of the bitmask protocol is modest and well-isolated (two new signal types, one shared atomic bitmask), while the runtime savings are substantial — especially for the large-result-set OLAP queries that pushdown aggregation targets.

The TRANSID_AI approach does have a latency advantage for queries with few matching rows per batch (<50), where the per-batch MATCH_REQ/CONF round-trip is a significant fraction of batch processing time. This accumulates over multiple batches: B batches add B × ~200 μs of serial latency. However, queries with so few matching rows per batch rarely benefit from pushdown aggregation at all — the aggregation engine setup cost already exceeds the savings from avoiding API round-trips. For the OLAP workloads where pushdown aggregation is valuable (hundreds or thousands of matching rows per batch), the per-batch round-trip is dwarfed by the scan processing time, while the TRANSID_AI signal flood would be catastrophic.

The bitmask approach also preserves the signal congestion safety of the aggregate path. DBLQH workers operate independently on row data and only interact with DBSPJ through bounded, deferred signals. This keeps the DBSPJ node free to coordinate other concurrent queries.
