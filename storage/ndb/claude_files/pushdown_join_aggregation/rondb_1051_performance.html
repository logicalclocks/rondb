RONDB-1051 — Hot-path micro-optimizations for PK read, TUX index-key read, and interpreter single-column reads

This document describes the 17 commits making up the RONDB-1051 performance work. The changes target three of the most heavily executed code paths in an NDB data node: the primary-key lookup path (DBACC → DBTUP), the TUX ordered-index key-attribute read path (DBTUX → DBTUP), and the interpreter single-column read path used by aggregation and vector search. All three are traversed on every LQHKEYREQ, every ordered-index scan step, and every per-row aggregation feed, so small instruction-level savings are multiplied by a huge call frequency.

Why these functions matter

Primary-key lookup path

LQHKEYREQ / ACCKEYREQ
  → Dbacc::execACCKEYREQ
    → Dbacc::readTablePk  (per PK hit)
      → Dbtup::accReadPk
        → Dbtup::tuxReadPk
          → readFunctionArray[attrId] (per PK column)

This chain runs for every PK read that hits the NDB hash index — essentially every single-row SELECT/UPDATE/DELETE, every Rondis GET/SET, every REST PK-read, every pushed-down join row. On busy clusters this is hundreds of thousands of calls per LDM thread per second.

TUX ordered-index key-attribute read path

SCAN_FRAGREQ (index scan)
  → Dbtux::scanNext / Dbtux::findNext
    → Dbtux::readKeyAttrs  (per scanned row, per comparison)
      → Dbtup::tuxReadAttrsOpt
        → setup_fixed_part, prepare_read, readAttributes

Dbtux::readKeyAttrs is called to fetch the key columns of a row for ordered-index comparisons during lookups, range scans, and pushed-down join probes. Every scanned row goes through it; the cumulative overhead on large range scans dominates.

Interpreter single-column read path

SCAN_FRAGREQ (scan with aggregation) / interpreter dispatch
  → AggInterpreter::ProcessRec / JoinAggInterpreter::ProcessRec / VecSearchInterpreter::ProcessRec
    → Dbtup::readSingleAttribute  (per row × per group-by / aggregate / vector column)
      → readFunctionArray[attrId](...) (per column)

Aggregation and vector-search interpreters read one column at a time in very tight per-row loops. On a scan of N rows with G group-by columns and A aggregate inputs, this is roughly N × (G + A) single-column reads per fragment per scan — potentially millions per query.

Where the savings come from:

  • −30 instr — prepare_read skipped for fixed-only PKs (the overwhelmingly common case)
  • −30 instr — three out-of-line calls collapse to inlines: readTablePk, accReadPk, tuxReadPk. Each eliminates ~6 instr of frame + arg marshalling + bl + ret.
  • −15 instr — cross-TU bl to readKeyAttributes removed (inlined into tuxReadPk).
  • −7 instr — SimpleReadTag KRS constructor skips seven default-init stores.
  • −3 instr — Dbtup hot-pointer group co-located; single-ldr reachable at low offset; pointer re-reload eliminated in accReadPk.
  • +2 instr — two prfm tuple prefetches added. Tradeoff: 2 instr cost, hides potentially hundreds of cycles of DRAM latency.

Note: the saving grows linearly with PK column count (each column still goes through the read function dispatch), but the framework portion — the ~90 instructions of bl / frame / KRS-init overhead — is fixed per call. That is why the percentage saving is largest on single-column PKs and the absolute saving is largest on all PKs.

Binary-size impact

The per-callsite inlining (particularly accReadPk, readTablePk, tuxReadAttrsOpt) moves bodies into each caller. On paper this grows the text segment, but in practice the effect on ndbmtd size is small — the functions are small and each has only a few hot callers. The deletion of readKeyAttributes (77 lines) and the extraction of readTablePkTupleDeletedSlow (143 cold instructions now out-of-line) offset some of the inlining growth.

The prod_build ndbmtd binary at HEAD contains:

  • Dbtux::readKeyAttrs (Uint32* overload): 110 instructions total including bounds checks, error paths, and assertions. Hot path is ~50 instructions.
  • Dbtup::tuxReadPk: 270 instructions (includes the inlined readKeyAttributes body).
  • Dbacc::readTablePkTupleDeletedSlow: 143 instructions (cold path, out-of-line).
  • Dbtup::tuxReadAttrsCommon: 128 instructions (cold, only called on tuple-version mismatch).

Why these savings compound

The PK-read path is the dominant micro-operation in an NDB LDM thread. An LDM thread on a modern server processes on the order of 105 – 106 LQHKEYREQs per second; each one goes through execACCKEYREQ → readTablePk → accReadPk → tuxReadPk. Every instruction removed from that chain is paid back a million times a second per thread.

The TUX key-attr read path scales with rows scanned. A single range scan touching a million rows invokes Dbtux::readKeyAttrs at least a million times — often more, for comparison during binary search in the index tree. The 50-instruction reduction there translates directly into reduced per-row CPU on every index scan.

Defensive measures kept intact

  • All VM_TRACE/ERROR_INSERT assertions are preserved; the poison_debug() helper fills formerly implicitly-initialised KeyReqStruct fields with 0xF3 so any stray read in a debug build still surfaces as corruption, not stack garbage.
  • The cold paths (version mismatch, deleted tuple) remain fully exercised by the existing testJoinAgg*, testCteNdbApi, and rondis test suites.
  • Every fast-path shortcut (skipped KRS fields, skipped prepare_read, dropped Operationrec* argument) is documented in the header with the audit explaining why each skipped field is not read on the relevant path.
