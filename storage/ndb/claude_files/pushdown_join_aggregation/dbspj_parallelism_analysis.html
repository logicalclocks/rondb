DBSPJ Scan Chain Parallelism & Outer Join Match Tracking

1. DBSPJ Pipelined Execution Model

DBSPJ processes scan chains using a pipelined execution model. Each DBSPJ instance handles root scan fragments one at a time (m_fragCount=1 per instance). When a root fragment completes, it immediately triggers child scans without waiting for other root fragments.

This pipelining is by design for non-aggregation joins — it maximizes throughput by overlapping scan I/O across tree levels.

Observed Behavior

In a 3-level scan chain customer → orders → lineitem:

scanFrag_CONF node=0 frag=0 rows=1 done=2 frags_complete=0/1  ← customer frag 0 done
scanFrag_send FRAGREQ node=1 rangeCnt=1                        ← orders starts IMMEDIATELY
...8 order SCAN_FRAGREQs sent...

scanFrag_CONF node=0 frag=6 rows=1 done=2 frags_complete=0/1  ← customer frag 6 done
scanFrag_send FRAGREQ node=1 rangeCnt=1                        ← orders starts AGAIN
...8 more order SCAN_FRAGREQs sent...

Each customer fragment triggers a full cycle: customer frag N → orders scan (all 8 frags) → lineitem scan (all 8 frags) → complete → SCAN_NEXTREQ → customer frag N+1.

2. The Two Bugs Found

Bug A: range_no Collision Across Batches

m_agg_range_cnt resets between customer fragment cycles. Orders from different customer fragments get the same range_no. The match bitmask can't distinguish them.

This was the initial hypothesis. However, debugging revealed that the actual bug was different — see Bug B.

Bug B: COLLECTION_MAP Iteration Order Mismatch

handleAggLeafScanComplete iterated the parent node's row buffer (COLLECTION_MAP) in hash order, but the match bitmask range_no was assigned in TRANSID_AI arrival order during scanFrag_parent_row. These orders differ, causing NULL rows to be sent to the wrong parent row.

Concrete example from logs:

EventOrderCorrelationfixupCorr (range_no)
TRANSID_AI arrives first300xd80
TRANSID_AI arrives second310x361

DBLQH correctly sets match bitmask bit 0 (range_no=0 = order 30 matched). But handleAggLeafScanComplete iterates the MAP in hash order:

Map positionCorrelationOrderAssumed range_no
00x3631 (WRONG — should be 30)0
10xd830 (WRONG — should be 31)1

Result: bit 0 is set (matched) but maps to order 31 instead of order 30. Order 30 appears unmatched → NULL row sent to order 30 instead of 31.

3. The Fix

Recording Correlations in Range Order

In scanFrag_parent_row, when assigning fixupCorr, record the parent correlation in a m_agg_range_corrs[] array indexed by range_no:

Uint32 range_idx = data.m_agg_range_cnt++;
fixupCorr = range_idx;
data.m_agg_range_corrs[range_idx] = rowRef.m_src_correlation;

Correlation-Based Row Lookup

In handleAggLeafScanComplete, when the parent uses COLLECTION_MAP:

  1. Build a corr→row_ptr lookup by iterating the map once
  2. For each range_no, look up m_agg_range_corrs[range_no] to get the target correlation
  3. Find the matching row_ptr in the lookup
  4. If unmatched, send NULL row using the correct parent row
struct CorrRow { Uint32 corr; const Uint32 *row_ptr; };
CorrRow corr_rows[MaxCorrelationId];  // 4096 entries, ~48KB on stack

// Build lookup from map (hash order)
for (map iteration) {
  corr_rows[n++] = { correlation, row_ptr };
}

// Iterate in range_no order using m_agg_range_corrs
for (range_no = 0; range_no < num_ranges; range_no++) {
  target_corr = data.m_agg_range_corrs[range_no];
  if (!matched(range_no)) {
    row = find_by_corr(corr_rows, target_corr);
    sendJoinAggNullRow(row);
  }
}

Fast Path: All Ranges Matched

Common case optimization: if all bitmask bits are set, skip the entire NULL injection loop (no CorrRow building, no iteration).

Bug Scenario (Before Fix)

handleAggLeafScanComplete: bitmask = 0x1 (only range_no=0 matched — order 30 had lineitems with qty>3) Iterating COLLECTION_MAP in hash order: position 0: corr=0x36 (order 31) — range_no=0 → matched=1 ✓ position 1: corr=0xd8 (order 30) — range_no=1 → matched=0 ✗ → sendJoinAggNullRow for order 30 (WRONG! should be 31) Result: order 30 gets NULL, order 31 gets aggregated value Expected: order 30 gets aggregated value, order 31 gets NULL

Fixed Scenario

handleAggLeafScanComplete: bitmask = 0x1 (only range_no=0 matched) Using m_agg_range_corrs[] for correlation-based lookup: range_no=0: target_corr = range_corrs[0] = 0xd8 (order 30) → matched=1 ✓ range_no=1: target_corr = range_corrs[1] = 0x36 (order 31) → matched=0 ✗ → find row with corr=0x36 in map → sendJoinAggNullRow for order 31 ✓
