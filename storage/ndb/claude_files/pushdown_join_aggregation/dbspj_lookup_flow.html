DBSPJ Lookup Node: KeyInfo & AttrInfo Flow

This document traces the lifecycle of m_send.m_keyInfoPtrI and m_send.m_attrInfoPtrI section pointers for lookup nodes in DBSPJ, comparing testJoinAggSpj (2-node query) and testCteDbtc (8-node CTE query).

Both tests use a self-join pattern on the same table to push aggregation down to data nodes. The key difference: testCteDbtc wraps two copies of the aggregation inside CTE subtrees, adds a separate main query with its own aggregation, and tests that the CTE materialization pipeline doesn't interfere with normal SPJ execution.

-- Common table used by both tests:
CREATE TABLE src (
  pk  BIGINT PRIMARY KEY,
  grp BIGINT,
  val BIGINT
) ENGINE=NDB;

-- Test data (5 rows):
INSERT INTO src VALUES (1,1,10),(2,1,20),(3,2,30),(4,2,40),(5,3,50);

1. TreeNode::m_send Initialization

// Dbspj.hpp — TreeNode constructor (line 968-971)
m_send.m_correlation = 0;
m_send.m_keyInfoPtrI = RNIL;   // No key section yet

Every TreeNode starts with RNIL section pointers. They must be populated during the build phase before lookup_send() uses them.

2. Build Phase: How Sections Are Created

2.1 lookup_build() (DbspjMain.cpp:6275-6474)

For QN_LOOKUP nodes, lookup_build() is the m_build function. It creates the base LqhKeyReq template and calls parseDA() to process the node's tree bits and parameter data.

// lookup_build(), line 6386
err = parseDA(ctx, requestPtr, treeNodePtr,
              nodeDA, treeBits, paramDA, paramBits);

// After parseDA:
//   m_send.m_keyInfoPtrI = set by key parsing (or pattern stored)
//   m_send.m_attrInfoPtrI = set by attrInfo parsing (or RNIL fallback)
//   T_KEYINFO_CONSTRUCTED = set if key built at runtime from parent row
//   T_ATTRINFO_CONSTRUCTED = set if attrInfo expanded with linked data

2.2 parseDA() Key Section (DbspjMain.cpp:12710-12778)

NI_KEY_LINKED Store key pattern in m_keyPattern, set T_KEYINFO_CONSTRUCTED m_send.m_keyInfoPtrI stays RNIL (key built at runtime)
NI_KEY_PARAMS / NI_KEY_CONSTS Expand pattern directly into fixed key section m_send.m_keyInfoPtrI = fixed key (non-RNIL)

2.3 parseDA() AttrInfo Section (DbspjMain.cpp:12784-13197)

The attrInfo block is entered when:

RNIL Fallback (line 13178): OUTSIDE the attrInfo block above, parseDA() checks if m_send.m_attrInfoPtrI is still RNIL and creates a minimal 6-word interpreted program (header + ExitOK). This ensures every lookup node gets a valid attrInfo after parseDA().

  Uint32 tmp[6] = {0, 1, 0, 0, 0, Interpreter::ExitOK()};
  appendToSection(treeNodePtr.p->m_send.m_attrInfoPtrI, tmp, 6);
}

2.4 T_ONE_SHOT (DbspjMain.cpp:6410-6469)

// lookup_build(), line 6410

T_ONE_SHOT means: "sections are used once and consumed by sendSignal." Set only on the root node. Child lookup nodes do NOT get T_ONE_SHOT.

3. Execution Phase: How Sections Flow Through lookup_send()

3.1 lookup_parent_row() (DbspjMain.cpp:7055-7382)

Called when the parent scan produces a row. For each parent row:

// 1. Construct key from parent row (line 7097-7183)
if (T_KEYINFO_CONSTRUCTED) {
  expand(ptrI, m_keyPattern, rowRef);  // key from parent
  m_send.m_keyInfoPtrI = ptrI;        // store constructed key
}

// 2. Handle attrInfo (line 7194-7336)
Uint32 attrInfoPtrI = m_send.m_attrInfoPtrI; // SAVE base value
if (T_ATTRINFO_CONSTRUCTED) {
  tmp = dupSection(attrInfoPtrI);     // duplicate base
  expand(tmp, m_attrParamPattern, rowRef); // append linked data
  m_send.m_attrInfoPtrI = tmp;        // use constructed version
}

// 3. Compute hash + target node (line 7188-7192)
computeHash(m_send.m_keyInfoPtrI);
getNodes() -> receiverRef

// 4. Send (line 7367)
lookup_send(signal, requestPtr, treeNodePtr);

// 5. Restore base attrInfo for next parent row (line 7369-7372)
if (T_ATTRINFO_CONSTRUCTED) {
  m_send.m_attrInfoPtrI = attrInfoPtrI; // restore SAVED base
}

3.2 lookup_send() (DbspjMain.cpp:6482-6800)

// Read current section pointers (lines 6540-6541)
Uint32 keyInfoPtrI = m_send.m_keyInfoPtrI;
Uint32 attrInfoPtrI = m_send.m_attrInfoPtrI;

// === AGGREGATION ROUTING (lines 6544-6609) ===
if (T_CTE_SCAN) {
  // CTE path: use m_cteAggStateKeys[cteIdx * MAX_NDB_NODES + nodeId]
  JoinAggFlag = 1;
  variableData[4] = cteAggKey;
} else if (T_AGGREGATE_LEAF) {
  // Main query path: use m_aggStateKeys[nodeId] + leafIdx encoding
  JoinAggFlag = 1;
  variableData[4] = encodeAggStateKey(baseKey, leafIdx);
}

// === SECTION HANDLING (lines 6614-6674) ===
if (T_ONE_SHOT) {
  // Pass sections directly, consume them (set to RNIL)
  m_send.m_attrInfoPtrI = RNIL;
  m_send.m_keyInfoPtrI = RNIL;
} else {
  // DUPLICATE sections for multi-use

  if (!T_KEYINFO_CONSTRUCTED) {
    keyInfoPtrI = dupSection(keyInfoPtrI);   // dup BASE key
  } else {
    m_send.m_keyInfoPtrI = RNIL;  // consume constructed key
  }

  if (!T_ATTRINFO_CONSTRUCTED) {
    attrInfoPtrI = dupSection(attrInfoPtrI); // dup BASE attrInfo
    // ^^^ CRASH if attrInfoPtrI is RNIL ^^^
  } else {
    m_send.m_attrInfoPtrI = RNIL;  // consume constructed attrInfo
  }
}

// Attach sections and send LQHKEYREQ (lines 6677-6783)
handle.m_ptr[0] = keyInfoPtrI;
handle.m_ptr[1] = attrInfoPtrI;
sendSignal(ref, GSN_LQHKEYREQ, signal, ..., &handle);

4. testJoinAggSpj: 2-Node Query

SQL Equivalent

-- Table: src (pk BIGINT PRIMARY KEY, grp BIGINT, val BIGINT) ENGINE=NDB
-- 5 rows: (1,1,10), (2,1,20), (3,2,30), (4,2,40), (5,3,50)

-- The query is a self-join with aggregation:
SELECT COUNT(*), SUM(t2.val)
FROM src t1
JOIN src t2 ON t1.pk = t2.pk;

-- Result: COUNT=5, SUM=150
-- The self-join by PK produces one row per PK (same as src),
-- then the aggregation engine computes COUNT(*) and SUM(val)
-- across all matched rows.

Query Tree

Query Tree:
  Node 0: QN_SCAN_FRAG (root scan on src — produces t1 rows)
    treeBits: NI_AGGREGATE | NI_LINKED_ATTR
    Linked attr: pk (passed to child for join key)

  Node 1: QN_LOOKUP (agg leaf — looks up t2 by pk from t1)
    treeBits: NI_HAS_PARENT | NI_KEY_LINKED | NI_AGGREGATE | NI_AGGREGATE_LEAF
    paramBits: 0 (no PI_ATTR_LIST, no PI_ATTR_INTERPRET)
    Key pattern: col(0) = parent's linked pk

Node 0 scans src, passes each row's pk as a linked attribute. Node 1 looks up src by that pk (self-join). Because Node 1 has NI_AGGREGATE_LEAF, its results feed into the JoinAgg engine (not the API). The engine accumulates COUNT and SUM across all rows, then sends the final aggregated result to the API.

4.1 Build Phase for Node 1 (QN_LOOKUP)

StepActionResult
Build lookup_build() Create base LqhKeyReq template m_lookup_data.m_lqhKeyReq populated
Build parseDA() key NI_KEY_LINKED: store pattern in m_keyPattern T_KEYINFO_CONSTRUCTED set, m_send.m_keyInfoPtrI = RNIL
Build parseDA() attrInfo No NI_ATTR_* bits, no PI_ATTR bits → attrInfo block SKIPPED m_send.m_attrInfoPtrI still RNIL
Build parseDA() RNIL fallback Line 13178: creates 6-word ExitOK program m_send.m_attrInfoPtrI = valid section (6 words)
Build T_ONE_SHOT ctx.m_start_signal == NULL (node 1 is not root) T_ONE_SHOT NOT set

4.2 Execution Flow for Node 1

// For each parent scan row:
1. lookup_parent_row():
   - T_KEYINFO_CONSTRUCTED: expand key from parent row
   - T_ATTRINFO_CONSTRUCTED: NOT set, so attrInfo = base (6-word ExitOK)
   - Call lookup_send()

2. lookup_send():
   - T_AGGREGATE_LEAF: set JoinAggFlag, encode aggStateKey
   - NOT T_ONE_SHOT: enter duplication path
   - NOT T_KEYINFO_CONSTRUCTED... wait, it IS T_KEYINFO_CONSTRUCTED
     so: m_send.m_keyInfoPtrI = RNIL (consume constructed key)
   - NOT T_ATTRINFO_CONSTRUCTED:
     dupSection(attrInfoPtrI) where attrInfoPtrI = 6-word ExitOK
     SUCCESS: creates copy for this send
   - Send LQHKEYREQ with key + attrInfo sections
Why it works: The RNIL fallback in parseDA() at line 13178 ensures m_send.m_attrInfoPtrI is ALWAYS non-RNIL after build. Each lookup_send() call duplicates this base section (6-word ExitOK). The base is never consumed (only the duplicate is consumed by sendSignal). So it works for multiple parent rows.

5. testCteDbtc: 8-Node CTE Query

SQL Equivalent

-- Table: src (pk BIGINT PRIMARY KEY, grp BIGINT, val BIGINT) ENGINE=NDB
-- 5 rows: (1,1,10), (2,1,20), (3,2,30), (4,2,40), (5,3,50)

-- Two CTEs materialize aggregation results into hash tables,
-- then the main query runs a self-join with its own aggregation:
WITH
  cte0 AS (
    -- CTE 0: accumulates COUNT(*) and SUM(val) into a hash table
    -- Internally: scan src (node 1) + lookup src by pk (node 2)
    -- The self-join pattern is used to push aggregation to data nodes
    SELECT COUNT(*), SUM(val) FROM src t1 JOIN src t2 ON t1.pk = t2.pk
  ),
  cte1 AS (
    -- CTE 1: accumulates COUNT(*) into a hash table (same pattern)
    SELECT COUNT(*) FROM src t1 JOIN src t2 ON t1.pk = t2.pk
  )
-- Main query: independent self-join with aggregation
-- Verifies that CTE materialization doesn't break the main query
SELECT COUNT(*), SUM(t2.val)
FROM src t1 JOIN src t2 ON t1.pk = t2.pk;

-- Expected: COUNT=5, SUM=150 (same as testJoinAggSpj)
-- The CTEs are materialized but their results are not used by the
-- main SELECT in this test — the test verifies the CTE pipeline
-- doesn't interfere with main query execution.

Query Tree

Query Tree:
  Node 0: QN_CTE_SUBTREE (cteId=0, numNodes=2)
    Container for CTE 0 materialization. Not a real scan/lookup.

  Node 1:   QN_SCAN_FRAG (CTE 0 scan on src — produces t1 rows)
              treeBits: NI_AGGREGATE | NI_LINKED_ATTR
              Linked attr: pk (passed to child lookup)

  Node 2:   QN_LOOKUP (CTE 0 agg leaf — looks up t2 by pk)
              treeBits: NI_HAS_PARENT | NI_KEY_LINKED |
                        NI_AGGREGATE | NI_AGGREGATE_LEAF
              Key pattern: col(0) = parent's linked pk
              Rows feed into CTE 0's JoinAgg hash table

  Node 3: QN_CTE_SUBTREE (cteId=1, numNodes=2)
  Node 4:   QN_SCAN_FRAG (CTE 1 scan — same pattern)
  Node 5:   QN_LOOKUP (CTE 1 agg leaf — same pattern)

  Node 6: QN_SCAN_FRAG (main scan on src — produces t1 rows)
              treeBits: NI_AGGREGATE | NI_LINKED_ATTR

  Node 7: QN_LOOKUP (main agg leaf — looks up t2 by pk)
              treeBits: NI_HAS_PARENT | NI_KEY_LINKED |
                        NI_AGGREGATE | NI_AGGREGATE_LEAF

Nodes 1-2 and 4-5 have T_CTE_SCAN flag (set post-build). Their aggregation results go to CTE hash tables via m_cteAggStateKeys. Nodes 6-7 have RT_AGGREGATE on the Request and use m_aggStateKeys for the main query aggregation.

5.2 Expected Execution Flow for Node 2

// CTE phase starts: checkPrepareComplete() starts CTE scan (node 1)
// Node 1 scan produces rows, triggering lookup_parent_row() on node 2

1. lookup_parent_row():
   - T_KEYINFO_CONSTRUCTED: expand key from parent row (node 1's linked pk)

   - NOT T_ONE_SHOT: enter duplication path
   - T_KEYINFO_CONSTRUCTED: consume key, set m_send.m_keyInfoPtrI = RNIL
   - NOT T_ATTRINFO_CONSTRUCTED:
     dupSection(attrInfoPtrI) where attrInfoPtrI = 6-word ExitOK
     SHOULD SUCCEED (same as testJoinAggSpj)
   - Send LQHKEYREQ with key + attrInfo sections
THE CRASH: ArrayPool::getPtr at line 6662 in dupSection(tmp, attrInfoPtrI). This means attrInfoPtrI is invalid (RNIL or corrupt). But based on the build analysis above, it should be a valid 6-word section. Where does it become invalid?

Possible causes to investigate:

  1. m_send.m_attrInfoPtrI was released somewhere between build and execution (during CTE phase setup, section cleanup, or batch reset)
  2. The section was consumed by a prior call (but T_ATTRINFO_CONSTRUCTED is not set, so the duplication path shouldn't consume the base)
  3. The checkTableError() ndbassert at line 6488 fires for CTE nodes with m_tableOrIndexId=0 in debug builds, but this returns 0 for system table 0 so it shouldn't crash (would need verification)
  4. A different node's section operation corrupts this node's section pool entry

6. Flags Summary

FlagSet WhenEffect in lookup_send()
T_ONE_SHOT ctx.m_start_signal != NULL (root node only) Pass sections directly, consume (set to RNIL). No duplication.
T_KEYINFO_CONSTRUCTED NI_KEY_LINKED in tree bits Key was built by lookup_parent_row(). Consume it (set to RNIL).
T_ATTRINFO_CONSTRUCTED NI_ATTR_LINKED in tree bits AttrInfo was expanded with linked parent data. Consume it.
T_CTE_SCAN Node inside CTE subtree (post-build marking) Use m_cteAggStateKeys for aggStateKey routing.
T_AGGREGATE_LEAF NI_AGGREGATE_LEAF in tree bits Use m_aggStateKeys for aggStateKey routing (main query only).
T_ATTR_INTERPRETED Always set for lookup nodes (lookup_build line 6393) DBLQH processes attrInfo as interpreted program.

7. Section Lifecycle: Build → Execution

BUILD PHASE:
  TreeNode constructor     m_send.m_attrInfoPtrI = RNIL
       |
  parseDA() attrInfo      [if NI_ATTR_* bits: build section]
       |                  [else: skip]
       |
  parseDA() RNIL fallback  if still RNIL: create 6-word ExitOK
       |
  Build complete           m_send.m_attrInfoPtrI = valid section
       |
  --- time passes ---
  CTE SETUP (DBTC creates hash tables)
  CTE scan starts (checkPrepareComplete)
       |
EXECUTION PHASE:
  Parent scan row arrives
       |
  lookup_parent_row()     save base attrInfoPtrI
       |                  [if T_ATTRINFO_CONSTRUCTED: dup + expand]
       |                  [else: use base directly]
       |
  lookup_send()           read m_send.m_attrInfoPtrI
       |                  [if T_ONE_SHOT: consume directly]
       |                  [elif !T_ATTRINFO_CONSTRUCTED: dupSection(base)]
       |                  [elif T_ATTRINFO_CONSTRUCTED: consume constructed]
       |
  sendSignal(LQHKEYREQ)  sections consumed by signal transport
       |
  lookup_parent_row()     [if T_ATTRINFO_CONSTRUCTED: restore base]
       |
  Next parent row...      base attrInfoPtrI still valid (not consumed)
Key invariant: For non-T_ATTRINFO_CONSTRUCTED nodes, the base m_send.m_attrInfoPtrI is NEVER consumed. Only duplicates are consumed by sendSignal. The base persists across all parent rows. This is why testJoinAggSpj works for multiple parent rows.
