1. Introduction

1.1 What RONDB-1050 delivers

RONDB-1050 is the body of work that turned the pushdown join aggregation foundation shipped in RONDB-733 into a complete Common Table Expression (CTE) materialisation and filter pushdown stack. Where RONDB-733 made it possible to push SUM / COUNT / MIN / MAX through multi-table joins down to data nodes, RONDB-1050 adds the ability to:

  • Materialise a CTE on the data nodes (no API round trip per row) and consume it as either a lookup on its synthetic primary key or a scan from any side of an outer or inner join, including as the main-query root.
  • Push WHERE filters into the CTE consumer using a CTE-safe subset of NDB's interpreted code: comparison operators, IS NULL, OR / DNF, column-vs-column, CASE, GREATEST / LEAST with NULL propagation, and inline type metadata for synthesised aggregate columns.
  • Aggregate strings (CHAR, VARCHAR, Longvarchar) with MIN / MAX, including a new wire format (AGG_CHAR_RESULT, marker 0xFF02) and a charset-aware multi-source merge on the API side.
  • Widen DECIMAL aggregates to BIGINT / BIGINT UNSIGNED / DOUBLE based on precision and scale, and treat normal-interpreter registers as typed (Option B retrofit) so mixed-type comparisons round-trip correctly.
  • Optimise scalar MIN(col) / MAX(col) into an ordered index scan with maxRows = 1, and use scanIndex inside a CTE body when the WHERE has bounded predicates.
  • Stream large CTE results back to the API with SCAN_NEXTREQ flow control, including state-lifetime guarantees across batches.
  • Handle LEFT JOIN with NULL injection on unmatched rows, promote LEFT to INNER when the WHERE rejects NULL on the RHS (Phase J), and promote WHERE col IS NULL on a LEFT JOIN's RHS to an ANTI-JOIN (Phase K).
  • Resolve CTE and stored-table names with proper scoping in declaration order (Phase I.23), with a hardened JOIN_AGG_COMPLETE lifecycle (Phase L) and a unified jump-table interpreter (Phase M).

1.3 Conventions

  • Phase tags in square pills point to in-tree plan documents under storage/ndb/claude_files/pushdown_join_aggregation/.
  • NDB-API means NdbQueryBuilder / NdbAggregator / NdbInterpretedCode.
  • RonSQL means the embedded SQL preparer / executor used by ronsql_cli and the RDRS REST surface, not the full MySQL handler. MySQL handler integration is out of scope for this document.
  • scanCte and lookupCte are the NDB-API operations that read from a materialised CTE; CTE_SCAN and CTE_LOOKUP are the corresponding planner / kernel op types.
  • Where a query depends on a particular kernel feature, the phase tag points to the doc that explains the kernel-side implementation; where it depends on a RonSQL feature, the phase tag points to the doc covering the RonSQL emit logic. Sometimes both apply.

2. Architecture

RONDB-1050 spans four layers: a kernel block layer that physically materialises CTEs and aggregates rows, an NDB API surface that exposes scanCte, lookupCte, and NdbAggregator to library users, a RonSQL parser / preparer that compiles SQL into NDB-API calls, and a test layer of NDB-API block tests and RonSQL MTR tests. The kernel layer itself is split across DBTC (transaction coordinator), DBSPJ (pushed-join coordinator), and DBLQH / DBTUP (per-LDM data + aggregation engine). The diagrams below trace the signal flow, the aggregation engine ownership model, the CTE result wire format, and the unified jump-table interpreter.

2.1 The four-layer stack

A user SQL statement enters the RonSQL preparer; the preparer plans CTE bodies, synthesises virtual NdbDictionary::Table objects for the materialised CTEs, builds an NDB query tree using NdbQueryBuilder, attaches an NdbAggregator to each aggregating leaf, and assembles NdbInterpretedCode programs for filters and per-row CASE expressions. The resulting query tree is sent to a data node, where DBTC opens the transaction, DBSPJ orchestrates the pushed join, and DBLQH executes scan or key operations against DBTUP, with AggInterpreter running on each participating LDM thread.

2.2 Signal flow and the JOIN_AGG lifecycle

Pushdown join aggregation uses three signal pairs — JOIN_AGG_SETUP, JOIN_AGG_COMPLETE, and JOIN_AGG_RELEASE — to bracket the per-batch lifecycle of a JoinAggregationState seized from DblqhProxy's transient pool. SETUP creates the per-LDM aggregator handles before any rows arrive; COMPLETE finalises and merges per-LDM state for delivery; RELEASE cleans up after the API has consumed results. Phase L hardened idempotency on COMPLETE so retried or stale signals never produce duplicates.

2.3 Aggregation engine

Aggregation runs on every LDM thread that hosts a fragment of the bottom-most scanned table. Each LDM owns its own AggInterpreter; rows are intercepted at DbtupExecQuery::handleJoinAggRow() after the WHERE filter passes and before sendReadAttrinfo. There are two concurrency strategies: mutex-based (one shared interpreter, group locks) and mutex-free (per-LDM interpreter, merged at Complete time). The mutex-free strategy dominates for join aggregation; per-LDM state is shipped to the LDM co-located with the requesting DBTC instance via JOIN_AGG_REDISTRIBUTE_REQ for final merge before delivery.

2.4 CTE materialisation buffer

A CTE result row is delivered to consumers as a kernel-built buffer with three sections: parent linked projections at the head (so child operations can read parent columns from a fixed offset), GROUP BY keys with a [tableId=0, schemaVersion=0] prefix identifying them as virtual-table columns, and aggregate result items. For numeric-only aggregate slots the result is delivered as AGG_RESULT: an array of fixed 16-byte AggResItem structs. When any aggregate slot is a string MIN or MAX, the same array is delivered as AGG_CHAR_RESULT (marker 0xFF02) with an appended per-group string-payload region after the array. The numeric encoding is unchanged; only string slots use the appended region.

2.5 Three interpreters unified

RonDB's interpreted code originally came in three flavours: the normal NDB-API interpreter, the aggregation interpreter inside AggInterpreter, and the CTE-safe filter interpreter that runs inside scanCte / lookupCte. Phase A introduced a single jump-table dispatch (s_cte_filter_handlers); Phase C reused it for aggregation; Phase M removed the last aggregation-specific control-flow opcode by emitting an embedded normal-interpreter compare. Today all three flavours dispatch through the same handler table, with per-call flags such as IFLAG_DISALLOW_BACKWARD_JUMPS selecting the safe subset.

3.1 Direct aggregation over real tables (no CTE)

Q1 Three-way INNER JOIN, GROUP BY on root, SUM on leaf RONDB-733 base

The original pushdown join aggregation shape: a join chain whose root carries the GROUP BY key and whose leaf carries the aggregated column. DBSPJ ships rows through the chain inside the data nodes; only one row per group is returned to the API.

SELECT c.c_region, SUM(l.l_quantity)
FROM customer AS c
JOIN orders AS o ON o.o_custkey = c.c_id
JOIN lineitem AS l ON l.l_orderkey = o.o_id
GROUP BY c.c_region;
Demonstrates
  • Linked-attribute propagation: c.c_region reaches the leaf as a kernel-level linked column for GROUP BY hashing.
  • Per-LDM aggregation, redistribute, owner-LDM merge before delivery.
  • One JoinAggregationState spans the whole batch.

Source: mysql-test/suite/ronsql/t/ronsql_join_agg.test; storage/ndb/block_unit_test/testJoinAggNdbApi.cpp

Q2 Multi-batch aggregation with high-cardinality GROUP BY RONDB-733 / Phase L

When the result set has more groups than fit in one batch, DBSPJ pages results back to the API with SCAN_NEXTREQ; JoinAggregationState survives across batches and Phase L hardened the COMPLETE protocol so retried signals are idempotent.

SELECT o.o_id, COUNT(*), SUM(l.l_amt)
FROM orders AS o
JOIN lineitem AS l ON l.l_orderkey = o.o_id
GROUP BY o.o_id;
Demonstrates
  • Batched delivery via SCAN_NEXTREQ.
  • Eviction policies (testJoinAggNdbApi maxGroups stress).
  • Phase L idempotency on retried JOIN_AGG_COMPLETE_REQ.

Source: storage/ndb/block_unit_test/testJoinAggNdbApi.cpp tests 13-19

3.2 Scalar CTE

Q3 Scalar MAX from a CTE Phase I.17

A CTE body whose SELECT contains only aggregate outputs and no GROUP BY produces a single-row materialised result. Phase I.17 wired this shape end-to-end including the per-node redistribute that ships the lone row to the DBTC-co-located owner LDM.

WITH s AS (SELECT MAX(v) AS m FROM scalar_t)
SELECT m FROM s;
Demonstrates
  • Scalar materialisation with a synthetic single-row virtual table.
  • Owner-only emission via cteScanShouldEmitScalar().
  • Top-level wrap of an aggregate function around the SELECT list.

Source: mysql-test/suite/ronsql/t/ronsql_cte_scalar.test

Q4 Cross-join two scalar CTEs with top-level GREATEST Phase I.17 / I.21

Two scalar CTEs joined as a comma cross-product produces a one-row result. Phase I.17 added the dummy-key lookupCte pattern so a 1-PK virtual table can be looked up without a real key. Phase I.21 added guardrails so this implicit-aggregate wrap stays scoped to scalar CTE expressions.

WITH lo AS (SELECT MIN(v) AS lo FROM scalar_t),
     hi AS (SELECT MAX(v) AS hi FROM scalar_t)
SELECT GREATEST(lo.lo, hi.hi) FROM lo, hi;
Demonstrates
  • Cross-join (comma) of two scalar CTEs as the watermark shape from testCteNdbApi Test 20.
  • Implicit MAX-wrap of GREATEST at the top level (Phase I.21 keeps this restricted to scalar CTE chains).

Source: mysql-test/suite/ronsql/t/ronsql_cte_scalar.test Test 6

Q5 Scalar MIN/MAX optimised to ordered index + LIMIT 1 Phase I.10

If the scalar CTE body's only output is MIN(col) or MAX(col) over a NOT NULL indexed column, the planner emits an ASC / DESC ordered scanIndex with maxRows = 1 instead of the full hash-aggregate path.

WITH top AS (SELECT MAX(amt) AS m FROM orders)
SELECT m FROM top;
Demonstrates
  • Index-path optimisation: kernel reads one row instead of the entire fragment.
  • Falls back to baseline materialisation if the column is nullable, unindexed, or the body is not a clean MIN/MAX.

Source: mysql-test/suite/ronsql/t/ronsql_cte_minmax_index.test

3.3 Grouped CTE

Q6 Single-table grouped MIN/MAX/SUM/COUNT Phase B / D

The base grouped-CTE shape: GROUP BY on a real-table column, four aggregate slots. The result is materialised as a kernel-side virtual table that the main query can scan or look up.

WITH sums AS (
  SELECT o_custkey AS k,
         MIN(o_amt) AS lo,
         MAX(o_amt) AS hi,
         SUM(o_amt) AS total,
         COUNT(*)   AS cnt
  FROM cte_orders
  GROUP BY o_custkey)
SELECT k, lo, hi, total, cnt FROM sums;
Demonstrates
  • Grouped CTE materialisation with multiple aggregate slots in one program.
  • Phase D inline-type opcode used when the main query filters on aggregate output.

Source: mysql-test/suite/ronsql/t/ronsql_cte_basic.test

Q7 CTE body with two-table JOIN + GROUP BY, re-aggregated in main Phase D / I.7

The classic shape that motivated this whole project. The CTE materialises per-customer revenue from a join inside its body; the main query joins the materialised CTE to cte_customer and re-aggregates. Two GROUP BY layers, one materialisation cut.

WITH revenue AS (
  SELECT o.o_custkey AS k, SUM(l.l_price) AS r
  FROM cte_orders AS o
  JOIN cte_lineitem AS l ON l.l_custkey = o.o_custkey
  GROUP BY o.o_custkey)
SELECT revenue.k, SUM(revenue.r)
FROM cte_customer AS c
JOIN revenue ON revenue.k = c.c_id
GROUP BY revenue.k;
Demonstrates
  • Two-table CTE body with linked-attribute SUM at the leaf.
  • CTE_LOOKUP from main query to materialised virtual table by virtual PK k.
  • Re-aggregation on the main side of the join.

Source: mysql-test/suite/ronsql/t/ronsql_cte_basic.test Test 2

Q8 CTE body with scanIndex and WHERE bounds Phase I.9

If a CTE body has WHERE predicates that match an ordered indexed column, the planner emits scanIndex with key bounds instead of scanTable + interpreted-code filter. Residual conjuncts still go through the filter path.

WITH q4_orders AS (
  SELECT o_custkey AS k, SUM(o_amt) AS t
  FROM cte_orders
  WHERE o_orderdate >= 20250101
    AND o_orderdate <= 20250331
  GROUP BY o_custkey)
SELECT k, t FROM q4_orders;
Demonstrates
  • Index-path scan inside a CTE body, replacing a full-fragment scan.
  • Residual WHERE predicates demoted to interpreted-code filter.

Source: mysql-test/suite/ronsql/t/ronsql_cte_index_body.test

3.4 CTE as main-query root

Q9 lookupCte as main-query root with PK constant Phase I.7

When the main query is SELECT ... FROM cte WHERE pk = const with all virtual-PK columns equality-bound, the planner emits qb->lookupCte() as the root operation. Phase I.7 added the prepare-time WHERE walk that detects this shape; partial-key / no-WHERE cases fall back to scanCte + inline filter.

WITH sums AS (
  SELECT o_custkey AS k, SUM(o_amt) AS t
  FROM cte_orders GROUP BY o_custkey)
SELECT k, t FROM sums WHERE k = 100;
Demonstrates
  • Hash lookup on the synthetic virt PK with no WHERE residual.
  • Typed constValue dispatch for synthetic columns (m_attrSize uninitialised on raw NdbDictionary::Column).

Source: mysql-test/suite/ronsql/t/ronsql_cte_root_lookup.test; testCteNdbApi.cpp Test 11

Q10 scanCte as main-query root, projection-only Phase E.1 / E.3

The scanCte root path exists for SELECTs without aggregation that read every CTE row. Phase E.1 added the kernel handshake; E.3 covers projection-only main queries.

WITH sums AS (
  SELECT o_custkey AS k, SUM(o_amt) AS t
  FROM cte_orders GROUP BY o_custkey)
SELECT k, t FROM sums ORDER BY k;
Demonstrates
  • scanCte as the root operation of the main query tree.
  • Multi-batch SCAN_NEXTREQ correctness when the materialised result is large.

Source: mysql-test/suite/ronsql/t/ronsql_cte_scan.test

3.5 CTE as joined child / chained CTEs

Q11 Real-table root + CTE_LOOKUP child (non-aggregating) Phase I.8

Projection-only join from a real-table root to a CTE child. The main query has no aggregation, so the result is row-by-row pass-through after the CTE_LOOKUP fans out per parent key.

WITH sums AS (
  SELECT o_custkey AS k, SUM(o_amt) AS t
  FROM cte_orders GROUP BY o_custkey)
SELECT c.c_id, c.c_name, sums.t
FROM cte_customer AS c
JOIN sums ON sums.k = c.c_id;
Demonstrates
  • Pass-through drain: the receiver buffer pre-registers all virt-table cols in attrId order.
  • TSV header deferred to first row to keep empty-result behaviour matching the mysql client baseline.

Source: mysql-test/suite/ronsql/t/ronsql_cte_pk_join.test; testCteNdbApi.cpp Test 17

Q12 Chained CTEs: c0 feeds c1 feeds the main query Phase E.2 / L

CTEs can reference earlier CTEs in declaration order. Each link adds another GROUP BY layer of linked-attribute aggregation; the planner resolves names with declaration-order scoping (Phase I.23).

WITH c0 AS (
       SELECT grp AS g, SUM(val) AS s0
       FROM t GROUP BY grp),
     c1 AS (
       SELECT g, SUM(c0.s0) AS s1
       FROM c0 GROUP BY g)
SELECT g, SUM(c1.s1) FROM c1 GROUP BY g;
Demonstrates
  • Sequential CTE dependency through a chain of virtual tables.
  • Phase L's per-record correlation across chained pushed batches.

Source: mysql-test/suite/ronsql/t/ronsql_cte_chained.test

Q13 Cross-CTE join via dummy-key lookupCte Phase I.17 / I.21

Two scalar CTEs cross-joined: implemented as a 1-PK virtual-table lookupCte with a constant dummy key. Phase I.21 keeps this dummy-key shape scoped to scalar CTE child lookups so it doesn't leak into normal queries.

WITH a AS (SELECT SUM(x) AS sx FROM t1),
     b AS (SELECT SUM(y) AS sy FROM t2)
SELECT a.sx, b.sy FROM a, b;
Demonstrates
  • NdbQueryBuilder dummy-key lookupCte (testCteNdbApi.cpp Test 20 pattern).
  • setParent on a scalar virtual table to express the cross-product as a join.

Source: mysql-test/suite/ronsql/t/ronsql_cte_scalar.test

3.6 Outer-join CTEs

Q14 Real-table LEFT JOIN CTE with NULL injection outer-join 1 / 5

Customers without matching orders still produce a row, with NULLs where the CTE columns would go. The kernel injects a virt-table NULL row at agg-feed time when NdbQueryOperation::isRowNULL() reports the unmatched marker.

WITH sums AS (
  SELECT o_custkey AS k, SUM(o_amt) AS t
  FROM cte_orders GROUP BY o_custkey)
SELECT c.c_id, c.c_name, sums.t
FROM cte_customer AS c
LEFT JOIN sums ON sums.k = c.c_id;
Demonstrates
  • CTE_LOOKUP outer-join child with kernel NULL injection (Phase 1 / Phase 5).
  • Pass-through drain substitutes NULL into a transient effective_attrs[] when isRowNULL is true.

Source: mysql-test/suite/ronsql/t/ronsql_cte_outer_join.test Tests 2/5/6

Q15 scanCte LEFT JOIN real-table outer-join 2

The CTE is the LEFT side and a real table is the RIGHT side. Phase 2 of the outer-join sub-plan validated this shape against testCteNdbApiOuterJoin Test 1.

WITH sums AS (
  SELECT o_custkey AS k, SUM(o_amt) AS t
  FROM cte_orders GROUP BY o_custkey)
SELECT sums.k, sums.t, c.c_name
FROM sums
LEFT JOIN cte_customer AS c ON c.c_id = sums.k;
Demonstrates
  • scanCte as outer-join LEFT-side parent.
  • Real-table child readTuple returning NULL where unmatched.

Source: mysql-test/suite/ronsql/t/ronsql_cte_outer_join.test Test 1

Q16 LEFT-to-INNER promotion when WHERE rejects NULL on RHS Phase J

If a LEFT JOIN's WHERE clause rejects NULL on the optional side, the join is semantically inner. RonSQL promotes LEFT_OUTER_JOIN to INNER_JOIN at plan time so the kernel takes the cheaper path.

SELECT c.c_id, sums.t
FROM cte_customer AS c
LEFT JOIN sums ON sums.k = c.c_id
WHERE sums.t > 0;
Demonstrates
  • Plan-time rewrite: WHERE forbids NULL on sums.t so the LEFT semantics are redundant.
  • Inner-join machinery faster than the outer-join path.

Source: phase doc cte_filter_phase_j.md

Q17 ANTI-JOIN promotion: WHERE col IS NULL on LEFT JOIN RHS Phase K

The dual of Q16: when the WHERE explicitly requires the RHS to be NULL, the planner promotes the LEFT JOIN to an ANTI-JOIN, returning only LHS rows that have no match. The kernel's routeCteLookup ANTI flag is preserved through forwarding (the "route flag-stripping gotcha" resolved in Phase K).

SELECT c.c_id, c.c_name
FROM cte_customer AS c
LEFT JOIN sums ON sums.k = c.c_id
WHERE sums.k IS NULL;
Demonstrates
  • Customers with no orders, expressed via the standard "anti-pattern" SQL.
  • Phase K's ANTI_JOIN_FLAG end-to-end through the route forwarder.

Source: phase doc cte_filter_phase_k.md

3.7 Filter pushdown

Q18 Inline-type WHERE on aggregate output Phase D / D2

The CTE_LOOKUP filter compares an aggregate-output column without a real AttributeDescriptor. The type travels in the program word itself (BRANCH_MEM_OP_ARG_INLINE_TYPE); Phase D2 widened the encoding to MIN/MAX virt types (Bigint / Bigunsigned / Double).

WITH sums AS (
  SELECT o_custkey AS k, SUM(o_amt) AS t
  FROM cte_orders GROUP BY o_custkey)
SELECT k, t FROM sums WHERE t > 1000;
Demonstrates
  • Per-CTE-row filter on a synthesised column without a kernel descriptor.
  • Inline type encoding allows the receiver to compare correctly.

Source: mysql-test/suite/ronsql/t/ronsql_cte_basic.test Test 9

Q19 OR / DNF on CTE_LOOKUP Phase I.2

Top-level OR is pushed down via DNF expansion: the WHERE is rewritten into disjunctive normal form and emitted as a series of branch-on-match instructions in the CTE filter program.

WITH sums AS (...)
SELECT sums.k, sums.t
FROM cte_customer AS c
JOIN sums ON sums.k = c.c_id
WHERE sums.k = 100 OR sums.k = 300;
Demonstrates
  • Disjunction handled in the kernel's interpreted-code filter.
  • Not expanded into multiple round trips on the API side.

Source: mysql-test/suite/ronsql/t/ronsql_cte_or.test

Q20 Column-vs-column on CTE_LOOKUP Phase I.3

A WHERE that compares two columns of the CTE row (or a CTE column to a parent linked column) instead of a column to a constant. Phase I.3 added a 1-line NdbInterpretedCode API for the col-vs-col Bigint compare.

SELECT sums.k, sums.t
FROM cte_customer AS c
JOIN sums ON sums.k = c.c_id
WHERE sums.t > c.c_credit_limit;
Demonstrates
  • Two virt-column registers compared in-kernel.
  • Bigint-only in this phase; sub-Bigint widening is Phase I.5 v5 / I.18.

Source: mysql-test/suite/ronsql/t/ronsql_cte_colvscol.test

Q21 CASE referencing a CTE column Phase I.4

A CASE expression in a WHERE clause whose conditions reference CTE columns. Phase I.4 routed CASE-condition emit through simplify_ce so it normalises like any other expression.

SELECT sums.k, sums.t
FROM cte_customer AS c
JOIN sums ON sums.k = c.c_id
WHERE CASE WHEN sums.t > 1000 THEN c.c_id ELSE 0 END > 0;
Demonstrates
  • CASE inside CTE filter, evaluated per row in the kernel.
  • Phase I.19 added boundary-fix coverage for literal normalisation in CASE atoms.

Source: mysql-test/suite/ronsql/t/ronsql_cte_case.test

Q22 GREATEST / LEAST n-ary with NULL propagation I.5 v2b / v7

n-ary GREATEST / LEAST compile to SVM pair-ops (Phase I.5 v2b). With nullable operands, expression-local NULL propagation makes only the immediately-following aggregate skip the row (Phase I.5 v7 + new kOpSetRegNull).

WITH bounds AS (
  SELECT c_id, GREATEST(c_a, c_b, c_c) AS g
  FROM v6_t)
SELECT c_id, g FROM bounds;
Demonstrates
  • SVM-style multi-arg lowering via embedded normal-interpreter compares.
  • Localised NULL skip: COUNT(*) / SUM elsewhere in the program still update.

Source: ronsql_cte_greatest_least_v2b.test, ronsql_cte_greatest_least_v4.test

Q23 IS NULL on aggregate output Phase I.1

A WHERE that filters on whether an aggregate output is NULL. Phase I.1 added IS NULL / IS NOT NULL recognition in the CTE filter and the inline-type opcode encoding.

WITH sums AS (...)
SELECT c.c_id
FROM cte_customer AS c
LEFT JOIN sums ON sums.k = c.c_id
WHERE sums.t IS NULL;
Demonstrates
  • NULL-aware filter on a synthesised aggregate column.
  • When combined with LEFT JOIN, frequently promoted to ANTI-JOIN (Phase K).

Source: phase doc cte_filter_phase_i1.md

3.8 Type widening and typed registers

Q24 DECIMAL widening in MIN / MAX (with range guard) I.6 F.1 / I.22

DECIMAL(N,0) widens to BIGINT or BIGINT UNSIGNED; DECIMAL(N,S>0) widens to DOUBLE. Phase I.22 rejects scale-zero DECIMALs whose precision exceeds the kernel's 64-bit target (signed precision > 18 or unsigned precision > 19).

WITH stats AS (
  SELECT o_grp AS k,
         MIN(o_amt0) AS lo,   -- DECIMAL(10,0) -> BIGINT
         MAX(o_amt2) AS hi    -- DECIMAL(10,2) -> DOUBLE
  FROM dec_orders GROUP BY o_grp)
SELECT k, lo, hi FROM stats;
Demonstrates
  • Per-column widening decision based on precision and scale.
  • Inline-type filter accepts the widened types.

Source: mysql-test/suite/ronsql/t/ronsql_cte_decimal.test

Q25 Mixed-type compare with sign extension and BIGINT UNSIGNED beyond INT64_MAX Phase I.18

Phase I.18 retrofitted normal-interpreter registers to hold a NULL flag, an UNSIGNED flag, a FLOAT flag, and a 64-bit value (Option B). All eight integer widths sign-extend correctly, and BIGINT UNSIGNED > INT64_MAX no longer aliases to a negative comparison.

WITH bounds AS (
  SELECT c.c_id,
         CASE WHEN c.c_int8 > o.o_uint64
              THEN c.c_int8 ELSE o.o_uint64 END AS mx
  FROM v5_customer AS c
  JOIN v5_orders AS o ON o.o_custkey = c.c_id)
SELECT c.c_id, MAX(bounds.mx)
FROM v5_customer AS c
LEFT JOIN bounds ON bounds.c_id = c.c_id
GROUP BY c.c_id;
Demonstrates
  • Typed register compare: int8 vs uint64 lifted to a correct cross-sign Bigint compare.
  • FLOAT / DOUBLE arms use the same typed-register pipeline.

Source: mysql-test/suite/ronsql/t/ronsql_cte_greatest_least_v5.test

3.9 String MIN/MAX

Q26 Scalar VARCHAR MIN / MAX I.6 F.2

Single-row aggregation over a VARCHAR column. The kernel keeps per-(group, slot) state via AggResItem.value.val_ptr; the API receives AGG_CHAR_RESULT and exposes the bytes via NdbAggregator::Result::data_str(Uint32* len).

SELECT MIN(v) AS lo, MAX(v) AS hi
FROM str_t;
Demonstrates
  • AGG_CHAR_RESULT wire format end-to-end.
  • RonSQL ResultPrinter dispatches on aggregate output type (Phase I.6 S.5).

Q27 Grouped CHAR MIN / MAX with multi-partition merge I.6 S.1 / S.2

Multi-partition tables produce per-fragment partial winners; the API merges them charset-aware (no "first source wins" shortcut) using NdbSqlUtil::getType(typeId).m_cmp. Phase S.1 ensured the grouped public result length is exactly n_agg_results × sizeof(AggResItem) regardless of appended payload bytes.

SELECT grp,
       MIN(c) AS lo, MAX(c) AS hi
FROM str_minmax_char
GROUP BY grp;
Demonstrates
  • CHAR space padding handled correctly.
  • Charset-aware merge across multiple partitions.
  • Deep-copy of winner into API-owned memory; replaced buffers freed.

Source: storage/ndb/block_unit_test/testVarcharMinMax.cpp grouped section

Q28 String CTE re-aggregation through linked-attr strings I.6 F.4

A CTE materialises per-group string MIN / MAX; the main query joins to that CTE and re-aggregates the strings. Phase I.6 F.4 substituted the kernel's CTE delivery (buildCteLinkedBuffer, emitCteGroupOutput) and the JoinAggInterpreter::kOpLoadCol linked-attr arm so string payload bytes are shipped instead of val_ptr bits.

WITH s AS (
  SELECT grp, MIN(v) AS min_v, MAX(v) AS max_v
  FROM str_minmax
  GROUP BY grp)
SELECT MIN(s.min_v), MAX(s.max_v)
FROM s
JOIN str_groups AS g ON g.grp = s.grp;
Demonstrates
  • String aggregate slots flowing as linked attrs into a downstream AggInterpreter.
  • The CTE delivery path no longer ships kernel-local pointers in place of payload.

Source: mysql-test/suite/ronsql/t/ronsql_minmax_string.test Test 4

3.11 Robustness shapes

Q30 Partial-key join to multi-key CTE with AST rewrite I.16 / I.20

If a join binds fewer key columns than the multi-key CTE's virtual PK requires, emit_child_ops would otherwise reject. Phase I.16 introduced an AST rewrite that, where possible, swaps the CTE to root with the original parent demoted to a child, recovering a valid plan; Phase I.20 tightened the coverage check from a count to an ordered virt-PK match and added rewrite validation.

WITH mk_cte AS (
  SELECT g_a, g_b, SUM(amt) AS t
  FROM mk_t
  GROUP BY g_a, g_b)
SELECT p.p_id, mk_cte.t
FROM parent AS p
JOIN mk_cte ON mk_cte.g_a = p.p_a;
-- only 1 of 2 virt-PK columns bound; rewrite puts mk_cte at root
Demonstrates
  • AST rewrite at load_join that restructures the join order at parse time.
  • Coexists with LEFT_OUTER joins elsewhere in the chain.
  • If the rewrite cannot apply (full-count but wrong-column shape, partial coverage that breaks PK ordering), the planner rejects with a clear permanent error.

Source: mysql-test/suite/ronsql/t/ronsql_cte_partial_key.test

4. Out of scope / not yet covered

This section lists the things RONDB-1050 does not support, so that users of the NDB API and RonSQL surfaces know exactly where the boundary sits. It is split into three groups: items deferred to Phase N or later, shapes that are permanently rejected at prepare or build time, and capabilities that work in some layers but are not yet wired through every layer.

4.1 Phase N deferrals

Phase N (the wrap-up phase, see cte_filter_phase_n.md) closes or explicitly defers the last items left from the I.13 / I.14 / I.15 / I.25 catalogue. Items below are tracked but not necessarily landing as part of this release.

ItemWhat is missingWhere it bites
I.13 SQL-side batch-size The NDB API setBatchSize exists for CTE scans, but there is no RonSQL-facing knob to pass it through. RonSQL relies on the engine default. Tuning large CTE result streams from SQL today requires editing the RonSQLPreparer default rather than per-statement override.
I.14 Early close / LIMIT Behaviour of LIMIT applied to a CTE-rooted query: kernel cleanup on early query->close(), lifetime of the CTE materialised state when the consumer stops fetching. A query like SELECT * FROM cte LIMIT 5 works, but only the materialise-everything-then-take-5 path is exercised. LIMIT is not pushed into the CTE producer.
I.15 Multi-fragment / multi-node MTR Block tests (testJoinAggNdbApi, testCtePhase6) cover multi-fragment and multi-node CTE redistribute paths; the RonSQL MTR suite is single-fragment dominated. Phase N decides whether to add the MTR matrix or accept the block-test coverage. RonSQL coverage of partition redistribute is shallower than NDB-API coverage. The kernel paths are exercised; the SQL surface is not.
I.25 String CTE matrix A re-aggregation of string CTE MIN / MAX through a CTE-root joined to a non-unique ordered-index child returned NULL,NULL when first surfaced. The intended WHERE min_v < 'beta' shape needs MTR-quote-safe compare and clarified RonSQL string-literal parser semantics. Also tracked: a comparison matrix across signed / unsigned int, FLOAT, DECIMAL widening, strings, exposed date / time types and NULL semantics. String-CTE consumer correctness on indexed-non-unique join shapes; SQL literal-vs-column compare ergonomics.

4.2 Hard-rejected shapes

The following shapes are rejected at prepare or build time with a clear error. They are not bugs — they are conscious scope boundaries.

ShapeReasonWhere
I.22 DECIMAL > 18 (signed) or > 19 (unsigned) MIN/MAX The kernel's decimal2longlong / decimal2ulonglong target a 64-bit integer; precisions beyond those bounds cannot be represented losslessly. Phase I.22 added a prepare-time guard. Arbitrary-precision DECIMAL preservation is out of scope. RonSQL emit; clear error rather than silent overflow.
outer-join 3 CTE_SCAN as outer-join child Would require an unkeyed scan executed once per parent row (a cross-join shape). Dropped at the kernel level in cte_outer_join_phase_3.md; the RonSQL Phase G defensive rejection is preserved. NDB API and RonSQL.
I.16 / I.20 Partial-key joins lacking ordered virt-PK coverage A join into a multi-key CTE must bind the virtual-PK columns in order. Phase I.16 added an AST rewrite to put the multi-key CTE at root when possible; Phase I.20 tightened the coverage check from a count to an ordered match. RonSQL emit; rejected with a clear permanent error.
core Correlated CTE_SCAN A CTE that depends on a per-row value from the enclosing query is not supported. g_CteScanOpInfo.parent_row == 0. Both surfaces.
core Recursive CTEs The classic WITH RECURSIVE form is not supported; CTEs are materialised once per query. RonSQL parser rejects.
core UNION inside a CTE body CTE bodies are single SELECT blocks. UNION / UNION ALL are not part of the parser surface. RonSQL parser rejects.
core DISTINCT in aggregation SUM(DISTINCT ...), COUNT(DISTINCT ...) are not supported by the pushdown aggregator. RonSQL emit; NDB-API NdbAggregator has no DISTINCT primitive.
I.6 S.4 SUM / arithmetic over strings Only MIN and MAX are defined for string registers. SUM(varchar_col) etc. are rejected at finalise time with kErrUnsupportedStringOperation. NDB-API NdbAggregator finalize.
core CASE / GREATEST on string aggregate output Inline-type filter pushdown widens BRANCH_MEM_OP_ARG_INLINE_TYPE for numeric aggregate outputs; widening to string aggregate outputs is not in this release. WHERE CASE WHEN min_str < 'x' THEN ... END is rejected. RonSQL emit gates this shape; the kernel does not yet have the comparator wiring.

4.3 Layered but not fully surfaced

These capabilities work at one layer but are not exposed through every higher layer yet.

  • NDB API setBatchSize for CTE scans — works at the API; not surfaced to RonSQL (Phase N I.13).
  • Multi-fragment / multi-node CTE redistribute — exercised by NDB-API block tests; RonSQL MTR coverage is single-fragment dominated (Phase N I.15).
  • RonSQL EXPLAIN — understands and prints the major op kinds (CTE_SCAN, CTE_LOOKUP, INDEX_SCAN, INNER / LEFT_OUTER / ANTI_JOIN), but is not a full plan inspector and does not yet expose every per-op detail.
  • EXPLAIN ANALYZE with measured rows / batches: not implemented for CTE shapes.

5.4 Glossary

CTE_LOOKUP / CTE_SCAN
Planner / kernel op-types for consuming a materialised CTE by primary-key lookup or by scanning the materialised result. Map to lookupCte() and scanCte() in NdbQueryBuilder.
AggInterpreter
The DBTUP-resident aggregation engine that walks rows, evaluates aggregate functions, and stores per-group state. Lives in storage/ndb/src/kernel/blocks/dbtup/AggInterpreter.cpp.
JoinAggInterpreter
The variant of AggInterpreter used inside a pushdown join, with linked-attribute support and per-LDM ownership of intermediate state.
JoinAggregationState
The shared state struct seized from a transient pool in DblqhProxy, holding per-LDM AggInterpreter handles, GB-key hash maps, eviction policy, and request correlation.
Linked attributes
Output columns from a parent operation that the child operation reads through the kernel's shared per-row buffer (buildLinkedBuffer). For CTE materialisations, parent linked-projection bytes lead the buffer.
AGG_RESULT / AGG_CHAR_RESULT
Wire-format markers for kernel-to-API aggregation result delivery. AGG_RESULT is the original numeric-only encoding; AGG_CHAR_RESULT (marker 0xFF02, Phase I.6 F.2) prepends to the AggResItem array a per-group string-payload region, used when any slot is a string MIN / MAX.
Virt PK / virtual table
The synthetic NdbDictionary::Table RonSQL builds for each CTE: column types and primary-key marker bits, but no real attrSize / kernel descriptor. Consumers must route through aggregator-style delivery rather than the rowsize-based path (see project_synthetic_virt_table_gotcha.md).
Redistribute
The DBLQH→DBLQH signal exchange that ships per-LDM aggregate state to a single owner (the LDM co-located with DBTC) for final merge before delivery to the API.
Inline-type filter (BRANCH_MEM_OP_ARG_INLINE_TYPE)
An NdbInterpretedCode opcode added in Phase D so a CTE consumer can compare an aggregate-output column without an AttributeDescriptor: the type is encoded in the program word itself.
Pushdown filter interpreter / 3rd interpreter
The CTE-safe subset of the NDB interpreter used to evaluate WHERE filters inside scanCte / lookupCte. Backward jumps disabled (IFLAG_DISALLOW_BACKWARD_JUMPS); tuple-access opcodes unsupported. Phase M unified it with the aggregation interpreter behind the same jump table.
