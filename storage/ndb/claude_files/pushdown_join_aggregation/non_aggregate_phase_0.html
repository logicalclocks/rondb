RonSQL · Non-Aggregate Pushdown · Phase 0

Root Plan Cascade

How RonSQL chooses and executes the root access plan after Phase 0 — and where each choice sits on the optimality scale.

RONDB-733 companion · covers RonSQLPreparer, NdbQueryBuilder, DBSPJ · August 2026

What shipped. Phase 0 of the non-aggregate pushdown plan fixed two pre-existing defect classes and, in doing so, uncovered and fixed a data-node crash:

0a — the three PK-equality-covered root branches in emit_root_op silently dropped every WHERE conjunct that wasn't consumed as a key. They now apply those residuals as interpreted filters, with a safe fallback cascade.

0b — the pass-through result printer rejected temporal and DECIMAL columns outright and printed CTE temporal MIN/MAX outputs as raw packed integers. It now shares the aggregate path's column metadata and decoders.

Crash — aggregate queries without CTEs whose root was PK-equality-covered emitted a lookup-rooted query, a shape the JoinAgg protocol cannot serve. Both data nodes died on an ndbrequire. Fixed at three layers; the kernel now fails the query, not the node.

1 · From SQL to an executed plan

RonSQL builds its plan in two stages, and understanding the split is the key to reading any plan this document discusses:

  1. The planner stage (QueryPlanner::plan + select_root_scan_config) classifies every operation: the root becomes TABLE_SCAN, INDEX_SCAN (when a scan-config candidate binds an ordered index), or CTE_SCAN; children become PK_LOOKUP, UNIQUE_LOOKUP, INDEX_SCAN, or CTE_LOOKUP.
  2. The emit stage (emit_root_op) refines the root at NdbQueryBuilder-build time. This is where a TABLE_SCAN-classified root can become a single-row readTuple PK lookup, a PK-equality ordered-index scan, or a full-key lookupCte — decisions the planner never records.

One practical consequence, worth stating up front: EXPLAIN prints the planner's classification, not the emit refinement. A query that executes as a PK lookup still shows [ROOT] TABLE_SCAN. The emit-time branches in this document are therefore invisible in today's EXPLAIN output — a known observability gap, flagged in §6.

Before Phase 0, the emit refinements had a correctness bug: when the WHERE fully covered the primary key by equality, the branch built its keys from the matched conjuncts and discarded everything else. WHERE pk = 1 AND balance > 1000 executed as WHERE pk = 1 — silently, in shipped aggregate and pass-through shapes alike.

2 · The root decision cascade

This is the full decision sequence for a real-table root after Phase 0. Every edge either existed before (drawn in the neutral ink) or is new (drawn in the accent color). The invariant the cascade maintains: every fallback step is strictly more general and never less correct — the residual filter travels with whichever plan wins.

Reading each branch as a cost statement

readTuple PK lookup — the best possible plan for a fully-bound key: one hashed key access, one LQHKEYREQ to the one LDM thread owning the row, no fragment fan-out, no scan setup. The residual rides inside that same signal as an interpreted program, capped at 64 words (mirroring ha_ndbcluster's pushed-condition cap, since the program is copied into every LQHKEYREQ); a filtered-out row behaves as a lookup miss.

PK-equality ordered-index scan — the same single row reached through the ordered index: an equality bound on every PK column prunes the B-tree walk to that one key, and the residual runs as a per-row filter. It costs a scan-protocol round (per-fragment SCAN_FRAGREQs) rather than one lookup signal, but reads the same ~1 row. This is the landing spot when a scan child forbids a lookup root (NDB API rule), when aggregation forbids the lookup protocol, or when the residual outgrows the lookup cap.

scanTable + full filter — the terminal fallback: every fragment, every row, filter per row. Correct always; optimal only when nothing better exists. It is reached from this cascade only when the PK has no ordered index (USING HASH), which is exactly the shared test schema's shape — see the optimality table.

Two properties worth calling out because they are easy to get wrong and the implementation deliberately gets them right: the residual is residual-only — conjuncts consumed as keys are subtracted by pointer identity, so nothing is evaluated twice; and contradictory keys (pk = 1 AND pk = 2) resolve naturally — the last equality becomes the key, the orphaned first one lands in the residual, and the filter correctly returns the empty set (previously: the wrong row).

3 · Where predicates actually execute

Judging optimality requires one distinction above all others: bounds prune reads; filters prune only transfer. An equality or range bound is evaluated inside the ordered-index (TUX) walk and stops rows from ever being read. An interpreted filter runs in DBTUP after the row has been read, and only stops it from being returned or aggregated. A plan that turns a predicate into a bound is categorically better than one that turns it into a filter.

This is also why the known optimizer gap inherited from the join-root work matters (tracked in next_steps.md, not part of Phase 0): child-local constant bounds — o_orderdate ≥ X on an index (o_custkey, o_orderdate) — are still emitted as filters rather than bounds. Correct, but read-amplifying.

4 · The crash: two protocols, one missing edge

The first test run of the new family crashed both data nodes at DbspjMain.cpp:8748. The mechanism is a protocol split the emit layer wasn't respecting:

The bug was pre-existing and had simply never been exercised: every previously-green PK-equality aggregate query happened to involve a CTE, and any CTE forces the scan protocol (the materialisation scan is the query's first operation). The fix has three layers, each catching what the layer above lets through:

LayerSiteBehavior
1 · RonSQL emit emit_root_op, lookup_root_supported Never emits a lookup root for an aggregating scope unless a CTE materialisation scan precedes it. The query silently takes the (scan-rooted) PK-index or table-scan fallback instead.
2 · NDB API NdbQueryDefImpl constructor A query def with main-aggregation leaves, no CTEs, and a non-scan first operation fails prepare() with QRY_WRONG_OPERATION_TYPE (4820). Clean client-side error.
3 · Kernel Dbspj::validateAggregateFlags + the LqhKeyReq do_init RT_AGGREGATE with an empty m_aggNodes fails the build with InvalidAggregateFlags — query REF, node stays up. The do_init fix closes a second latent bug: lookup-protocol Requests come from a TransientPool (no constructors) and never cleared m_aggNodes, so recycled Requests carried stale bits.

The remaining runtime ndbrequire(m_aggNodes.get(nodeId)) sites stay deliberately: after layers 1–3, they can only fire on inconsistencies in DBTC-constructed data — a trusted-peer invariant, where crash-on-violation is this codebase's convention per the tiered response policy. The graceful failure sits exactly at the trust boundary, where API-controlled data (the query tree bits) enters the kernel.

The two genuine gaps, named

Gap 1 — the suboptimal row. An aggregate query with no CTE and a fully-bound hash PK full-scans for one row. Two real fixes exist, both out of Phase 0's scope: teach the JoinAgg protocol a lookup-request setup path (a DBTC/DBSPJ feature — the same machinery the local_execution_mode_plan.md feed work would touch), or simply have such deployments define an ordered index on the PK. Until then this shape is correct-but-blunt, and it is at least rare: a fully-bound PK under an aggregate usually means a one-row aggregate the application could have written as a plain lookup.

Gap 2 — observability. EXPLAIN cannot show any of this: the readTuple / PK-index / fallback choice happens at emit time, after the planner output EXPLAIN prints. Until EXPLAIN grows an emit-plan section, the authoritative way to know which plan ran is this cascade plus the query's shape — which is precisely why this document exists. Extending EXPLAIN to print the emitted root (and its residual placement) is the natural follow-up and would make the optimality table verifiable per query.

7 · Phase 0b: the pass-through printer

Pass-through (projection-only) queries stream raw rows rather than aggregates, and their printer previously understood only integers, floats, doubles and strings. Two failure classes existed in accepted shapes: real temporal/DECIMAL columns threw a hard error, and CTE MIN/MAX over temporal columns — which the kernel delivers as a Bigunsigned carrying the column's packed value — printed as raw integers, silently diverging from MySQL.

The fix reuses what the aggregate path already had. The column-metadata build (charset, precision, scale, temporal tag — resolved through CTE hops back to the source column) is now shared by both printer constructions, and the packed-temporal decoder was factored out of print_aggregate_result into one helper both paths call:

Column typeWire formDecode path
DATE / YEAR (raw column)3-byte / 1-byte little-endian — identical to the packed MIN/MAX formShared packed decoder, directly
DATETIME(n) / TIME(n) / TIMESTAMP(n) (raw)Big-endian packed binary, 5/3/4 + fsp bytesBytes re-packed to a Uint64, then the shared decoder (MySQL's own codecs; TIMESTAMP displayed in UTC via the lock-free converter — with tv_sec == 0 decoding as the zero timestamp 0000-00-00 00:00:00, MySQL's reserved encoding, never as the Unix epoch)
DECIMAL(p,s)Binary decimaldecimal_bin2str with the column's precision/scale
CTE MIN/MAX over any temporalBigunsigned virt column holding the packed valueMetadata pre-check: temporal tag + Bigunsigned ⇒ shared decoder. This was the silent-wrong-output case.
BIT · BINARY/VARBINARY · BLOB/TEXT · pre-5.6 temporals · Olddecimal—Still rejected, now with an error naming the type (matches the aggregate printer's envelope)

LEFT JOIN NULL substitution composes correctly with all of this: unmatched rows arrive as NULL attributes and print as NULL — never as a decode of stale bytes (locked in by test pt-6).
