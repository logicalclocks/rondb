1. Overview & Commit History

RONDB-1048 adds CTE (Common Table Expression) pushdown to the NDB join aggregation framework. A SQL query like WITH cte AS (SELECT ... GROUP BY ...) SELECT ... FROM t JOIN cte is compiled into a compound query tree where CTEs are materialized as distributed hash tables across data nodes, then queried via point lookups or full scans from the main SELECT.

Key Capabilities

  • Up to 4 CTEs per compound query (MAX_CTE_SUBTREES = 4)
  • Dependency-aware phased execution — CTEs are grouped into phases; dependent CTEs wait for their predecessors
  • Multi-node hash redistribution with flow control — each group is sent to its hash-owner node
  • CTE_LOOKUP — point lookups into the distributed hash table by GROUP BY key
  • CTE_SCAN — full iteration of a CTE hash table (for CTE-to-CTE dependencies)
  • Type-aware hashing with collation support for redistribution consistency

2. Query Tree Structure

A compound CTE query is serialized into a QueryTree containing three new node types alongside the existing QN_SCAN_FRAG and QN_LOOKUP:

Figure 1: Compound query tree with two CTEs (CTE 1 depends on CTE 0) and a main query

Node Type Details

Node Type OpType Size Key Fields Purpose
QN_CTE_SUBTREE 0x6 4 words cteId, numNodes Container wrapping an embedded CTE materialization sub-tree. Followed by numNodes standard nodes (SCAN_FRAG, LOOKUP) that form the CTE's scan+aggregate tree.
QN_CTE_LOOKUP 0x7 4 words cteId, numResultCols Point lookup into a materialized CTE hash table by GROUP BY key. Used in the main query to join against CTE results.
QN_CTE_SCAN 0x8 4 words cteId, numResultCols Full scan of a CTE hash table. Used when one CTE reads from an earlier CTE (CTE-to-CTE dependency).

4. End-to-End Lifecycle

Figure 5: End-to-end CTE lifecycle: SETUP → Materialize → Redistribute → Phase advance → Main Query

5. Phase 1: SETUP Signalling

DBTC receives SCAN_TABREQ from the API with CTE definitions (tableId, schemaVersion, depMask, aggProgram per CTE). It then sends JOIN_AGG_SETUP_REQ to every data node for both the main aggregation and each CTE.

Figure 6: SETUP phase sends JOIN_AGG_SETUP_REQ to every node for main + each CTE

aggKeys Section Format

After all SETUP_CONFs arrive, DBTC packs the aggStateKeys into the aggKeys section attached to SCAN_FRAGREQ:

// Main aggregation keys
[nodeId, aggStateKey] pairs...

// CTE keys separator
CTE_KEYS_MARKER (0xCCEE0000)
numCtes
cteFlags (bit 0 = CTE_SCAN_ALL_NODES if instances < nodes)

// Per CTE
[cteId, depMask, phase, nodeCount]
  [nodeId, aggStateKey] pairs...

6. Phase 2: CTE Materialization

DBSPJ receives SCAN_FRAGREQ, parses the aggKeys section (including CTE_KEYS_MARKER), and starts phase 0 CTE scans. Each CTE subtree executes its embedded scan + lookup nodes, feeding rows through the aggregation engine into a JoinGBHashTable on each node.

Figure 7: CTE materialization: DBSPJ drives scan → DBLQH accumulates into hash table

7. Phase 3: Hash Redistribution

When all CTE scans for a phase complete, each node's local hash table contains partial aggregation results. The redistribution phase sends each group to its hash-owner node (determined by hashKeyFull() % num_nodes) so that the final merged result resides on exactly one node.

Figure 8: Hash redistribution sends each group to its hash-owner node; mergeOneGroup() combines accumulators

Flow Control

Redistribution uses two levels of flow control:

  • Batch size: After sending 64KB of group data, the sender sets RI_NEED_CONF on the last REDISTRIBUTE_REQ and pauses until REDISTRIBUTE_CONF arrives.
  • Yield: After processing 256 groups, the sender yields via CONTINUEB to avoid monopolizing the thread.

Concurrent Receive

Multiple LDM threads can receive REDISTRIBUTE_REQ simultaneously. A m_redist_mutex protects the hash table state. If the receiver is still in FINALIZING state, incoming groups are queued in a page-based linked list (RedistQueueEntry) and drained later by processRedistQueue().

8. Phase 4: Multi-Phase CTE Execution

CTEs with dependencies are organized into execution phases. A CTE that depends on CTE 0 (via depMask=0x1) cannot start until CTE 0 is fully redistributed and in CTE_READY state.

Figure 9: Multi-phase CTE execution: each phase materializes, redistributes, then unlocks the next

9. Phase 5: Main Query Execution

After all CTE phases are complete, DBTC sends CTE_START_MAIN_REQ to all DBSPJ instances. DBSPJ transitions all CteContexts to CTE_READY, clears the RT_CTE_PHASE flag, and starts the main query root scan.

Figure 10: Main query CTE_LOOKUP flow: parent row → lookup key → hash table find → result

Lookup Queueing

If cte_parent_row() is called while a CTE is still in CTE_MATERIALIZING state (which happens during CTE-to-CTE dependencies), the lookup is not sent immediately. Instead, m_pendingCount is incremented and the row is queued. When the CTE transitions to CTE_READY (via execCTE_PHASE_START_REQ), pending lookups are flushed.

10. CTE-to-CTE Scan (QN_CTE_SCAN)

When a CTE depends on an earlier CTE, it uses QN_CTE_SCAN as its root "scan" node instead of QN_SCAN_FRAG. This scans all groups from the earlier CTE's hash table via CTE_SCAN_REQ.

Figure 11: CTE_SCAN_REQ iterates a materialized hash table in batches of 256 groups
CTE_SCAN_ALL_NODES flag: When the number of DBSPJ instances is less than the number of data nodes (e.g., 2 instances but 4 nodes), a single DBSPJ instance cannot rely on local-only scans. In this case, m_cteScanAllNodes is set and cte_scan_start() sends CTE_SCAN_REQ to all CTE nodes (not just the local one).
