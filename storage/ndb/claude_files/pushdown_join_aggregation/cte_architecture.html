1. Overview

RONDB-1048 adds CTE (Common Table Expression) pushdown to the NDB join aggregation framework. A SQL query like WITH cte AS (SELECT ... GROUP BY ...) SELECT ... FROM t JOIN cte is compiled into a compound query tree where CTEs are materialized as distributed hash tables across data nodes, then queried via point lookups or full scans from the main SELECT.

Key Capabilities

  • Up to 64 CTEs per compound query — dynamically allocated via lc_ndbd_pool_malloc(RG_QUERY_MEMORY), no fixed-size arrays
  • Uint64 dependency mask — depMask tracks inter-CTE dependencies as a 64-bit bitmask, serialized as 2 words in the wire format
  • Dependency-aware phased execution — CTEs are grouped into phases; dependent CTEs wait for their predecessors
  • Multi-node hash redistribution with flow control — each group is sent to its hash-owner node via type-aware hashing with collation support
  • CTE_LOOKUP — point lookups into the distributed hash table by GROUP BY key (used in both the main query and inside CTE subtrees for CTE-to-CTE joins)
  • CTE_SCAN — full iteration of a CTE hash table (for CTE-to-CTE dependencies that need all rows)
  • O(1) scan resume — hash table iterator state is saved between batches, avoiding O(N) skip on continuation
  • Single-row CTE optimization — CTEs with no GROUP BY (scalar subqueries) materialize on one node, skip redistribution, and cache the result in DBSPJ for signal-free serving
  • Graceful error handling — allocation failures and invalid input abort the query, never crash the node

5. Phase 1: SETUP Signalling

DBTC receives SCAN_TABREQ from the API with CTE definitions (tableId, schemaVersion, depMask as 2 words, aggProgram per CTE). It dynamically allocates CteInfo and JoinAggNodeState arrays as a single contiguous block via lc_ndbd_pool_malloc(RG_QUERY_MEMORY), then sends JOIN_AGG_SETUP_REQ to every data node for both the main aggregation and each CTE.

aggKeys Section Format (Uint64 depMask)

// Main aggregation keys
[nodeId, aggStateKey] pairs...

// CTE keys separator
CTE_KEYS_MARKER (0xCCEE0000)
numCtes
cteFlags (bit 0 = CTE_SCAN_ALL_NODES if instances < nodes)

// Per CTE
[cteId, depMask_lo, depMask_hi, phase, nodeCount]
  [nodeId, aggStateKey] pairs...

The keyData buffer is heap-allocated using MAX_NDB_NODES (runtime value, not compile-time ABS_MAX_NDB_NODES) and freed after appendToSection.

6. Phase 2: CTE Materialization

DBSPJ receives SCAN_FRAGREQ, parses the aggKeys section (including CTE_KEYS_MARKER and Uint64 depMask), and starts phase 0 CTE scans. Each CTE subtree executes its embedded scan + lookup nodes, feeding rows through the aggregation engine into a JoinGBHashTable (1024 buckets) on each node.

Only nodes with the T_CTE_SCAN flag participate in materialization. QN_CTE_LOOKUP and QN_CTE_SCAN nodes inside subtrees are excluded from this flag since they read from other CTEs.

7. Phase 3: Hash Redistribution

When all CTE scans for a phase complete, each node's local hash table contains partial aggregation results. The redistribution phase sends each group to its hash-owner node (determined by hashKeyFull() % num_nodes, type-aware with collation support) so that the final merged result resides on exactly one node.

Flow Control

  • Batch size: After sending 64KB of group data, the sender sets RI_NEED_CONF on the last REDISTRIBUTE_REQ and pauses until REDISTRIBUTE_CONF arrives.
  • Yield: After processing 256 groups, the sender yields via CONTINUEB.
  • Concurrent receive: m_redist_mutex protects hash table state. Incoming groups during FINALIZING are queued in a page-based linked list and drained later.

8. Phase 4: Multi-Phase CTE Execution

CTEs with dependencies are organized into execution phases computed from Uint64 depMask:

phase[c] = 0                                    if depMask[c] == 0
phase[c] = 1 + max(phase[d] for d in depMask[c]) otherwise

DBTC advances phases via cteAdvancePhase(): after redistribution completes for phase N, it sends CTE_PHASE_START_REQ(phase=N+1) to all DBSPJ instances. After all phases complete, it sends CTE_START_MAIN_REQ to start the main query.

9. Phase 5: Main Query Execution

After all CTE phases complete, DBTC sends CTE_START_MAIN_REQ. DBSPJ transitions all CteContexts to CTE_READY and starts the main query root scan. For each parent row, cte_parent_row() checks CTE state and calls cte_lookup_send() which sends CTE_LOOKUP_REQ to DBLQH. The hash table lookup returns the result as TRANSID_AI + CTE_LOOKUP_CONF.

If a CTE_LOOKUP's target CTE is still materializing (CTE-to-CTE dependency during phase execution), the lookup is queued via m_pendingCount and flushed when the CTE transitions to CTE_READY.

10. CTE-to-CTE Dependencies

A CTE that depends on an earlier CTE can use either mechanism to read from its predecessor's hash table:

Access PatternNode TypeWhen to UseInside Subtree
Full scan QN_CTE_SCAN Dependent CTE needs all rows (e.g., CTE 1 scans all of CTE 0) Yes — NOT marked T_CTE_SCAN
Point lookup QN_CTE_LOOKUP Dependent CTE joins CTE 0 by GROUP BY key (equi-join) Yes — NOT marked T_CTE_SCAN

Both node types can appear inside QN_CTE_SUBTREE containers. The build loop excludes them from the T_CTE_SCAN flag because they read from other CTEs rather than driving this CTE's materialization.

CTE_SCAN Batching

CTE_SCAN_REQ iterates the hash table in batches of 256 groups. Each group is sent as TRANSID_AI with GROUP BY keys + aggregate results + CORR_FACTOR. When a batch completes without EndOfData, DBSPJ sends a continuation CTE_SCAN_REQ. The scan resumes from the saved iterator position (see next section).

11. O(1) CTE Scan Resume

When CTE_SCAN_REQ resumes after a batch, the handler uses a saved hash table iterator instead of walking from begin() and skipping N groups:

// O(1) resume from saved position
Uint32 groupIdx = state->m_cteScan_groupsSent;
auto iter = (groupIdx == 0)
    ? gb_map->begin()
    : gb_map->iteratorAt(state->m_cteScan_iterBucket,
                         state->m_cteScan_iterRaw);

// ... send batch ...

// Save resume position
state->m_cteScan_groupsSent = groupIdx;
if (!endOfData && iter.valid()) {
  state->m_cteScan_iterBucket = iter.bucket();
  state->m_cteScan_iterRaw = iter.raw();
}

The iteratorAt(bucket, raw) method constructs a valid iterator at a saved position. Since the hash table is immutable during CTE_READY state, the saved pointer remains valid. The m_prev_link field is set to nullptr (erase not supported on resumed iterators).

13. Compound Query Execution Architecture

A CTE compound query tree has multiple root-level nodes (parentPtrI == RNIL): CTE subtree containers, CTE root scans, and the main query root. This required changes across DBTC and DBSPJ to handle the multi-root structure correctly.

13.1 DBTC: KeyInfo Parsing

The KeyInfo section (SCAN_TABREQ section 2) carries both the main aggregation program and optional CTE definitions:

KeyInfo layout:
  [boundsLen] [bounds...] [aggReceiverId]
  [aggProgram...]          // 0x0721 flat or 0x0722 multi-leaf
  [CTE_DEFS_MARKER]        // 0xCDE00000 (only if CTEs present)
  [numCtes]
  [per-CTE: tableId, schemaVersion, depMask_lo, depMask_hi,
            flags, progLen, prog...]

The data is linearized into a stack buffer (8192 words) for format-independent parsing. The agg program format is detected by magic: 0x0721 (old flat, word[0] & 0xFFFF = progLen) or 0x0722 (multi-leaf wrapper, walk per-leaf entries for total length). CTE_DEFS_MARKER prevents misinterpreting non-CTE leftover data.

DBTC CTE Signal Flow

13.4 Key Design Decisions

One DBSPJ instance per fragment: CTE queries require scanParallelism = fragCount so each fragment gets its own DBSPJ instance. Each CTE root scan processes exactly one fragment (m_rootFragId). DBTC enforces this and rejects requests with insufficient parallelism.
No intermediate SCAN_TABCONF for CTE JoinAgg: With all fragments running in parallel (no SCAN_NEXTREQ cycling), intermediate SCAN_TABCONFs are suppressed inside sendScanTabConf() when m_joinAgg && !release && m_numCtes > 0. Fragment list management still runs; only the signal to the API is skipped. The EndOfData path triggers JOIN_AGG_COMPLETE which finalizes aggregation before the final SCAN_TABCONF.
RT_AGGREGATE scope: Only main query nodes set RT_AGGREGATE (checked via ctx.m_cteSubtreeRemaining == 0 during build). CTE subtree nodes use the T_CTE_SCAN / JoinAggFlag path independently. This allows the main SELECT to be either an aggregate or a normal SPJ query.

14. CTE_LOOKUP Query Flow

This section traces the complete signal flow for a query where the main SELECT joins with a materialized CTE via CTE_LOOKUP_REQ.

14.1 Example SQL

WITH cte0 AS (
  SELECT grp, SUM(val) AS total
  FROM src t1 JOIN src t2 ON t1.pk = t2.pk
  GROUP BY grp
)
SELECT cte0.grp, cte0.total
FROM src t1
JOIN cte0 ON t1.grp = cte0.grp;

14.5 Key Format: P_ATTRINFO vs P_COL

The CTE hash table stores GROUP BY keys as AttributeHeader-encoded bytes: [AttrHeader(attrId, dataSize)] [column data]. The lookupGroup() function matches keys by raw byte comparison.

CTE Hash Table Key (stored during materialization):
┌─────────────────────┬──────────────────┐
│ AttributeHeader     │ Column Data      │
│ (attrId=1, size=8)  │ (BIGINT value)   │
│ 0x00010008          │ 0x00000001 0x0   │  ← grp=1
└─────────────────────┴──────────────────┘
         12 bytes total

CTE_LOOKUP Key (expanded from parent scan row):

  P_ATTRINFO(0) ─── includes header ──→  ✅ MATCH
  ┌────────────────┬────────────────┐
  │ 0x00010008     │ 0x00000001 0x0 │  12 bytes → lookupGroup finds it
  └────────────────┴────────────────┘

  P_COL(0) ─── strips header ──→  ❌ NO MATCH
  ┌────────────────┐
  │ 0x00000001 0x0 │  8 bytes → lookupGroup returns nullptr
  └────────────────┘
    (GROUP_NOT_FOUND error 1263)
Build-time validation: cte_lookup_build() validates the key pattern after parseDA(). If any pattern element uses P_COL instead of P_ATTRINFO, the build fails with InvalidTreeNodeSpecification and a log message, catching the error at query setup rather than at runtime with a silent GROUP_NOT_FOUND.

The CTE_LOOKUP node's parameters include PI_ATTR_INTERPRET (minimal ExitOK interpreter) and PI_ATTR_LIST (virtual column reads). DBSPJ's parseDA() constructs the AttrInfo sent with CTE_LOOKUP_REQ:

┌──────────────────────────────────────────┐
│ [0] initReadLen    = 0                   │  ← 5-word header
│ [1] execRegionLen  = 1                   │
│ [2] finalUpdateLen = 0                   │
│ [3] finalReadLen   = 6                   │
│ [4] subRoutineLen  = 0                   │
├──────────────────────────────────────────┤
│ [5] Interpreter::ExitOK()               │  ← exec region (1 word)
├──────────────────────────────────────────┤
│ [6] AttrHeader(attrId=0, size=0)        │  ← final read: grp key
│ [7] AttrHeader(attrId=1, size=0)        │  ← final read: SUM(val)

DBLQH processes the final-read section:
  attrId 0 → read GROUP BY key from hash table entry
  attrId 1 → read aggregate result (SUM) from accumulators

CTE_LOOKUP_CONF sent to DBSPJ for outstanding tracking.
TRANSID_AI goes directly to API (bypasses DBSPJ).

execCTE_LOOKUP_REQ:
  1. getJoinAggState(aggStateKey) → find CTE hash table
  2. Verify state == CTE_READY
  3. Copy key section to local buffer
  4. Copy AttrInfo to cattrInfoBuffer

     ├─ Found:  process final-read section

Virtual columns (from CTE with GROUP BY grp, SUM(val)):

This section traces the complete signal flow for a query where the main SELECT uses CTE_SCAN_REQ to iterate over a materialized CTE hash table and feed its results into a main aggregation interpreter. Main query has no base table scan: The main SELECT reads entirely from the materialized CTE. Node 3 (QN_CTE_SCAN) replaces a QN_SCAN_FRAG as the root of the main query, iterating the CTE hash table directly rather than scanning an NDB table.

16.4 Aggregation Feed vs Emit Paths

When DBLQH receives CTE_SCAN_REQ, it checks joinAggStateKey to decide which path to take:

execCTE_SCAN_REQ
      │
      ▼
joinAggStateKey != RNIL ?
      │
      ├── YES ──► cteScanAggFeed()         (Aggregation Feed Path)
      │           │
      │           │  CTE hash table groups are iterated.
      │           │  For each group:
      │           │    1. Format key columns + accumulators as a row
      │           │    2. Feed row into the MAIN JoinAggInterpreter
      │           │       (identified by joinAggStateKey)
      │           │    3. Main interpreter applies COUNT(*), SUM(total)
      │           │
      │           │  No TRANSID_AI sent — rows are consumed internally.
      │           │  Result: main hash table accumulates aggregates.
      │           │
      │           └─► CTE_SCAN_CONF (EndOfData=1)
      │
      └── NO ───► cteScanEmitResults()     (Emit Path)
                  │
                  │  CTE hash table groups are iterated.
                  │  For each group:
                  │    1. Format key columns + accumulators as a row
                  │    2. Send TRANSID_AI directly to DBSPJ
                  │    3. DBSPJ dispatches child nodes via startNextNodes
                  │
                  │  When all groups sent:
                  └─► CTE_SCAN_CONF (EndOfData=1)
Feed path is zero-copy to API: In the aggregation feed path, CTE rows never leave DBLQH. They are fed directly from the CTE hash table into the main aggregation interpreter on the same LDM thread. The API only receives the final aggregated result (e.g., a single row with COUNT and SUM) when JOIN_AGG_COMPLETE_REQ finalizes the main hash table.

Trigger joinAggStateKey != RNIL joinAggStateKey == RNIL
Rows sent to API None (consumed locally) All groups via TRANSID_AI
Batching CONTINUEB yield only (no API batching) CTE_SCAN_CONF / CTE_SCAN_NEXTREQ batching
Use case SELECT COUNT(*), SUM(total) FROM cte0 SELECT * FROM cte0 (no main agg)

16.5 Fragment-Per-Node Skip Logic

CTE hash tables are per-data-node, not per-fragment. They are created by DblqhProxy and shared across all LDM threads on the same node. When DBSPJ starts the scanCte node, it must avoid scanning the same hash table multiple times (which would produce N× duplicated results for N fragments on the same node).

Example: 2 data nodes, 4 fragments (2 per node)

DBSPJ gets rootFragIds: [0, 1, 2, 3]
numDataNodes = 2

  rootFragId=0  →  targetNodeId=node1  →  CTE_SCAN_REQ  ✓ (fires)
  rootFragId=1  →  targetNodeId=node2  →  CTE_SCAN_REQ  ✓ (fires)
  rootFragId=2  →  rootFragId >= N     →  SKIP           ✗ (empty result)
  rootFragId=3  →  rootFragId >= N     →  SKIP           ✗ (empty result)

Result: exactly 1 CTE_SCAN_REQ per data node.

Skip logic in cte_scan_start():
┌─────────────────────────────────────────────────────────┐
│  if (rootFragId >= numDataNodes) {                       │
│    // This fragment would scan a duplicate hash table    │
│    // Complete immediately with empty result             │
│    markNodeComplete(...)                                 │
│    return;                                               │
│  }                                                       │
│                                                          │
│  // Compute target: rootFragId maps 1:1 to data nodeId  │
│  Uint32 targetNodeId = nodeIds[rootFragId];              │
│  Uint32 baseKey = m_aggStateKeys[targetNodeId];          │
│  Uint32 key = encodeAggStateKey(baseKey, leafIdx);       │
│  // Send CTE_SCAN_REQ to DBLQH on targetNodeId          │
└─────────────────────────────────────────────────────────┘
Applies in both CTE and main phases: The fragment-per-node skip is unconditional — it fires whether the scanCte is in a CTE subtree (during materialization) or in the main query. CTE hash tables are always per-data-node regardless of execution phase.

16.6 CTE_SCAN Batching and Yielding

CTE hash tables can contain many groups. To avoid blocking the LDM thread, cteScanAggFeed uses CONTINUEB yielding to break the iteration into manageable chunks.

cteScanAggFeed() execution model:

  ┌─────────────────────────────────────────────────────────┐
  │ Entry: CTE_SCAN_REQ received                            │
  │                                                         │
  │ state.m_iterator = cteHashTable.begin()                 │
  │ state.m_groupsProcessed = 0                             │
  └────────────────────┬────────────────────────────────────┘
                       │
                       ▼
  ┌─────────────────────────────────────────────────────────┐
  │ PROCESSING LOOP (up to 256 groups per invocation)       │
  │                                                         │
  │ while (iterator != end) {                               │
  │   group = *iterator                                     │
  │   formatRow(group.keys, group.accumulators)             │
  │   mainAggInterpreter.feedRow(formattedRow)              │
  │   iterator++                                            │
  │   groupsProcessed++                                     │
  │                                                         │
  │   if (groupsProcessed % 256 == 0) {                     │
  │     // Save iterator state in CteScanIterState pool rec │
  │     // Schedule CONTINUEB to resume                     │
  │     signal→theData[0] = ContinueB::CTE_SCAN_AGG_FEED   │
  │     sendSignal(DBLQH_REF, CONTINUEB, ...)               │
  │     return;   // yield back to job scheduler            │
  │   }                                                     │
  │ }                                                       │
  └────────────────────┬────────────────────────────────────┘
                       │
                       ▼ (all groups processed)
  ┌─────────────────────────────────────────────────────────┐
  │ Send CTE_SCAN_CONF (EndOfData=1) back to DBSPJ          │
  └─────────────────────────────────────────────────────────┘

Timeline for 1000 groups:

  CTE_SCAN_REQ ──► process groups 0-255
                   ──► CONTINUEB ──► process groups 256-511
                                     ──► CONTINUEB ──► process groups 512-767
                                                       ──► CONTINUEB ──► 768-999
                                                                         ──► CTE_SCAN_CONF
                                                                              (EndOfData=1)

The CONTINUEB mechanism ensures that other signals (heartbeats, other scan operations, node failure handling) can be processed between chunks. The iterator state is preserved in a pool-allocated CteScanIterState record to support concurrent CTE_SCAN_REQ operations from multiple DBSPJ instances.

17. CTE Query Topology Variants

CTE pushdown supports seven distinct query tree topologies, determined by where lookupCte and scanCte operations appear in the tree (root vs internal, main query vs CTE subtree) and whether they carry aggregation. Each topology exercises a different signal path through DBSPJ and DBLQH.

17.1 lookupCte as Main Query Root (Test 11)

CTE0: scanTable(t1) ──► aggLeaf
                            │
                       [hash table]
                            │
Main: lookupCte(0, key=2)        ◄── root, constant key
           │
           ▼
      readTuple(t2)
lookupCte is the root of the main query with a constant key (no parent linkage).

Key Signal Path:

DBSPJ receives SCAN_TABREQ
  → CTE phase: SCAN_FRAGREQ to DBLQH → aggLeaf builds CTE 0 hash table
  → Main phase: only rootFragId==0 fires CTE_LOOKUP_REQ(cteId=0, key=2)
      → DBLQH: hash probe → TRANSID_AI result
      → DBSPJ startNextNodes → dispatches child readTuple via LQHKEYREQ
  • m_start_signal is consumed in cte_lookup_build. This prevents the child readTuple from misinterpreting the original SCAN_FRAGREQ as an LQHKEYREQ.
  • Only the fragment with rootFragId == 0 fires CTE_LOOKUP_REQ. All other fragments skip, since a constant-key lookup needs to execute exactly once across all fragments.

17.2 lookupCte as CTE Materialization Root (Test 12)

CTE0: scanTable(t1) ──► aggLeaf
                            │
                       [hash table 0]

           │

      aggLeaf
           │
      [hash table 1]

lookupCte roots a CTE subtree that re-aggregates CTE 0 output into CTE 1.

Key Signal Path:

DBSPJ receives SCAN_TABREQ
  → CTE phase 0: SCAN_FRAGREQ → aggLeaf builds CTE 0 hash table
  → CTE phase 1: rootFragId==0 fires CTE_LOOKUP_REQ(cteId=0, key=1)
      → TRANSID_AI → child aggLeaf feeds CTE 1 hash table via agg-feed path
  → Main phase: CTE_SCAN_REQ(cteId=1) → emit CTE 1 results
  • The lookupCte is marked T_CTE_SCAN, so it fires during CTE materialization, not the main query phase.
  • Constant-key branch: no T_KEYINFO_CONSTRUCTED flag set. The key value is baked into the QueryDef.

  → Main phase: SCAN_FRAGREQ for scanTable(t2)

The child aggLeaf routes its result through the joinAggStateKey into CTE 1's aggregator. This uses the agg-feed path in DBLQH, where the result is fed directly into the aggregation interpreter rather than returning to DBSPJ.

scanCte is the main query root and also an aggregate leaf — it re-aggregates CTE output.

Key Signal Path:

DBSPJ receives SCAN_TABREQ
  → CTE phase: SCAN_FRAGREQ → aggLeaf builds CTE 0 hash table
  → Main phase: CTE_SCAN_REQ with joinAggStateKey (non-RNIL)
      → DBLQH cteScanAggFeed: iterates all groups, feeds each into main aggregator
      → JOIN_AGG_COMPLETE_REQ → finalize → TRANSID_AI results
CTE_SCAN_REQ carries a non-RNIL joinAggStateKey, telling DBLQH to take the cteScanAggFeed path. Rows never leave DBLQH — results are accumulated in the main aggregator and emitted only at finalization. Fragment-per-node skip applies.

           │

  → CTE phase 0: SCAN_FRAGREQ → aggLeaf builds CTE 0 hash table
  → CTE phase 1: CTE_SCAN_REQ with joinAggStateKey=RNIL (non-agg-leaf)
      → DBLQH cteScanEmitResults: sends one TRANSID_AI per group back to DBSPJ
      → DBSPJ startNextNodes → child aggLeaf fires per emitted row
      → aggLeaf feeds each row into CTE 1 aggregator
  → Main phase: CTE_SCAN_REQ(cteId=1) → emit CTE 1 results
Because scanCte is NOT an aggregate leaf (T_AGGREGATE_LEAF not set), CTE_SCAN_REQ carries joinAggStateKey = RNIL. DBLQH takes the cteScanEmitResults path with CONTINUEB yielding. Fragment-per-node skip applies in both CTE phases and the main phase.

  → CTE phase: SCAN_FRAGREQ → aggLeaf builds CTE 0 hash table
  → Main phase: LQHKEYREQ for readTuple(key=2)
      → m_start_signal consumed in lookup_build (main root lookup)
      → TRANSID_AI result back to DBSPJ
      → cte_lookup_parent_row → extracts linked key from parent result
      → CTE_LOOKUP_REQ(cteId=0, key=linked) → hash probe → TRANSID_AI → API
The main root is a plain readTuple, not a CTE operation. m_start_signal is consumed in lookup_build (the standard lookup root consumption). The child lookupCte fires from the parent_row path with a key linked from the parent's TRANSID_AI result.

  • The joinAggStateKey in CTE_SCAN_REQ determines the DBLQH path: non-RNIL routes to cteScanAggFeed, RNIL routes to cteScanEmitResults.

18. Implementation Details and Bug Fixes

Key implementation details and bug fixes discovered during CTE development. These issues were non-obvious, often manifesting only with specific query shapes or data volumes.

18.1 Uint32Buffer Dangling Pointer Fix (NdbQueryOperation.cpp)

The prepareAttrInfo() function serializes QueryNodeParameters for each operation into a Uint32Buffer. The QN_CTE_LOOKUP and QN_CTE_SCAN cases had a dangling pointer bug.

Bug: attrInfo.addr(startPos) was called BEFORE attrInfo.append() calls. Since Uint32Buffer::alloc() doubles the internal buffer when full (initial size 32, grows to 64, 128...), the pointer returned by addr() becomes invalid after reallocation.

Symptom: For queries with 6+ operations (like Test 16's 7 nodes), the buffer grew past the initial 32-word allocation. The CTE param header (requestInfo, resultData, len) was written to freed memory — the new buffer had zeros. DBSPJ received paramLen=0 → error 20003 "unknown query operation".

BEFORE (buggy):
  Uint32 startPos = attrInfo.getSize();
  attrInfo.alloc(3);  // header space
  QN_CteScanParameters *param = (QN_CteScanParameters*)attrInfo.addr(startPos);
  // ^^^ pointer valid here
  attrInfo.append(...);  // may trigger realloc — pointer DANGLING
  attrInfo.append(...);  // more appends
  param->requestInfo = ...;  // WRITE TO FREED MEMORY

AFTER (fixed):
  Uint32 startPos = attrInfo.getSize();
  attrInfo.alloc(3);  // header space
  attrInfo.append(...);  // all appends first
  attrInfo.append(...);
  // NOW resolve pointer — buffer is stable
  QN_CteScanParameters *param = (QN_CteScanParameters*)attrInfo.addr(startPos);
  param->requestInfo = ...;  // safe write
The pointer from addr() must be resolved only after all buffer mutations are complete.

18.2 Multi-Fragment CTE Duplication Fix (DbspjMain.cpp)

Bug: cte_scan_start() originally only skipped excess rootFragIds (rootFragId >= numDataNodes) when NOT in CTE phase (!(m_bits & RT_CTE_PHASE)). During CTE materialization, ALL DBSPJ instances ran scanCte, each reading the same shared CTE hash table. With 8 fragments on 1 data node, results were 8× too large.

Root cause: The RT_CTE_PHASE guard was added thinking only main query scanCte needed the skip. But scanCte inside CTE subtrees (e.g., CTE 1 reading CTE 0 in Test 16) also needs the skip because CTE hash tables are shared across LDM threads via DblqhProxy.

Fix: Remove the RT_CTE_PHASE guard. Skip is now unconditional:

  if (requestPtr.p->m_rootFragId >= m_numDataNodes) {
    // Skip — CTE hash tables are per-data-node, only one LDM instance reads
    markNodeComplete(...)
  }

Real table scans use scanFrag_start(), not cte_scan_start(), so unaffected.

18.3 m_start_signal Consumption in cte_lookup_build

Bug: When lookupCte is the main query root (no parent, not in CTE subtree), the build loop's ctx.m_start_signal (pointing to SCAN_FRAGREQ) was not consumed. The next child node's lookup_build() interpreted SCAN_FRAGREQ as LQHKEYREQ, reading garbage for LqhKeyReq::getAttrLen — crash.

Fix: In cte_lookup_build(), consume m_start_signal when the node is the main root:

  if (ctx.m_start_signal &&
      ctx.m_cteSubtreeRemaining == 0 &&
      treeNodePtr.p->m_parentPtrI == RNIL) {
    ctx.m_start_signal = NULL;  // consume — lookupCte uses CTE_LOOKUP_REQ, not LQHKEYREQ
  }
The start signal must be consumed by the root node during build, preventing child nodes from misinterpreting it.
The m_start_signal mechanism is part of DBSPJ's build loop: the first node in the query tree consumes the initial request signal (SCAN_FRAGREQ or LQHKEYREQ) and sets m_start_signal = NULL so subsequent nodes parse their parameters from attrInfo sections rather than from a signal.
