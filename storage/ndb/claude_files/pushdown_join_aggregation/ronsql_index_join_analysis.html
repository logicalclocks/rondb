RonSQL Index Selection & Join Order

Analysis of the current (March 2026) implementation in RonSQLPreparer.cpp, QueryPlanner.cpp, and related files.

1  Overview

RonSQL processes a query in these phases:

Index selection and join planning happen in the plan / classify phase. The approach differs between single-table queries and join queries.

2  Single-Table Index Selection

Entry point: plan_index_and_filter() (RonSQLPreparer.cpp:1067). Called only when there is no JOIN clause.

2.1  Pipeline

1. simplify_ce() — normalize conditions to column OP constant
↓
2. collect_toplevel_conditions() — flatten AND tree into array of conjuncts
↓
3. generate_scan_config_candidates() — score every ordered index + table-scan baseline
↓
4. Pick candidate with highest goodness score

2.2  Expression Normalization

simplify_ce() (RonSQLPreparer.cpp:4593) ensures that every comparison has the column on the left and the constant on the right. If the constant is on the left, it swaps the operands and flips the operator (e.g., 5 > x → x < 5). This invariant simplifies downstream index matching.

2.3  Top-Level Condition Collection

collect_toplevel_conditions() (RonSQLPreparer.cpp:1109) recursively flattens nested AND nodes into a flat array m_toplevel_conditions[]. OR sub-trees are kept intact as single entries. Limit: 64 conjuncts.

2.4  Candidate Generation and Scoring

generate_scan_config_candidates() (RonSQLPreparer.cpp:1123) iterates every ordered index on the table, evaluates which conditions can serve as index bounds, and computes a goodness score.

Algorithm per index

  1. Walk index columns in prefix order (column 0, 1, 2, …).
  2. For each index column, scan m_toplevel_conditions[] for a matching comparison (=, >, >=, <, <=).
  3. A match sets lbound and/or ubound:
    • = sets both.
    • >=, > set lower bound.
    • <=, < set upper bound.
  4. A non-equality condition on a column blocks all later columns from being used as bounds.
  5. An unmatched column also blocks later columns.
  6. Matched conditions get condition_handling_map[i] = col_idx; unmatched ones stay at -1 (= apply as scan filter).

Goodness Scoring

Each matched condition contributes points that are accumulated:

FactorMultiplierWhen
Base100Always per matched condition
Non-VARCHAR bonus+10Column is not VARCHAR/LONGVARCHAR
Double-bounded×10Both lower and upper bound set (or equality)
No block×100Later index columns are still usable
PRIMARY index+1Index name is "PRIMARY" (tie-breaker)
Example
WHERE a = 1 AND b >= 2 on index (a, b, c)
  • Column a: equality → double-bounded, no block yet → 110 × 10 × 100 = 110,000
  • Column b: range → single-bounded, blocks later cols → 110
  • Column c: blocked → skipped
  • Total goodness: 110,110
Table scan goodness: 0. Index wins.

Condition Handling Map

After selection, every entry in m_toplevel_conditions[] is either:

condition_handling_map[i]Meaning
-1Apply as NdbScanFilter (pushed to data node)
>= 0Apply as index bound on that index column number

3  Join Order

Entry point: QueryPlanner::plan() (QueryPlanner.cpp:30).

Key Limitation: Fixed Left-to-Right Order
RonSQL does not reorder joins. The join order is exactly as written in the SQL statement. The parser produces a linked list of JoinClause nodes in textual order, and the planner iterates that list sequentially.

3.1  Root Operation

The root is always created as TABLE_SCAN in the planner (QueryPlanner.cpp:54). No index selection happens at plan time for the root in join queries — the decision is deferred to execution.

Execution-Time Root Access Selection

At execution time, execute_join() (RonSQLPreparer.cpp:3705–3817) determines the root access method in two steps:

  1. PK equality coverage check — collect_pk_equalities() (:3464) walks the WHERE clause recursively, extracts all pk_col = constant equalities, and sets pk_covered = true only if every primary key column has a matching equality constant. Only = is accepted (not ranges), and only column-vs-constant (not column-vs-column).
  2. Child operation type check — if PK is covered, scans ops[1..n] to see whether any child is a TABLE_SCAN or INDEX_SCAN (has_scan_child).

These two flags select one of three execution paths:

PathConditionsNDB API CallAccess
A pk_covered AND all children are lookups qb->readTuple(root_table, pk_keys, &opts) Primary key lookup — single-row access, no scan
B pk_covered AND at least one child is a scan qb->scanIndex(pk_ordered_idx, root_table, &bound, &opts) Ordered index scan on PK with equality bounds (effectively single-row, but as a scan — required because the NDB API does not support a lookup root with scan children)
C PK not covered, or Path B with no ordered PK index qb->scanTable(root_table, &opts) Full table scan with NdbScanFilter for WHERE conditions
Why Path B exists: NDB API lookup+scan constraint

The NDB API's NdbQueryBuilder requires that if any child operation is a scan (INDEX_SCAN), the root must also be a scan operation (scanTable or scanIndex). A readTuple root cannot have scan children in the SPJ tree. Path B works around this by using an ordered index scan on the primary key with equality bounds — logically equivalent to a PK lookup but expressed as a scan.

Path B Partition Pruning

NDB tables are hash-partitioned by their distribution key (which defaults to the primary key). A full table scan touches all fragments on all data nodes. Path B avoids this: the NDB API automatically prunes the scan to a single fragment when the index bounds cover all distribution key columns with equality constraints.

The pruning chain works as follows:

1. RonSQL creates NdbQueryIndexBound(pk_keys) — sets both low and high bounds to the same equality values for all PK columns
↓
2. At query execution, NdbQueryOperationImpl::isPrunable() (NdbQueryOperation.cpp:4106) calls checkPrunable()
↓
3. NdbQueryIndexScanOperationDefImpl::checkPrunable() (NdbQueryBuilder.cpp:1622) verifies three conditions:
#CheckPath B Status
1 Distribution key coverage — the index must contain all distribution key fields Pass — the PK ordered index covers all distribution key columns by definition
2 Equality bounds on all distribution keys — each distribution key column must have BoundEQ (not a range) Pass — NdbQueryIndexBound(pk_keys) sets identical low/high bounds (= equality) for every PK column
3 Single hash value — all bound pairs must hash to the same fragment via Ndb::computeHash() Pass — all columns have constant equality values, producing a single deterministic hash

When all three checks pass (prunable = true), the scan is reduced to a single fragment (NdbQueryOperation.cpp:3022–3034):

bool pruned = false;
const int error = isPrunable(pruned);
if (pruned) {
  rootFragments = 1;      // scan hits one fragment, not all
  m_fragsPerWorker = 1;
}
Path B performance summary

Thanks to automatic partition pruning, Path B is effectively equivalent to Path A (PK lookup) in terms of data access — it reads a single row from a single fragment on a single data node. The only overhead compared to a true readTuple() is the scan machinery setup, which is negligible. RonSQL does not need to call setPartitionId() or any other explicit pruning API — the NDB API detects the prunable bounds automatically.

Limitations of Root Index Selection in Joins
  • The root in join queries never uses plan_index_and_filter() (the goodness-scoring index selector). That function is single-table only.
  • The root can only use an ordered index on the PK columns (Path B). Non-PK ordered indexes are never considered.
  • Range conditions on PK columns (e.g., pk > 5) do not trigger any index use — only full PK equality coverage qualifies.
  • WHERE filters on root columns that are not PK equalities are applied as NdbScanFilter (pushed to data nodes), regardless of available indexes.

collect_pk_equalities() Details

Location: RonSQLPreparer.cpp:3464. Walks the WHERE AST recursively:

  • Descends into T_AND nodes.
  • Extracts T_EQUALS conditions where one side is a column in the root table's PK and the other is a constant.
  • Stores each matched constant into pk_const[k] indexed by PK column position.
  • After traversal, pk_covered is true only if every slot in pk_const[] has been filled.
  • Conditions with non-equality operators, column-vs-column comparisons, and OR sub-trees are all ignored — they never contribute to PK coverage.

3.2  Child Operations

For each JoinClause, the planner resolves the parent reference and selects the child access method in strict priority order:

Access TypeConditionIndex Used
PK_LOOKUP ON columns exactly match all PK columns (set match, any order) None (uses primary key directly)
UNIQUE_LOOKUP ON columns exactly match all columns of a UniqueHashIndex First matching unique index
INDEX_SCAN ON columns appear as a prefix of an OrderedIndex First matching ordered index
ERROR No suitable index found Throws RonSQLPermanentError

Child Partition Pruning

NDB tables are hash-partitioned across data node fragments. Whether a child operation touches one fragment or all of them depends on its access type:

Access TypePruningMechanism
PK_LOOKUP Single fragment DBSPJ hashes the full PK (constructed from linked parent values) via computeHash(), then asks DBDIH for the owning fragment (DIGETNODESREQ). The LQHKEYREQ is sent to that one fragment only.
UNIQUE_LOOKUP Single fragment Implemented as two lookups internally: first a PK lookup on the unique index table (hashed to one fragment), then a PK lookup on the main table using the returned PK (hashed to one fragment). Both are single-fragment.
INDEX_SCAN Depends on index Pruned to a single fragment only if the index bounds (linked from parent) cover the entire distribution key with equality constraints. Otherwise scans all fragments.

INDEX_SCAN Pruning Details

At query definition time, NdbQueryIndexScanOperationDefImpl::appendPrunePattern() (NdbQueryBuilder.cpp:2148) checks whether the child scan's index bounds cover the full distribution key. If so, it serializes a SF_PRUNE_PATTERN into the QueryTree definition.

At execution time in DBSPJ, when a parent row arrives for a prunable child scan (scanFrag_parent_row(), DbspjMain.cpp:8059):

1. Expand the prune key from linked parent column values
↓
2. computePartitionHash() — hash the distribution key
↓
3. getNodes() — ask DIH which fragment owns that hash value
↓
4. Append range to only that fragment's scan buffer
↓
5. scanFrag_send() sends SCAN_FRAGREQ to the single matching fragment

Without SF_PRUNE_PATTERN, the range is broadcast to all fragments.

When is an INDEX_SCAN child prunable?

Pruning requires that the ordered index prefix used as bounds covers all distribution key columns with equality constraints. For tables using the default distribution (hash of PK), this means the index must have the full PK as a prefix and the ON clause must provide equality on all PK columns — at which point a PK_LOOKUP would have been selected instead.

In practice, INDEX_SCAN children are rarely pruned. The common case is a foreign-key join (ON child.fk = parent.pk) where fk is not the child's distribution key — the scan must touch all fragments. Pruning only occurs with custom distribution keys or when the index happens to cover the full distribution key as a prefix.

3.3  Index Matching Details

isPrimaryKey()

  • Requires exact set match: number of ON columns must equal number of PK columns, and every ON column must appear in the PK.
  • Column order in the ON clause does not matter.
  • Partial PK matches are not accepted.

findUniqueIndex()

  • Scans all UniqueHashIndex entries on the table.
  • Requires exact set match: index column count = ON column count, all match.
  • Returns first matching index (no scoring).

findOrderedIndex()

  • Scans all OrderedIndex entries on the table.
  • Allows prefix match: the index may have more columns than the ON clause requires.
  • ON columns must appear within the first N columns of the index (where N = number of ON columns).
  • Returns first matching index (no scoring).

3.4  Parent Resolution

Each child operation must reference exactly one parent. The parent is identified by the table alias in the ON condition. All ON conditions in a single JOIN must reference the same parent table.

The parent must be a previously defined operation (lower index in JoinPlan::ops[]). Forward references are rejected.

4  WHERE Filter Classification for Joins

Entry point: classify_where_by_table() (RonSQLPreparer.cpp:955).

4.1  Algorithm

  1. Flatten top-level AND into conjuncts (same as single-table).
  2. For each conjunct, recursively determine which table's columns it references (classify_ce_table()).
  3. Assign the conjunct to that table's filter: m_join_where_ce[table_idx].
  4. Constant-only conditions are assigned to the root (table 0).

4.2  Cross-Table Conditions

If a single conjunct references columns from two or more tables (e.g., a.x = b.y outside of ON), it is classified as cross-table (-2) and rejected with an error.

Exception: Subquery Cross-Table Filters
For correlated scalar subqueries rewritten as joins, cross-table filters (e.g., l.qty > o.min_qty) are handled specially: they are compiled into BranchReg conditional aggregation instructions instead of scan filters. This bypasses the cross-table restriction.

4.3  Filter Application at Execution

During execute_join(), each child operation gets its per-table filter attached as NdbInterpretedCode via NdbScanFilter:

// For each child operation i:
if (m_join_where_ce[i] != NULL) {
    NdbScanFilter filter(&interpreted_code);
    filter.begin(NdbScanFilter::AND);
    apply_filter(&filter, m_join_where_ce[i]);
    filter.end();
    opts.setInterpretedCode(interpreted_code);
}

Filters are pushed to data nodes and evaluated during the scan, reducing network traffic.

5  Subquery Rewriting & Outer Join Handling

SELECT-list correlated scalar subqueries are rewritten into explicit JOIN clauses for multi-leaf pushdown aggregation. All injected joins use LEFT OUTER JOIN so that unmatched parent rows produce NULL aggregates instead of disappearing from the result.

5.1  Transformation Example

Before (user SQL)After (internal AST)
SELECT o.id,
  (SELECT SUM(l.qty)
   FROM lineitem l
   WHERE l.order_id = o.id) AS total,
  (SELECT COUNT(s.id)
   FROM shipment s
   WHERE s.order_id = o.id) AS ships
FROM orders o
 
SELECT o.id,
       SUM(l.qty)  AS total,
       COUNT(s.id) AS ships
FROM orders o
  LEFT JOIN lineitem l
    ON l.order_id = o.id
  LEFT JOIN shipment s
    ON s.order_id = o.id
GROUP BY o.id

5.4  Step 2: Merge (merge_same_table_subqueries)

Location: RonSQLPreparer.cpp:2547. Groups subqueries that share the same (table, inner_join_col, outer_join_col) triple into a single leaf operation with a combined aggregation program.

Merging criteria (all three must match):

  • inner_table_name — same physical table
  • inner_join_col — same inner join column
  • outer_join_col — same outer join column

When merging, column qualifiers referencing different aliases of the same table are remapped to the base alias, so load_join() resolves them against a single joined table.

5.5  Step 3: Rewrite (rewrite_select_subqueries_as_joins)

Location: RonSQLPreparer.cpp:2614. For each MergedLeaf:

  1. Create a JoinClause with:
    • join_type = LEFT_OUTER_JOIN (always — use_inner_join is always false)
    • table = inner table reference
    • conditions = single equi-join ON condition from the correlation predicate
  2. Append the JoinClause to the end of the outer query's join list.
  3. Auto-inject GROUP BY on the outer correlation key column. Also adds all other non-aggregate COLUMN outputs to GROUP BY (functionally dependent on the correlation key).
  4. Clear m_col_is_inner flags so that subquery table columns participate in normal column loading.
Why LEFT OUTER JOIN?

A correlated scalar subquery returns NULL when no inner rows match the outer row. To preserve this semantic after rewriting to a join, the join must be LEFT OUTER. An INNER JOIN would eliminate outer rows with no matching inner rows, changing the result set.

Example: if order 21 has no lineitems, (SELECT SUM(l.qty) …) returns NULL. With LEFT OUTER JOIN, order 21 stays in the result with SUM = NULL. With INNER JOIN, order 21 would disappear.

5.6  Outer Join Match Tracking in DBSPJ

After rewriting, the injected LEFT OUTER JOINs are processed by the normal SPJ push-down engine. DBSPJ handles NULL injection for unmatched parent rows:

  1. Each parent row fires a child scan on the leaf table.
  2. If the child scan returns rows, they pass through the aggregation interpreter normally.
  3. If the child scan returns no rows (no match), DBSPJ's handleAggLeafScanComplete() detects unmatched parent rows via a bitmask (m_agg_match_bitmask) and injects NULL-extended pseudo-rows into the aggregation.
  4. The aggregation interpreter handles NULLs per SQL semantics:
    • COUNT(*) — increments (counts the NULL row)
    • COUNT(col) — does NOT increment (NULL skipped)
    • SUM / MIN / MAX — skip NULL values

Match Tracking Flags

In DbspjMain.cpp, during validateAggregateFlags(), DBSPJ enables match tracking on relevant tree nodes:

FlagSet OnPurpose
T_BUFFER_MATCH Scan ancestor of outer-joined aggregate leaf Track which parent rows got at least one child match
T_BUFFER_ROW Intermediate lookup parents Buffer parent row data for NULL row construction

5.7  Cross-Table Filter Execution

Cross-table filters (e.g., l.qty > o.min_qty) cannot be pushed as regular scan filters because they reference columns from a parent table. Instead, they are compiled into conditional aggregation using BranchReg opcodes:

1. LoadLinkedColumn(outer_proj_pos, reg_outer) — load parent column via linked projection
↓
2. LoadColumn(inner_attr_id, reg_inner) — load inner column from current row
↓
3. BranchRegXx(reg_inner, reg_outer, skip_count=2) — skip if NOT(condition)
↓ (not skipped)
4. LoadColumn(agg_col, reg) + Sum/Count/Min/Max(slot, reg)

The branch instruction is inverted: it skips the aggregation when the filter does NOT match. Mapping:

SQL FilterSkip When NOT MatchOpcode
inner > outerinner <= outerBranchRegLe
inner >= outerinner < outerBranchRegLt
inner < outerinner >= outerBranchRegGe
inner <= outerinner > outerBranchRegGt
inner = outerinner != outerBranchRegNe
inner != outerinner = outerBranchRegEq

If either register is NULL, the branch always skips (NULL comparison = no match).

5.8  Multi-Leaf Aggregation Program Construction

During execute_join(), one NdbAggregator is created per MergedLeaf. Each aggregator programs:

  1. GROUP BY columns — from the outer query. Parent-table GROUP BY columns use GroupByLinked() with linked projections.
  2. Per-subquery aggregates — iterates all SelectSubqueryLeaf entries in the merged group, emitting LoadColumn + aggregate instruction for each. Cross-table filters insert BranchReg before the load/aggregate pair.
  3. Finalize — the aggregator is attached to the corresponding leaf operation via opts.setAggregation().

The wire format uses a 0x0722 header distinguishing multi-leaf sections from the old 0x0721 single-leaf format. DblqhProxy parses both formats with backward compatibility.

7  Current Limitations

#LimitationImpact
1 No join reordering. Order is always SQL left-to-right. Suboptimal plans when the user writes tables in a poor order. A small dimension table scanned first would be better as a lookup child.
2 No index scoring for joins. findUniqueIndex() and findOrderedIndex() return the first match, not the best. If multiple indexes cover the join columns, the choice is arbitrary (depends on NDB dictionary iteration order).
3 Limited root index selection for joins. The root in join queries never uses plan_index_and_filter() (goodness scoring). It can only use PK lookup (Path A) or ordered PK index scan with equality bounds (Path B) — see §3.1. Non-PK ordered indexes on the root table are never used. Range conditions on PK columns do not trigger index use. Only full PK equality coverage activates an optimized root access path.
4 Cross-table WHERE conditions rejected. Conditions like a.x > b.y outside ON clauses cause an error. Users must restructure queries. (Exception: subquery cross-table filters are handled via BranchReg opcodes.)
5 OR conditions cannot be split across index bounds. An OR stays as a single filter conjunct. Queries like WHERE a = 1 OR a = 2 use scan filter instead of two index bounds.
6 No cost-based optimization. Scoring uses static heuristics, not table statistics or cardinality estimates. The best index may not be selected when conditions have very different selectivities.
