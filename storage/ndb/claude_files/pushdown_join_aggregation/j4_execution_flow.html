Order 31 NULL Result Analysis

The Query

SELECT o.id AS order_id,
  (SELECT SUM(l.price) FROM j_lineitem AS l
   WHERE l.order_id = o.id AND l.qty > 3) AS big_total
FROM j_customer AS c
JOIN j_orders AS o ON o.cust_id = c.id;

Pushed Query Tree

  customer (root table scan)
      │
      ▼
  orders (index scan on idx_orders_cust, bound = c.id)
      │
      ▼
  lineitem (index scan on idx_li_order, bound = o.id, AGGREGATE LEAF)
      Aggregation: GROUP BY o.id
                   LoadLinkedColumn(o.min_qty, reg2)
                   LoadColumn(l.qty, reg1)
                   BranchRegLe(reg1, reg2, skip=2)  ← skip if l.qty ≤ o.min_qty
                   LoadColumn(l.price, reg0)
                   Sum(slot0, reg0)

Part 1: Single Data Node Execution

With 1 data node, all data is local. One DBSPJ instance handles the entire query. All fragments are on the same node.

Single node: Works correctly. Both orders 30 and 31 are processed in the same DBSPJ instance. The lineitem scan receives bounds for BOTH orders in one batch. The scan returns rows for both. Order 31's lineitem (qty=3) reaches handleJoinAggRow, creates the group, but BranchReg skips the aggregation → UNDEFINED accumulator → NULL result.

Part 2: Two Data Nodes Execution

With 2 data nodes, tables are partitioned across nodes. Each node has its own DBSPJ instances. The NDB API sends SCAN_TABREQ to DBTC which distributes work across multiple DBSPJ instances (one per TC thread per node).

The Batch Timing Problem

The problem occurs when the orders scan returns results in MULTIPLE batches.

The orders index scan on cust_id=3 sends SCAN_FRAGREQs to all fragments across both nodes. If the batch size is small or the fragment distribution causes order 30 to arrive in batch 1 and order 31 in batch 2, the following happens:

Why the Restart Sometimes Fails

Root cause hypothesis: The scanFrag_parent_batch_complete() mechanism relies on a specific state machine transition:

TN_ACTIVE → TN_INACTIVE (all frags done) → parent_batch_complete → TN_ACTIVE (restart)

The problem occurs when:
  1. The lineitem scan completes (TN_INACTIVE) while orders is still fetching batch 2
  2. Orders batch 2 arrives → order 31 triggers scanFrag_parent_row(lineitem)
  3. scanFrag_parent_batch_complete() is called to restart lineitem
  4. The restart resets fragment counters and sends new SCAN_FRAGREQs
But: if the timing differs (e.g., orders scan completes fully BEFORE lineitem processes all its results), the state machine may be in a different state when the restart is attempted.

Alternative hypothesis: The lineitem scan's reportAncestorsComplete() may trigger completion of the orders node prematurely, or the orders scan may not call scanFrag_parent_batch_complete() for the lineitem node if the lineitem was started with a different batch coordination path.

Key debugging questions:
  1. Does scanFrag_parent_batch_complete() get called for the lineitem node after order 31 arrives?
  2. What is the lineitem node's state when order 31's scanFrag_parent_row() is called?
  3. Does the lineitem scan actually restart with the new bound for order_id=31?
  4. Is the SCAN_FRAGREQ for the restarted lineitem scan actually sent to DBLQH?

The Correct Flow (What Should Happen)

For order 31 to produce a NULL result, this must happen:
  1. Customer 3 row → orders index scan → returns orders 30 AND 31
  2. Both orders trigger scanFrag_parent_row(lineitem)
  3. Both bounds (order_id=30, order_id=31) are sent to lineitem scan
  4. Lineitem scan processes ALL fragments:
    • Fragment with id=108,109,110: order_id=30 → 3 rows → handleJoinAggRow × 3
    • Fragment with id=111: order_id=31 → 1 row → handleJoinAggRow × 1
  5. For order 31's row (qty=3): BranchRegLe skips Sum → accumulator UNDEFINED
  6. GROUP BY creates group "31" with UNDEFINED accumulator → NULL in result
The key is that steps 2-3 must complete before the lineitem scan starts. If orders returns results in multiple batches, lineitem must be restarted for each batch to process all order bounds.
