Architectural rule for Phase M
------------------------------

Aggregation programs must not contain BranchReg control flow.

Filtering happens before aggregation.  Any predicate that needs branch
logic must use the normal interpreter / filter execution path.  CASE-like
conditional value selection in aggregation uses kOpEmbeddedInterp, not
aggregation-program BranchReg opcodes.

Implementation note:
  It is acceptable to extend kOpEmbeddedInterp so the embedded normal
  interpreter can return a special "stop aggregation program for this
  row" code.  This can be simpler than moving every remaining
  cross-table predicate into a separate filter program, and it does not
  duplicate branch semantics because comparison and branching still live
  in the normal interpreter.

   Current area:
     Around the merged select-subquery leaf aggregator setup.

   Current shape:
     LoadLinkedColumn(outer)
     LoadColumn(inner)

   Current BranchReg calls:
     BranchRegLe
     BranchRegLt
     BranchRegGe
     BranchRegGt
     BranchRegNe
     BranchRegEq

   This is the original RONDB-1044 pattern and must move to normal
   filter execution, or to kOpEmbeddedInterp with a normal-interpreter
   predicate that can stop the aggregation program for this row.

2. RonSQL join aggregation cross-table WHERE fallback

   File:
     storage/ndb/src/ronsql/RonSQLPreparer.cpp

   Current area:
     programAggregator_join(), around the cross_table_where_filters
     handling.

   Current shape:
     Remaining cross-table filters are emitted as BranchReg conditional
     aggregation.  A hidden sentinel COUNT accumulator is appended so
     result handling can suppress groups where every row skipped the
     aggregate block.

   Current BranchReg calls:
     BranchRegLe
     BranchRegLt
     BranchRegGe
     BranchRegGt
     BranchRegNe
     BranchRegEq

   The OR fallback also combines BranchReg with Skip to emulate boolean
   control flow inside the aggregation program.  This must be replaced
   by normal interpreter execution, either as a normal filter program or
   as a kOpEmbeddedInterp stop-program predicate.

3. RonSQL SVM GREATEST / LEAST pair-op lowering

   Files:
     storage/ndb/src/ronsql/RonSQLPreparer.cpp
     storage/ndb/src/ronsql/AggregationAPICompiler.hpp
     storage/ndb/src/ronsql/AggregationAPICompiler.cpp
     storage/ndb/src/ronsql/RonSQLPreparer.hpp

   Current SVM operations:
     Greatest2
     Least2
     FORALL_PAIR_OPS

   Current lowering:
     Greatest2 expands to BranchRegGe + Mov.
     Least2 expands to BranchRegLe + Mov.

   This is committed Phase I.5 v2b work.  It must be redesigned before

Phase M.1 guard checklist
-------------------------

Progress after M.1
------------------

Implemented the common kOpEmbeddedInterp stop-program result:

  AGG_EMBEDDED_INTERP_STOP_PROGRAM

Both aggregation interpreter variants now treat that embedded output as
"stop this row's aggregation program".  RonSQL select-subquery
cross-table filters have been moved from NdbAggregator::BranchReg* to
the embedded normal-interpreter condition generator, using a local skip
offset when the per-subquery predicate is false.  They do not use the
stop-program result because a merged leaf may contain multiple subquery
aggregate slots.

Remaining production RonSQL BranchReg emitters:

  [x] Phase I.5 v2b Greatest2 / Least2 lowering.
  [x] Join aggregation cross-table WHERE fallback in programAggregator_join().

The join aggregation fallback now emits embedded normal-interpreter
predicates and uses AGG_EMBEDDED_INTERP_STOP_PROGRAM when a row fails a
remaining cross-table WHERE filter.  The replacement covers the existing
integer column / integer constant / + / - / * expression shapes and the
OR / AND atom flattening used by cross_table_where_filters.  MUL_REG_REG
was enabled in the aggregation embedded-interpreter handler table so this
path is available in the aggregation interpreter variants.

The v2b Greatest2 / Least2 pair-op lowering now emits an embedded
normal-interpreter comparison.  The embedded program imports the relevant
aggregation registers through READ_AGG_REG_TO_REG, compares them with the
normal BRANCH_*_REG_REG opcodes, and returns a one-instruction skip over
Mov when the destination register should be kept.

At this point, RonSQL production code no longer calls
NdbAggregator::BranchReg*.  testCteNdbApi Test 21 has also been moved
from BranchRegGe to the embedded compare path.

The public NDB API BranchReg* methods, the kOpBranchReg* aggregation
opcodes and the aggregation interpreter compatibility handlers have been
removed.  The remaining non-documentation BranchReg hits are
BranchRegEqNull / BranchRegNeNull in the normal DBTUP interpreter; those
are not aggregation opcodes.

Before Phase M is considered complete, rerun the inventory command and
verify:

  [x] No RonSQL production path calls NdbAggregator::BranchReg*.
  [x] No AggregationAPICompiler SVM op lowers to BranchReg*.
  [x] No aggregation interpreter variant accepts kOpBranchReg*.
  [x] No direct NDB API test uses BranchReg* as a required feature.
  [ ] RonSQL cross-table filter tests still cover the same SQL semantics.
  [ ] CASE aggregation tests still use kOpEmbeddedInterp for conditional
      value selection.
  [ ] Remaining BranchReg references are either normal-interpreter
      BranchRegEqNull / BranchRegNeNull, Phase M documentation, or
      explicitly obsolete historical notes.
