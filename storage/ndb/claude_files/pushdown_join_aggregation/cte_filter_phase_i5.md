# Phase I.5 — GREATEST / LEAST (n-ary)

## Status

**v1 shipped, then superseded by v2b.**  v1's CaseExpr-based
two-arg lowering was replaced by v2b's `Greatest2` / `Least2` SVM
pair-op path — n=2 and n>2 both flow through the same SVM
chain.  v1's `m_greatest_least_conditions` /
`is_greatest_least_condition` infrastructure was removed at the
same time.

The original v1 design described in this doc is preserved for
historical context, but the live implementation is documented in
`cte_filter_phase_i5_v2b.md` (with `cte_filter_phase_i5_v2.md`
covering v2a's col-vs-col CASE atom path, which still applies to
explicit user-written CASE conditions).

## Background

`GREATEST(a, b, ...)` and `LEAST(a, b, ...)` are MySQL n-ary scalar
functions returning the largest / smallest of their arguments.  RonSQL
has no parser surface for them today and no generic function-call rule
— each function gets its own hardcoded grammar rule (DATE_ADD,
EXTRACT, CASE).

`testCteNdbApi.cpp` Test 21 (line 5621-5715) builds `GREATEST` for a
single aggregator output via `BranchRegGe + Mov + Max` — a
register-based path that RonSQL doesn't emit.  That path is **not**
the I.5 target; it requires a register-based CASE-condition codegen
that is also part of the deferred Test-21 work mentioned in
`cte_filter_phase_i4.md` "Cleanly-rejected shapes".

The pragmatic I.5 lowering target is **CASE-chain expansion at parse
time**, reusing the existing `AggregationAPICompiler::CaseExpr` IR and
the embedded-interp emit path that I.4 just stabilised.  For two
arguments:

```
GREATEST(x, y)  →  CASE WHEN x >= y THEN x ELSE y END
LEAST(x, y)     →  CASE WHEN x <= y THEN x ELSE y END
```

For three or more arguments, the lowering is left-associative:

```
GREATEST(a, b, c)  →  GREATEST(GREATEST(a, b), c)
                   →  CASE WHEN (CASE WHEN a >= b THEN a ELSE b END) >= c
                       THEN (CASE WHEN a >= b THEN a ELSE b END)
                       ELSE c
                       END
```

Each operand is duplicated under `CaseExpr` once for the condition and
once for the THEN arm; the existing `AggregationAPICompiler` already
handles such reuse (`usage` ref-count + `program_usage`).

## Problem

Two latent gaps block the natural lowering:

1. **Embedded CASE conditions are restricted to `=` / `!=`.**
   `generate_embedded_condition` at `RonSQLPreparer.cpp:8093` does
   `ndbrequire(atom->op == T_EQUALS || atom->op == T_NOT_EQUALS)`.
   `>=` / `<=` (and `>`, `<`) crash the preparer rather than emit the
   inequality branch.  The kernel side has full support — the
   `BranchCol` / `BranchMem` / `BranchMem` opcode encodings take a
   `Interpreter::BinaryCondition` field that already names `LT`, `LE`,
   `GT`, `GE`.  This is purely a RonSQL-side restriction.

2. **Embedded CASE conditions are column-vs-constant only.**
   `val_side = atom->args.right` is fed to `encode_constant` at
   line 8122, which assumes the right-hand side is a literal.  A
   column-vs-column condition (`x >= y` where both are columns) needs
   a different code path — load both into registers and `BranchRegGe`,
   matching Test 21's NDB-API shape.  RonSQL doesn't emit register-
   based CASE today.  Lifting this is significantly bigger and is
   therefore **deferred** to a follow-up phase paired with the
   register-based CASE work.

I.5 v1 lifts gap (1) and exploits the existing column-vs-constant
embedded path.  It restricts GREATEST/LEAST operands to shapes the
embedded path can emit.

## Scope (v1)

**Accepted shapes.**  GREATEST/LEAST with two or more operands where:

- Each operand is a column reference or an integer constant.
- At least one operand is a column reference (else there is nothing
  to evaluate per row — could fold at parse time but not worth it
  for v1).
- For each pairwise comparison generated by the lowering, the two
  sides must be in the column-vs-constant shape supported by the
  embedded interp:
  - The condition is `<lhs_chain> >= <rhs_chain>` where one chain is a
    column / nested-CaseExpr-of-columns-and-constants and the other
    is a constant.
  - In practice this means the **last** operand can be a column or
    constant and all earlier operands must include at most one
    distinct column variable.  Reject other shapes cleanly.

  *Simplification for v1*: require at most one distinct column
  reference across all operands.  This trivially satisfies the
  embedded-condition shape because every comparison reduces to
  `<column-or-CaseExpr-built-from-it> CMP <constant-or-CaseExpr-of-
  constants>` — provably column-vs-constant after CaseExpr is treated
  as the producing column.  Multi-column GREATEST/LEAST is deferred.
- Column type is `Bigint` (matching the I.3 / I.4 register/embedded
  paths).

**Rejected shapes (clean errors):**

- Multi-column GREATEST/LEAST (`GREATEST(a, b)` with `a` and `b`
  distinct columns) — rejected with a message pointing at the
  register-based CASE follow-up.
- Float / decimal / string operands — rejected; same reason as I.3.
- GREATEST/LEAST with a CTE *aggregate* output as a column reference
  — rejected, mirroring the `BRANCH_MEM_OP_ARG_INLINE_TYPE`
  aggregate-output reject path I.4 already installed.
- GREATEST/LEAST nested under another GREATEST/LEAST or arithmetic
  is fine grammatically but the resulting `usage` graph must still
  satisfy the column-vs-constant invariant.

## What shipped (v1)

### RonSQL grammar

- `Keywords.hpp` — `kwdef(GREATEST)`, `kwdef(LEAST)`.
- `RonSQLParser.y` — new `T_GREATEST` / `T_LEAST` tokens; two
  `arith_expr` rules:

  ```
  | T_GREATEST T_LEFT arith_expr T_COMMA arith_expr T_RIGHT
      { $$ = context->lower_greatest_least($3, $5, /*is_greatest*/true); }
  | T_LEAST T_LEFT arith_expr T_COMMA arith_expr T_RIGHT
      { $$ = context->lower_greatest_least($3, $5, /*is_greatest*/false); }
  ```

  Three-or-more arguments are caught by bison as a syntax error.

### Lowering helper — `Context::lower_greatest_least`

`lower_greatest_least(a, b, is_greatest)` lives on the parser
context.  Validates that each operand is `Load` (column ref) or
`LoadConstantInteger`, that at least one is a column, and — when
both are columns — that they have the same `col_idx` (same column
referenced twice degenerates to just `a`; distinct columns rejected
with a v2 pointer).

The condition is normalised so the **column ends up on the LHS** of
the `<=` / `>=` comparison.  This is required because
`generate_embedded_condition` does `ndbrequire(col_side->op ==
T_IDENTIFIER)` on the atom's left operand, so a literal naive
lowering of `GREATEST(150, sums.k)` (which would put `150` on the
left) would crash.  After swap, the comparison op flips:

| call shape                | condition built                | THEN/ELSE  |
|---------------------------|--------------------------------|------------|
| `GREATEST(col, const)`    | `col >= const`                 | THEN=col, ELSE=const |
| `GREATEST(const, col)`    | `col <= const`                 | THEN=const, ELSE=col |
| `LEAST(col, const)`       | `col <= const`                 | THEN=col, ELSE=const |
| `LEAST(const, col)`       | `col >= const`                 | THEN=const, ELSE=col |

THEN/ELSE assignment preserves the original operand identity (so
`a` is always THEN, `b` is always ELSE), which keeps `CaseExpr`'s
SVM lowering byte-equivalent regardless of operand order.

### NULL-propagation rejection

MySQL's `GREATEST(NULL, …)` / `LEAST(NULL, …)` return `NULL`, but a
plain `CASE WHEN col CMP K THEN col ELSE K END` lowering returns the
non-null branch when `col` is `NULL`.  Adding NULL propagation in v1
would require a multi-arm CASE; instead, v1 **rejects nullable
column operands cleanly**.

The rejection is wired through a new `RonSQLPreparer::
m_greatest_least_conditions` array — `lower_greatest_least` pushes
the synthesized condition pointer into it at parse time, and
`generate_embedded_condition` calls a new
`is_greatest_least_condition(ce)` helper after column resolution.
If the resolved column is nullable, the preparer rejects with
"GREATEST/LEAST on nullable column operands is not yet supported".

### Embedded-condition inequality lift

`generate_embedded_condition` previously did `ndbrequire(atom->op ==
T_EQUALS || atom->op == T_NOT_EQUALS)`.  Replaced with a `require_prm`
that also accepts `T_LT / T_LE / T_GT / T_GE`, plus a full
direct/invert mapping for the `Interpreter::BinaryCondition` field:

```
direct: T_EQ→EQ T_NEQ→NE T_LT→GT T_LE→GE T_GT→LT T_GE→LE
invert: T_EQ→NE T_NEQ→EQ T_LT→LE T_LE→LT T_GT→GE T_GE→GT
```

The inversion in the inequality cases accounts for the embedded
`BRANCH_*_OP_ARG` family's quirk (kernel `Interpreter::LT/LE/GT/GE`
branch on the *opposite* relation between col and const — see
`DbtupExecQuery.cpp:7257-7260` and `CLAUDE.md` "NdbInterpretedCode:
Inverted Inequality Branches").  The existing `=` / `!=` mapping is
unchanged.

### AggregationAPICompiler accessors

Added to `AggregationAPICompiler_Expr`:

```cpp
bool isLoadConstantInt() const;
Uint32 getConstantIdx() const;
```

The constant value is then read via the already-public
`m_constants[idx].int_64`.

### Lowering helper — `RonSQLPreparer::lower_greatest_least`

New helper on the parser context (or a free function in the
preparer).  Walks the operand list left-associatively, building
nested `CaseExpr` nodes:

```cpp
Expr* lower_greatest_least(ExprList* operands, bool is_greatest) {
  AggregationAPICompiler* agg = get_agg();
  Expr* acc = operands->head;
  for (ExprNode* n = operands->next; n != NULL; n = n->next) {
    Expr* nxt = n->expr;
    // Build cond_expr `acc CMP nxt`
    ConditionalExpression* lhs = expr_to_condexpr(acc);
    ConditionalExpression* rhs = expr_to_condexpr(nxt);
    ConditionalExpression* cond;
    init_cond(cond, lhs, is_greatest ? T_GE : T_LE, rhs);
    acc = agg->CaseExpr(cond, acc, nxt);
  }
  return acc;
}
```

`expr_to_condexpr` is a new helper: given an `Expr*`, materialise a
matching `ConditionalExpression*`.  Cases:

- `Expr` is `Load(col_idx)` →
  `cond_expr{op = T_IDENTIFIER, col_idx = expr->idx}`.
- `Expr` is `LoadConstantInteger(constant_idx)` →
  `cond_expr{op = T_INT, constant_integer = m_constants[idx].int_64}`.
- Otherwise (arithmetic / nested CASE / etc.) — reject with a clean
  parser error pointing at the v1 shape restriction.  `CaseExpr`
  nodes themselves cannot be expressed as a `ConditionalExpression`
  under the current cond_expr grammar, but the v1 shape ensures
  they appear only as the *whole-expression* (output position),
  never as a comparison operand inside the lowering — the lowering
  always compares each operand to the running accumulator's
  *original-leaf* representation, not the CaseExpr.

  Concretely, the lowering above re-uses `acc` as the comparison
  LHS *and* the THEN arm.  For correctness, we want the comparison
  LHS to be the *unwrapped* accumulator (the CaseExpr's effective
  value), not a re-evaluation.  But per the v1 single-column
  invariant, every operand reduces to either the same column or a
  constant, so we can compare the *current operand* to the *next
  operand* directly — equivalent for sort order on `>=`/`<=` but
  much simpler:

  ```
  GREATEST(a, b, c)  ≡  CASE WHEN a >= b THEN
                          (CASE WHEN a >= c THEN a ELSE c END)
                        ELSE
                          (CASE WHEN b >= c THEN b ELSE c END)
                        END
  ```

  However, this alternative is exponential in size.  Stick with the
  left-associative chain and require the comparison LHS to be a
  raw operand at each step:

  ```
  GREATEST(a, b, c)  ≡  CASE WHEN <pair-max(a,b)> >= c THEN
                                <pair-max(a,b)>
                              ELSE c END
  ```

  …but `<pair-max(a,b)>` is a CaseExpr, which we can't currently
  inline-emit as a comparison side.  **Resolution**: lock the v1
  scope to **two operands only** for the first commit.  Three-
  argument and higher GREATEST/LEAST gets a follow-up commit once
  the register-based CASE codegen lands and CaseExpr can appear as
  a comparison operand.

### Revised v1 scope (after the lowering snag)

**v1 ships GREATEST(x, y) / LEAST(x, y) — exactly two operands.**

- One operand is a column reference; the other is an integer
  constant (or both are columns, but columns must reduce to the
  same `col_idx` — degenerate but cheap to allow).
- Lowering: single CaseExpr with the inequality condition.
- Three-or-more-argument forms: rejected with a clean error
  pointing at the follow-up.

This is the only scope the embedded-condition path can support
without register-based CASE work.  The grammar still admits
n-ary syntax; the lowering helper rejects n>2 cleanly.

### Lift the inequality CASE-condition restriction

`RonSQLPreparer.cpp:8093`:

```cpp
ndbrequire(atom->op == T_EQUALS || atom->op == T_NOT_EQUALS);
```

Replace with:

```cpp
require_prm(atom->op == T_EQUALS || atom->op == T_NOT_EQUALS ||
            atom->op == T_LT || atom->op == T_LE ||
            atom->op == T_GT || atom->op == T_GE,
            "CASE condition atom: only =, !=, <, <=, >, >= supported.");
```

Update the branch-direction logic at lines 8237-8246 to map the new
ops:

```cpp
Interpreter::BinaryCondition cond;
auto direct = [&](TokenKind op) -> Interpreter::BinaryCondition {
  switch (op) {
    case T_EQUALS:     return Interpreter::EQ;
    case T_NOT_EQUALS: return Interpreter::NE;
    case T_LT:         return Interpreter::LT;
    case T_LE:         return Interpreter::LE;
    case T_GT:         return Interpreter::GT;
    case T_GE:         return Interpreter::GE;
    default: ndbabort();
  }
};
auto invert = [&](TokenKind op) -> Interpreter::BinaryCondition {
  switch (op) {
    case T_EQUALS:     return Interpreter::NE;
    case T_NOT_EQUALS: return Interpreter::EQ;
    case T_LT:         return Interpreter::GE;
    case T_LE:         return Interpreter::GT;
    case T_GT:         return Interpreter::LE;
    case T_GE:         return Interpreter::LT;
    default: ndbabort();
  }
};
cond = is_and ? invert(atom->op) : direct(atom->op);
```

(NB: the **NDB interpreter inverted-branch** quirk noted in
`storage/ndb/claude_files/pushdown_join_aggregation/CLAUDE.md` is for
the **register**-based `branch_col_*` instructions.  The embedded
`BRANCH_ATTR_OP_ARG` / `BRANCH_MEM_OP_ARG` family does **not** invert —
verify by reading `interpreterNextLab`'s `BRANCH_ATTR_OP_ARG` case and
the `branchAttrXX` helper.  If it does invert, swap `direct`/`invert`.)

## Cleanly-rejected shapes (deferred to I.5 v2 / v3 / v4)

- GREATEST/LEAST with three or more arguments — needs CaseExpr-as-
  comparison-side support in `generate_embedded_condition`, which in
  turn needs the register-based CASE codegen path.  → **I.5 v2**.
- GREATEST/LEAST over two distinct columns (`GREATEST(t.a, t.b)`) —
  needs register-based CASE codegen; matches Test 21's NDB-API shape.
  → **I.5 v2**.
- GREATEST/LEAST over float / decimal / string — needs the I.3-style
  encoding work; defer to the relevant per-type phase.  → **I.5 v3**
  if not absorbed by the I.6 string-MIN/MAX work.
- GREATEST/LEAST referencing CTE aggregate output — same defer as
  CASE-condition-on-CTE-aggregate (I.4 deferred).  → **I.5 v3** or
  bundled with the I.4 follow-up.
- GREATEST/LEAST with **nullable column operands** — MySQL returns
  NULL when any argument is NULL; the v1 single-CASE lowering would
  return the non-null branch instead.  Currently rejected at preparer
  time (after column resolution) with a clear message.  → **I.5 v4**.

## Follow-up phases

### I.5 v2 — n-ary GREATEST/LEAST + multi-column comparison

**Pre-requisite**: register-based CASE codegen path in RonSQL.  Today
`generate_embedded_condition` only supports column-vs-constant
comparisons via `BRANCH_ATTR_OP_ARG` / `BRANCH_MEM_OP_ARG` /
`BRANCH_MEM_OP_ARG_INLINE_TYPE`.  Register-based CASE means: load
each side into a register (`READ_ATTR_INTO_REG` /
`READ_LINKED_TO_MEM` + `READ_INT64_MEM_TO_REG`) and branch via
`BranchRegGe` / `BranchRegLe` / `BranchRegEq` etc., matching the
shape `testCteNdbApi.cpp` Test 21 emits at NDB-API level.  This is
the same codegen path that I.4 catalogued as deferred and that I.11
(cross-join of two scalar CTEs) and the Test-21 row-vs-row CASE
shape both need.

Once that lands:

1. **n>2 GREATEST/LEAST** lowers to a register-based comparison chain
   instead of nested `CaseExpr`.  Pseudocode:
   ```
   GREATEST(a, b, c, …):
     load a → r1
     for each subsequent operand x:
       load x → r2
       if r2 > r1: r1 := r2     // Mov r2 → r1
     emit final r1 as the agg input
   ```
   This is one Load per operand + (n-1) BranchRegLe/Mov pairs — much
   smaller than the exponential CaseExpr nesting.

2. **Multi-column GREATEST/LEAST** (`GREATEST(t.a, t.b)` with `a` and
   `b` distinct) is the same register chain; column-vs-column is no
   harder than column-vs-constant once both sides go through registers.

3. **Multi-column CASE conditions** (`WHEN sums.gross > sums.net …`)
   land for free — same Test-21 shape, same emit pattern.  This
   bundles I.5 v2 with the deferred Test-21 work and the
   register-cmp half of I.11.

Test plan extends I.5 v1's MTR file with three-argument and
distinct-column shapes; rejection tests 7-8 from v1 flip to positive.

### I.5 v3 — wider operand types

**Pre-requisite**: per-type encoding work in
`encode_constant` / `read_int64_to_reg_const` analogues.  Today the
embedded path is Bigint-only because `READ_INT64_MEM_TO_REG` and the
constant-encoding pipeline assume signed 64-bit.  Float / decimal /
string need:

- Float (Float32/Float64): a `READ_FLOAT_MEM_TO_REG` analogue or a
  bit-equivalent comparison via integer regs (signed-zero-aware).
  Bundle with the float-comparison work I.3 also defers.
- Decimal: routed through the same machinery as the I.6
  `cte_filter_minmax_strings_plan.md` decimal sub-phase.
- String / VARCHAR: charset-aware comparison; coupled with I.6 sub-
  phase F.2 (kernel agg over strings) and F.3 (RonSQL CTE filter on
  string MIN/MAX).  May be absorbed entirely into I.6 once that
  lands; if so, I.5 v3 collapses to a "GREATEST/LEAST works on the
  newly-supported types" smoke-test phase.

Also covers: GREATEST/LEAST with a CTE *aggregate* output as an
operand — same `BRANCH_MEM_OP_ARG_INLINE_TYPE` aggregate-output
work I.4 deferred.  Bundle with that follow-up if I.4's deferred
piece lands first.

### I.5 v4 — NULL propagation for nullable operands

**Goal**: lift the v1 "nullable column operand" rejection so
`GREATEST(nullable_col, K)` and friends return MySQL-correct
results — i.e. `NULL` when any operand is `NULL`, otherwise the
greatest/least non-null value.

**Why deferred from v1**: a single-arm `CASE WHEN col CMP K THEN
col ELSE K END` lowering returns `K` (the non-null branch) when
`col IS NULL`, contradicting MySQL semantics.  Adding null
propagation at v1 time would have required either a multi-arm
CASE encoding the IS-NULL test or a new aggregator-side
nullability marker — both meaningfully bigger than the v1
surface, and v1's user-visible reach (NOT NULL columns) is the
common case.

**Implementation options**:

1. **Multi-arm CASE encoding** (most local).  Lower
   `GREATEST(col, K)` to a two-WHEN CASE:
   ```
   CASE
     WHEN col IS NULL THEN NULL
     WHEN col >= K THEN col
     ELSE K
   END
   ```
   This requires:
   - Multi-WHEN-arm CASE in the AggregationAPICompiler IR
     (today CaseExpr supports a single WHEN).  The SVM
     instruction set + `programAggregator` + `programAggregator_join`
     would each gain a multi-arm dispatch.
   - `IS NULL` as an embedded-condition atom on a column.  The
     kernel `BRANCH_*_OP_ARG` family already encodes
     `Interpreter::NULL_CMP_*` semantics, but the RonSQL preparer
     doesn't emit `IS NULL` atoms in CASE conditions today.
   - A nullable result type from `CaseExpr` (so downstream
     aggregators handle `NULL` correctly when the THEN/ELSE
     arm propagates `NULL`).
   - Test coverage that mirrors v1 Tests 1-6 with one nullable
     column and a NULL-row in the dataset; assert RonSQL matches
     MySQL native.

2. **Register-based GREATEST/LEAST with explicit null mask**
   (bundled with v2).  If v2 lands first, GREATEST/LEAST emit
   moves to a register-based opcode chain — those opcodes can
   short-circuit on a NULL flag from `READ_LINKED_TO_MEM` /
   `READ_ATTR_INTO_REG` and propagate `NULL` natively without
   the multi-arm CASE detour.  In that world v4 collapses to a
   "drop the nullable-column rejection" change in
   `lower_greatest_least` plus the test additions.

**Sequencing**: prefer (2) — bundle v4 with v2 — because the
multi-arm CASE machinery in (1) doesn't have other consumers in
RonSQL today, while the register-based path in v2 also unlocks
n-ary, multi-column, and Test-21-style register CASE conditions.
If v2 stalls for unrelated reasons, fall back to (1).

**Test plan**: a fresh MTR file (or extension of
`ronsql_cte_greatest_least.test`) with a `NULL`-bearing fixture:

| Shape | Expected |
|-------|----------|
| `GREATEST(nullable_col, K)` over a row where `nullable_col IS NULL` | `NULL` |
| `GREATEST(nullable_col, K)` mixed NULL + non-NULL rows | per-row NULL or greatest |
| `LEAST(nullable_col, K)` mirror | mirror |
| `SUM(GREATEST(nullable_col, K))` aggregating a mixed-NULL CTE column | matches MySQL `SUM(GREATEST(...))` (NULL rows excluded) |

Once shipped, the v1 rejection check at
`is_greatest_least_condition(ce)` is removed and the
`m_greatest_least_conditions` array becomes obsolete.

## Risks

1. **Inverted-branch confusion.**  The NDB interpreter inverts
   `branch_col_<op>` for the register family; the embedded
   `BRANCH_ATTR_OP_ARG` / `BRANCH_MEM_OP_ARG` family may or may not.
   Verify by reading `interpreterNextLab` and the `branchAttrXX`
   helper before implementing the inequality lift.  Adjust
   `direct`/`invert` mappings to match.

2. **Existing CASE callers passing inequality ops by accident.**  The
   `ndbrequire` at line 8093 may have been masking a parser-side
   filter that prevents inequality CASE conditions from reaching the
   preparer at all.  Search for upstream rejections of inequality
   CASE conditions; if found, lift them too.

3. **CASE-condition raw-word size accounting.**  Lines 8125-8131
   compute `total_branch_words` from the existing column-vs-constant
   shape.  Inequality is the same encoding (only the cond field
   differs), so accounting is unchanged.  Confirm during
   implementation.

4. **Parse-time error messaging.**  GREATEST/LEAST with three or more
   arguments needs a clear "not yet supported" error rather than a
   crash.  Test 7 verifies this.
