RDRS Memory Changes

Everything rdrs2 needs so that an idle pod stops restarting, a loaded pod stops growing without bound, and a row or blob of any size can be returned. Four code changes, one chart change, full test coverage, implemented on 26.02 and merged to 26.10 with one extra commit for the write and delete paths that 26.02 does not have.

3. Change 4: a limit on operations per batch

This is listed before the buffer design because it is independent of it and small.

Today nothing bounds the number of operations in a batch. The request body is capped at 1 MiB, which still allows about 17 000 minimal operations. BatchMaxSize, which reads like a cap, is the number of operations sent to NDB per execution loop at pkr_operation.cpp:1295, and the request is parsed and buffered in full before that loop runs. The Go server rejected batches above BatchMaxSize; rdrs2 lost that check.

4. Change 2: buffers

This section is the complete buffer design. It explains how buffers are used today, the proposal with one rule per subsection and an example each, how large a buffer must be and why that differs between 26.02 and 26.10, what it saves, and the code changes.

4.1 The problem in one example

A batch read of three rows, each 200 bytes, arrives at rdrs2. The server takes one request buffer and one response buffer from its pools. With the default configuration those are 2 MiB and 10 MiB. The batch uses about 1 KB of the request buffer and about 1 KB of the response buffer, holds both until the JSON has been sent, and returns them. For the lifetime of that HTTP request, 12 MiB of memory was reserved to carry 2 KB of data.

With 64 worker threads, 64 such HTTP requests in flight hold 768 MiB. The pool never frees buffers, so the peak stays allocated. On a 500 MiB pod this is the single largest reason traffic can push rdrs2 past its limit.

The buffers are this large for one reason: rdrs2 does not know in advance how big a row will be, and a row can contain a blob. So every operation is promised the whole configured size, and the configured size is set to the largest row anyone wants to return, 5 MiB by default.

The fix is to let a value that does not fit continue into the next buffer. Then the buffer only has to be large enough for the part of a row that is bounded, and blobs can be any size.

4.2 How buffers are used today

4.2.1 One operation

A single primary key read writes one operation request into a request buffer and gets one response back in a response buffer. Each response starts with a 36-byte header of nine 4-byte words. Every address inside a response is an offset from the start of that response, not from the start of the buffer. That is what lets many responses be packed into one buffer.

4.2.2 A batch

A batch takes one request buffer and one response buffer and packs the operation requests and the responses one after another. The controller keeps a heap-side array with one entry per operation that records where that operation's response starts. Nothing about the batch is written inside the buffers.

Operations are only started in the lower half of a buffer. Once the write position passes the halfway mark, the next operation goes into a fresh buffer from the pool, and the buffer that filled up records which operation opened the new one. That link is the chain. When the HTTP request finishes, release walks the chain from entry 0 and returns every buffer.

4.2.3 Why a response buffer is 10 MiB

When an operation starts, it is told how much it may write: the space left in its buffer, which the halfway rule keeps at 5 MiB or more. Every value is appended with a capacity check, and a blob is checked against the whole remaining space before the first byte is read. If a value does not fit, the batch fails with "Response buffer overflow". Nothing ever continues into another buffer.

So the configured RespBufferSize is the largest row rdrs2 can return, and the buffer is twice that so the promise survives packing. The number 5 MiB has no documented origin; it came from the first Go server in 2024 and was carried over. Request buffers follow the same rule with ReqBufferSize, 1 MiB doubled to 2 MiB.

Example, today

A batch of 2 000 reads of 200-byte rows needs about 800 KB of response space. It takes one response buffer, fills it to about 800 KB, and holds 10 MiB. A second batch with one 6 MiB blob fails, because 6 MiB is more than the 5 MiB promise, even though 10 MiB are allocated.

4.3 The proposal

Make buffers small. Keep each response's fixed header and fixed data part in one buffer, exactly as today. Let the blob part continue into the next buffer of the chain. Five rules, each with an example.

4.3.1 Rule 1: a response's fixed part stays in one buffer

An operation's header, column table and every bounded value are written into one buffer, its home. The reader resolves them from one base pointer, exactly as today. Nothing changes for integers, dates, decimals, strings, or binary columns.

Example

A feature store row with 40 columns and 30 KB of data has a fixed part of about 31 KB: 36 bytes of header, 644 bytes of column table, and the values as text with terminators. It lands in one buffer, whole.

4.3.2 Rule 2: a start reserve instead of the halfway mark

Before placing an operation, the writer checks how much of the current buffer is free. If less than the start reserve is free, the operation starts in a fresh buffer. The reserve is the largest fixed part any operation can have, a compile-time constant explained in section 4.4. With that, rule 1 (4.3.1) holds without doubling the buffer.

Example, 26.02 limits

Response buffer 512 KiB, reserve 188.6 KiB. Operations may start while less than 323.4 KiB are used. A batch of 200-byte rows starts about 800 operations in one buffer before moving to the next. A batch of 30 KB rows starts 11. The worst possible row, 188.6 KiB of fixed part, starts at 0 and a second one starts right after it at 188.6 KiB.

On the request side the writer knows more than the reserve: the encoder computes each operation's upper bound before writing (section 4.6, create_native_request), and the chain is handed that bound. An operation starts in a fresh buffer when less than the larger of the reserve and its own bound is free. This is what keeps a lowered StartReserveOverride harmless for requests, where there is no rule 5 retry: the pool test's 4 KiB reserve would otherwise let a third column-less operation (104 KiB of name reservation) be placed in the 48 KiB left behind two others and be refused with 400.

4.3.3 Rule 3: blob and text values spill

A blob is read from NDB in 32 KiB chunks and copied into the response, as today. When a chunk does not fit, the writer copies the part that fits, fills the buffer to its last byte, takes the next buffer from the pool, links it to the chain, and continues at offset 0. Continuation buffers have no header. The blob's column table entry is the same four words as today: its length, and an address. The address is an offset in the response's virtual stream: the home buffer's bytes first, then that response's continuation buffers in chain order. A first blob therefore has a home-buffer offset as today; a second blob in the same row, which starts inside a continuation buffer, has an offset past the home buffer's end. Values written before the blobs keep plain home offsets, so nothing changes for them.

TEXT columns take the same path with one difference. Today the Text branch stages the raw bytes in the response buffer and then converts them to utf8mb4, trims and JSON-escapes them into a new string before appending. The conversion works on whole characters, so the escaped output, not the raw bytes, is what spills. The implementation stages the raw TEXT in a buffer local to the Text branch, freed once the escaped copy is written (not in the request's arena, which would hold it until the request ends), runs the existing conversion and escaping, and writes the escaped result through the same write-with-spill primitive the Blob branch uses. The transient cost is the TEXT length in that staging buffer plus the three temporary copies the conversion already makes today, about five times the value for a few milliseconds; a streaming converter that avoids the staging copy is a later refinement.

The reader is handed the buffer chain and the operation index. It notices that address plus length runs past the end of the home buffer and builds a segment list: the tail of the home buffer, then whole buffers along the chain, until the length is consumed. Base64 encoding of a segmented value is a loop with one encoder state, and the bundled libbase64 already has that streaming API.

Example

Figure 3: a 10 MiB blob with 512 KiB buffers. 502 KiB fit behind the fixed part in buffer 1. Nineteen full buffers follow. The last 10 KiB land in buffer 21. The chain holds 21 buffers for the lifetime of the HTTP request and returns them together.

4.3.4 Rule 4: blobs are written last

Today the writer walks the read columns in request order and writes each value inline. If a blob sat in the middle of the row and spilled, every column after it would land in a continuation buffer and rule 1 (4.3.1) would break. Writing blobs first is worse: the fixed part would then follow the blob into whatever buffer it ended in, so the header would be in one buffer and the values in another.

Writing blobs last costs almost nothing. The column table stores an address per value, so physical order and table order are independent. The writer makes two passes over the read columns, bounded columns first, then blob and text columns. Table entries are filled by column index instead of by write count, so entry i still matches request column i and the reader is untouched.

4.3.5 Rule 5: a retry, so the start reserve is a heuristic and not a promise

The start reserve is computed from limits and code paths. If it is ever wrong, the result must still be right. So if an operation overflows its buffer and did not start at offset 0, the writer takes a fresh buffer and writes that operation again from offset 0, where it has the whole buffer. The row is already in the NDB record; this is a second formatting pass, not a second read. The writer records an overflow flag whenever a capacity check fails, so the retry decision does not depend on matching error text. Only an operation whose fixed part is larger than a whole buffer fails, with the same error as today. Since the buffer size is computed from the same limits, that can only mean the expansion constant is wrong, which is a code fix and not a configuration change.

Example

Suppose a future column type expands text eight times instead of six, and a row's fixed part is 240 KiB where the start reserve expected at most 188.6 KiB. The operation starts at offset 300 KiB of a 512 KiB buffer, overflows at 512 KiB, is retried at offset 0 of a fresh buffer, and succeeds. Packing lost one partly used buffer. Correctness lost nothing.

4.4 How large must a buffer be? The home buffer question

Rule 1 only works if the largest possible fixed part fits in a buffer with room to spare. This section computes that largest fixed part from the limits in the code, shows that it changes between 26.02 and 26.10, and makes the code derive it rather than carry a number.

4.4.1 What is in a fixed part, and how much it can grow

The response stores every value as text with a terminator. Numbers, dates and decimals expand a little. Character columns expand a lot, in two steps that both happen inside the response buffer: CHAR and VARCHAR values are converted to utf8mb4, then JSON-escaped. Binary values are copied raw; their base64 happens later, outside the pool.

So the worst row is one made entirely of control characters in single-byte VARCHAR columns, which expands six times. Nobody stores that, but the writer must not corrupt memory if someone does, and the retry in rule 5 (4.3.5) covers the case where even this estimate is wrong.

4.4.4 Derive every size from the limits at compile time

buffer_sizes.hpp computes the minimum buffer, the start reserve and the default buffer from the same kernel limits the data node uses. The code never contains an NDB-derived byte count. rdrs_const.h only points to it.

// buffer_sizes.hpp, from MAX_ROW_BYTES to the last static_assert, as at HEAD
/* The NDB row limit in bytes: every non-blob value of a row together. */
constexpr Uint32 MAX_ROW_BYTES = MAX_TUPLE_SIZE_IN_WORDS * 4;

/* A character column is converted to utf8mb4 (at most 3 bytes per source
 * byte for any single-byte charset) and then JSON-escaped (a control
 * character becomes \u00xx, 6 bytes). A byte that grew to 3 is non-ASCII
 * and is never escaped, so the two factors do not multiply: 6 is the
 * ceiling per source byte. */
constexpr Uint32 MAX_TEXT_EXPANSION = 6;

/* Upper bound accepted for Internal.OperationIDMaxSize, so the operation
 * id can be counted in the minimums below. */
constexpr Uint32 MAX_OPERATION_ID_RESERVE = 4096;

/* Space the request encoder reserves for column names when an operation
 * names none and every table column must be filled in later from the
 * dictionary: an offset array, then per column a type word, a length word,
 * the name and its terminator, 4-aligned. Matches what
 * PKRRequest::addReadColumns/addReadColumnName write. */
constexpr Uint32 REQ_COLNAME_RESERVE =
    ADDRESS_SIZE + ((MAX_ATTRIBUTES_IN_TABLE + 1) * ADDRESS_SIZE) +
    (MAX_ATTRIBUTES_IN_TABLE *
     (ADDRESS_SIZE + rdrs_align4(ADDRESS_SIZE + MAX_ATTR_NAME_SIZE + 1)));

/* Largest fixed part of one response: header, status message, operation
 * id, column table (count plus four words per column), every value as
 * escaped text, one terminator per value, alignment slack. */
constexpr Uint32 MIN_RESP_BUFFER =
    PK_RESP_HEADER_END + RS_STATUS_MSG_LEN +
    rdrs_align4(MAX_OPERATION_ID_RESERVE + 1) + ADDRESS_SIZE +
    (MAX_ATTRIBUTES_IN_TABLE * 4 * ADDRESS_SIZE) +
    (MAX_ROW_BYTES * MAX_TEXT_EXPANSION) + MAX_ATTRIBUTES_IN_TABLE +
    ADDRESS_SIZE;

/* Largest operation request: header, db and table names, the primary key
 * (count, per column two pointer words plus the name, all key bytes with a
 * length word each), the operation id, and the column-name reservation.
 * A key whose JSON text exceeds the NDB key limit is placed by
 * native_request_upper_bound instead. */
constexpr Uint32 MIN_REQ_BUFFER =
    PK_REQ_HEADER_END +
    (2 * rdrs_align4(ADDRESS_SIZE + MAX_ATTR_NAME_SIZE + 1)) + ADDRESS_SIZE +
    (MAX_ATTRIBUTES_IN_INDEX *
     ((3 * ADDRESS_SIZE) +
      rdrs_align4(ADDRESS_SIZE + MAX_ATTR_NAME_SIZE + 1))) +
    (MAX_KEY_SIZE_IN_WORDS * 4) + (MAX_ATTRIBUTES_IN_INDEX * 2 * ADDRESS_SIZE) +
    rdrs_align4(ADDRESS_SIZE + MAX_OPERATION_ID_RESERVE + 1) +
    REQ_COLNAME_RESERVE;

/* A new response (or operation request) may only start in a buffer that
 * still has this much room; otherwise it goes to a fresh buffer. */
constexpr Uint32 RESP_START_RESERVE = MIN_RESP_BUFFER;
constexpr Uint32 REQ_START_RESERVE = MIN_REQ_BUFFER;

/* The buffer sizes: the power of two above twice the minimum, so that
 * several responses pack into one buffer. Not settings; see the design
 * document for why a user-chosen value can only be worse. */
constexpr Uint32 DEFAULT_RESP_BUFFER = rdrs_next_pow2(2 * MIN_RESP_BUFFER);
constexpr Uint32 DEFAULT_REQ_BUFFER = rdrs_next_pow2(2 * MIN_REQ_BUFFER);

static_assert(DEFAULT_RESP_BUFFER >= 2 * MIN_RESP_BUFFER,
              "response buffer must hold two worst-case responses");
static_assert(DEFAULT_REQ_BUFFER >= 2 * MIN_REQ_BUFFER,
              "request buffer must hold two worst-case operation requests");
static_assert(DEFAULT_RESP_BUFFER % ADDRESS_SIZE == 0 &&
              DEFAULT_REQ_BUFFER % ADDRESS_SIZE == 0,
              "buffer sizes must be word aligned");
/* A limit increase that outgrows what one buffer can address fails the
 * build here rather than the first wide read after a merge. */
static_assert(MIN_RESP_BUFFER < (1U << 30) && MIN_REQ_BUFFER < (1U << 30),
              "a single buffer must stay addressable with 32-bit offsets");

Compared with the first draft of these formulas, the code adds the status message (RS_STATUS_MSG_LEN, 256 bytes) and the operation id, reserved at MAX_OPERATION_ID_RESERVE (4 096 bytes) because OperationIDMaxSize is a setting bounded by a PROBLEM check at that number, rounds every name to a word, and uses the corrected column-name reservation REQ_COLNAME_RESERVE from section 4.6. rdrs_next_pow2 rounds twice each minimum up to a power of two. On 26.02 the minimums evaluate to 193 104 B (188.6 KiB) and 122 180 B (119.3 KiB), and the buffers are 512 KiB and 256 KiB. MAX_ROW_BYTES replaces the old MAX_TUPLE_SIZE_IN_BYTES; the old MAX_TUPLE_SIZE_IN_BYTES_ENCODED is gone, since nothing sizes a whole-row base64 buffer any more.

Neither size is user configurable. RespBufferSize today is the only knob that sets the largest row rdrs2 can return, which is the one reason anyone touches it; with spilling that reason is gone, and every other value a user could choose is worse than the computed one. The same holds for ReqBufferSize: an operation request has no blobs and its maximum follows from the limits. So both keys are removed, the server uses DEFAULT_RESP_BUFFER and DEFAULT_REQ_BUFFER, and a new --print-limits flag prints the computed values (print-config is generated from the settings and cannot print a non-setting). The two old keys are removed; rdrs2 warns about and ignores a configuration key it does not know, so a file that still sets them starts with a warning naming each. A bug on 26.10-main, fixed by this change. Upstream 26.10-main defined MAX_TUPLE_SIZE_IN_BYTES as the literal 7501 × 4 = 30 004 while the kernel allows 72 000. The per-column checks at pkr_operation.cpp:908 and pk_base_operation.cpp:295 rejected any CHAR, VARCHAR or binary value above 30 004 bytes with ERROR_TOO_LARGE_ROWS, so a legal 32 614-byte VARCHAR failed in rdrs2. On RONDB-1144-26-10 those checks use MAX_ROW_BYTES, derived from MAX_TUPLE_SIZE_IN_WORDS (pkr_operation.cpp:957, pk_base_operation.cpp:313).

5. Change 3: pool ceiling, idle shrink, stats

Change 2 makes each buffer small. This change bounds how many there are and gives surplus back. All of it lives in buffer_manager.hpp plus one timer.

7.1 Pod-level worst case: 64 batches of 512 operations at once

The operation limit bounds one batch; the pod is bounded by the cap, not by the thread count. With 64 HTTP requests in flight, each a 512-operation batch, the buffers held, counted in whole buffers rather than bytes written, are:

64 batches of 512 operations, buffers held26.0226.10
typical, columns named, about 300 B per operation: two 256 KiB request buffers per batch on 26.02, one 2 MiB on 26.1032 MiB128 MiB
worst, no columns named: two operations share a request buffer, 256 buffers per batch4 GiB32 GiB
responses on top, if every read returns a widest row: two per response buffer+ 8 GiB+ 16 GiB

No pod holds the worst case and the design does not try to. The first batches take buffers up to the pool budget and the rest get 503 until buffers return: a 503 storm under abuse, no OOM kill, and full service for the typical case, which a 500 MiB pod holds many times over. On 26.10 the worst case is dominated by the 832 KiB column-name reservation per operation; that is the deferred refinement in section 10.1 and this is the scenario where it would pay off.

The idle figures after the change were confirmed on Linux on 2026-10-15: 43 MiB idle before any load (section 8.6).

8.6 Memory regression

One MTR test that is the reason for all of this, rdrs2-golang_memory_regression (Linux only, it reads /proc): a dedicated rdrs2 with MaxBuffers 256, PreAllocatedBuffers 8, BufferShrinkAfterS 30 and 8 threads, the cap a pod with a small memory limit would derive. Two workers POST widest-row batches for 60 seconds while the driver samples RssAnon of the process every 5 seconds. The batch size is not a fixed 400: an operation that names no columns reserves the room for every column name of the table, so the driver computes how many of them share one request buffer from rdrs_limits and sizes the batch so both workers together use half the cap above the preallocation (124 operations on 26.02). Two assertions: once warm, 10 seconds in, no sample exceeds the warm value by more than 10 % plus 32 MiB, which catches a leak; and the final sample is at most idle + MaxBuffers × (ReqBufferBytes + RespBufferBytes) + 64 MiB, which catches a pool that does not honour its cap. Today's code is killed by this load on a 500 MiB limit; the test pins that it stays under. The samples are written to var/log/rdrs2-golang_memory_regression.report.txt.

Measured on Linux, 2026-10-15 (AlmaLinux 8.10, glibc 2.28, 64 CPUs, release build, all 18 benchmarks run 10 s each against one server, then 75 s idle): the memory regression test passes (RssAnon between 40 and 70 MiB under the widest-row batch load, final 41 MiB, bound 266 MiB). Resident memory of rdrs2 at idle before any load is 43 MiB against 335 MiB for the old binary; the peak of the whole run is set by the 4 MiB-blob benchmark at 1 038 MiB against 1 542 MiB, and after the run the process settles at 418 MiB against 870 MiB. Pod sizing that follows from that with the default NumThreads 64 and BufferPoolSharePercent 50: request 1 GiB and limit 2 GiB where multi-megabyte blobs are read (about 2x headroom over the measured peak); request 512 MiB and limit 1 GiB without large blobs (non-blob peaks stayed at or below 520 MiB). Heavier parallel blob traffic than the benchmarks' default parallelism needs a higher limit.

8.7 Benchmarks

Eight Go benchmarks cover the chained paths: BenchmarkWidestRow, BenchmarkBlobHalfBuffer, BenchmarkBlobSpill, BenchmarkBlob4MiB and BenchmarkTextHalfBuffer in pkread; BenchmarkMaxOperations, BenchmarkWidestRows16 and BenchmarkBlobSpillInBatch in batchpkread. They send requests from b.RunParallel workers. A failed request fails the benchmark through testutils.ParallelTB, which reports with Errorf and ends only that worker, because FailNow from a worker goroutine would leave the benchmark waiting. The Linux A/B results and the memory measurements are summarised in sections 2 and 8.6.

9.2 Merge to 26.10

The intent is that no size and no test needs retyping, and that every place where 26.10 needs an edit fails to compile rather than silently keeping the old behaviour. What makes that true:

  • No size literal in the code. Every buffer size, reserve and minimum is a constexpr over MAX_ATTRIBUTES_IN_TABLE, MAX_TUPLE_SIZE_IN_WORDS, MAX_ATTR_NAME_SIZE, MAX_ATTRIBUTES_IN_INDEX and MAX_KEY_SIZE_IN_WORDS. On 26.10 they evaluate to 1 MiB response and 2 MiB request buffers without anyone typing them.
  • No size literal in the tests. The Go and MTR tests build their widest tables from rdrs_limits, so TestWidestRowFitsHomeBuffer runs 4 095 columns on 26.10 by itself.
  • The static_asserts fail the build if a future limit outgrows 32-bit buffer offsets (MIN_* below 230), so a limit increase is caught at compile time and not at the first wide read.
  • The stale MAX_TUPLE_SIZE_IN_BYTES on 26.10, which rejected legal rows above 30 004 bytes, is replaced by MAX_ROW_BYTES and disappears in the merge.

10. What is left

10.1 Deliberately out of scope for this round

  • Column-name reservation from the dictionary. Would cut the 26.10 request buffer from 2 MiB to about 512 KiB, but it moves the reservation from create_native_request to create_response and complicates the request encoder. Not needed for correctness on either branch. Deferred.
  • NumThreads derived from the CPU limit. Not doing it. The chart exposes NumThreads so it can be set per deployment; the default stays 64.
  • A cap on the JSON arena per HTTP request. The arena grows with the response and is released per request. It is bounded indirectly by MaxBuffers and MaxOperationsPerBatchRequest. Out of scope; too many changes already.

10.2 Correction: scan reads do not use the pool

An earlier draft listed scans as sharing the pool design. They do not. scan_read_ctrl.cpp builds its response in a RapidJSON string buffer reserved at ScanRespBufferSize, 256 KiB, per request (scan_read_ctrl.cpp:220) plus an arena, and never calls the buffer manager. Nothing in this document touches scans, and ScanRespBufferSize stays a setting.

10.3 Decided: the buffer cap follows the pod's memory

A fixed count is wrong for one of the two pod sizes we run: 256 pairs is generous on a 500 MiB pod and far too small for a 10 GiB pod serving a high workload. So the default cap is derived from the memory limit at startup, as change 3 describes: half of the pod for the pools, divided by the size of one pair. The pool grows on a bigger pod without anyone touching a setting, and MaxBuffers remains as an explicit override.

What this is not: it is not a runtime watchdog that reads memory usage on every request. That was part of the earlier broad design and stays in the backlog. One read of the limit at startup is about twenty lines, has no per-request cost, and gives the scaling that matters. If a pod is resized, rdrs2 restarts anyway.

Tests: BufferArrayManager.DeriveMaxBuffers, DetectMemoryLimitFromCgroupFiles and InitDerivesCapFromLimit, with injected limit values and both cgroup layouts. --print-limits prints the cap and the limit it came from (MaxBuffers, MemoryLimitBytes); no test checks those two fields. TestPoolExhaustedReturns503 sets MaxBuffers explicitly so it does not depend on the test host's memory.

10.4 Metric names

No existing metric is renamed, relabelled or removed. The customer's HPA reads rdrs_endpoints_response_status_count, and dashboards read the other four existing families, http_request_duration_seconds, rdrs_http_connection_count, rdrs_rondb_connection_state and rdrs_rondb_total_ndb_objects. All stay exactly as they are. The pool metrics shipped as new families only, under the names proposed here: one gauge family rdrs_buffer_pool with labels pool=request|response and state=in_use|free|peak|allocated; one counter family rdrs_buffer_pool_events with labels pool and event=rejected|retry|shrunk|allocated, where allocated counts mmap calls; and one gauge family rdrs_limits with label name=max_columns|max_row_bytes|req_buffer_bytes|resp_buffer_bytes|min_req_buffer_bytes|min_resp_buffer_bytes|max_operations_per_batch_request|max_buffers|memory_limit_bytes.
