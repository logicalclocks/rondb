RDRS Buffer Chaining

Why every rdrs2 request holds 12 MiB of buffer today, and how to make buffers small without limiting how large a row or a blob can be. The design must build and work on 26.02 and, after a merge, on 26.10 without anyone editing a size.

rdrs2 · storage/ndb/rest-server2/server/src · facts checked on upstream/26.02-main and upstream/26.10-main · 2026-10-14

1. The problem in one example

A batch read of three rows, each 200 bytes, arrives at rdrs2. The server takes one request buffer and one response buffer from its pools. With the default configuration those are 2 MiB and 10 MiB. The batch uses about 1 KB of the request buffer and about 1 KB of the response buffer, holds both until the JSON has been sent, and returns them. For the lifetime of that HTTP request, 12 MiB of memory was reserved to carry 2 KB of data.

With 64 worker threads, 64 such HTTP requests in flight hold 768 MiB. The pool never frees buffers, so the peak stays allocated. On a 500 MiB pod this is the single largest reason traffic can push rdrs2 past its limit.

The buffers are this large for one reason: rdrs2 does not know in advance how big a row will be, and a row can contain a blob. So every operation is promised the whole configured size, and the configured size is set to the largest row anyone wants to return, 5 MiB by default.

The fix is to let a value that does not fit continue into the next buffer. Then the buffer only has to be large enough for the part of a row that is bounded, and blobs can be any size.

2. How buffers are used today

2.1 One operation

A single primary key read writes one operation request into a request buffer and gets one response back in a response buffer. Each response starts with a 36-byte header of nine 4-byte words. Every address inside a response is an offset from the start of that response, not from the start of the buffer. That is what lets many responses be packed into one buffer.

2.2 A batch

A batch takes one request buffer and one response buffer and packs the operation requests and the responses one after another. The controller keeps a heap-side array with one entry per operation that records where that operation's response starts. Nothing about the batch is written inside the buffers.

Operations are only started in the lower half of a buffer. Once the write position passes the halfway mark, the next operation goes into a fresh buffer from the pool, and the buffer that filled up records which operation opened the new one. That link is the chain. When the HTTP request finishes, release walks the chain from entry 0 and returns every buffer.

2.3 Why a response buffer is 10 MiB

When an operation starts, it is told how much it may write: the space left in its buffer, which the halfway rule keeps at 5 MiB or more. Every value is appended with a capacity check, and a blob is checked against the whole remaining space before the first byte is read. If a value does not fit, the batch fails with "Response buffer overflow". Nothing ever continues into another buffer.

So before this change the configured RespBufferSize was the largest row rdrs2 can return, and the buffer is twice that so the promise survives packing. The number 5 MiB has no documented origin; it came from the first Go server in 2024 and was carried over. Request buffers follow the same rule with ReqBufferSize, 1 MiB doubled to 2 MiB.

Example, today

A batch of 2 000 reads of 200-byte rows needs about 800 KB of response space. It takes one response buffer, fills it to about 800 KB, and holds 10 MiB. A second batch with one 6 MiB blob fails, because 6 MiB is more than the 5 MiB promise, even though 10 MiB are allocated.

3. The proposal

Make buffers small. Keep each response's fixed header and fixed data part in one buffer, exactly as today. Let the blob part continue into the next buffer of the chain. Five rules, each with an example.

3.1 Rule 1: a response's fixed part stays in one buffer

An operation's header, column table and every bounded value are written into one buffer, its home. The reader resolves them from one base pointer, exactly as today. Nothing changes for integers, dates, decimals, strings, or binary columns.

Example

A feature store row with 40 columns and 30 KB of data has a fixed part of about 31 KB: 36 bytes of header, 644 bytes of column table, and the values as text with terminators. It lands in one buffer, whole.

3.2 Rule 2: a start reserve instead of the halfway mark

Before placing an operation, the writer checks how much of the current buffer is free. If less than the start reserve is free, the operation starts in a fresh buffer. The reserve is the largest fixed part any operation can have, a compile-time constant explained in section 4. With that, rule 1 holds without doubling the buffer.

Example, 26.02 limits

Response buffer 512 KiB, reserve 188.6 KiB. Operations may start while less than 323.4 KiB are used. A batch of 200-byte rows starts about 800 operations in one buffer before moving to the next. A batch of 30 KB rows starts 11. The worst possible row, 188.6 KiB of fixed part, starts at 0 and a second one starts right after it at 188.6 KiB.

On the request side the writer knows more than the reserve: the encoder computes each operation's upper bound before writing (section 6, create_native_request), and the chain is handed that bound. An operation starts in a fresh buffer when less than the larger of the reserve and its own bound is free. This is what keeps a lowered StartReserveOverride harmless for requests, where there is no rule 5 retry: the pool test's 4 KiB reserve would otherwise let a third column-less operation (104 KiB of name reservation) be placed in the 48 KiB left behind two others and be refused with 400.

3.3 Rule 3: blob and text values spill

A blob is read from NDB in 32 KiB chunks and copied into the response, as today. When a chunk does not fit, the writer copies the part that fits, fills the buffer to its last byte, takes the next buffer from the pool, links it to the chain, and continues at offset 0. Continuation buffers have no header. The blob's column table entry is the same four words as today: its length, and an address. The address is an offset in the response's virtual stream: the home buffer's bytes first, then that response's continuation buffers in chain order. A first blob therefore has a home-buffer offset as today; a second blob in the same row, which starts inside a continuation buffer, has an offset past the home buffer's end. Values written before the blobs keep plain home offsets, so nothing changes for them.

TEXT columns take the same path with one difference. Before this change the Text branch staged the raw bytes in the response buffer and then converts them to utf8mb4, trims and JSON-escapes them into a new string before appending. The conversion works on whole characters, so the escaped output, not the raw bytes, is what spills. The implementation stages the raw TEXT in a buffer local to the Text branch, freed once the escaped copy is written (not in the request's arena, which would hold it until the request ends), runs the existing conversion and escaping, and writes the escaped result through the same write-with-spill primitive the Blob branch uses. The transient cost is the TEXT length in that staging buffer plus the three temporary copies the conversion already makes today, about five times the value for a few milliseconds. Because that heap is outside the pool, a value whose escaped form (at least its raw length over the character set's minimum character width) could not fit even if the response pool held every buffer its cap allows is refused with 503 before any of it is allocated, the answer a blob of that size gets from the pool; the conversion buffer is allocated without throwing, so a failure there is an error status. A streaming converter that avoids the staging copy is a later refinement.

The reader is handed the buffer chain and the operation index. It notices that address plus length runs past the end of the home buffer and builds a segment list: the tail of the home buffer, then whole buffers along the chain, until the length is consumed. Base64 encoding of a segmented value is a loop with one encoder state, and the bundled libbase64 already has that streaming API.

Example

Figure 3: a 10 MiB blob with 512 KiB buffers. 502 KiB fit behind the fixed part in buffer 1. Nineteen full buffers follow. The last 10 KiB land in buffer 21. The chain holds 21 buffers for the lifetime of the HTTP request and returns them together.

3.4 Rule 4: blobs are written last

Today the writer walks the read columns in request order and writes each value inline. If a blob sat in the middle of the row and spilled, every column after it would land in a continuation buffer and rule 1 would break. Writing blobs first is worse: the fixed part would then follow the blob into whatever buffer it ended in, so the header would be in one buffer and the values in another.

Writing blobs last costs almost nothing. The column table stores an address per value, so physical order and table order are independent. The writer makes two passes over the read columns, bounded columns first, then blob and text columns. Table entries are filled by column index instead of by write count, so entry i still matches request column i and the reader is untouched.

3.5 Rule 5: a retry, so the start reserve is a heuristic and not a promise

The start reserve is computed from limits and code paths. If it is ever wrong, the result must still be right. So if an operation overflows its buffer and did not start at offset 0, the writer takes a fresh buffer and writes that operation again from offset 0, where it has the whole buffer. The row is already in the NDB record; this is a second formatting pass, not a second read. The writer records an overflow flag whenever a capacity check fails, so the retry decision does not depend on matching error text. Only an operation whose fixed part is larger than a whole buffer fails, with the same error as today. Since the buffer size is computed from the same limits, that can only mean the expansion constant is wrong, which is a code fix and not a configuration change.

Example

Suppose a future column type expands text eight times instead of six, and a row's fixed part is 240 KiB where the start reserve expected at most 188.6 KiB. The operation starts at offset 300 KiB of a 512 KiB buffer, overflows at 512 KiB, is retried at offset 0 of a fresh buffer, and succeeds. Packing lost one partly used buffer. Correctness lost nothing.

4. How large must a buffer be? The home buffer question

Rule 1 only works if the largest possible fixed part fits in a buffer with room to spare. This section computes that largest fixed part from the limits in the code, shows that it changes between 26.02 and 26.10, and makes the code derive it rather than carry a number.

4.1 What is in a fixed part, and how much it can grow

The response stores every value as text with a terminator. Numbers, dates and decimals expand a little. Character columns expand a lot, in two steps that both happen inside the response buffer: CHAR and VARCHAR values are converted to utf8mb4, then JSON-escaped. Binary values are copied raw; their base64 happens later, outside the pool.

character, then JSON-escaped≤ 6a control character 0x00 to 0x1f becomes \u00xx; a quote or backslash becomes 2 bytes (mystring.cpp:76)
character, both steps≤ 6a byte that converted to 3 is non-ASCII and is never escaped, so the factors do not multiply
integer, date, decimal≤ 21, 30, 69 per valuestd::to_string, MAX_DATE_STRING_REP_LENGTH, DECIMAL_MAX_STR_LEN_IN_BYTES
binary, varbinary, bit1raw copy

So the worst row is one made entirely of control characters in single-byte VARCHAR columns, which expands six times. Nobody stores that, but the writer must not corrupt memory if someone does, and the retry in rule 5 covers the case where even this estimate is wrong.

4.4 Derive every size from the limits at compile time

buffer_sizes.hpp computes the minimum buffer, the start reserve and the default buffer from the same kernel limits the data node uses. The code never contains an NDB-derived byte count. rdrs_const.h only points to it.

// buffer_sizes.hpp, from MAX_ROW_BYTES to the last static_assert, as at HEAD
/* The NDB row limit in bytes: every non-blob value of a row together. */
constexpr Uint32 MAX_ROW_BYTES = MAX_TUPLE_SIZE_IN_WORDS * 4;

/* A character column is converted to utf8mb4 (at most 3 bytes per source
 * byte for any single-byte charset) and then JSON-escaped (a control
 * character becomes \u00xx, 6 bytes). A byte that grew to 3 is non-ASCII
 * and is never escaped, so the two factors do not multiply: 6 is the
 * ceiling per source byte. */
constexpr Uint32 MAX_TEXT_EXPANSION = 6;

/* Upper bound accepted for Internal.OperationIDMaxSize, so the operation
 * id can be counted in the minimums below. */
constexpr Uint32 MAX_OPERATION_ID_RESERVE = 4096;

/* Space the request encoder reserves for column names when an operation
 * names none and every table column must be filled in later from the
 * dictionary: an offset array, then per column a type word, a length word,
 * the name and its terminator, 4-aligned. Matches what
 * PKRRequest::addReadColumns/addReadColumnName write. */
constexpr Uint32 REQ_COLNAME_RESERVE =
    ADDRESS_SIZE + ((MAX_ATTRIBUTES_IN_TABLE + 1) * ADDRESS_SIZE) +
    (MAX_ATTRIBUTES_IN_TABLE *
     (ADDRESS_SIZE + rdrs_align4(ADDRESS_SIZE + MAX_ATTR_NAME_SIZE + 1)));

/* Largest fixed part of one response: header, status message, operation
 * id, column table (count plus four words per column), every value as
 * escaped text, one terminator per value, alignment slack. */
constexpr Uint32 MIN_RESP_BUFFER =
    PK_RESP_HEADER_END + RS_STATUS_MSG_LEN +
    rdrs_align4(MAX_OPERATION_ID_RESERVE + 1) + ADDRESS_SIZE +
    (MAX_ATTRIBUTES_IN_TABLE * 4 * ADDRESS_SIZE) +
    (MAX_ROW_BYTES * MAX_TEXT_EXPANSION) + MAX_ATTRIBUTES_IN_TABLE +
    ADDRESS_SIZE;

/* Largest operation request: header, db and table names, the primary key
 * (count, per column two pointer words plus the name, all key bytes with a
 * length word each), the operation id, and the column-name reservation.
 * A key whose JSON text exceeds the NDB key limit is placed by
 * native_request_upper_bound instead. */
constexpr Uint32 MIN_REQ_BUFFER =
    PK_REQ_HEADER_END +
    (2 * rdrs_align4(ADDRESS_SIZE + MAX_ATTR_NAME_SIZE + 1)) + ADDRESS_SIZE +
    (MAX_ATTRIBUTES_IN_INDEX *
     ((3 * ADDRESS_SIZE) +
      rdrs_align4(ADDRESS_SIZE + MAX_ATTR_NAME_SIZE + 1))) +
    (MAX_KEY_SIZE_IN_WORDS * 4) + (MAX_ATTRIBUTES_IN_INDEX * 2 * ADDRESS_SIZE) +
    rdrs_align4(ADDRESS_SIZE + MAX_OPERATION_ID_RESERVE + 1) +
    REQ_COLNAME_RESERVE;

/* A new response (or operation request) may only start in a buffer that
 * still has this much room; otherwise it goes to a fresh buffer. */
constexpr Uint32 RESP_START_RESERVE = MIN_RESP_BUFFER;
constexpr Uint32 REQ_START_RESERVE = MIN_REQ_BUFFER;

/* The buffer sizes: the power of two above twice the minimum, so that
 * several responses pack into one buffer. Not settings; see the design
 * document for why a user-chosen value can only be worse. */
constexpr Uint32 DEFAULT_RESP_BUFFER = rdrs_next_pow2(2 * MIN_RESP_BUFFER);
constexpr Uint32 DEFAULT_REQ_BUFFER = rdrs_next_pow2(2 * MIN_REQ_BUFFER);

static_assert(DEFAULT_RESP_BUFFER >= 2 * MIN_RESP_BUFFER,
              "response buffer must hold two worst-case responses");
static_assert(DEFAULT_REQ_BUFFER >= 2 * MIN_REQ_BUFFER,
              "request buffer must hold two worst-case operation requests");
static_assert(DEFAULT_RESP_BUFFER % ADDRESS_SIZE == 0 &&
              DEFAULT_REQ_BUFFER % ADDRESS_SIZE == 0,
              "buffer sizes must be word aligned");
/* A limit increase that outgrows what one buffer can address fails the
 * build here rather than the first wide read after a merge. */
static_assert(MIN_RESP_BUFFER < (1U << 30) && MIN_REQ_BUFFER < (1U << 30),
              "a single buffer must stay addressable with 32-bit offsets");

Compared with the first draft of these formulas, the code adds the status message (RS_STATUS_MSG_LEN, 256 bytes) and the operation id, reserved at MAX_OPERATION_ID_RESERVE (4 096 bytes) because OperationIDMaxSize is a setting bounded by a PROBLEM check at that number, rounds every name to a word, and uses the corrected column-name reservation REQ_COLNAME_RESERVE from section 6. rdrs_next_pow2 rounds twice each minimum up to a power of two. On 26.02 the minimums evaluate to 193 104 B (188.6 KiB) and 122 180 B (119.3 KiB), and the buffers are 512 KiB and 256 KiB. MAX_ROW_BYTES replaces the old MAX_TUPLE_SIZE_IN_BYTES; the old MAX_TUPLE_SIZE_IN_BYTES_ENCODED is gone, since nothing sizes a whole-row base64 buffer any more.

Neither size is user configurable. RespBufferSize was, before this change, the only knob that set the largest row rdrs2 can return, which is the one reason anyone touches it; with spilling that reason is gone, and every other value a user could choose is worse than the computed one. The same holds for ReqBufferSize: an operation request has no blobs and its maximum follows from the limits. So the server uses DEFAULT_RESP_BUFFER and DEFAULT_REQ_BUFFER, and a new --print-limits flag prints the computed values. Both old keys are removed; rdrs2 warns about and ignores a configuration key it does not know, so a file that still sets them starts with a warning naming each. The request side is what makes 26.10 expensive, and only because 192 bytes are reserved per column name before the dictionary is consulted. Sizing that column-name reservation from the real column count and name lengths, which create_response already knows, would bring the request minimum on 26.10 back under 512 KiB. That is a later refinement and does not change the chaining design.

A bug on 26.10-main, fixed by this change. Upstream 26.10-main defined MAX_TUPLE_SIZE_IN_BYTES as the literal 7501 × 4 = 30 004 while the kernel allows 72 000. The per-column checks at pkr_operation.cpp:908 and pk_base_operation.cpp:295, both in the BINARY/VARBINARY branch, reject a binary value above 30 004 bytes with ERROR_TOO_LARGE_ROWS, although the kernel accepts VARBINARY values up to 32 614 bytes since 451b0bddcea (in-memory var parts of up to 8158 words). CHAR and VARCHAR are not affected: they go through Append_char, which sizes its conversion buffer from the value, and the JSON stage already allocates base64 space for values of 30 004 bytes and more. Checked against upstream 26.10-main at 9e3195b9621, where the literal is still in place. On RONDB-1144-26-10 those checks use MAX_ROW_BYTES, derived from MAX_TUPLE_SIZE_IN_WORDS (pkr_operation.cpp:957, pk_base_operation.cpp:313).

Two things chaining alone does not change. The JSON for a blob is built outside the pool while its buffers are still held, so a 10 MiB blob still costs about 13.4 MiB of JSON while the response is being written; chaining fixes the pool side only. Review found that this made the pool cap an incomplete bound: at 512 MiB, a batch of 80 reads of 2 MiB blobs fitted the cap (321 of 341 buffers) while its buffers plus two JSON copies (the arena buffer and the response string) came to about 586 MiB. The fix has two parts. The JSON is written once, straight into the response body; the feature store reserves its body once and frees each feature as it is appended. And the cap charges each buffer pair 7/3 of its size: values are copied into the JSON as they are (text is stored escaped, numbers as text) except binary, which base64 grows by 4/3, and the column names come from the request buffer, so a pair's JSON is at most 4/3 of the pair and buffers plus JSON at most 7/3. Everything the cap admits then fits in BufferPoolSharePercent of the limit whatever the value sizes are, and the 80-blob batch is answered 503 by the pool instead of being OOM-killed. Two gaps remain, by decision. First, once the handler hands its response to Drogon and returns its buffers, the body is out of the pool's sight: Drogon 1.9.7 copies header and body into a send buffer (HttpResponseImpl::renderToBuffer), trantor keeps whatever the socket has not taken in the connection's write buffer, and pipelined responses wait until the earlier ones on their connection are sent. Sustained pipelined or slow-client traffic of large blobs can therefore queue more than the share leaves. Bounding it would mean streaming the JSON out of the pool buffers until the socket has taken it; that is not planned. Heavy blob workloads run with more memory instead: the chart defaults to a 2 GiB limit and request, and rdrs2 warns at startup below 2 GiB. Second, the feature store's Avro-decoded complex features can grow beyond 4/3 when decoded to JSON. And the pool still needs a ceiling and an idle shrink, which are separate changes; chaining makes each request and response pair under that ceiling 16 times cheaper on 26.02 and 4 times cheaper on 26.10.

A third limit sits on the value itself. Chaining removed the old implicit bound (a value had to fit in what was left of one response buffer), so Internal.MaxBlobTextValueBytes, default 2 MiB of stored bytes, bounds what a read may return for one BLOB or TEXT column; 0 removes it. The check uses the length NDB reports once the operation has executed, before any of the value is read, so an oversized value costs neither pool buffers nor heap. It fails only that operation, with 413 naming the column: a single read answers 413, a batch sub-response carries 413 while the other operations return their rows, and the feature store answers 413 with error code 22, "Feature value too large." The response pool cap still bounds values when the limit is 0.

Unchanged

The header layout, the column table layout, the per-operation address scheme, the JSON output, the pool's two mutexes, the request-side encoding, and the write path of every bounded column. Merge checklist for 26.10

  • No limit-derived size typed as a literal in the new code. The one literal, MAX_OPERATION_ID_RESERVE = 4096, is a bound on the OperationIDMaxSize setting.
  • Every size comes from MAX_ATTRIBUTES_IN_TABLE, MAX_TUPLE_SIZE_IN_WORDS, MAX_ATTR_NAME_SIZE, MAX_ATTRIBUTES_IN_INDEX and MAX_KEY_SIZE_IN_WORDS.
  • The existing arrays already scale: pk_bitmap_words[MAX_ATTRIBUTES_IN_TABLE / 32] and REQ_COLNAME_RESERVE in buffer_sizes.hpp, used at encoding.cpp:138 and :244, follow the macros.
  • The buffer sizes are the constexpr values and not settings, so --print-limits shows the right number on each branch and no config file can carry a stale one across the merge.
  • static_asserts that each default is at least twice its minimum, that both sizes are word aligned, and that MIN_RESP_BUFFER and MIN_REQ_BUFFER stay below 230 so 32-bit offsets still work; a future limit increase fails the build instead of the first wide read.
