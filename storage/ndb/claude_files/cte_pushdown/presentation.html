Why Naive JOINs Don't Work

Problem 1: Cross Product

SELECT f.*, COUNT(p.id), COUNT(v.id)
FROM user_profile f
JOIN purchases p ON p.user_id = f.user_id
JOIN page_views v ON v.user_id = f.user_id
GROUP BY f.user_id

10 purchases × 20 views = 200 rows per user

Aggregates are inflated and wrong

Problem 2: Massive GROUP BY

SELECT f.*, d.*, h.*, COUNT(p.id)
FROM user_profile f
JOIN user_embeddings d ON ...
JOIN user_history h ON ...
JOIN purchases p ON ...
GROUP BY f.user_id, f.age, f.gender,
  f.country, ... -- 258 columns!

Impractical and slow

The Solution: SQL CTEs

WITH
  purchase_agg AS (
    SELECT user_id,
           COUNT(*) AS n_purchases,
           SUM(amount) AS total_spend
    FROM purchases
    WHERE ts > '2026-01-01'
    GROUP BY user_id
  ),
  view_agg AS (
    SELECT user_id,
           COUNT(*) AS n_views,
           SUM(duration) AS total_time
    FROM page_views
    WHERE ts > '2026-01-01'
    GROUP BY user_id
  )
-- Main query: no GROUP BY needed
SELECT
  f.*, e.*, h.*,              -- 258 features
  p.n_purchases,              -- real-time
  p.total_spend,
  v.n_views, v.total_time
FROM user_profile f
JOIN user_embeddings e
  ON e.user_id = f.user_id     -- PK-PK
JOIN user_history h
  ON h.user_id = f.user_id     -- PK-PK
LEFT JOIN purchase_agg p
  ON p.user_id = f.user_id     -- 1:1
LEFT JOIN view_agg v
  ON v.user_id = f.user_id     -- 1:1
WHERE f.user_id IN (1001, 1002)

✓ No GROUP BY on 258 columns

Functional dependency: user_id is PK of all feature tables. No GROUP BY needed in the main query.

✓ No cross product

Each CTE aggregates independently. Main query joins only 1:1 results. Correct aggregates guaranteed.

Today: Subquery Aggregation (Implemented)

RONSQL
SELECT
  f.user_id, f.age, f.country,
  e.bert_enc_0, e.item2vec_0,
  h.total_orders, h.churn_score,

  -- Real-time aggregates (subqueries):
  (SELECT COUNT(*)
   FROM purchases p
   WHERE p.user_id = f.user_id
     AND p.ts > '2026-03-01'
  ) AS n_purchases_30d,

  (SELECT SUM(p.amount)
   FROM purchases p
   WHERE p.user_id = f.user_id
     AND p.ts > '2026-03-01'
  ) AS total_spend_30d,

  (SELECT COUNT(*)
   FROM page_views v
   WHERE v.user_id = f.user_id
     AND v.ts > '2026-03-01'
  ) AS n_views_30d

FROM user_profile f
JOIN user_embeddings e
  ON e.user_id = f.user_id
JOIN user_history h
  ON h.user_id = f.user_id
WHERE f.user_id = 1001;

✓ Fully pushed to NDB today

RonSQL decorrelates each subquery into a LEFT OUTER JOIN with multi-leaf pushdown aggregation. All 3 subqueries execute as separate aggregate leaves in one pushed query tree.

✓ Subquery merging

The two purchases subqueries (COUNT, SUM) are merged into a single table scan with multiple aggregate accumulators — one scan, two results.

Limitations

Hidden GROUP BY: all non-aggregate SELECT columns (f.*, e.*, h.*) are implicitly part of the GROUP BY. With 258 feature columns, this forces grouping on all of them internally.

Single-table only: each subquery scans one table. CTEs will enable joins inside aggregation and explicit GROUP BY with multiple output columns.

Full Feature Store Query: CTE with Joins

Fraud detection: enrich purchases with merchant risk scores before aggregation:

WITH
  risky_purchases AS (
    SELECT t.user_id,
      COUNT(*) AS n_risky_txns,
      SUM(t.amount) AS risky_spend,
      MAX(m.risk_score * t.amount)
        AS max_risk_exposure
    FROM transactions t
    JOIN merchants m              -- join in CTE
      ON m.merchant_id = t.merchant_id
    WHERE t.ts > '2026-03-27'
      AND m.risk_score > 0.7
    GROUP BY t.user_id
  ),
  login_patterns AS (
    SELECT user_id,
      COUNT(*) AS n_logins_1h,
      COUNT(DISTINCT ip_address)
        AS n_distinct_ips
    FROM login_events
    WHERE ts > '2026-03-28 12:00'
    GROUP BY user_id
  )
-- Main query: Feature View
SELECT
  f.age, f.country,           -- profile
  f.account_age_days,
  e.bert_enc_0, e.bert_enc_1, -- embeddings
  e.item2vec_0,
  h.total_orders,             -- history
  h.avg_spend, h.churn_score,
  r.n_risky_txns,             -- CTE agg
  r.risky_spend,
  r.max_risk_exposure,
  l.n_logins_1h,              -- CTE agg
  l.n_distinct_ips
FROM user_profile f
JOIN user_embeddings e
  ON e.user_id = f.user_id    -- PK
JOIN user_history h
  ON h.user_id = f.user_id    -- PK
LEFT JOIN risky_purchases r
  ON r.user_id = f.user_id    -- 1:1
LEFT JOIN login_patterns l
  ON l.user_id = f.user_id    -- 1:1
WHERE f.user_id IN (5001, 5002)

How the CTE Join Gets Pushed

CTE "risky_purchases" Sub-Tree: (own Request, reuses full join+agg infra) SCAN transactions WHERE ts > '2026-03-27' | +-- PK LOOKUP merchants filter: risk_score > 0.7 | +-- JoinAggInterpreter GROUP BY user_id COUNT(*), SUM(amount), MAX(risk_score * amount) | v [Hash Table] key: user_id vals: n_risky_txns, risky_spend, max_risk_exposure
Main Query Tree: SCAN user_profile WHERE user_id IN (5001, 5002, 5003) | +-- PK LOOKUP user_embeddings | +-- PK LOOKUP user_history | +-- CTE_LOOKUP risky_purchases | hash table lookup by user_id | +-- CTE_LOOKUP login_patterns hash table lookup by user_id

The CTE join (transactions JOIN merchants) reuses 100% of existing pushed join infrastructure. Only the result routing changes: hash table instead of API.
