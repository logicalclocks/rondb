## 1. Goal

All RonSQL development is to be tested against the SQL that the
Hopsworks Feature Store actually generates for online serving. The
Hopsworks query builder produces SQL text (RonSQL templates plus their
MySQL twins). We need, in this tree:

1. A **RonSQL query builder** that reproduces the Hopsworks
   `PreparedStatementBuilder` output for a declarative feature-view
   spec (feature groups, joins, aggregations, collect, filters,
   single/batch).
2. A **test framework** with a set of Feature Group tables, a fair
   amount of deterministic data, and a driver that executes the
   generated SQL on **both MySQL and RonSQL** and compares.
3. **Prepared (named) benchmark queries** generated by the framework,
   runnable against RonSQL and MySQL with latency/phase reporting.
4. A **random query generator** that generates feature-view specs (and,
   beyond that, RonSQL-envelope queries) on the fly, executes them on
   both engines and verifies them, with reproducible seeds and a
   findings ledger.

The user runs all builds and tests; every phase below ends with the
exact commands to run.

## 2. Survey findings (P0)

### 2.1 Hopsworks side — what the builder emits

`PreparedStatementBuilder` does **not** derive RonSQL from the Calcite
tree. It hand-assembles three template families with `StringBuilder`
from the metadata objects, and every RonSQL template is gated: when a
gate fails the DTO simply lacks `queryRonsql` / `snowflakeTemplates`
and the client falls back to the MySQL statement or RDRS `/scan`.

| Emitter | Method (line) | Shape |
|---|---|---|
| Collect (last-N rows per entity, single entity only) | `buildRonsqlCollectTemplate` (:780) | `WITH t AS (SELECT cols FROM `fg_v` WHERE `pk` = ? [AND filters] ORDER BY `order_col` DESC LIMIT N) SELECT cols FROM t;` |
| Pushdown aggregation | `applyRonsqlAggregate` (:484), outputs from `aggregateOutputs` (:442) | `SELECT FN(`f`) AS `f_fn`, ... FROM `fg_v` WHERE `pk` = ? [AND filters] [AND `event_time` >= ?];` and batch `SELECT `k`, ... WHERE `k` IN (?) ... GROUP BY `k`;` |
| Snowflake nested subtree | `buildRonsqlSnowflakeTemplates` (:966) → `buildSnowflakeStatement` (:1067) | `WITH `b` AS (SELECT hopcols[, rootpk], COUNT(*) AS `hw_cnt` FROM `root_v` WHERE pk = ? / pk IN (?) GROUP BY hopcols[, rootpk]) SELECT `jN`.`col` AS `prefixcol`, ... [, `b`.`pk` AS `pk`] FROM `b` JOIN `child_v` AS `jN` ON `jN`.`right` = `b`.`left` [JOIN deeper ...];` |

Key facts the framework must reproduce (full detail in
`shape_catalog.md`):

- Table reference is the bare backticked `<fg_name>_<version>`; the
  database travels beside the statement (`ronsqlDatabase` on the DTO).
  MySQL twins are qualified `` `db`.`table` ``.
- `?` is a client-side convention: RonSQL has no parameter binding; the
  client substitutes typed literals. Batch `IN (?)` becomes a literal
  list. The trailing window `?` becomes a TIMESTAMP literal computed
  client-side as `now - aggregateWindow` (RonSQL has no `NOW()`).
- GREATEST/LEAST keys are folded as `MAX(GREATEST(a, b)) AS a_b_greatest`
  (row-wise scalar wrapped in an explicit aggregate).
- Filters are re-rendered from the persisted filter tree: AND-only
  (any OR → no filters, statement rejected for collect/aggregate),
  operators `= <> > >= < <= LIKE`, numeric literals validated against
  `-?\d+(\.\d+)?`, strings `''`-doubled with control chars and
  backslashes refused, booleans refused, feature-vs-feature refused.
- Snowflake CTE always carries a dummy `COUNT(*) AS hw_cnt` so the CTE
  is a grouped aggregation; GROUP BY over the hop columns yields the
  distinct hop values. Aliases: `b` for the subtree root CTE, `j<idx>`
  for nested nodes. Output aliases carry the feature-view prefix.
- Join semantics are modelled by **how many templates** are emitted:
  all-INNER subtree → one combined statement; all-LEFT subtree → one
  chain template per nested join (a deep miss loses only that node);
  mixed INNER/LEFT → no templates.
- Gates (statement suppressed): batch with composite entity key
  (tuple IN unverified); a hop not covering the child's **full**
  primary key (partial-key join scans 1:N); join type not INNER/LEFT;
  mixed subtree; cross-featurestore FG; conditionless join; snowflake +
  filters on collect/aggregate FGs (throws).
- Definition-time gates (`QueryController.java:323-530`): functions
  `count sum min max avg` per feature, `greatest least` over 2+
  **integer** features; SUM/AVG numeric only; MIN/MAX not over complex
  types; windowed aggregation needs a **TIMESTAMP** event_time that is
  the **last primary-key column** (online history layout: PK =
  (entity..., event_time)); window ≤ 100 years and ≤ TTL; no duplicate
  output names.
- Online table DDL (`OnlineFeaturegroupController.buildCreateStatement`
  :410): `CREATE TABLE IF NOT EXISTS `db`.`fg_v`(cols..., PRIMARY KEY
  (`k1`,`k2`) [USING HASH]) ENGINE=ndbcluster COMMENT='...' [TABLESPACE]`;
  type mapping: INT/TINYINT/SMALLINT/BIGINT/FLOAT/DOUBLE/DECIMAL/DATE/
  TIMESTAMP pass through, `boolean` → `tinyint`, `string` →
  `VARCHAR(100)`, everything else → `VARBINARY(100)`; the event_time
  column gets `STORAGE MEMORY`; optional `KEY ttl_index(event_time)` and
  `KEY idx_<cols>(...)` secondary indexes. Default PK index type is
  hash + ordered (no `USING HASH`) unless the user asks for HASH.

### 2.3 Gaps this framework fills

1. No Hopsworks-shaped schema or data (naming `<fg>_<v>`, VARCHAR(100)
   string keys, TIMESTAMP event_time as last PK column, tinyint
   booleans, hash-only vs hash+ordered PKs, secondary `idx_*` indexes).
2. No executor for `?`-templates (typed literal substitution, IN-list
   expansion, window literal), and no **vector-level** oracle
   (templates + client fold vs MySQL serving statement + client fold).
3. No random query generator or fuzzer anywhere in the tree.
4. No benchmark queries with the exact Hopsworks shapes (the `fs_*`
   registry entries are TPC-H based and were written before the
   builder existed).
5. **Risk R1 (found during P0):** RonSQL here accepts a non-aggregate
   CTE body only as a *single-row key lookup* (all PK columns bound by
   equality, `RonSQLPreparer.cpp:1905-1925`). The Hopsworks collect
   template binds only the entity part of a `(entity, event_time)` key
   and adds ORDER BY / LIMIT, so it is very likely **rejected** by
   `analyze_ctes()`. Meanwhile the *direct* single-table shape
   `SELECT cols FROM fg WHERE entity = ? ORDER BY ts DESC LIMIT N` is
   supported since the ORDER BY / LIMIT plan Phases 3-4b (2026-08-21,
   `ronsql_orderby_limit_plan.md`). The Hopsworks comment "RonSQL
   rejects non-aggregate projections in a plain select" is stale for
   this tree. E1 must verify this first; the outcome decides whether
   the engine gains the CTE-wrapped shape or Hopsworks changes its
   template (or both).

## 3. Architecture and decisions

### D1 — Implementation language: Go, inside `tools/rondb-cli`

New package `tools/rondb-cli/internal/fsq/` ("feature-store query")
plus shell commands `.fs_load`, `.fs_verify`, `.fs_bench` (via the
existing registry), `.fs_fuzz`. Rationale: rondb-cli already has the
REST and MySQL clients, the benchmark runners with latency/phase
collection, a multi-threaded loader (`tpch.go`), `{KEY}` substitution,
and is built by CMake into `runtime_output_directory/rondb` and
exported to MTR as `$RONDB_CLI`. Go's concurrency suits both bulk
loading and benchmarking. MTR tests call the binary with `--exec`
exactly as they call `ronsql_cli` today.

Rejected alternatives: (a) running the Java builder itself — it is an
EJB with Calcite/JPA dependencies inside another repo, unusable from
MTR; (b) Perl/Python generators — would duplicate the clients and the
bench runners.

### D2 — Fidelity to the Java builder: 1:1 port + golden-fixture conformance

The three emitters and their gates are ported method-for-method (same
names, same order of string appends, same alias rules). Fidelity is
enforced by **golden fixtures**: a small Java test utility in the
Hopsworks tree (same pattern as `TestPreparedStatementBuilder`, which
already builds entities by hand and invokes the private emitters via
reflection) dumps `{spec → templates}` JSON for a fixture set; the JSON
is checked into this tree under
`tools/rondb-cli/internal/fsq/testdata/hopsworks_golden/` and a Go unit
test asserts byte-identical output. When Hopsworks changes, the
fixtures are regenerated and the diff shows exactly what moved. Until
the Java dumper exists (it needs a Hopsworks Maven build), the fixtures
are hand-transcribed from `TestPreparedStatementBuilder.java`
(assertions at :403, :431-440, :533-544, :589-599, :652) and marked as
such.

### D3 — Data model: a synthetic Hopsworks-shaped online feature store

Database `fs_test` (MTR) / `fs_bench` (benchmark), tables named
`<fg>_<version>`, DDL produced by a port of `buildCreateStatement`, so
the framework creates tables exactly like Hopsworks does (including
`STORAGE MEMORY` on event_time, hash-only vs hash+ordered PK,
`idx_<cols>` secondary indexes, VARCHAR(100) strings, tinyint
booleans). Four feature-group kinds, deterministic closed-form data
from a seed + scale factor, controlled NULL and join-miss rates. Full
design in P2; the initial table set is listed in §4 P2.

### D4 — Three oracles

- **L1 — same-text differential.** The identical statement text (after
  `?` substitution) runs on MySQL (same NDB tables, `time_zone='+00:00'`)
  and on RonSQL through RDRS `/ronsql` (TEXT output) and optionally
  `ronsql_cli`; sorted TSV compare with type-aware canonicalization
  (DOUBLE/FLOAT relative tolerance, DECIMAL scale normalization,
  TIMESTAMP fraction normalization, NULL spelling). This is the
  `ronsql_compare.inc` contract, re-implemented natively in Go for the
  CLI paths and reused verbatim for MTR.
- **L2 — vector-level equivalence.** For a feature-view spec the
  framework emits the RonSQL template set *and* the MySQL serving
  statement(s) (`applyMysqlAggregate` twin; the `ROW_NUMBER() OVER
  (PARTITION BY pk ORDER BY ts DESC)` collect wrapper documented in
  `ConstructorController.wrapOnlineCollect`; the LEFT/INNER join chain
  for snowflake), runs both, applies the documented **client-side
  post-processing** to each side (collect sort/fold, snowflake
  per-chain overlay, batch GROUP BY empty-set defaults COUNT=0 / NULL,
  prefix application), and compares the assembled feature vectors per
  entity. This catches semantic drift that L1 cannot (e.g. LEFT-chain
  miss handling, window bound inclusivity).
- **L3 — rejection oracle** for the envelope-level random generator:
  every generated query is classified against the documented envelope
  (`cte_test_authoring_guide.md`, `_discovery_log.md`,
  `RonSQLPreparer.cpp` reject strings) as *expected-supported* or
  *expected-rejected*; outcomes are `PASS`, `CLEAN-REJECT`,
  `WRONG-RESULT`, `ERROR-UNEXPECTED`, `TIMEOUT/HANG`, `CRASH`
  (RDRS connection loss). Only the last four are failures.

### D5 — Two random generators, one ledger

- **Spec-level generator** (E6): random feature-view specs (choose FGs,
  star or snowflake topology, join types, selected features, aggregate
  specs, collect N and order column, filters, single/batch, entity
  keys drawn from the data) → ported emitter (gates included) → L1 +
  L2. Mirrors what Hopsworks can ever send. Specs that the gates
  suppress are still valuable: the framework then verifies that the
  MySQL fallback statement is executable and, optionally, tries the
  RonSQL shape anyway to learn whether the gate is still needed.
- **Envelope-level generator** (E7): random RonSQL statements over the
  same schema *beyond* the Hopsworks shapes (LEFT JOIN, several CTEs,
  HAVING, ORDER BY/LIMIT on aggregates, IN lists, filters on hop
  tables, composite keys, string keys, NULL hops, DATE/TIMESTAMP
  bounds) with the L3 oracle. Finds engine bugs ahead of Hopsworks
  adopting a shape.
- Shared machinery: seed + case index → reproducible SQL; per-query
  timeout; **shrinking** (drop CTEs, joins, filters, projections until
  the failure disappears); a findings ledger in the `_discovery_log.md`
  format under `mysql-test/suite/ronsql_fs/findings/`.

### D6 — Benchmarks: named prepared queries, twins on both engines

A new registry category `fs_hw` in `ronsql_bench.go` whose SQL is
*generated by the framework at build time* (Go `go:generate` or a unit
test that fails when the registry drifts from the emitter) so the
benchmark shapes are exactly the Hopsworks shapes. Entries:
`fs_hw_agg_point`, `fs_hw_agg_window`, `fs_hw_agg_batch{10,100,1000}`,
`fs_hw_agg_greatest`, `fs_hw_collect{5,50}`, `fs_hw_snow1_point`,
`fs_hw_snow2_point`, `fs_hw_snow1_batch100`, `fs_hw_left_chain`,
`fs_hw_strkey_point`, `fs_hw_composite_point`. Each has a MySQL twin
(`.bench_sql`), `{KEY}` substitution over the entity domain, and the
`x-ronsql-phases` breakdown. `ronsql_bench_matrix.py` gets
`--queries fs_hw` and a `.fs_load` step. Reported: p50/p95/p99, rows,
phases; regression thresholds recorded in `benchmarks.md`.

### D7 — MTR integration: suite `ronsql_fs`

- `mysql-test/suite/ronsql_fs/my.cnf` copied from `ronsql_cte/my.cnf`.
- `include/fs_schema.inc` + `include/fs_data.inc` generated **by the Go
  framework** (`rondb .fs_emit_mtr`) and checked in, so MTR needs no Go
  at run time for the golden tests; `ronsql_compare.inc` with
  `$strict_diff=yes` and `$suppress_ronsql_cli=yes` (join queries; the
  CLI's dictionary-cache caveat).
- `t/ronsql_fs_templates.test` — every catalog shape, several key
  values, single + batch, filters, LEFT chains (the golden regression).
- `t/ronsql_fs_vectors.test` — L2 driven through `$RONDB_CLI .fs_verify
  --vectors --seed N --count M`, summary output only (counts), failures
  dumped under `$MYSQLTEST_VARDIR/log/`.
- `t/ronsql_fs_fuzz.test` — bounded spec-level fuzz (fixed seed,
  ~200 cases) and envelope fuzz (~200 cases), summary-only output.
- Topology and JIT mirror suites (`ronsql_fs_ng2r2`, `ronsql_fs_jit`)
  as one-line wrappers once the base suite is green.

## 5. Execution phases

Dependencies: E1 → E2 → E3 → {E4, E5, E6} → E7 → E8. E5 can start as
soon as E1 (data) and E2 (emitter) exist.

### E1 — Schema, data, and the R1 probe — CODE WRITTEN (see `phase_e1.md`)

Scope:
- `fsq/ddl`: port of `buildCreateStatement` + `getOnlineType` (Go),
  unit-tested against the DDL strings in the FSDB fixtures.
- `fsq/data`: deterministic generator (seed + scale factor) producing
  rows for every FG in P2; two sinks: (a) NDB-API-free SQL emitter that
  writes `INSERT ... SELECT` over a digits table (MTR scale, mirrors
  `cte_data.inc`), (b) parallel batch loader over RDRS batch write or
  MySQL multi-row INSERT (bench scale; reuse `loadTPCHTable`).
- Shell: `.fs_load <sf> [threads] [batch] [--db fs_bench]`,
  `.fs_drop`, `.fs_emit_mtr <dir>`.
- MTR: `suite/ronsql_fs/my.cnf`, `include/fs_schema.inc`,
  `include/fs_data.inc`, `include/fs_drop.inc`, `t/ronsql_fs_smoke.test`
  (row counts + three hand-written L1 compares: one aggregate, one
  snowflake, one collect in **both** the CTE-wrapped and the direct
  single-table form — this is the R1 probe).
Files: `tools/rondb-cli/internal/fsq/{ddl,data}/*.go`,
`tools/rondb-cli/internal/shell/fs.go`, `mysql-test/suite/ronsql_fs/**`.
Verification (user runs):
```
cd <build> && make rondb-cli rdrs2 ronsql_cli -j8
cd <build>/mysql-test && ./mtr --suite=ronsql_fs ronsql_fs_smoke --record   # first time
./mtr --suite=ronsql_fs ronsql_fs_smoke
```
Exit: smoke test green; R1 outcome recorded in `phase_e1.md` and the
catalog updated (S6 status); decision taken on the collect shape.

### E2 — Spec model and emitter port with golden conformance

Scope: `fsq/spec`, `fsq/emit` (all three emitters, `aggregateOutputs`,
`renderRonsqlCondition`, `renderRonsqlLiteral`, `conjunctiveFilterConditions`,
`buildRonsqlSnowflakeTemplates`/`buildSnowflakeStatement`, batch/single,
prefixes, all gates), `fsq/mysqltwin` (`applyMysqlAggregate`, collect
wrapper, scan wrapper, snowflake join chain). Unit tests: the
transcribed golden fixtures from `TestPreparedStatementBuilder.java`
plus table-driven gate tests. Optional (Hopsworks repo): `HopsworksGoldenDump`
JUnit utility producing the fixture JSON.
Verification:
```
cd tools/rondb-cli && go test ./internal/fsq/...
```
Exit: every catalog shape reproduced byte-identically for the fixture
set; gates covered.

### E3 — Executors, canonicalization, L1 verify, golden MTR test

Scope: `fsq/bind`, `fsq/exec` (RDRS with `x-ronsql-phases`, ronsql_cli
subprocess, MySQL), `fsq/canon`, `.fs_verify [--shape S1..S9] [--keys N]
[--batch 10] [--db fs_test]` printing per-case PASS/FAIL and a summary
line; `t/ronsql_fs_templates.test` generated by `.fs_emit_mtr` (static
SQL via `ronsql_compare.inc`, one case per shape × key class ×
single/batch × filter variant, plus EXPLAIN pins for PK_LOOKUP /
CTE_LOOKUP where stable).
Verification:
```
./mtr --suite=ronsql_fs ronsql_fs_templates --record ; ./mtr --suite=ronsql_fs
./mtr --suite=ronsql_fs setup --start-and-exit   # then:
<build>/runtime_output_directory/rondb --mysql-port <p> --rdrs-port <r> --no-rondis
.fs_load 0.1 ; .fs_verify --all
```
Exit: all supported shapes green under `$strict_diff=yes`; unsupported
ones recorded as rejection-asserts or `# NEXT-PHASE` probes with a
findings entry.

### E4 — L2 vector-level equivalence

Scope: `fsq/vector`: client-side folds for both paths (collect sort +
fold to array, snowflake overlay per chain with LEFT miss semantics,
batch GROUP BY defaults, prefix application, window literal from one
UTC reference), `.fs_verify --vectors`, `t/ronsql_fs_vectors.test`.
Exit: vectors identical for every spec in the catalog over ≥ 100 keys
including miss/NULL-hop entities; any semantic divergence between the
RonSQL template path and the MySQL path documented (these are Hopsworks
issues, not engine issues, and go to the ledger with a `hopsworks`
tag).

### E5 — Benchmarks

Scope: `fs_hw` registry entries generated from the emitter (a Go test
asserts the registry equals the emitter output), MySQL twins,
`.bench_ronsql fs_hw_*`, `.bench_sql fs_hw_*`, `KeySQL` over the entity
domain, `KeySpan` for batch ranges, `ronsql_bench_matrix.py --queries
fs_hw` + `.fs_load` step, `benchmarks.md` with the first numbers
(interpreter and JIT arms, 1 and 8 threads) and thresholds.
Verification:
```
./mtr --suite=ronsqlcrunch setup --start-and-exit
python3 storage/ndb/claude_files/compiled_interpreter/ronsql_bench_matrix.py \
    --no-load --fs-load 1 --queries fs_hw --threads 1,8 --seconds 5 --out /tmp/fs_hw_run1
```
Exit: report produced; the RDRS schema-cache overhead (~400 µs
`listIndexes` per request, see `ronsql_bench_matrix.md`) called out
separately from engine time.

### E6 — Spec-level random generator

Scope: `fsq/fuzz/spec`: seeded spec sampler within the definition-time
gates, run through emit → bind → L1 (+ L2 when `--vectors`), outcome
classification, shrinking, `--seed --count --timeout --dump-dir`,
`t/ronsql_fs_fuzz_spec.test` (fixed seed, ~200 cases, summary only),
ledger `suite/ronsql_fs/findings/spec_fuzz.md`.
Exit: 10k cases at MTR scale with zero unclassified failures, or every
failure filed in the ledger with a minimal repro.

### E7 — Envelope-level random generator

Scope: `fsq/fuzz/envelope`: RonSQL AST sampler over the FS schema with
probe productions; L3 classification table; `t/ronsql_fs_fuzz_env.test`;
ledger `envelope_fuzz.md`. Priority constructs: LEFT JOIN chains from a
CTE (target shape for all-LEFT subtrees), multiple CTEs (one per FG,
joined in the main query — the "CTE per feature group" pattern), IN
lists up to 1000, string keys, filters on hop tables, HAVING, ORDER BY
+ LIMIT on aggregates, DATE/TIMESTAMP bounds with `DATE_SUB`.
Exit: same criterion as E6; each new engine finding cross-referenced to
`_discovery_log.md` conventions.

### E8 — Hardening and CI

Scope: topology mirrors (`ronsql_fs_ng2r2`, `ronsql_fs_ng4r2`), JIT
mirror (`ronsql_fs_jit` with fallback-delta pins), flake controls
(schema-dist suppressions, retry on RonSQL retryable errors), docs
(`CLAUDE.md` in this directory, `ronsql_cli_benchmarks.md` cross-links),
a `refresh` script for golden fixtures, and a one-page "how to add a
shape" guide.
Exit: `./mtr --suite=ronsql_fs,ronsql_fs_jit,ronsql_fs_ng2r2` green ×3
runs.

## 6. Risks and open questions

| Id | Risk / question | Mitigation / decision needed |
|---|---|---|
| R1 | Collect template (non-aggregate CTE body over a partial key with ORDER BY/LIMIT) likely rejected by RonSQL here; direct single-table form is supported | E1 probes both; decide engine extension vs Hopsworks template change; keep both forms in the catalog |
| R2 | TIMESTAMP window literal: format, fractional seconds, time zone (RonSQL is UTC-only; MySQL session tz must be `+00:00`) | bind layer emits `'YYYY-MM-DD HH:MM:SS[.ffffff]'`; MySQL executor sets `time_zone='+00:00'`; `ronsql_timestamp.test` is the reference |
| R3 | Batch `IN (?)` expands to an OR chain at parse time; 1000-key lists may hit size limits (`rdrs_size_limits.md`) or slow planning | benchmark `fs_hw_agg_batch1000`; record max working list size; ledger entry if it degrades |
| R4 | String entity keys (`VARCHAR(100)`, common in Hopsworks) in PK lookups, IN lists and GROUP BY; collation/charset | dedicated FG `customers_str_1`; canonicalization for string output |
| R5 | DOUBLE/FLOAT SUM ordering and DECIMAL formatting differ between engines | L1 tolerance rules in `fsq/canon`; benchmark shapes prefer BIGINT/DECIMAL |
| R6 | Snowflake all-LEFT chains: RonSQL `CTE_LOOKUP` is inner; MySQL LEFT JOIN yields NULLs on a miss | L2 models the client overlay; E7 tests native `LEFT JOIN` from a CTE as the future single-statement shape |
| R7 | GROUP BY hop column with NULL hop values (nullable FK) | data model includes NULL hops; catalog notes expected behaviour on both engines |
| R8 | Composite entity keys: single statements only (batch gated) | covered by `balances_1`; E7 probes tuple `IN` to see whether the gate can be lifted |
| R9 | Hopsworks emits inner `JOIN` even for LEFT subtrees (per-chain templates); a future single-statement `LEFT JOIN` form changes the catalog | keep shape ids stable, add `S8b` when it lands |
| R10 | RDRS never wires `schema_cache` (≈400 µs `listIndexes` per request) | report phases separately; note in `benchmarks.md`; possible follow-up ticket |
| R11 | Keeping the Go port in sync with Hopsworks | golden fixtures (D2); a `HOPSWORKS_REF` commit hash recorded in `fsq/emit/doc.go` |
| R12 | `ronsql_cli` dictionary-cache caveat for joins | MTR uses `$suppress_ronsql_cli=yes` for join shapes, as the CTE suites do |
| Q1 | Should `/scan` fallback semantics be modelled? | Recommend no (REST typed read, not SQL) |
| Q2 | Hopsworks `hw_cnt` dummy: should RonSQL accept a CTE with GROUP BY and no aggregate so the dummy can go? | E7 probe; potential engine improvement |
| Q3 | Where should the Java golden dumper live (Hopsworks repo PR vs local-only script)? | Decide in P3 review |
