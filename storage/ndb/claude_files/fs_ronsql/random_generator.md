# Random query generator design (P4, v1 — 2026-09-08)

**Status: E6 (spec-level generator) built 2026-09-11 — `fsq/fuzz`,
`.fs_fuzz spec|show|replay`, `t/ronsql_fs_fuzz_spec.test`, see
`phase_e6.md`; E7 (envelope-level generator) not built.** Builds on
`framework_design.md` (§6 executors, §7 canonicalization, §8 vector
oracle, §10 CLI) and `data_model.md` (§6 key classes).

---

## 1. Two generators, one runner

| | Spec-level (`.fs_fuzz spec`) | Envelope-level (`.fs_fuzz envelope`) |
|---|---|---|
| samples | feature-view specs (joins, aggregations, collect, filters, batch) | RonSQL statements over the same schema |
| goes through | the ported Hopsworks emitter and its gates | a small RonSQL AST renderer |
| asks | "does everything Hopsworks can emit today run and agree with MySQL?" | "does the engine hold up on the shapes Hopsworks will want next, and does it reject cleanly what it does not support?" |
| oracles | L1 same-text, L2 vectors, gate assertions | L1 same-text, L3 rejection classification |
| finds | engine bugs on production shapes, Hopsworks semantic drift (ledger tag `hopsworks`) | engine bugs and missing rejections ahead of Hopsworks adoption |

Both share the runner (§2), the outcome classifier (§3), the shrinker
(§6), and the ledger (§7).

## 2. Runner and reproducibility

- **Seeding.** One run has a `seed` (uint64) and produces cases
  `0..count-1`. Case `i` uses its own PRNG `rand.New(rand.NewPCG(seed,
  uint64(i)))` (Go `math/rand/v2`), so any single case can be
  regenerated by `(seed, i)` without replaying the run, and adding
  cases never perturbs earlier ones. The generator version is part of
  the case ID (`spec-v1-<seed>-<i>`), and a grammar change bumps the
  version rather than silently changing what old IDs mean.
- **Schema and key domain** come from `fsq/data` for the given `--sf`,
  so literals and keys are drawn from values that exist (or, by class,
  deliberately do not exist).
- **Budget.** `--count N` cases, `--timeout` per engine request
  (default 30 s spec / 15 s envelope), `--max-rows` cap (default
  10 000 rows per result; a case whose MySQL result exceeds it is
  `SKIP(too-large)` and the generator is tuned so this is rare),
  `--threads` workers (default 4; hazard cases §5.4 run single-threaded).
- **Loop per case:** generate → (spec) validate + emit + bind, or
  (envelope) render → run MySQL → run RDRS (and `ronsql_cli` when
  enabled) → classify → compare → record. Every case writes one
  `CASE` line (`framework_design.md` §10); failures are dumped and, if
  `--shrink`, shrunk before the next case starts.
- **Replay.** `--replay <file.json>` re-runs the cases of a ledger or
  dump (used after an engine fix to flip ledger rows to FIXED).

## 3. Outcome classification (L3)

RDRS behaviour (from `rest-server2/server/src/ronsql_ctrl.cpp` and
`db_operations/ronsql/ronsql_operation.cpp`): a successful statement
is HTTP 200 with the selected output format (JSON for typed correctness
checks, TEXT for supplemental formatting); **every RonSQL error is HTTP 500** with
a text body — `Caught exception: <message>` for a
`RonSQLPermanentError`, `Caught RonSQLRetryableError after 10
attempts: <message>` when retries are exhausted; rate limiting is
HTTP 429; malformed request/database is HTTP 400.

| outcome | rule | counts as |
|---|---|---|
| `PASS` | both engines 200/OK and canonical results equal (L1), vectors equal (L2) | success |
| `CLEAN-REJECT` | RDRS 500 with `Caught exception:` and the message matches an entry of the expectation table (§5.3) for a construct the case contains; MySQL succeeded | success (expected) |
| `REJECT-UNEXPECTED` | RDRS permanent error for a case the table says should run, or a message not in the table | failure |
| `WRONG-RESULT` | both engines 200 but results differ | failure |
| `MYSQL-ERROR` | MySQL rejected the statement | generator bug (failure of the framework, not the engine) |
| `RETRY-EXHAUSTED` | body contains `RonSQLRetryableError` | failure (ledger, like D12) |
| `TIMEOUT` | RDRS request exceeded `--timeout` and the crash probe passes | failure (HANG class) |
| `CRASH` | transport error or timeout followed by a failed `Probe()` (RDRS down or `SELECT 1` on MySQL reports NDB unavailable) | failure; the run stops (`--continue-after-crash` overrides) |
| `GATED` | spec-level only: the ported Hopsworks gate suppressed the template; asserted against the expected gate | success |
| `SKIP` | result too large, or construct excluded by flags | neutral |

Production alias/schema differences are failures. Only explicitly
designated envelope cases may use `--relaxed-headers` and informational
`HEADER-ONLY`; a zero-row result has no RonSQL column list (JSON or
TEXT), so two empty results are equal by construction. Until F9 is
fixed, generated `MIN`/`MAX` over a DATE/TIMESTAMP column yields an
unparsable JSON body: match it through the expectation table
(`KNOWN-ERROR`), do not count it as a crash or a wrong result. Preserve
nullness and exact numeric tokens through the typed executor; apply the requirements-mode rules in the framework
design separately from regression/discovery allowances.

## 4. Spec-level generator (E6)

### 4.1 Sampling procedure

1. **Left feature group** (join index 0): pick from the entity FGs
   (`customers_1` 60 %, `customers_str_1` 20 %, `balances_1` 10 %,
   `profiles_1` 10 %). Select 0–3 of its plain features.
2. **Topology**: star only (55 %), snowflake (35 %), both (10 %).
   Star nodes: 1–3 joins with `parentIndex = 0`, each one of:
   aggregate FG (`transactions_1`, `sessions_1`, `balance_hist_1`,
   `transactions_str_1` when the root is string-keyed), collect FG
   (same set), plain FG (a second entity FG on the same key). Snowflake:
   a nested subtree rooted at the left FG or at a star node, depth 1–3
   over the FK graph `customers → regions → countries`,
   `transactions → merchants`, `profiles → regions → countries`, with
   1–2 children per node.
3. **Join types**: LEFT (the feature-view default) 60 %, INNER 30 %,
   mixed within a subtree 7 % (expect no templates), RIGHT/FULL 3 %
   (expect no templates).
4. **Join conditions**: full child PK (85 %), partial PK (10 %, expect
   gate), none (5 %, expect gate). Left features are the FK columns of
   the parent; the generator knows the FK graph from the schema.
5. **Aggregate spec** (for aggregate nodes): 1–4 entries; keys drawn
   from numeric features (SUM/AVG), any non-complex feature (MIN/MAX/
   COUNT), `*` (COUNT), integer pairs/triples for GREATEST/LEAST
   (`amount,fee`, `age,credit_score`, `duration,pages`); 10 % of specs
   deliberately violate the type matrix (SUM over a string, GREATEST
   over a decimal, duplicate output names) and expect the
   definition-time `GateError`. Window: none 40 %, 1 h / 24 h / 7 d /
   30 d / 90 d otherwise; 5 % use a window on an FG without event time
   (gate).
6. **Collect** (for collect nodes): ordinary `N ∈ {1, 5, 50}`, plus
   configured N/width boundary cases and named invalid specs. Choose
   either the default event time or a valid explicit order column
   from the edge fixtures; `collectAscending` 50 %. Preserve persisted
   struct field types/order and include at least one valid value field.
   Exercise every collect gate from the shape catalog.
7. **Filters**: 0 (50 %), 1 (30 %), 2–3 AND leaves (17 %), one OR
   node (3 %, expect the `COLLECT_UNSUPPORTED_ONLINE_FILTER` gate on
   collect/aggregate FGs). Leaf = feature × condition (`= <> > >= < <=
   LIKE`) × literal from the feature's value domain (§`data_model.md`
   5) via `bind.LiteralFor`; 5 % choose a boolean feature or a
   feature-vs-feature comparison (gate). Filters are pinned to a join
   index 50 % of the time.
8. **Mode**: single (60 %), batch 10 (20 %), batch 100 (15 %), batch
   1000 (5 %). Composite-key roots in batch mode expect the
   tuple-`IN` gate.
9. **Keys**: drawn by key class (`data_model.md` §6) with weights:
   ordinary 50 %, no-rows 10 %, exactly-N 10 %, bound-aligned 10 %,
   NULL hop 5 %, dangling hop 5 %, missing entity (key outside 1..E)
   10 %. Batches mix classes.
10. **Options**: `inferenceHelperColumns` / `loggingMetaData` /
    `featureVectorWithInferenceHelpers` each 10 % (they change the
    selected feature sets; a few features are flagged helper/label
    at random).

The edge FGs in `data_model.md` §11 participate in sampling, including
full/partial composite child hops and legal complex/binary snowflake
projections. Apply operation-specific Hopsworks gates, not blanket
complex-type exclusions. Mandatory deterministic coverage is tracked
independently of random hit counts.

### 4.2 What is checked per case

- `spec.Validate` outcome matches the intended gate (from step 5/7).
- `emit.Build` outcome matches the expected template set: which
  statements carry `QueryRonsql` / `SnowflakeTemplates`, how many
  chain templates (all-LEFT = one per nested node), none for mixed.
- For each RonSQL template: L1 against its own text on MySQL (the
  template is valid SQL for both once bound; the same-text oracle is
  the strongest signal of an engine bug).
- With `--vectors`: L2 between the RonSQL template set and the MySQL
  twins after client folds, for every key in the case.
- With `--probe-gated`: for a gated case, bind and run the *would-be*
  RonSQL statement anyway (e.g. batch composite-key `IN`) and record
  the outcome under tag `gate-probe` — evidence for lifting a
  Hopsworks gate when the engine handles the shape.

### 4.3 Expected volume

At 4 threads and sf 0.01 a spec case costs ~5–20 statements; 2 000
cases ≈ 10 minutes. The MTR test runs 200 cases at seed 1.

## 5. Envelope-level generator (E7)

### 5.1 AST

```
Stmt     := [CTEs] SELECT Outputs FROM Root Joins* [WHERE Cond] [GROUP BY cols] [HAVING Cond] [ORDER BY items] [LIMIT n]
CTE      := name AS (SELECT Outputs FROM Table Joins* [WHERE Cond] [GROUP BY cols] [ORDER BY items] [LIMIT n])
Root     := Table AS alias | CTE name
Join     := [LEFT] JOIN (Table AS alias | CTE name) ON child.col = parent.col [AND ...]   -- equi, parent already in scope
Outputs  := Column | Agg(Column|Expr) [AS alias] | COUNT(*) | GREATEST/LEAST(...)
Cond     := atom | Cond AND Cond | Cond OR Cond | NOT Cond | col IS [NOT] NULL | col IN (list) | col LIKE 'p'
atom     := col op literal | col op col | GREATEST/LEAST(...) op literal | col op DATE_SUB('ts', INTERVAL n UNIT)
```
The renderer always writes explicit `AS` aliases (RonSQL rejects
`orders o`), backticks every identifier (as Hopsworks does), qualifies
every column when more than one table is in scope, and terminates with
`;`.

### 5.2 Productions and weights (v1)

| production | weight | notes |
|---|---|---|
| single-table aggregate with WHERE on the PK prefix (S1-like) | 15 % | baseline that must always pass |
| single-table projection-only + ORDER BY + LIMIT (S6b) | 10 % | ordered compare |
| "CTE per feature group": 1–3 aggregating CTEs keyed by entity, main SELECT joins them to the entity table (`customer JOIN cte ON cte.k = c.pk`), main aggregates or projects | 20 % | the shape Hopsworks would emit for a multi-FG vector in one statement |
| snowflake from a CTE root with INNER hops (S7-like), depth 1–3, 1–2 children | 15 % | |
| snowflake from a CTE root with **LEFT** hops (S8b) | 10 % | target shape for all-LEFT subtrees |
| batch: `IN (list)` of 1 / 10 / 100 / 1000 keys + GROUP BY key | 8 % | request-size probe |
| filters: IN lists, LIKE, IS [NOT] NULL, DATE_SUB bounds, OR/DNF, NOT | 8 % | mixed into the above |
| HAVING, ORDER BY on GROUP BY columns / aggregate aliases + LIMIT on aggregates | 6 % | |
| CTE body ORDER BY / LIMIT (non-aggregate body over a partial key, the S6 CTE form; aggregate body top-N) | 4 % | S6 form expects `CLEAN-REJECT` until the engine changes |
| known-unsupported probes (§5.3, "expect reject" rows) | 4 % | must reject cleanly |

Literals come from the data formulas so predicates hit (e.g. `amount
BETWEEN` is not in the grammar, but `amount >= 500 AND amount < 700`
is); key-bound WHEREs are preferred so results stay small; unbounded
scans over history tables are allowed only with `LIMIT` or with a
GROUP BY on the entity key (≤ 15 E/16 rows).

### 5.3 Expectation table

The table maps a construct present in the generated AST to the
expected outcome and the RonSQL message pattern (from
`RonSQLPreparer.cpp` / `QueryPlanner.cpp` strings and
`cte_test_authoring_guide.md`). It is data (`fuzz/expect.go`), and a
mismatch in either direction is a finding.

| construct | expected | message pattern |
|---|---|---|
| non-aggregate CTE body that is not a single-row PK lookup (S6 CTE form) | reject | `Non-aggregating CTE body is not a single-row key lookup` |
| partial-key CTE lookup | reject | `Partial CTE lookup key not supported` |
| CTE_SCAN as an outer-join child | reject | `CTE_SCAN as outer-join child is not supported` |
| INNER JOIN below a LEFT JOIN | reject | `INNER JOIN below a LEFT JOIN is not supported` / `INNER JOIN below LEFT JOIN not supported` |
| join column without a usable index (no PK/unique/ordered index) | reject | `Cannot push join: no suitable index on join columns` |
| join on a BLOB/TEXT column | reject | `BLOB/TEXT columns cannot be used as join columns` |
| ORDER BY / LIMIT inside a subquery | reject | `ORDER BY / LIMIT in a subquery is not supported` |
| GREATEST/LEAST compared with `=` / `!=` in WHERE | reject | `GREATEST/LEAST with = or != in a WHERE clause is not supported` |
| GREATEST/LEAST over a non-integer column | reject | `GREATEST/LEAST column operand must be an integer` |
| AVG over a string / temporal column | reject | `AVG over string columns` / `AVG over temporal columns` |
| ORDER BY target not a GROUP BY column or aggregate alias (aggregate query) | reject | ResultPrinter `validate_orderby_columns` message |
| index hint on a joined table | reject | `Index hints (FORCE/USE/IGNORE INDEX) are only supported on the` root |
| cross-table WHERE (`a.x > b.y`) outside the supported forms | reject | `Cross-table WHERE conditions` |
| implicit alias (`orders o`), DISTINCT, BETWEEN, UNION, OFFSET | reject | parser `Syntax error` / unimplemented keyword |
| everything else in §5.2 | run | — |

Rows are added as the engine grows; the same table drives the
`ExpectReject` column of the deterministic case matrix
(`framework_design.md` §9), so there is exactly one place where
"known unsupported" is recorded.

### 5.4 Hazards

Shapes with a recorded HANG or CRASH history
(`mysql-test/suite/ronsql_cte/findings/_discovery_log.md`: D4/D12
col-vs-col in a CTE body, D5 real–CTE–real chains, D6 high-cardinality
CTE under a large root scan, D18 string MIN/MAX re-aggregation, D19
main WHERE on a parent column, D20 reversed multi-key lookup, D23
CTE_LOOKUP with no selected columns) are **not generated by default**.
`--include-hazards` enables them, single-threaded, with a 10 s
timeout and a crash probe after each; a passing hazard case is
reported as `PASS(hazard)` so the ledger row can be flipped to FIXED.
Since the discovery log is TPC-H based, each hazard has an
FS-schema translation in `fuzz/hazards.go` (e.g. D6 ≙ CTE keyed by
`transactions_1.event_time` under a `transactions_1` root scan).

## 6. Shrinking

Delta debugging over the case's own structure, re-running the full
classification after each step and keeping a step only if the failure
class (and, for `WRONG-RESULT`, the first differing column) is
preserved:

- spec-level: drop joins (leaves first), drop selected features,
  drop aggregate entries, drop filters, remove the window, reduce
  batch size (1000 → 100 → 10 → 1 → single), reduce collect N, drop
  helper options, replace a string-keyed FG by the integer-keyed twin.
- envelope-level: drop CTEs not referenced by the failing path, drop
  joins (deepest first), drop WHERE conjuncts, drop projections
  (keeping one), drop GROUP BY columns, drop ORDER BY/LIMIT/HAVING,
  shrink IN lists by halving, replace literals by the simplest value
  in the domain.

Budget `--shrink-steps` (default 200) and `--shrink-timeout` (default
5 min). `TIMEOUT`/`CRASH` cases are shrunk only with
`--include-hazards` (each step is a hazard). The minimal case is
written next to the original (`<id>.min.json` / `.min.sql`) and is
what goes into the ledger.

## 7. Ledger

`mysql-test/suite/ronsql_fs/findings/<generator>_fuzz.md`, same
columns as `_discovery_log.md`:

```
| # | Family | Shape | Symptom | Repro (minimal) | Disposition |
```
- `#` = `F<n>` (framework findings), Family = spec / envelope / hazard
  / hopsworks / framework; Symptom = the outcome class plus the first
  divergence; Repro = the minimal bound SQL (or spec JSON path);
  Disposition = OPEN / EXPECTED (row added to §5.3) / FIXED (replay
  green, engine commit) / HOPSWORKS (semantic drift to report
  upstream) / FRAMEWORK (generator or canonicalization bug).
- A machine-readable `findings.json` sits beside it with the case ID,
  seed, generator version, shape signature, outcome, dump paths.
- **Dedup by shape signature**: a structural fingerprint (shape kind,
  construct set, join depth, key class, mode) so that one engine bug
  produces one row however many seeds hit it; the row keeps a hit
  count.
- **Triage workflow**: OPEN → decide (engine gap → ticket in the
  engine tree and row EXPECTED with its §5.3 pattern; Hopsworks
  semantics → HOPSWORKS; generator/canon bug → FRAMEWORK, fixed here)
  → `--replay` after a fix → FIXED.

## 8. CLI

```
.fs_fuzz spec     --seed S --count N [--sf 0.01] [--db fs_test] [--vectors] [--probe-gated]
                  [--threads 4] [--timeout 30s] [--max-rows 10000] [--shrink] [--dump-dir P]
                  [--ledger P] [--json P] [--quiet]
.fs_fuzz envelope --seed S --count N [--sf] [--db] [--include-hazards] [--only prod1,prod2]
                  [--threads] [--timeout 15s] [--max-rows] [--shrink] [--dump-dir] [--ledger] [--json] [--quiet]
.fs_fuzz replay   --file findings.json|dump.json [--shrink]
.fs_fuzz show     --seed S --index I [--kind spec|envelope]      # print the case without running it
```
Output follows the `CASE` / `SUMMARY` contract; `SUMMARY` adds
`clean_reject=<n> reject_unexpected=<n> wrong=<n> timeout=<n> crash=<n>
mysql_error=<n>`. Exit code 0 iff no failure class occurred
(`--allow-known` treats outcomes matching an EXPECTED ledger row as
success).

MTR (`t/ronsql_fs_fuzz_spec.test`, `t/ronsql_fs_fuzz_env.test`): seed
1, 200 cases each, hazards off, 4 threads, `--allow-known`, result
file = the `SUMMARY` line only; nightly: seeds by date, 5 000 cases,
`--shrink`, ledger appended.

## 9. Unit tests (`fsq/fuzz`, no cluster)

- determinism: `(seed, i)` → identical spec/AST across runs and
  independent of `count`;
- every generated spec passes `spec.Validate` unless it was built to
  violate a named gate, and then it fails with exactly that gate;
- every rendered envelope statement parses with the MySQL grammar
  subset the renderer targets (a small Go syntax checker for
  balanced parentheses, alias rules, qualified columns);
- expectation table: each row has a construct detector and a
  message regex, and each regex matches at least one string literal
  in `RonSQLPreparer.cpp`/`QueryPlanner.cpp` (test reads the sources);
- shrinker: on a synthetic oracle ("fails iff the spec contains join
  X and filter Y") converges to exactly {X, Y};
- hazard translations exist for every `D<n>` row marked HANG/CRASH
  and OPEN in the discovery log.
