## 2. Decisions / notes

- Placeholders are resolved on the bare SQL before the RonSQL prefix, so
  the MySQL baseline runs the identical text.  A batch list renders as
  `k1, k2, …` inside the parentheses the emitter already wrote (`IN (?)`
  on RonSQL, `IN ?` bound to `(…)` on the twin).
- `{ACCT}` and `{CUR}` of one statement refer to the same account
  (currency drawn from that account's `1 + a mod 3` currencies), so a
  composite point read hits an existing pair about 2/3 of the time and
  an absent currency otherwise — the serving mix, visible through the
  `rows` phase counter.
- Keys are drawn uniformly, so about 1/16 of point reads hit an empty
  history and 1/16 a 300-row one (data_model.md classes); `--key-class`
  stays an E5 stretch item.
- Plan pins are deliberately few until the first run shows the EXPLAIN
  vocabulary for single-table aggregates and the collect index-order
  plan: snowflake entries pin `[ROOT] CTE_SCAN` and `[INNER]`,
  `hash_point` pins `TABLE_SCAN`; every fs_hw warmup prints its EXPLAIN
  into the matrix case log so the pins can be tightened from evidence.
- The fs_hw descriptions carry the shape id and the expected rows per
  request in brackets, so the matrix report and `.bench_ronsql list` show
  the cross-reference to `shape_catalog.md` without another table.
- `.bench_vector` (end-to-end feature-vector assembly per request) is not
  built in this cut; the per-statement numbers plus section G answer
  questions 1–3 of `benchmarks.md` §1.

## 4. Failure guide

- `registry generation failed` in the listing: the emitter refused a
  bench view; the error names the entry.
- `.fs_load failed` in the matrix: the data set or checksums; run
  `.fs_load` interactively with the same arguments.
- A warmup error on one entry aborts that case only; `collect5_cte` is
  expected to fail on RonSQL until F0 is fixed.
- `Plan pin missing`: a warning, not a failure — compare the printed
  EXPLAIN with `benchmarks.md` §7 and tighten or correct the pin.

## 5. Results

### Run 1 — `prod_build`, sf 1, 2026-09-11 (incomplete: 109 of ~300 cases)

The matrix ran the 1-thread cases through `fs_hw_strkey_batch100`, where
the pushed-aggregation mysqld arm crashed (F10) and the driver aborted
with a traceback after writing `report.md` / `results.json` (now
`bench_results/2026-09-11-prod_build-run1/`; findings in
`findings/bench.md`, numbers and reading in `benchmarks.md` §8):

- F10 mysqld crash (VARCHAR GROUP BY key + IN list, pushed aggregation),
  F11 pushed point aggregates failing with NDB error 4120 — both on the
  MySQL side; the driver now ends the matrix cleanly with a report when
  the cluster stops answering instead of raising from the counters.
- F12 RonSQL IN lists execute as a table scan: S3 batch serving is
  200–1000× slower than MySQL — the headline result.
- F13 snowflake point reads 3–4× slower than MySQL (CTE_SCAN round trips).
- Point aggregates and collect at parity (~100–120 µs); JIT no effect;
  RDRS schema cache warm (`load` 1–2 µs).

Plan pins were tightened to the observed EXPLAIN wording (`Execute as
index scan.` / `Execute as table scan.` / `Body root: …` / `[ROOT]
CTE_SCAN` / `[INNER] PK_LOOKUP` / `[LEFT JOIN] PK_LOOKUP` / `ORDER BY:
index order …` / `Result limited to N rows.`); no pin warning fired in
run 1 with the initial pins.  The golden dump changes with the pins
(rerun `-update`).
