1. Scope, conventions and the blocks involved

DBSPJ executes a pushed join (a query tree of lookup and scan operations) on behalf of DBTC. One DBSPJ instance exists per TC instance and runs in the same thread as that DBTC instance (mt.cpp:7304 getInstanceNo / 7400 thread map: case DBTC: case DBSPJ:; DbspjMain.cpp:822 execSTTOR: c_tc = globalData.getBlock(DBTC, instance())). DBSPJ issues the per-table operations to DBLQH (or to the query-thread block DBQLQH through the virtual block V_QUERY) on any data node and gets the result rows it needs for the join back as TRANSID_AI; rows that only the client needs go from DBTUP straight to the API.

The document follows a request from its start signal to its release. A Request is one SPJ query instance (one LQHKEYREQ or one SCAN_FRAGREQ from DBTC). It owns a list of TreeNodes (one per query operation, of type lookup, scanFrag, CTE lookup, CTE scan or CTE subtree container). A scanFrag TreeNode owns a list of ScanFragHandles, one per fragment it scans.

Conventions. "LQH" means DBLQH or DBQLQH. A code reference reads DbspjMain.cpp:4583 Dbspj::abort(); references without a file name are to storage/ndb/src/kernel/blocks/dbspj/DbspjMain.cpp. Line numbers are those of the committed tree (HEAD 6598f4a65e3); while this was written the working tree had uncommitted edits to DbspjMain.cpp (new error inserts 17535-17539) that shift lines after ~10500 by up to 80. Finding IDs (S-n) are explained in section 10, with trigger, test and confidence.

2.5 Counter accounting rules

The single most important invariant: every signal SPJ expects back is represented exactly once in Request::m_outstanding, and every handler that retires one calls checkBatchComplete() (or checkPrepareComplete()) before returning (comment at :3716-3721). Within a batch every node also has a batch sub-state held in the request bitmasks: completed (bit set in m_completed_tree_nodes: nothing outstanding), running (bit clear) and suspended (in m_suspended_tree_nodes). When a node becomes completed, handleTreeNodeComplete() checks whether all predecessors of later nodes in the execution plan (m_next_nodes) are complete and not suspended, and then calls resumeBufferedNode() and/or m_parent_batch_complete() on them (:4506, :4532 reportAncestorsComplete). 6a. Lookup-only join (LQHKEYREQ root)

7. Concurrency and ordering assumptions

7.1 Thread placement

  • DBSPJ instance i runs in the thread of DBTC instance i (a TC thread, or a receive thread when there are none). DBTC->DBSPJ signals of one query are therefore delivered in send order, and DBSPJ may read c_tc->m_distribution_handle directly to pick query-thread instances (:9687, :13932).
  • DIH is called synchronously with EXECUTE_DIRECT_MT (DIH_SCAN_TAB_REQ, DIGETNODESREQ, DIH_SCAN_TAB_COMPLETE_REP); DIH protects that data with a per-table mutex (DbdihMain.cpp:17181 start_scan_on_table). The results are posted back to DBSPJ as self-signals to get a real-time break (:12276-12297).
  • Root fragments are always on the own node (:11800, :11827); child scans and lookups go to any node. Local reads go to a query thread chosen per request (get_lqhkeyreq_ref/get_scan_fragreq_ref), disk reads always to the owning LDM (:9680-9696, :13891-13981). For a remote node with query threads, the REQ goes to V_QUERY and the receiving node picks the thread; DBSPJ learns the executing instance from senderRef in the first CONF/REF/HBREP and must not send a NEXTREQ before that (ndbrequire at :5055, :14824).

7.3 Crossing scenarios checked

  • Close vs. CONF in flight (F11, F8): handled.
  • SCAN_NEXTREQ vs. abort in progress: the NEXTREQ clears RS_WAITING, sees RS_ABORTING and only re-checks completion; the reply is the REF when the abort drains (:5183-5190).
  • NEXTREQ after node failure while waiting: tombstone (T13, T14).
  • Node failure during the NODE_FAILREP sweep: a second sweep can visit a request twice; the handlers are idempotent (failed fragments get m_ref=0, lookups zero their per-node count), and abort() returns early when already aborting.
  • Null-row REQ in flight during abort: always local; the CONF or REF retires it and the deferred restart is not performed while aborting (:11134).

7.4 Where the two neighbours' assumptions meet

  • Close from DBTC while DBSPJ's CONF is in flight: DBTC ignores the crossing status-0 CONF and keeps waiting (DbtcMain.cpp:19438-19455); DBSPJ then replies to the close with the final CONF. If DBSPJ's crossing CONF was final, DBTC releases the fragment and DBSPJ ignores the close. Both sides agree.
  • Close from DBSPJ to a DBLQH scan that is parked waiting for a join-aggregation SETUP: the parked request is not in DBLQH's transaction hash, so the close is dropped (DblqhMain.cpp:25776-25810, 18833-18843); the replayed scan then answers with a normal CONF that DBSPJ ignores while it waits for a close reply that never comes (S-17).
  • HBREP after the final reply: both DBSPJ (ndbrequire(getGuardedPtr)) and DBTC (systemErrorLab outside LQH_ACTIVE) stop the node on it. DBLQH sends HBREPs only while scanning, in the same thread as the CONF; DBSPJ forwards them without checking its own state (S-18).
  • Abort while a node is still TN_INACTIVE: scanFrag_abort treats an inactive node as having nothing open, but during the first scanFrag_send of a batch the node is TN_INACTIVE while some SCAN_FRAGREQs are already out (S-19).
