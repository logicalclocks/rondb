DBSPJ attribute-information protocol

How a pushed join is serialized by NdbQueryBuilder, carried by DBTC, parsed and validated by DBSPJ, and turned into the KeyInfo and AttrInfo of each LQHKEYREQ and SCAN_FRAGREQ that DBSPJ sends to DBLQH. Covers RonDB's join aggregation and CTE extensions, a word-level worked example, and suspected weaknesses. Source tree: RonDB 26.10 (branch RONDB-1124-spj-fixes). Everything here was checked against the code on 2026-10-28; line numbers are approximate, so each citation also names the function.

1. Overview: the path and the sections at each hop

The NDB API serializes a pushed join (NdbQueryDef) as a QueryTree, with one QueryNode per operation. When the query is executed it adds a QueryParameters block with one parameter node per QueryNode. Tree and parameters are concatenated into a single AttrInfo section. This one section is the entire "program" that DBSPJ receives. DBTC never looks inside it: it forwards the section verbatim to a DBSPJ instance on the node that holds the root fragment.

3.3 Optional part of a parameter node (order is fixed)

  1. Key parameter values (PI_KEY_PARAMS): for each parameter of the op, in addParamRef order: [byteLen][value words, zero padded] (serializeParams() 5972-6005). DBSPJ treats each length word as an AttributeHeader with attrId 0 (getDataSize = words). NULL values are refused by the API (Err_KeyIsNULL), but nothing in DBSPJ refuses them (P-6).
  2. Interpreted program (PI_ATTR_INTERPRET).
  3. User projection (PI_ATTR_LIST): [n] followed by n AttributeHeaders (size 0). The API appends RANGE_NO when needed and CORR_FACTOR64 as the last entry for every op of a scan query (serializeProject() 5953-5968). For CTE readers it adds virtual column ids 0..n-1 + CORR_FACTOR64 (6420-6515).
How parameter values are matched to patterns. The parameter numbers in P_PARAM / P_PARAM_HEADER are indices into the op's own parameter list, the values serialized in part 1. DBSPJ builds a row header over the first cnt values (cnt comes from the pattern header) and indexes it by val (expand() 15925, 15995). The prune pattern re-walks the same list from the start (origParam, parseScanFrag 12079). The root op never has parameter values: its key or bounds are already in KeyInfo (assignParameters() starts at i=1, NdbQueryOperation.cpp:2915-2924). For a unique-index access the values go in the index node's parameter block.
The parameter walk is buildRowHeader(hdr, param.ptr, cnt). It advances param.ptr by the declared sizes and never checks param.end. See P-4.

4.2 The build loop (build() 2040-2538)

  1. loop = getNodeCnt(word0); 0 or > NDB_SPJ_MAX_TREE_NODES (32) gives 20017.
  2. For each node: peek one word from each reader (the results are ignored, see P-20), then check node_len < 32768 (20009, the size of m_buffer0) and param_len < 32768 (20010, m_buffer1).
  3. getWords the node into m_buffer0 (20004 if short) and the params into m_buffer1 (20005 if short).
  4. Op types must be equal (20003). Deprecated v1 params are widened in place (P-1). getOpInfo(); unknown type gives 20003.
  5. Call OpInfo::m_build(ctx, req, qn, qp) with qn->len and qp->len set to the plain lengths.
  6. CTE bookkeeping: inside a subtree, record m_cteId and set T_CTE_SCAN or T_CTE_INDIRECT_FEED (2314-2420).
  7. After the loop: validateAggregateFlags() (20022), buildExecPlan() (its return value is ignored, P-19), and initRowBuffers() (MAP or LIST with capacity MaxCorrelationId).

Each builder sets up a DABuffer {ptr, end} for the node and one for the params: ptr = optional, end = optional + (len - NodeSize). It also checks that len ≥ NodeSize (20004 / 20005). CTE readers move nodeDA.ptr past the type info first.

5. How DBSPJ builds child KeyInfo/AttrInfo from parent rows

5.1 Storing parent rows

execTRANSID_AI() (5271) copies the row into m_buffer1. It builds a RowPtr::Header {m_len, m_offset[]} on the stack (tmp[2+MAX_ATTRIBUTES_IN_TABLE]) by walking the AttributeHeaders (buildRowHeader 15340). It requires the last column to be CORR_FACTOR32 (getCorrelationData, ndbrequire 15484-15486) and then calls startNextNodes(), which in turn calls each child's m_parent_row.

A node keeps its rows when it has T_BUFFER_ROW or T_BUFFER_MAP. These flags are set by a child's P_PARENT, by the execution plan, by aggregate match tracking, or by congestion. storeRow() (5598) writes:

[list link (2 words, COLLECTION_LIST only)] [match mask (1 word, T_BUFFER_MATCH)]

The stored pattern holds only P_DATA, P_COL, P_UNQ_PK, P_ATTRINFO and P_PARENT, because params were converted to P_DATA at build. Keys are expanded from API P_DATA tokens (up to 0xFFFF words each) or from parent column values (up to 18000 words), and their length is never limited. Trigger: a lookup child with NI_KEY_CONSTS and P_DATA(4000) under a scan root. Also a linked key from a long parent column, or a prune key. Test: expect a REF. Fix: make the size check an error return.

P-4 — unchecked P_PARAM index and parameter walk (high)

P-4. expand() 15925-15992 and 15995-16080; buildRowHeader(…, src, cnt) 15363. val < paramCnt is only an ndbassert. A larger val indexes the stack array tmp[1+4096] out of range or reads uninitialised entries, and the resulting offset is used to copy getDataSize(*ptr) words into the key. The parameter walk advances by the declared sizes (up to 16383 words each) without checking param.end. Data read out of bounds (from m_buffer1, which may hold another query's last TRANSID_AI row, or beyond) ends up in KeyInfo sent to DBLQH. Trigger: NI_KEY_PARAMS, header 0x00010001, P_PARAM(0x400); or one parameter whose length word is 0xFFFC. Test: expect 20007 or 20005.

P-5 — pattern tokens read past the node (high)

P-9 — parent column index not validated (high)

P-9. appendColToSection / appendAttrinfoToSection / appendPkColToSection 15490-15571 read row.m_header->m_offset[col] for col up to 0xFFFF and never compare it with m_header->m_len, which is the parent's linked count + 1. Trigger: child key [P_COL(300)], or [P_UNQ_PK(0)] on an INT parent column. P-10 — JoinAgg flag without an aggKeys section [RonDB] (high)

P-10. DBTC copies the JoinAgg flag to the SCAN_FRAGREQ (DbtcMain.cpp:17780). It only parses the KeyInfo, builds aggKeys and attaches them when keyLen != 0 (17443, 18500, 20674). With MultiFrag, a fragId is read as fragCnt and ndbrequire(reader.step(offset)) fires (1732). The aggKeys parser is otherwise all ndbrequire, and it assumes CTE block c has cteId == c without checking. Test: raw SCAN_TABREQ(JoinAgg, 2 sections); expect a REF.

P-16 — pseudo-columns in API read lists (medium)

P-16. PI_ATTR_LIST is copied verbatim (16655-16663), and NI_LINKED_ATTR ids are shifted into headers without filtering (16714-16723). DBTUP honours FLUSH_AI with the next 3 words used as resultRef/resultData/routeRef (DbtupRoutines.cpp:3413-3419). A client can therefore make DBTUP send TRANSID_AI to any block. Confidence is medium because whether signal-scope filtering intercepts this was not checked.

P-24 — API signal to a block instance without a handler (reproduced)

P-24. The sender check in SimulatedBlock.hpp 2558-2563 (checkSignalSender) uses the scope of the GSN from the central table, not whether the receiving block instance handles it. SCAN_TABREQ is External, so it passes for any block. Sent to DBTC instance 0, which on ndbmtd is the DbtcProxy with no SCAN_TABREQ handler, it reaches handle_execute_error (SimulatedBlock.cpp 2850-2856), and the node stops with "Illegal signal received (GSN 32 not added), block: 245, instance: 0". A signal from another node to a missing handler should be dropped and reported (reportMaliciousSignal), and only a local one should stop the node. Test: testSpjMalformed -n P24 (the control request sent to DBTC instance 0).
