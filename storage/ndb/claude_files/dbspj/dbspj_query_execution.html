DBSPJ query execution

How pushed joins and pushed join aggregation execute in the RonDB data nodes: DBSPJ, its interplay with DBTC, DBLQH and the NDB API, which query shapes can be pushed, and where the weak spots are. 1. Summary

  • What DBSPJ is. A per-TC-thread block that executes a tree of up to 32 key lookups and ordered-index/table scans (a "pushed join") on behalf of one API query. It does no row reading itself: it turns each parent row into child LQHKEYREQs or range bounds for child SCAN_FRAGREQs, sends them to LDM or query threads anywhere in the cluster, and correlates results with 32-bit correlation ids. Rows for the application go directly from the LDM to the API; only columns needed to drive children come back to DBSPJ.
  • Who decides what. mysqld (ha_ndbcluster_push.cc) or RonSQL decide which tables form a tree and which join semantics apply; the NDB API serializes the tree and assembles joined rows (and finishes outer/semi/anti join semantics, which are only hints to the kernel); DBTC splits the root over fragments and DBSPJ workers; DBSPJ plans the execution order and batches.
  • What can be pushed. Scan or lookup roots; lookup children and ordered-index REF children with exact-type linked keys; inner, outer, semi and anti joins with nest-completeness rules for scan children; sorted results only from the root; committed reads only; no BLOB/TEXT in the select list; no user-defined partitioning; no LIMIT.
  • Join aggregation. RonDB extends SPJ so that an aggregate leaf feeds rows into per-node aggregation state in DBLQH instead of the API, coordinated by DBTC (SETUP / COMPLETE / RELEASE), with outer-join NULL-row injection by DBSPJ, star (multi-leaf) and CTE extensions. From mysqld it is off by default (ndb_join_pushdown_aggregate).
  • Top concerns (section 8): the API merges partial aggregates with operations decoded from data words (E-1); join-aggregation self-continuation never resets child-scan batch accounting and can silently skip child scans (E-2); outer-join aggregation loses or mis-evaluates NULL-extended rows in several cases (E-3, E-4, E-6, E-8); mysqld's join-aggregation pushdown can return wrong results for some shapes (E-9 to E-12); string grouping is not collation-consistent (E-5); and a debugging log line runs for every self-continued batch in production (E-27).

2. Architecture overview

2.1 Where DBSPJ runs

  • One DBSPJ worker per TC thread. DBSPJ is a multi-instance block whose instance count equals the TC worker count, and instance n is mapped onto the same thread as DBTC instance n (with no TC threads, both live in the receive threads). mt.cpp ~7303 (getNumBlockInstances: case DBTC: case DBSPJ: return ndbMtTcWorkers), mt.cpp ~7400 (thread mapping). A DBSPJ worker keeps a pointer to its co-located DBTC (Dbtc *c_tc, Dbspj.hpp) and uses it for the query-thread distribution handle (get_scan_fragreq_ref(&c_tc->m_distribution_handle, ...) in scanFrag_send).
  • DbspjProxy (a DbgdmProxy) only creates the workers and fans out SET_DOMAIN_ID_REQ (location-domain updates) to them. Query signals go straight to workers. DbspjProxy.cpp
  • Which DBSPJ gets a request. The API sends TCKEYREQ/SCAN_TABREQ with the viaSPJ flag to DBTC. DBTC forwards to DBSPJ instead of DBLQH:
    • Lookup-rooted query: to DBSPJ on the node that DIH chose for the root key; the own instance (own thread) when that node is the TC's own node, otherwise a round-robin instance (cspjInstanceRR++ % 120) + 1 that the receiver folds onto its existing instances. DbtcMain.cpp ~5726 (tckeyreq routing)
    • Scan-rooted query: one SCAN_FRAGREQ per worker. Fragment locations are sorted by node and bundled into "MultiFrag" requests (fragId list in a trailing section) so that a worker scans node-local fragments. Without bundling, a scan pruned to a single own-node fragment uses the own instance, otherwise round robin. DbtcMain.cpp ~18340 (sendDihGetNodesLab), ~18890 (sendDihGetNodeReq), ~20690 (sendScanFragReq MultiFrag)
    • How many fragments per worker is decided by the API: unordered non-aggregate scans use rootFragments / #dataNodes (one worker per data node); ordered (merge-sorted) scans, pruned scans and, by default, aggregate scans use one fragment per worker; aggregate scans can opt in to setFragsPerWorker(K) bundling. NdbQueryOperation.cpp ~3760 (NdbQueryImpl::prepareSend)
  • Where the work runs. DBSPJ only plans, routes and correlates. Rows are read by LDM threads (DBLQH/DBTUP/DBTUX) or, for committed reads, by query threads: lookups are addressed to get_query_block_no(node) (the virtual V_QUERY block if the target node has query threads), and local scans are distributed via the TC's distribution handle. SimulatedBlock.hpp ~2313; DbspjMain.cpp ~13890 (scanFrag_send)
  • Replica choice. DBSPJ only does committed reads, so for READ_BACKUP tables it prefers a replica on its own node, then one in its own location domain (simple round robin among them). Fully replicated tables pass anyNode to DIH. User-defined partitioning is not supported (distr_key_indicator = 0). DbspjMain.cpp ~11519 (getNodes), ~11487 (check_own_location_domain)

2.2 From an NdbQueryDef to a tree of TreeNodes

The API serializes the query into the ATTRINFO section of the request: a QueryTree (one QueryNode per operation) followed by QueryParameters (one QueryNodeParameters per operation). Each request (one per worker) is a Request record; each operation becomes a TreeNode.

  • Entry points: execLQHKEYREQ (lookup-rooted, DbspjMain.cpp ~1216) and execSCAN_FRAGREQ (scan-rooted, ~1580). Both allocate a Request from the query-memory arena, call build(), store the request in a hash keyed by (transid, senderData), then prepare() and checkPrepareComplete(). A scan request also unpacks the MultiFrag fragId list and the join-aggregation key section ([nodeId, aggStateKey] pairs, optional query tag, optional CTE key/owner blocks) before the build.
  • build() ~2041 loops over at most NDB_SPJ_MAX_TREE_NODES (= 32, ndb_limits.h:434) nodes, checks that node and parameter op types agree, converts the deprecated QN_SCAN_FRAG_v1/QN_SCAN_INDEX_v1 formats, and dispatches to the node type's m_build. After the loop: validateAggregateFlags(), buildExecPlan(), initRowBuffers().
  • parseDA() ~16082 is shared by all node types. It decodes the DABits (QueryTree.hpp ~96): the parent list (exactly one parent: only trees, no DAGs), key patterns (NI_KEY_LINKED/NI_KEY_PARAMS/NI_KEY_CONSTS), interpreted code (PI_ATTR_INTERPRET scan filter; NI_ATTR_LINKED for parent values used as filter parameters), the user projection (PI_ATTR_LIST) and the linked-attribute projection for children (NI_LINKED_ATTR, always followed by a CORR_FACTOR32 read). Join semantics come from NI_INNER_JOIN, NI_FIRST_MATCH, NI_ANTI_JOIN; aggregation from NI_AGGREGATE/NI_AGGREGATE_LEAF.
  • Linked keys and parameters are kept as patterns (P_COL, P_UNQ_PK, P_PARAM, P_PARAM_HEADER, P_PARENT, P_ATTRINFO, P_DATA, QueryTree.hpp ~607) and are expand()ed against each parent row at run time. Constant keys are expanded once at build time.
  • A node becomes non-leaf when it projects linked attributes (T_LEAF is cleared in parseDA when NI_LINKED_ATTR is present), so leaf-ness is a property of the node's own projection, available already while it is being built.

2.4 Request lifecycle

  1. Build (above). Errors before the request is stored produce an early LQHKEYREF/SCAN_FRAGREF; malformed trees are additionally reported to the data-node security layer (flagMaliciousTreeNode).
  2. Prepare. Every non-root scan node (T_NEED_PREPARE) asks DIH for the table's fragment count and a scan cookie (DIH_SCAN_TAB_REQ, executed directly, answered to itself via a signal to get a real-time break), then allocates one ScanFragHandle per fragment. A const-pruned child resolves its single fragment here. scanFrag_prepare ~12251, execDIH_SCAN_TAB_CONF ~12316
  3. Start the root (and for compound CTE queries, the CTE subtrees whose dependencies are met).
  4. Batches. Every signal sent increments Request::m_outstanding; replies decrement it. When it reaches zero, batchComplete() runs ~3767: it computes the cursor nodes for the next batch (prepareNextBatch), possibly continues internally (sorted root, join aggregation, CTE phase), otherwise sends SCAN_FRAGCONF to DBTC with completedOps = m_rows and an activeMask of nodes that still have rows (sendConf ~4259), then waits (RS_WAITING) for SCAN_NEXTREQ.
  5. Complete / cleanup. When no node is active, an optional complete phase runs (T_NEED_COMPLETE), the final CONF is sent and all TreeNodes, row pages and arena memory are released.

2.5 Distribution over fragments and nodes

  • Root scan: the fragments to scan are given by DBTC in the request (one fragId, or the MultiFrag list). The root is T_ONE_SHOT: its key info (bounds) is used once. scanFrag_build ~11735
  • Child scan: scans all fragments of its table from every worker, unless pruned. A linked prune pattern (SF_PRUNE_LINKED) computes the partition per parent row and only that fragment receives the range; a constant prune key (T_CONST_PRUNE) reduces the scan to one fragment; a single-fragment table is treated as const-pruned. Pruning is dropped for tables with partition hash fanout > 1. parseScanFrag ~12060, scanFrag_parent_row ~12649
  • Lookup child: per parent row DBSPJ computes the hash itself (computeHash, computePartitionHash) and asks DIH for the node (getNodes, DIGETNODESREQ direct). lookup_parent_row ~10007
  • Parallelism. A child scan does not necessarily send to all its fragments at once. scanFrag_parallelism() ~13203 returns all remaining fragments when the API asked for Parallelism_max (SFP_PARALLEL → T_SCAN_PARALLEL), otherwise it is adaptive: it uses a moving average plus two standard deviations of the observed rows-per-key fanout (m_recsPrKeyStat) and record size (m_recSizeStat) to choose how many fragments fit in the remaining batch, with a floor of the root fragment count, rounding to even rounds and raising parallelism if per-fragment batches would exceed MAX_PARALLEL_OP_PER_SCAN_SPJ (4000). Local fragments are sent first. A skew offset (rootFragId * rootFragCnt) % fragCount spreads different workers over different fragment subsets.

3. Execution model

3.1 Lookup nodes

  • Each parent row produces one LQHKEYREQ: a dirty, simple (committed) read, interpreted if the node has a filter or linked parameters. lookup_build ~9087 (setDirtyFlag/setSimpleFlag), lookup_parent_row ~10007, lookup_send ~9359
  • If the key expands to NULL the request is not sent: an equality match is impossible. A lookup-rooted request still emits the TCKEYREF(626) the protocol requires; a scan request simply skips it (outer-joined aggregate leaves inject a NULL row instead, see section 5).
  • Replies: in a lookup-rooted request a leaf replies directly to the API (SPJ "fakes" being TC so LQH can route a REF), and SPJ sends an extra TCKEYCONF naming the node so the API can detect node failure (lookup_sendLeafCONF). In a scan request every lookup replies to DBSPJ.
  • Errors 626 (not found) and 899 (interpreter exit-nok, i.e. the pushed filter rejected the row) are soft: the branch just produces no row. Any other error aborts the whole request. lookup_execLQHKEYREF ~9803
  • A unique-index lookup is two TreeNodes: an index lookup (T_UNIQUE_INDEX_LOOKUP) that projects NDB$PK, then a base-table lookup. The API addresses the table's operation number (index node number + 1) in the active mask. prepareNextBatch ~4180

3.2 Scan nodes (table and ordered-index scans)

  • QN_SCAN_FRAG covers full table scans and ordered index scans (the table id is the index id; RangeScanFlag). Full-table scans are always TUP scans (never ACC) so they can run in query threads. scanFrag_send ~14000
  • All SPJ fragment scans are committed reads without locks; the root SCAN_FRAGREQ is asserted to have lock mode 0, no hold-lock, read-committed (debug asserts only). scanFrag_build ~11745
  • A child scan is always a range scan on an ordered index: each parent row contributes one bound set to the fragment's range list, tagged with the parent's row id in the 12-bit range_no field (scanFrag_fixupBound). The child's batch is only sent when the parent's batch is complete (scanFrag_parent_batch_complete), so one SCAN_FRAGREQ carries a multi-range scan for up to a whole parent batch.
  • Pushed filters and linked filter parameters: if the child has NI_ATTR_LINKED, a parameter section is built per parent row and appended per range; DBLQH/DBTUP selects the parameter set by range number. scanFrag_parent_row (T_ATTRINFO_CONSTRUCTED)
  • For a leaf scan with NI_FIRST_MATCH or NI_ANTI_JOIN, the FirstMatch flag is passed to LQH, which then returns at most one row per range. scanFrag_build ~12018

3.3 Correlation ids

Every row a non-leaf returns carries a 32-bit correlation (CORR_FACTOR32): the parent's row id in the upper 16 bits and the row's own id in the lower 16. Ids are only unique within one batch of one worker.

  • Scan child rows: (range_no << 16) | (corrIdStart + n), where range_no is the parent row id from the bound and corrIdStart is assigned by DBSPJ per SCAN_FRAGREQ (data.m_corrIdStart += bs_rows). DblqhMain.cpp ~26350, ~6635; DbspjMain.cpp ~14060
  • Lookup child rows: (parentCorr << 16) + (parentCorr & 0xffff), i.e. a lookup reuses its parent's id so that a grandchild can be correlated even when the lookup has no projection. lookup_parent_row ~10290
  • The 12-bit bound field limits a parent batch to MaxCorrelationId = 4096 rows (DbspjMain.cpp ~274). scanFrag_getBatchSize caps non-leaf scans by the remaining ids; the API caps the batch rows of any scan that has children at 0x1000 / fragsPerWorker (NdbQueryOperation.cpp ~6076).

3.4 Row buffering

  • Rows are only buffered where the plan needs them: T_BUFFER_ROW (the row), T_BUFFER_MATCH (a TreeNode bitmask of which descendants matched), T_BUFFER_MAP (random access by row id instead of a FIFO list). storeRow lays out [match mask][row header][row or only its correlation]. storeRow ~5598, initRowBuffers ~2868
  • Memory: each TreeNode has a RowBuffer of 32 KB pages taken from the global memory manager (RT_SPJ_DATABUFFER, NDB_ZONE_LE_32) via a block-local free list; releaseGlobal returns pages above the 95th percentile of recent use every 10-100 ms. There is no per-request row-memory quota: a request fails with OutOfRowMemory/OutOfQueryMemory only when global pages run out. allocPage ~5879, releaseGlobal ~5914
  • Requests, TreeNodes, fragment handles and pattern buffers come from an arena allocator in query memory (RT_SPJ_ARENA_BLOCK); per-node arrays and CTE metadata use lc_ndbd_pool_malloc(RG_QUERY_MEMORY).
  • Rows are released per batch in cleanupBatch for all nodes that get new rows in the next batch.

3.5 Execution plans: parallel vs sequential

buildExecPlan() ~2966 derives an execution order (m_next_nodes) from the query topology (m_child_nodes):

  • Lookup-rooted requests and multi-leaf aggregation use planParallelExec: every child starts as soon as its parent row arrives.
  • Scan requests use planSequentialExec ~3128: inner-joined lookups are chained (greedily, possibly before a scan that precedes them in the API's order), then one inner-joined scan branch is appended recursively, then outer-joined branches are started in parallel after the inner sequence. A non-match early in the chain avoids issuing the later operations for that row.
  • When an operation is planned after a node that is not its parent, the parent's rows are buffered (T_BUFFER_MAP|T_BUFFER_ROW) and looked up by correlation id. When an intermediate scan executes between a node and its scan ancestor, the node gets TN_EXEC_WAIT | TN_RESUME_NODE: it is not driven row by row but resumed by resumeBufferedNode after its dependencies complete, iterating the buffered parent rows and skipping those whose required inner-join matches are missing in the scan ancestors' match bitmasks. appendTreeNode ~3270, resumeBufferedNode ~6087
  • Congestion control: a scan with lookup children gets T_CHK_CONGESTION. When the request has 256 or more outstanding signals, parent rows are buffered and their correlation ids queued instead of sending LQHKEYREQs; they are resumed (at most 32 at a time) when outstanding signals drop to 128. DbspjMain.cpp ~298, execTRANSID_AI ~5490, resumeCongestedNode ~6165

3.6 Batching and who drives the next batch

  • The API sets batch_size_rows/batch_size_bytes per scan operation (root: per worker; children: getMaxBatchRows() * fragsPerWorker). Lookups inherit the batch size of their closest scan ancestor. NdbQueryOperation.cpp ~6007 (calculateBatchedRows), ~6315 (QN_SCAN_FRAG params)
  • DBSPJ splits a node's remaining batch budget over the fragments it scans in parallel (bs_rows = availableBatchRows / parallelism, capped at 4000) and keeps sending to not-yet-started fragments while budget remains (m_batch_chunks). When a MultiFrag request carries more fragments than the API planned for, the batch is not enlarged; it is divided over more fragments. scanFrag_send ~13331; DbtcMain.cpp ~20700
  • A batch ends when m_outstanding reaches zero. DBSPJ then reports SCAN_FRAGCONF with activeMask. DBTC forwards the result as SCAN_TABCONF; the API consumes the rows and sends SCAN_NEXTREQ, which DBSPJ applies to the cursor nodes chosen by prepareNextBatch: the deepest active scans, and (with RT_REPEAT_SCAN_RESULT) only the last active one. batchComplete ~3767, prepareNextBatch ~4100, execSCAN_NEXTREQ ~5134
  • Exceptions where DBSPJ continues by itself without an API round trip: the sorted root (below), join aggregation when no row was produced for the API (handleJoinAggNextBatch, which sends SCAN_HBREP to DBTC at most every 20 ms to keep the scan timers alive), and CTE materialization phases (handleCtePhaseNextBatch). ~3957, ~3998, ~4058
  • Row counting: completedOps counts only rows the API will receive through its per-operation receivers (nodes with a user projection), so the API can tell when all TRANSID_AI of a batch have arrived. Aggregate scan leaves always report 0 from DBLQH; aggregate lookup leaves report their evicted groups in LQHKEYCONF.readLen (see E-14). scanFrag_execSCAN_FRAGCONF ~14360, lookup_execLQHKEYCONF ~9969

3.7 Bushy scans and NI_REPEAT_SCAN_RESULT

Two sibling scans under one parent (a "bushy" or X-scan) produce a cross product per parent row. With NI_REPEAT_SCAN_RESULT set by the API, only one active scan is advanced per batch; the other scans that are not ancestors of it are marked T_SCAN_REPEATABLE, keep their range keys, and are re-executed (scanFrag_parent_batch_repeat) so that the API never has to buffer more than the current batch. Without it, all active scans advance together and the API must buffer and iterate the cross product itself. scanFrag_build ~11710, prepareNextBatch ~4113, scanFrag_parent_batch_repeat ~14083

Repeated scans re-read data from LDM: for a parent row with m rows in scan A and n in scan B where B needs k batches, A's result for that parent batch is fetched up to k times.

3.8 Sorted (ordered index) root

Only the root can return rows in index order (SFP_SORTED_ORDER → T_SORTED_ORDER; the API asserts it is the root). Ordered queries always use one fragment per worker, and the API merge-sorts the per-worker streams. If the query also has scan children (RT_MULTI_SCAN), DBSPJ fetches one root row per round (batch_size_rows = 1, parallelism 1) so that child rows of later root rows cannot be interleaved out of order; as an optimization batchComplete immediately fetches the next root row while estmMaxKeys() predicts that the children's results still fit in the batch. parseScanFrag ~12210, scanFrag_send ~13520, batchComplete ~3880

3.10 Filters and conditions

  • A per-operation scan filter is interpreted code in the parameter section (PI_ATTR_INTERPRET); it runs in DBTUP before the projection and sends nothing for rejected rows (lookups: soft error 899).
  • Conditions that compare against an ancestor's column are pushed as a filter whose parameters come from the parent row (NI_ATTR_LINKED + pattern of P_ATTRINFO entries expanded per parent row into the interpreter's subroutine/parameter area). lookup_parent_row ~10150 (layout comment), scanFrag_parent_row
  • NI_ATTR_INTERPRET (a program in the tree part) is supported by the parser but, per the code comment, "seems to never have been used, nor tested"; attribute parameter patterns without NI_ATTR_LINKED and subroutines in PI_ATTR_INTERPRET are guarded by ndbassert(false) "never been tested". parseDA ~16408, ~16478, ~16545

3.11 Where results flow

  • The user projection of each operation (PI_ATTR_LIST) is read first and flushed by FLUSH_AI straight from the LDM/query thread to the API receiver; linked attributes plus the correlation are read next and sent to DBSPJ. For scan requests a FLUSH_AI is always inserted so that the route reference is TC (for TRANSID_AI_R). parseDA ~16590
  • DBSPJ itself never forwards row data to the API (except cached CTE rows). This is why the API, not DBSPJ, must assemble the joined rows from per-operation result streams by correlation id.
  • In aggregating requests only the aggregate leaf sends results; user projections of other nodes are suppressed (suppressFlushAI). parseDA ~16560

3.12 Errors, aborts and node failures

  • abort() marks the request RS_ABORTING, calls each node's m_abort (closing open fragment scans) and lets outstanding replies drain; the final reply is a SCAN_FRAGREF/TCKEYREF with the first error.
  • NODE_FAILREP walks all requests in real-time slices; a request that depends on a failed node, or whose requesting TC died (RT_REQUESTER_FAILED), is aborted with NodeFailure. A waiting request whose TC is alive is left as an RS_ABORTED tombstone until its SCAN_NEXTREQ arrives. execNODE_FAILREP ~1003, nodeFail_checkRequests ~1090, nodeFail ~4608
  • Schema changes: each node checks its table's schema version (checkTableError) before sending; a dropped or altered table aborts the query.
E-19 (medium-high on the code; needs a non-standard client): the build path still has crash or overflow points on request data that the data-node security work otherwise validates: ndbabort() on a constant key or constant prune key containing NULL (parseDA ~16308, parseScanFrag ~12158) and on a child scan with a fixed key (scanFrag_parent_row ~12915); expand() copies a P_DATA block of up to 0xFFFF words without checking it against the pattern end, and checks P_PARAM indexes only with ndbassert (~15925-15970); computeHash copies the key into tmp32[MAX_KEY_SIZE_IN_WORDS] with only an ndbassert on its size (~11380). On the DBTC side, parseJoinAggKeyInfo uses ndbrequire on API-supplied lengths (~30914, ~31060). The standard NDB API never produces these (it rejects NULL keys with 4316).
E-20 (low-medium): a CTE query whose main root is a lookup computes the root's hash and node in lookup_start with ndbrequire(err == 0) after computeHash and getNodes (~9337, ~9339). Both can fail on ordinary data or DIH errors (e.g. a key that cannot be transformed in its collation, error 290); lookup_parent_row handles the same errors with abort().

4.3 mysqld pushability rules

Most of the logic is in ndb_pushed_builder_ctx (storage/ndb/plugin/ha_ndbcluster_push.cc) and the AccessPath/join-nest model in ha_query_plan.cc. JOIN::push_to_engines() calls ndbcluster_push_to_engine() (ha_ndbcluster.cc ~15724), which, if ndb_join_pushdown is ON (default), runs make_pushed_join() (push.cc ~646): every table is tried as a root in plan order; for each, candidate children are accepted (is_pushable_with_root, accept_query_plan), the parent of each child is chosen as the earliest valid ancestor to get a bushy tree (optimize_query_plan), and the NdbQueryDef is built (build_query). Then join aggregation, then single-table aggregation are considered, then conditions of non-children are prepared, and fixup_pushed_access_paths() rewrites the plan.

  • Root access types: PK or unique-key lookup (EQ_REF, also REF on a unique hash index), ordered-index REF/INDEX_SCAN (bound supplied at run time with setBound, ordering with setOrdering when the plan uses index order), table scan, and MRR/range: a range on an ordered index is a multi-range scanIndex with one bound per range; a range on a PK/unique hash key is a lookup root driven per key. A root needs at least one pushed child.
  • Child access types: PK/unique lookups and ordered-index REF (equality on a key prefix). Range, MRR, index-merge, full scans and INDEX_SCAN children are refused. Dynamic range and REF_OR_NULL are never pushed (undecided at prepare time).
  • Key values: constants (copied with save_in_field; NULL constants are not pushed), columns of pushed ancestors (linkedValue, possibly a grandparent, Item_equal substitution to find a common parent), and columns of tables before the root in the same scope (paramValue, scan roots only, at most 16; a NULL value cancels the push at execution with Warning 1296). Linked columns must have identical definitions (Field::eq_def) and must not be virtual generated columns.
  • Plan scopes: the pushed join must lie in one Query_scope. BKA inner (MRR), hash-join build sides, non-inner hash probes, SORT (filesort), and the separate query blocks for aggregation, materialization, weedout, window functions etc. split scopes. Upper scopes can only supply parameters.
  • Outer, semi and anti joins: lookups have no extra restrictions. An outer- or anti-joined scan child requires that every table in the embedding nests (below the root's nest) is pushed, has no remainder condition, and that no FILTER sits between the table and the root (is_pushable_within_nest, is_pushable_as_child_scan, validate_join_nest). Semi-joined tables get MatchFirst; semi-join scan children need the whole semi-join nest pushed; scans outside the nest may not depend on skip-read semi-join tables. Outer-joined tables get setFirstInnerJoin/setUpperJoin nest hints.
  • Conditions: a child's condition is prepared with const tables (scan roots only) and pushed ancestors as parameters (Ndb_param → cmp_param, at most 16 parameters); each referenced parent becomes a forced ancestor. A remainder condition stays in a FILTER and restricts outer/semi scan children. The root's own condition is prepared after the join is built. Interpreted code is generated at execution; for lookup children code of 64 words or more is not attached and mysqld evaluates it instead (ha_ndbcluster.cc ~15986).
  • Table and statement restrictions: only LM_CommittedRead (no FOR UPDATE, FOR SHARE, LOCK IN SHARE MODE, no UPDATE/DELETE targets), no BLOB/TEXT in the read set, no user-defined partitioning (ha_ndbcluster.cc ~15854). No checks for fully replicated, READ_BACKUP, triggers, foreign keys or hidden PK. HA_EXTRA_KEYREAD disables push at execution.
  • Limits and switches: 32 SPJ operations (unique lookups count 2); 16 pre-root key fields; 16 condition parameters; ndb_join_pushdown (ON), ndb_join_pushdown_aggregate (OFF), ndb_join_pushdown_aggregate_outer_join (OFF), ndb_pushdown_aggregate (single table, OFF). LIMIT is never pushed (LIMIT 1 is modelled as a semi-join nest); ORDER BY is pushed only as a sorted root.

4.5 Query shapes from RonSQL

RDRS does not build NdbQuery trees itself; RonSQL (storage/ndb/src/ronsql/RonSQLPreparer.cpp) does. Only joins and queries reading a CTE go through DBSPJ (execute_join); single-table aggregates, COUNT(*) shortcuts, PK IN-list aggregates and single-table pass-through use plain NDB scans or key reads.

  • CTE subtrees first, each with a body root (table scan or index scan with the aggregator attached, scalar MIN/MAX as an ordered scan with setMaxRows(1) plus a self-join leaf, scanCte for chained CTEs, or a multi-operation body), then defineCte().
  • Main root: scanCte, lookupCte (all virtual PK columns bound), an index scan (IN lists become a multi-range scanIndex), readTuple for full-PK roots without scan children, a PK-equality ordered index scan when there are scan children, or a filtered table scan; setFragsPerWorker from a hint.
  • Children: readTuple (PK/unique), scanIndex with linked equality bounds and constant or linked range bounds, lookupCte, scanCte; INNER → MatchNonNull, LEFT → MatchAll, SEMI → MatchNonNull|MatchFirst, ANTI → MatchNullOnly. LEFT joins whose inner side is later referenced by a null-rejecting INNER join are promoted to INNER (promote_left_joins()).
  • RonSQL never asks for a sorted root in joins; ORDER BY and LIMIT on join results are done in RonSQL. Limits: 32 operations, 8 join-key columns.
E-29 (high on mechanism, performance): the NDB API only checks a root scan for pruning when its bound is supplied with NdbQuery::setBound() at execution (m_prunability starts as Prune_No, NdbQueryOperation.cpp ~2781, ~2965, isPrunable ~5170). RonSQL and CTE roots put their bounds in the definition, so e.g. a PK-equality root scan with scan children is sent to all fragments.

5.2 Main (non-CTE) aggregation, signal by signal

  1. SCAN_TABREQ with the JoinAgg flag; KEYINFO = [boundsLen, bounds, aggReceiverId, program(s), CTE block, column meta].
  2. After DIH fragment locations are known, DBTC sends JOIN_AGG_SETUP_REQ to every connected node in c_alive_nodes plus its own node (independent of fragment placement) and starts the fragment scans without waiting for SETUP_CONF (RONDB-1120 P2c). sendDihGetNodesLab ~18498, sendJoinAggSetupReqs ~31495

E-1 (high on the mechanism, medium-high end to end): NdbAggregator::initForResults (NdbAggregator.cpp ~239-252), which builds the API-side merger, decodes every program word as an instruction, including the data words of LoadConst/LoadDouble, DECIMAL metadata and embedded CASE bodies. A data word whose top 6 bits happen to equal an aggregate opcode overwrites agg_ops_[slot], and the merge then uses the wrong function (e.g. MAX partials summed across nodes, COUNT over empty input returned as NULL). The multi-leaf combiner (NdbQueryOperation.cpp ~4340) has the same flaw.
E-24 (high on the code, low-medium likelihood): API-side robustness of the aggregate path. execAggTRANSID_AI (NdbQueryOperation.cpp ~2323) records the row offset before allocating, and on allocation failure neither counts the row nor sets an error, so the query waits until the 4008 timeout; all groups are buffered without a limit until end of data. prepareAggregation (~4246) allocates m_aggReceivers without initializing it, and a partial getNdbScanRec() failure leaves garbage entries that postFetchRelease (~2854) releases.
E-27 (high): handleJoinAggNextBatch (DbspjMain.cpp ~4000) calls g_eventLogger->info("AGGT(%u) SPJ agg self-continue ...") unconditionally, marked "TEMPORARY fs_batch phase-timing probe", although the AGGT macro that should wrap it is disabled. E-28 (medium-high): continueJoinAggSend (DblqhMain.cpp ~21178) compares the cumulative number of groups sent with m_max_batch_rows (256), so after the first 256 groups every further group costs a JOIN_AGG_SEND_REQ/CONF round trip with DBTC, which always grants 256 more.

5.3 DBSPJ's part in detail

  • Validation (validateAggregateFlags ~2554): all main-query nodes carry NI_AGGREGATE; at least one NI_AGGREGATE_LEAF; every aggregate leaf is a tree leaf; several leaves must share one parent; ancestors of leaves get T_AGGREGATE_ANCESTOR. Outer-joined ancestors and outer-joined scan leaves switch on row/match buffering in their scan ancestor (RT_AGG_ANCESTOR_MATCH).
  • Projections: non-leaf nodes have their user projection and FLUSH_AI suppressed, so their rows only reach DBSPJ (linked columns) and are not counted in m_rows.
  • Execution plan: single-leaf trees use the sequential plan; multi-leaf (star) trees use the parallel plan.
  • Outer joins (switch ndb_join_pushdown_aggregate_outer_join in mysqld):
    • Lookup leaf, key not found: DBLQH itself aggregates a NULL-extended row (handleOuterJoinAggKeyNotFound, DblqhMain.cpp ~16615) and answers CONF.
    • NULL join key: DBSPJ sends JOIN_AGG_NULL_ROW_REQ with the parent's linked columns to a local LDM instance (sendJoinAggNullRow).
    • Scan leaf: the LQH scan sets a bit per matched range; the bitmask comes back on the closing SCAN_FRAGCONF, DBSPJ ORs it over fragments (mergeAggMatchBitmask) and, when the leaf scan completes, sends NULL rows for parent rows whose range never matched (handleAggLeafScanComplete ~10555, using m_agg_range_corrs to map range numbers back to parent rows).
    • Outer-joined intermediate node without a match: the scan ancestor's match bitmask identifies the parent rows, and propagateNullToAggLeaf walks down to the leaf, NULL-ing every node in between (handleAggAncestorComplete ~10817, handleScanAggAncestorComplete ~10764).
E-2 (medium): when DBSPJ continues a join aggregation by itself (handleJoinAggNextBatch, also used for CTE phases), it calls cleanupBatch(requestPtr, done=false) (~4004). With done=false, scanFrag_parent_batch_cleanup (~15102) does not reset a child scan's m_corrIdStart, m_totalRows and m_totalBytes; those are reset only when the child itself gets a NEXTREQ or after a CONF to the API. For a non-leaf child scan (scan → scan → leaf) that completes within each root batch, the budget in scanFrag_getBatchSize therefore shrinks with every self-continued root batch. When it reaches 0 (byte budget below one estimated row, or the 4096 correlation ids used up), scanFrag_send returns without sending ("No batch buffer left", ~13378) and without activating the node: that parent batch's child rows are never aggregated (release builds), and the next scanFrag_parent_batch_complete hits ndbassert(m_frags_complete == m_fragCount) (~13080, debug builds). Upstream uses done=false only in the sorted-root path, guarded by estmMaxKeys().
E-3 (medium-high): handleAggAncestorComplete defers NULL injection for an outer-joined lookup ancestor until its scan ancestor has completed all fragments (~10860), but cleanupBatch releases the buffered root rows of every earlier root batch. Unmatched intermediate parents from earlier batches never get their NULL row, so COUNT(*) over a 3-table LEFT JOIN chain undercounts once the root needs several batches. Two cases in ndb_push_agg_dist/t/ndb_push_agg_dist_extended.test (~233, ~348) are disabled with "COUNT(*) mismatch when inner JOIN + LEFT JOIN are pushed together".
E-4 (high on the code): for a NULL-extended row, JoinAggInterpreter::ProcessRec skips kOpEmbeddedInterp (the CASE condition) and falls into the THEN arm (JoinAggInterpreter.cpp ~1273). SUM(CASE WHEN oj2.v > 5 THEN 1 ELSE 0 END) or COUNT(CASE ...) over a LEFT JOIN counts every unmatched row as 1; conditions on parent (linked) columns are also ignored for those rows.
E-6 (medium): for an outer-joined lookup leaf, only "key not found" (626) produces a NULL row in DBLQH. If the row exists but the pushed ON-condition filter rejects it, DBLQH answers LQHKEYREF(899), which DBSPJ treats as a soft error and ignores (lookup_execLQHKEYREF ~9830); handleAggAncestorComplete only handles ancestors, not leaves. The parent row then contributes nothing, e.g. COUNT(*) ... t1 LEFT JOIN t2 ON t2.pk = t1.a AND t2.c > 5 undercounts. Scan leaves are not affected (filtered rows do not set the match bit).
E-7 (high on the code, medium impact): processNullExtendedRow runs without a leaf index (JoinAggInterpreter.cpp ~2157; called from DblqhMain.cpp ~16675 and ~20691), and JOIN_AGG_NULL_ROW_REQ carries leaf 0, so in a multi-leaf query the NULL row is processed by whichever leaf program was installed last. RonSQL's LEFT OUTER multi-leaf subqueries reach this.
E-8 (medium): join-nest structure is not sent to the kernel (only NI_INNER_JOIN per node), so t1 LEFT JOIN (t2 JOIN t3 ...) and (t1 LEFT JOIN t2) JOIN t3 look the same to DBSPJ. NULL injection is then inconsistent: propagateNullToAggLeaf stops at an inner-joined intermediate node (~10465) but injects into an inner-joined leaf. Each behaviour is right for one of the two SQL readings and wrong for the other. RonSQL now promotes LEFT→INNER where the INNER condition is null-rejecting (promote_left_joins()), and the analysis in join_nest_semantics_plan.md notes the leaf-position dependence; mysqld genuine nests are not restricted.
E-13 (low-medium): in a star (multi-leaf) query with two scan leaves, every non-root scan has NI_REPEAT_SCAN_RESULT, so a scan leaf that needed several rounds is re-registered for repetition (scanFrag_parent_batch_repeat ~14083). handleJoinAggNextBatch skips non-active cursor nodes, but if the batch also produced evicted groups (m_rows > 0), the API-driven execSCAN_NEXTREQ restarts the repeated leaf (~5245) and feeds the same rows into the aggregation a second time.
E-18 (high that it crashes, low likelihood): DBTC snapshots the SETUP node set once per query; DBSPJ resolves nodes lazily for every lookup and child-scan fragment. A node included (INCL_NODEREQ) after the snapshot that becomes readable while a long aggregate query runs can be chosen by getNodes (READ_BACKUP/location domain or primary), and ndbrequire(m_aggNodes.get(nodeId)) in lookup_send (~9484) or scanFrag_send (~13830) stops the data node. CTE feeds instead park and fail with 1274.

5.4 DBTC state machine

  • ScanRecord::scanState (Dbtc.hpp ~2064): WAIT_JOIN_AGG_SETUP (briefly, while SETUPs are sent) → RUNNING (fragment scans, and the whole CTE stage) → WAIT_JOIN_AGG_COMPLETE → CLOSING_SCAN with fire-and-forget RELEASE on success, or WAIT_JOIN_AGG_RELEASE → abortScanLab on failure. WAIT_CTE_COMPLETE is retired.
  • Sub-machines: m_aggSetupState (NOT_STARTED → IN_FLIGHT → DONE | CANCELLED) and one AggCompleteRecord per COMPLETE round (main and each CTE): IDLE → WAIT_COMPLETE → COMPLETE | FAILED. Stale and duplicate CONFs are dropped by record validity, state and a per-node pending bit.
  • Data-node failure: handleJoinAggNodeFailure (~31388) fakes the missing SETUP_REF/COMPLETE_REF/RELEASE_CONF and fails the query with 286. Nothing is retried, so partial aggregates are never fed twice. TC failure: DBDIH sends JOIN_AGG_NODE_FAIL_REP to the local DblqhProxy, which releases states coordinated by the dead TC. API failure: the close is deferred until outstanding replies drain.
  • Timers: fragment timers are kept alive by SCAN_HBREP from DBLQH and DBSPJ; there is no DBTC timer for the main COMPLETE or a waited RELEASE, and ZJOIN_AGG_TIMEOUT (1257) is never raised.
  • Error codes the API can see: 286 node failure; 270 close during an aggregation wait; 274 fragment timeout; 217 query memory/section allocation; 218 no SETUP sent; 290 malformed KEYINFO; 1270 CTE main scan got a mid-fragment batch; 1274/1275 park timeout / park pool exhausted (temporary); DBLQH 1250-1275 and DBTUP 1860-1872 (1860 overflow, 1861 unsupported type, 1864 DECIMAL precision, 1870 out of aggregation memory, temporary).

5.5 Group routing and CTE owner lists

  • Main aggregation: no routing between nodes. Every node aggregates the leaf rows it executes into one state; DBTC gives exactly one API receiver, so all partial groups are merged in one API thread.
  • CTEs: DBTC's SETUP node set (ascending node ids) is the owner list, sent in every SETUP and in DBSPJ's aggKeys section. Groups are redistributed to owner = list[hash % count] (GBHashTable::hashKeyFull: collation-aware via strnxfrm, NULL hashes to a sentinel and equals NULL); DBSPJ's cte_lookup_send uses the same formula to route a CTE_LOOKUP_REQ (~7147). Scalar, single-row, LIMIT and single-group CTEs use the DBTC node as constant owner. A CTE_SCAN maps virtual fragment K to the K-th owner.
  • Any node failure since SETUP aborts a CTE query (conservative: also unrelated failures); cte_lookup_send aborts if a node in its topology died.
E-23 (medium): the redistribution receiver requires keyWords <= 1023 with ndbrequire (DblqhMain.cpp ~24721, ~24805) but the sender does not check, so a CTE grouped on a very wide key in a multi-node cluster can stop the receiving node.
E-5 (medium-high): grouping by strings is not collation-consistent. The API merger compares group keys as raw bytes on the join path (gb_cmp_ is only set in NdbAggregator::Finalize, not in initForResults), while each node stores the first-seen raw key of a collation-equal group, so 'abc' on one node and 'ABC' on another become two output rows. In the kernel, GBHashTable::findInBucket (AggHashTable.hpp ~763) requires equal key byte length before the collation compare, so 'a'/'á' or PAD SPACE variants become separate groups even on one node.

5.6 CTEs (compound queries) inside DBSPJ

A compound query carries CTE subtrees before the main tree. QN_CTE_SUBTREE is a container that announces how many of the following nodes belong to CTE c; those nodes get m_cteId = c, and the subtree's root scan (or CTE reader) is marked T_CTE_SCAN and feeds the CTE's aggregation state instead of the API. QN_CTE_LOOKUP probes a materialized CTE by group key (point lookup routed to the owner node); QN_CTE_SCAN scans all groups of a materialized CTE from DBLQH. Each CTE has a CteContext (NOT_STARTED → MATERIALIZING → LOCAL_DONE → READY, or FAILED) and a dependency mask; a DAG scheduler in DBTC broadcasts CTE_PHASE_START_REQ per ready CTE and finally CTE_START_MAIN_REQ. Single-row CTEs have a per-request probe cache (miss or full row) in DBSPJ. cte_subtree_build ~7860, cte_lookup_send ~6918, cte_scan_start ~8265, execCTE_PHASE_START_REQ ~8916, execCTE_START_MAIN_REQ ~9004; Dbspj.hpp CteContext

E-17 (high on the accounting, low likelihood without error inserts): DBTC counts expected CTE reports per SCAN_FRAGREQ sent (registerCteScanFragHandle ~20438), but sendFragScansLab may pause with CONTINUEB after more than 4 local sends. If all early workers report a CTE before the rest are sent, execCTE_PHASE_COMPLETE_REP (~32968) starts redistribution on partial data.

5.7 Memory and eviction

  • All aggregation memory comes from RG_QUERY_MEMORY (programs, per-thread interpreters, 32 KB group chunks, string MIN/MAX buffers, redistribution pages). There is no spill to disk.
  • State records: a per-node pool of JoinAggStatePoolSize (default 256, range 1-4096); exhaustion gives SETUP_REF 20008. Identity hash and park pool: 16384 entries each (1275 when exhausted).
  • Budget: initial max(available/100, 4) pages split over threads, growing in steps up to all pages available at SETUP, per interpreter. There is no per-query or node-wide cap.
  • At the limit: main aggregation evicts a group early to the API as a partial row (JoinAggInterpreter::evictOneGroup, picks the chunk with fewest live groups among the 10 newest) and continues; the API merges evicted partials with later ones. CTE mode fails with 1870.
E-21 (medium-high): one large GROUP BY can take all free query memory (no cap), and AggInterpreterBase::initChunkAllocator (~1893) computes available_pages * 32768 in 32 bits, which wraps at 4 GiB of free query memory and can give spurious evictions or 1870.
E-14 (medium): eviction accounting. For lookup leaves DBSPJ adds the eviction count from LQHKEYCONF.readLen to m_rows (lookup_execLQHKEYCONF ~9982), which disables self-continuation and sends a mid-fragment SCAN_FRAGCONF whose completedOps the API adds to the worker receiver's outstanding count, while the rows went to the aggregate receiver (and are counted again in numResultRows); expected symptom a stall or 4117, and 1270 for CTE main scans. Separately, Dblqh::sendEvictedAggGroup (~16603) increments the shared m_rows_sent without atomics from any LDM/query thread.
E-22 (medium): the 10 ms park deadline (joinAggParkSweep) turns a SETUP that is processed late on a busy node into temporary error 1274; RonSQL retries, but mysqld returns the error to the client.

5.9 What mysqld pushes, and fallback

  • Attempted after a pushed join was built, if ndb_join_pushdown_aggregate is ON, the output order is not taken from index order, and no unpushable FILTER is found (ndb_has_unpushable_filter_for_aggregate). ndb_push_aggregation (ha_ndbcluster_push_agg.cc ~1580) then requires every table of the query block in the one pushed join, supported aggregates, plain GROUP BY fields, no semi/anti join, outer joins only with ndb_join_pushdown_aggregate_outer_join, and no table with a remainder condition.
  • It builds the NdbAggregator program, forces a chain by re-parenting each table to the previous one (~1664), rebuilds the query, rejects it if any operation still has more than one child, and replaces the pushed join. fixup_pushed_access_paths removes the AGGREGATE path (or keeps TEMPTABLE_AGGREGATE) and the NLJs to pushed children.   • Single-table aggregation (ndb_pushdown_aggregate) is a separate path through NdbScanOperation aggregation, not DBSPJ.
  • Fallback only happens at plan time. There is no runtime retry without pushdown; errors while draining the aggregate become HA_ERR_INTERNAL_ERROR (ndb_init_aggregate_results ~1870), even though draining finishes before the first row is returned.
E-9 (medium-high): the forced chain re-parents a table under the previous table even when that table is outer-joined and unrelated. 6. Performance characteristics and known limitations

6.1 What pushing saves

  • Round trips. Without pushdown a join over n tables costs at least one API-to-data-node round trip per table per batch (with BKA/MRR) or per row (nested loop with eq_ref). A pushed join costs one round trip per batch of the whole tree; the per-row child operations are issued inside the cluster, mostly node-locally (READ_BACKUP and location-domain preference, local fragments first).
  • Data not shipped. Linked columns travel LDM → DBSPJ only; rows eliminated by pushed filters never leave the LDM; inner-join sequencing avoids issuing operations for rows that already failed an inner match. With join aggregation the API receives groups instead of joined rows.
  • CPU placement. Committed reads run in query threads when available, spreading lookups over more cores than the owning LDM thread.

6.3 Per-request memory

  • Fixed: a Request plus up to 32 TreeNodes (each with a m_scanFragReq copy, bitmasks, pattern heads) and one ScanFragHandle per fragment per scan node, all from the query-memory arena. A child scan over a table with F fragments allocates F handles in every worker.
  • Variable: range-key sections per fragment (one bound per parent row), constructed attrinfo per parent row (linked filter parameters), buffered rows, deferred correlation lists, and for aggregation the match bitmasks (m_agg_range_corrs: 4096 words per outer-joined aggregate leaf) and CTE metadata (3 × MAX_NDB_NODES words per CTE).
  • Exhaustion produces OutOfQueryMemory, OutOfRowMemory or OutOfSectionMemory (DbspjErr), which aborts the query (error-insert tests 17001-17122 exercise these paths).

6.4 Worst-case shapes

  • Unpruned scan child of a scan root over many fragments with low selectivity per key: W×F fragment scans per batch, mostly empty.
  • Two or more bushy scan children with large fan-out per parent row: repeated re-reads.
  • ORDER BY via index on the root with scan children: one root row per internal round.
  • Deep chains of outer-joined scans: every outer branch waits for the inner sequence and buffers parent rows with match bitmasks.
  • Join aggregation with an outer-joined scan leaf under a multi-fragment root: per-batch match bitmasks merged across fragments, plus JOIN_AGG_NULL_ROW_REQ per unmatched parent row.
