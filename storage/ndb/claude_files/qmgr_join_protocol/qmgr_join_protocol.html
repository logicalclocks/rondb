Phase 1 · Register

A starting node asks every data node it is connected to

In QMGR start phase 1 the starting node sends CM_REGREQ to every data node it has a transporter connection to, and again every 3 seconds until the president accepts it with CM_REGCONF.

In a cluster start there is no president yet. The nodes elect one in check_startup: among the nodes that can restore the newest GCI, the lowest node id wins. The election waits up to StartPartialTimeout for missing nodes.

The president includes one node at a time. While it is including one, it refuses all others.

New: each round of the 3 s loop takes a new start key, so a timer left over from an earlier round cannot start a second loop after an aborted inclusion restarts it.

AnswerSent byMeans
CM_REGCONFPresidentAccepted: carries the president, a dynamic id and the cluster members
ZELECTIONNode without a presidentAn election is going on
ZNOT_PRESIDENTMemberAsk the president
ZBUSY_PRESIDENTPresidentBusy including another node, try again
ZBUSYPresidentYour inclusion was aborted, ask again when 6 s have passed

All answers other than CM_REGCONF are CM_REGREF with that cause.

Before the patches

One missing link stopped every start

  • The president waited with no time limit, and nothing was logged.
  • The timer meant for this case was dead code, after a return:
  /**
   * Set timer
   */
  return;
  signal->theData[0] = ZREGREQ_MASTER_TIMELIMIT;
  signal->theData[1] = c_start.m_startKey;
  sendSignalWithDelay(QMGR_REF, GSN_CONTINUEB,
                      signal, 30000, 2);
  • It would not have helped as written. It fails the starting node, and a node that has not started exits when another data node fails or disconnects. In a cluster start every starting node then exits with error 2308, and the next start stalls the same way.

New · The decision

After 10 seconds the president always aborts

Every member and X support CM_ADD(Abort)?
26.02.13 and later 26.02 releases, 26.10.0 and later. An older node would keep X half included.

System restart
It goes on if the other nodes can restore all data, NDBCNTR checks node groups and GCI. Else it completes once X or another node of its node group joins. X asks once more.

abort

Initial start
The start keeps waiting for X unless it is in --nowait-nodes, so the cluster is not created without it.

abort

A node that cannot connect to every member cannot take part in the start. Waiting for it only keeps out the starting nodes that can.

  • After the abort the president answers the node's CM_REGREQ with ZBUSY for 6 s, then tries it again. The other starting nodes get in first.
  • The refusal ends after 6 s, also during a cluster start. A start that needs the node, say nodes 5 and 6 of one node group that cannot reach member 4, would otherwise never complete, even once the links are up.
  • The president logs what the abort means: other nodes join, the cluster start goes on, or it cannot complete and why.

New · What the aborted node does

A cluster start asks once more, a node restart exits at once

Cluster start, first abort
X forgets the members and asks again: links that were not up yet get a second chance.

ask again

Cluster start, second abort
Retrying for ever in the same process would not help a node that cannot reach a member, a new process sets up its links from scratch.

exit

Node restart, first abort
CM_ADD(Abort) carries startingNodeExits: the cluster runs without X, its node restart fails.

exit

X exits with error 6054, Connection setup failed. With StopOnError=0 its angel allocates the node id again and starts it, with the default StopOnError=1 it stays down.

No restart waits for a stalled inclusion

System restart ndb.ndb_sr_unreachable_node

  1. 0 s

    Node 1 wins the election and includes nodes one at a time

  2. 0 s

    Node X cannot reach a member, its prepare stalls

  3. 10 s

    Abort: X is left out, QMGR phase 1 completes

  4. 10 s + restart

    The other three nodes finish the system restart

  5. 16 to 26 s

    X asks once more, is aborted again and exits

  6. link up

    X is included and joins in a node restart

System restart, a node group cut off ndb.ndb_sr_unreachable_node_group

  1. 0 s

    Node 4 is included before nodes 5 and 6

  2. 0 s

    Nodes 5 and 6 cannot reach node 4

  3. 10, 20 s

    Both are aborted, node group {5,6} is empty

  4. 20 s

    NDBCNTR waits, the restart cannot complete

  5. from 26 s

    5 and 6 exit at the second abort, their angels get the node ids after 20 s

  6. link up

    5 and 6 are included, the system restart completes

Node restart ndb.ndb_nr_unreachable_node

  1. 0 s

    Node 4 cannot reach node 3, its prepare stalls

  2. 0 to 10 s

    Node 2 restarts and gets ZBUSY_PRESIDENT

  3. 10 s

    Abort, node 4 exits, node 2 is included

  4. 10 s on

    Node 2 restarts, the angel starts node 4

  5. each start

    Node 4 exits while the link is missing

  6. link up

    Node 4 is included and joins
