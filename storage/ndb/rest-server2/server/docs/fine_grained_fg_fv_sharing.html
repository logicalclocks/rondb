Fine-Grained Feature Group / Feature Sharing in Hopsworks

The two access-control systems — cross-project sharing (shared_feature_store / shared_feature_group / shared_feature) and in-project restricted access (restricted_feature_group_access / restricted_feature_access) — their table semantics, grant lifecycle, per-backend enforcement, and the recursive feature-view checks.

Purpose of this document This is a study of how the feature is built in Hopsworks, produced before porting the equivalent enforcement to the RonDB REST server (RDRS2). It is descriptive, not a design for RDRS2 — that comes next. 1. Overview — two independent systems

Hopsworks has two orthogonal fine-grained access mechanisms that are easy to conflate because both can limit access down to individual features (columns) of a feature group:

Cross-project sharingIn-project restricted access
Tablesshared_feature_store, shared_feature_group, shared_featurerestricted_feature_group_access, restricted_feature_access
Granteea project (shared_with_project)a user (granted_to_user)
Semanticsadditive grant on top of normal project membershipallow-list for members who otherwise see nothing
TriggerData Owner shares FS / FG / columns with another projectmember holds project role FEATURE_STORE_RESTRICTED (“Feature store restricted”)
JIRA / migrationFSTORE-1905, V45__..._column_level_permissions.sqlFSTORE-1940, V46__..._restricted_feature_access.sql
Core commitc0957d9d5b (18-Dec-2025)c43ca1153b (14-Jan-2026)
Owning controllersShareFeatureStoreController, ShareFeatureGroupControllerFeatureGroupRestrictedAccessController
Mutually exclusive, not layered For a given (project, user) exactly one of the two systems applies. The single choke point AccessController routes every decision by the caller's project team role: FEATURE_STORE_RESTRICTED members are checked against the restricted_* tables only; everyone else against the shared_* cascade only (§5).

Why the feature touches so many subsystems: a Hopsworks feature group is simultaneously materialised in four backends, each with its own access primitive:

BackendStoresAccess primitiveColumn-level?
RonDBonline FG (row store)native per-user GRANT SELECT (cols)✅ native column grant
HopsFSoffline FG (parquet/Hudi files)POSIX ACL on directory❌ directory-level only
ArrowFlight (FlyingDuck)external FGs + partial offline readssigned super-user query, encrypted connectors✅ query-time projection
OpenSearchembedding vectorsField-Level-Security role + mapping✅ FLS field list

Because feature views (FV) and training datasets (TD) are derived objects projecting columns out of one or more FGs, a second class of work (FSTORE-2026 / HWORKS-2744) makes their authorization recursive over constituent FGs so derived objects cannot be used as a side channel to read un-granted data (§7–§8).

3.1 The three tables

docker/migration/sql/ddl/V45__[FSTORE-1905]_column_level_permissions.sql — all three are ndbcluster tables in the hopsworks catalog. JPA entities in io.hops.hopsworks.persistence.entity.featurestore.share; facades in hopsworks-common/.../featurestore/share/.

TableKey columnsshared_entirely?Meaning
shared_feature_store feature_store→feature_store(id), shared_with_project→project(id), shared_by→users(uid), shared_on ✅ default 1 An entire feature store shared with a project (or a placeholder — see below).
shared_feature_group same + feature_group→feature_group(id) ✅ default 1 One FG shared with a project — whole FG or column subset.
shared_feature feature_group + feature VARCHAR(63) (the column name, not an FK — features aren't first-class entities) + shared_with_project ❌ (it is the leaf) One named column of one FG shared with a project.

All foreign keys are ON DELETE CASCADE, so dropping a feature store / FG / project / user automatically revokes its shares. The V45 migration also backfills shared_feature_store from existing full-store dataset_shared_with rows (with shared_entirely = 1) and then deletes those redundant rows — see §3.3 for what remains of the legacy mechanism.

3.2 The shared_entirely short-circuit hierarchy

The shared_entirely flag lets a broad grant subsume the finer tables. Read authorization walks top-down and returns at the first satisfied level:

1. own project?                                  → full access
2. shared_feature_store.shared_entirely = 1 ?    → full access (whole store)
3. shared_feature_group.shared_entirely = 1 ?    → full access (whole FG)
4. else → intersect requested columns with shared_feature rows for (FG, project)
Marker rows When you share a single FG but the parent store has no share row yet, the controller creates a shared_feature_store row with shared_entirely = 0 (ShareFeatureGroupController.java:169–174). This placeholder never grants store-wide access — it exists so the store shows up in the receiving project's store listings (FeaturestoreController.getProjectFeaturestores uses findSharedWithProject, which ignores the flag). It is removed again when the last FG share from that store is revoked (:433–438). Likewise a shared_feature_group row with shared_entirely = 0 means “consult shared_feature for the exact columns.”
PK + event-time always included Column-subset shares are always augmented with the FG's primary-key and event-time columns (addPrimaryKeysAndEventTime, ShareFeatureGroupController.java:237–248) so the shared subset stays queryable and joinable. You cannot hide PKs or event time via a partial share. The restricted system does the same (§4).

3.3 Lifecycle — REST API, who shares, no accept flow

Two JAX-RS sub-resources under a project's feature store, in hopsworks-api/.../api/featurestore/share/. Every method is gated @AllowedProjectRoles({DATA_OWNER}) — only a Data Owner of the owning project can share (receiver-side revoke needs a Data Owner of the receiving project). The target project is identified purely by numeric id.

EndpointAction
POST .../featurestores/{fsId}/share?project={id}Share the whole store (shared_entirely=1).
DELETE .../share?project={id} / DELETE .../share/received?featurestore={id}Owner-side / receiver-side revoke.
POST .../share/featuregroups/{fgId}?project={id}&feature=c1&feature=c2Share one FG. Empty feature set ⇒ whole FG; non-empty ⇒ column subset.
DELETE .../share/featuregroups/{fgId}?project={id} (+ /received)Revoke an FG share.
GET variantsList shares.
No accept / invitation flow Unlike the legacy dataset_shared_with (which had a pending state and acceptShared), these shares are immediate and unconditional: the metadata row and all backend permissions (HopsFS ACLs, RonDB grants, OpenSearch) are applied synchronously in the same call. There is no timer bean in the new path — the “timer bean” comment in V45 refers to the legacy dataset PermissionsFixer.

Sharing an FG enforces two invariants (ShareFeatureGroupController.java:155–168): FEATURE_STORE_ALREADY_SHARED if the store is already shared entirely with that project, and FEATURE_GROUP_ALREADY_SHARED if any FG row already exists — no silent widening/narrowing; unshare first.

Project lifecycle hooks (ProjectController.java)

  • Member added (:2125–2126) — addUserToSharedFeatureStores / addUserToSharedFeatureGroups replay all existing shares for the new member (entirely-shared → ACL + RonDB grant; partially-shared → online grant only). Skipped entirely for FEATURE_STORE_RESTRICTED members (:2124–2127).
  • Member removed (:2404–2405) — reverse.
  • Project deleted (:1373, :1876) — unshareAllFeatureStores / unshareAllFeatureGroup for shares received by the dying project; owning-side rows die by DB cascade.
  • Project created — the configured default feature store is auto-shared (ProjectService.java:725 → shareDefaultFeatureStore); an import wizard can per-FG-share all HopsFS-materialised FGs of the default project (FeaturestoreService.java:381).

3.4 Read-side logic — checkIfShared & filterSharedFeatures

hopsworks-common/.../featurestore/share/ShareFeatureGroupController.java — @Stateless, @TransactionAttribute(NEVER).

public boolean checkIfShared(Project project, Featuregroup fg) {          // L498–513
  if (fg.getFeaturestore().getProject().equals(project)) return true;      // own store
  if (sharedFeatureStoreFacade
        .findByFeatureStoreAndSharedEntirelyWithProject(fg.getFeaturestore(), project).isPresent())
    return true;                                                            // whole store
  return sharedFeatureGroupFacade
        .findByFeatureGroupAndSharedWithProject(fg, project).isPresent();   // any FG share
}

checkIfShared uses any FG share at level 3 (a partial share still makes the FG visible). Column narrowing is done separately by filterSharedFeatures (L532–562), which returns the full list for levels 1–3 and otherwise intersects the requested columns with the shared_feature rows. There is also a stricter checkIfSharedEntirely, used to decide whether a query needs the super-user executor (§6.3).

4. In-project restricted access (restricted_* tables)

The second system, added by FSTORE-1940 one migration after sharing. A project member holding the fifth project role FEATURE_STORE_RESTRICTED (“Feature store restricted”) starts with access to nothing in the feature store; a Data Owner then explicitly grants access to individual FGs, or individual features within an FG. It is a pure allow-list — absence of a row means no access — and it is scoped to a user, not a project.

4.1 The two tables

docker/migration/sql/ddl/V46__[FSTORE-1940]_restricted_feature_access.sql — ndbcluster, cascade FKs. Entities in io.hops.hopsworks.persistence.entity.featurestore.access.

TableKey columnsMeaning
restricted_feature_group_access feature_store, feature_group, granted_to_user→users(uid), granted_by, granted_on, can_access_entirely (default 1) “User U may access FG G.” can_access_entirely=1 ⇒ all columns; =0 ⇒ only the columns in the child table.
restricted_feature_access restricted_feature_group_access→parent row(id), feature VARCHAR(63), granted_to_user, granted_by, granted_on One named column granted within the parent FG grant.
Structural difference from the shared tables shared_feature FKs directly to feature_group, but restricted_feature_access FKs to its parent grant row — a per-feature grant cannot exist without its per-FG parent, and deleting the parent cascades the children. The parent's can_access_entirely plays the same role shared_entirely plays on shared_feature_group.

As with sharing, PK + event-time columns are force-added to any per-feature grant (addPrimaryKeysAndEventTime, FeatureGroupRestrictedAccessController.java:159–170).

4.2 The role & grant lifecycle

  • ProjectRoleTypes.FEATURE_STORE_RESTRICTED("Feature store restricted") — hopsworks-persistence/.../project/team/ProjectRoleTypes.java:48; also AllowedRoles.java:48. A project team role, in the same slot as Data owner / Data scientist / Observer.
  • On add-member, restricted members are deliberately not wired into existing cross-project shares (ProjectController.java:2124–2127), and their online DB user is created with zero schema grants — updateUserOnlineFeatureStoreDB (OnlineFeaturestoreController.java:292–302) only grants for DATA_OWNER / DATA_SCIENTIST. They accumulate only the explicit per-FG / per-column grants.

Grants are managed via hopsworks-api/.../featurestore/access/FeatureGroupRestrictedAccessResource.java, a sub-resource of a feature group, all methods @AllowedProjectRoles({DATA_OWNER}):

EndpointAction
POST grantAccess?user=<email>&feature=<set>No feature params ⇒ whole-FG grant (can_access_entirely=1); with them ⇒ per-feature grant.
DELETE revokeAccess?user=<email>Remove the grant (children cascade).
GET getUsersGrantedAccess()List grants for the FG.

grantRestrictedAccess (FeatureGroupRestrictedAccessController.java:90–137) re-verifies the target user actually holds the restricted role, writes the rows, then — if the FG is online-enabled — immediately issues the RonDB grant (§6.1) and, if the FG has an embedding, the OpenSearch FLS role (§6.4). There are no HopsFS ACLs for restricted users; offline reads are enforced at the API layer plus super-user execution (§6.3).

5. How the two systems compose — AccessController routing

hopsworks-common/.../util/AccessController.java — @Stateless, @TransactionAttribute(NEVER). Every REST resource that lists or fetches a feature-store entity routes authorization through here.

protected boolean checkIfRestricted(Project project, Users user) {        // L393–400
  Optional<ProjectTeam> projectTeam = project.getProjectTeamCollection().stream()
      .filter(t -> t.getUser().equals(user)).findFirst();
  return projectTeam.isPresent() &&
      projectTeam.get().getTeamRole().equals(ProjectRoleTypes.FEATURE_STORE_RESTRICTED.getRole());
}

public boolean hasAccess(Project userProject, Users user, Featuregroup fg) {  // L137–145
  boolean restricted = checkIfRestricted(userProject, user);
  if (restricted) {
    return featureGroupRestrictedAccessController.checkIfUserHasAccess(user, fg);
  } else {
    return shareFeatureGroupController.checkIfShared(userProject, fg);
  }
}

Every access method branches the same way — filterAvailableFeatureGroups (L361–368), filterAvailableFeatures (L379–390), the FV overloads (§7). If the user is restricted, the shared_* tables are never consulted for them, and vice versa. Callers such as the online preview/query paths throw FEATUREGROUP_NO_ACCESSIBLE_FEATURES when the filtered column list comes back empty.

Method familyRole
hasAccess(Project[, Users], X)Boolean gate for one entity; the Users overload adds the restricted routing.
verifyAccess(...)Throwing gate for the query/data path — walks the query's join tree and throws FEATURE_NOT_SHARED listing exactly which columns are missing. (RESTCode 268 — surfaced as HTTP 400, not 403; RESTCodes.java:1847.)
filterAvailable{FeatureGroups,FeatureViews,Features}(...)The listing filter — only accessible items survive.
hasAccess{Fgs,Fvs,Tds,Models,Connectors}Batch variants grouped by feature store to minimize round-trips. Note: the FV/TD batch variants are a coarse fast-path (own-project or whole-store only, no FG recursion), used by search/provenance.

5.1 What if both mechanisms apply to the same user?

Rows in both table sets can coexist for the same feature group — e.g. FG G is shared into project B (a shared_feature_group row, grantee = project B) while user U in B also has a restricted_feature_group_access row for G (grantee = U). There is nothing preventing that state in the database. But at decision time the two are never merged — no union, no intersection. checkIfRestricted(project, user) reduces to one boolean (U's team role in the calling project), and the router takes exactly one branch. The other table set is simply inert for that user:

SetupBranch takenOutcome
U is Data Scientist in B; FG shared to B; U also has (stale) restricted_* rowssharedAccess via the share. The restricted rows are dead metadata — never consulted.
U is FEATURE_STORE_RESTRICTED in B; FG shared to B; U has no restricted grantrestrictedDeny. The project-level share is invisible to a restricted member — that is the point of the role.
U is restricted in B; FG shared to B (entirely) and U has a restricted grant for 2 columnsrestrictedAllow, but only the 2 granted columns (+ PK/event-time). The broader project share does not widen U's view.
Same user, two projects: restricted in B, Data Owner in C; both projects can reach FG Gper-projectThe branch is chosen per calling project: requests from C use the shared cascade, requests from B use the allow-list.

Why a switch and not an OR/AND: the two systems have opposite default semantics. Sharing is additive (project members see the project's data plus whatever is shared in); restricted access is a default-deny allow-list. OR-ing them would let every restricted user inherit all project-wide shares — the allow-list guarantee collapses. AND-ing them would deny normal users everything (they have no restricted rows). The role is the selector for which semantics a member gets.

The backends mirror the same exclusivity so the metadata switch and the physical grants agree: on add-member, share replay is skipped for restricted members (ProjectController.java:2124–2127); their online DB user gets no schema-wide grant (OnlineFeaturestoreController.java:292–302 grants only for Data owner / Data scientist); HDFS refuses to add restricted members to feature-store dataset groups (HdfsUsersController.addNewMember, :639–643); and the PermissionsFixer timer bean skips them too (PermissionsFixer.java:269–272).

Role transitions are the seams Changing a member's role flips the switch instantly at the API layer, but backend state can lag:
  • Data Scientist → restricted (demotion): updateMemberRole calls updateUserOnlineFeatureStoreDB with the new role, which matches neither grant branch — so no grant is issued, but no revoke happens either (the revoke lives inside grantUserPrivileges and only runs when a grant is issued). The user's old GRANT SELECT ON db.* survives in MySQL; only the Hopsworks API layer cuts them off immediately.
  • Restricted → Data Scientist (promotion): a schema-wide SELECT is granted (revoking schema-level grants first). The user's restricted_* rows stay behind, dormant — if the user is later demoted again, the old allow-list resurrects as-is.
  • HdfsUsersController.changeMemberRole (:741) lacks the restricted+feature-store-dataset guard that addNewMember and the PermissionsFixer both have.

6. Per-backend enforcement — one metadata grant, four mechanisms

The tables in §3–§4 are only metadata. When a grant row is inserted or deleted, the controllers synchronously push real permissions to up to four backends. The sharing dispatch point is grantFeatureGroupAccess (ShareFeatureGroupController.java:192–215):

// Offline (HopsFS) only when the WHOLE FG is shared AND it is HopsFS-backed
if (featuregroup.getDataSource().getConnector() == null && features.isEmpty()) {
  grantOfflineFeatureGroupAccess(featuregroup, sharedWithProjectTeam, dfso);
  grantOfflineFeatureStoreExecPrivileges(featuregroup.getFeaturestore(), sharedWithProjectTeam, dfso);
}
onlineFeaturestoreController.setupOnlineFeatureStore(sharedWithProject);
if (featuregroup.isOnlineEnabled()) {
  onlineFeaturegroupController.shareOnlineFeatureGroup(featuregroup, sharedWithProjectTeam, features);
  embeddingController.shareEmbeddingFeatureGroup(featuregroup, sharedWithProjectTeam, features);
}

6.1 RonDB — native per-user GRANT SELECT (columns) (online)

Every project member has a per-user DB account: onlineDbUsername(project, user) = <project>_<user> clipped to 32 chars (OnlineFeaturestoreController.java:589), with a random password stored as a Hopsworks secret and a per-user JDBC connector. Grants are issued over an admin connection when a share/grant row changes, when a member is added/removed, or on role change. OnlineFeaturestoreFacade.grantDataScientistPrivileges (:226–260) has three variants:

GRANT SELECT ON db.*        TO dbUser;              -- feature-store level
GRANT SELECT ON db.table    TO dbUser;              -- whole feature group
GRANT SELECT (col1,col2,..) ON db.table TO dbUser;  -- column subset (partial / restricted)

The column list is the granted set after PK + event-time augmentation. grantUserPrivileges revokes-then-regrants, so re-shares don't stack. If multi-region is enabled the grant is replayed on the secondary region (async via OperationLog).

Who actually reads under these grants Online feature serving is not executed by Hopsworks Java: PreparedStatementBuilder (hopsworks-api, :117) hands prepared-statement templates to the client SDK, which connects through the per-user JDBC connector — so JDBC/SDK reads run as the grantee and RonDB's own privilege system enforces everything, including column-level visibility, with no proxy.
The RDRS gap This GRANT model constrains only MySQL/JDBC-protocol reads. The RonDB REST server (RDRS/RDRS2) authenticates with Hopsworks API keys, reads rows directly through the NDB API under a service identity, and never sees the per-user table/column GRANTs. No Hopsworks code pushes column-level restrictions into RDRS — FSTORE-1905/1940 column enforcement is JDBC-path only. This is the gap the RDRS2 port must close (§10).

6.2 HopsFS — POSIX ACLs (offline, whole-FG only, sharing only)

grantOfflineFeatureGroupAccess (L250–272) creates a dedicated HopsFS group <fsId>__<fgId>__shared, sets a READ_EXECUTE ACL (ACCESS + DEFAULT scope) on the FG's directory, then adds each receiving project member's per-project HDFS username into that group. A sibling exec-group grant lets members traverse down to the FG directory. Whole-store shares instead add each member to the FS dataset with READ_ONLY via the standard dataset ACL path (addUserToFeatureStoreACL, ShareFeatureStoreController.java:420–425).

Why offline is whole-group only HopsFS ACLs are directory-level POSIX permissions — there is no way to hide individual columns inside parquet files at the filesystem layer, hence the features.isEmpty() guard. Partial offline reads instead go through the ArrowFlight super-user path (§6.3). External FGs (connector != null) skip HopsFS entirely. Restricted access never drives HopsFS ACLs at all — offline enforcement for restricted users is purely API-layer + super-user execution.

6.3 ArrowFlight — signed + encrypted super-user queries (external / partial offline)

Neither a POSIX ACL nor a per-user GRANT can cover (a) partial offline reads, (b) external FGs whose connector credentials must not be exposed, or (c) restricted users (who have no HopsFS grants). Those queries run as a super user through FlyingDuck. The trigger is AccessController.requiresSuperUserExec (L402–406):

return checkIfRestricted(project, user)                                // restricted role
    || !shareFeatureGroupController.checkIfSharedEntirely(project, fg)  // partial share
    || fg.getFeaturegroupType() == ON_DEMAND_FEATURE_GROUP;             // external FG

When super-user exec is required:

  • Authorize first — ConstructorController.construct (L146) runs verifyAccess over the whole query tree; any inaccessible column ⇒ FEATURE_NOT_SHARED.
  • Column projection — filterAvailableFeatures narrows the query to only the granted columns before SQL generation (empty ⇒ FEATUREGROUP_NO_ACCESSIBLE_FEATURES); the filtered list becomes both the SELECT and the DTO's features map (ArrowFlightController.java:342–354).
  • Connector encryption — PKIUtils.encryptText (L66–107): hybrid AES-256-GCM + RSA-OAEP to FlyingDuck's certificate. The connector block holds super-user DB credentials; only FlyingDuck can decrypt, so the user never sees them.
  • Query signing — BaseHadoopClientsService.getMessageSignatureBase64 (L162–175) signs the entire serialized DTO JSON (SQL + allowed-column list + filters + encrypted connectors) with Hopsworks' super-user private key (SHA256withRSA). FlyingDuck verifies before honoring a super-user query — any client tampering with the SQL, column list, or filters breaks the signature. The permitted column set is fixed at sign time.

6.4 OpenSearch — Field-Level Security for embeddings

Embedding FGs store vectors in an OpenSearch index. EmbeddingController maps granted column names to prefixed index fields (toEmbeddedFeatureNames, L457) and calls OpensearchVectorDatabase.grantRestrictedAccess (vector-db, L387–410), which creates one security role per (index, identity):

role  fls_<index>_<identity>:  index_patterns=[index], allowed_actions=["read"],
                              fls=[ "col1","col2" ]   // or "*" for whole-FG
rolesmapping fls_<index>_<identity>:  users=["<identity>"]

The identity is the receiving project name for a cross-project share (shareEmbeddingFeatureGroup, L401) or <project>__<user> for a restricted grant (grantRestrictedEmbeddingAccess, L431) — matching the JWT subject minted by OpenSearchJWTController.createTokenForELKAsUser. OpenSearch strips fields outside the FLS list server-side before results leave the cluster. Revoke deletes the mapping then the role, tolerating 404.

7. Recursive feature-view / training-dataset checks

Before FSTORE-2026 The original FV/TD checks were flat: return featureView.getFeaturestore().getProject().equals(userProject) — a pure own-project test, no traversal into constituent FGs, and no user-scoped overload. This is the hole.

FSTORE-2026 makes FV access conjunctive over its constituent feature groups (AccessController.java:102–124):

public boolean hasAccess(Project userProject, FeatureView fv) {
  if (fv.getFeaturestore().getProject().equals(userProject)) return true;       // own project
  if (sharedFeatureStoreFacade
        .findByFeatureStoreAndSharedEntirelyWithProject(fv.getFeaturestore(), userProject).isPresent())
    return true;                                                                 // whole store shared
  if (fv.getFeatures() != null && !fv.getFeatures().isEmpty()) {
    return fv.getFeatures().stream()
        .map(TrainingDatasetFeature::getFeatureGroup).filter(Objects::nonNull).distinct()
        .allMatch(fg -> hasAccess(userProject, fg));   // FV → every constituent FG must be shared
  }
  return false;
}

The user-aware overload (L147–172) goes one level deeper for restricted users: it groups the FV's features by FG and, per FG, requires that every column the FV projects survives filterAvailableFeatures (accessible.size() == fvFeatures.size()) — catching a user granted some columns of an FG but not the specific ones the FV needs. Training datasets delegate to their feature view in the user-aware overload; the project-level hasAccess(Project, TrainingDataset) (L126–135) is deliberately coarser — owner or whole-store share only, TDs are not reachable via FG- or feature-level shares.

7.1 Decision matrix (single-FV endpoint)

ScenarioResult
Own project (even a degraded FV whose FGs were unshared/deleted)Allow
Whole feature store shared with caller's projectAllow
Cross-project, all constituent FGs shared (entirely, or all needed columns)Allow
Cross-project, any constituent FG / column missingDeny (FEATURE_NOT_SHARED, HTTP 400)
Restricted user, all FV columns grantedAllow
Restricted user, any FV column not grantedDeny

At the FV endpoint level access is all-or-nothing — one boolean per FV. Column filtering to a subset happens at the FG / query-construction layer (filterAvailableFeatures in FeaturegroupController, OnlineFeaturegroupController, ArrowFlightController, ConstructorController); the FV check reuses that filter but converts “any column missing” into full deny. Listing endpoints silently omit inaccessible FVs via filterAvailableFeatureViews.

7.2 HWORKS-2744 — deny single-FV read when a constituent FG is inaccessible

Between FSTORE-2026 and HWORKS-2744, the single-FV GET's verifyAccess got wrapped in a try/catch that swallowed FEATURE_NOT_SHARED for everyone — intended so an owner could still view/delete a degraded FV. But swallowing it unconditionally reopened the leak. HWORKS-2744 replaces the swallowed call with the recursive gate (FeatureViewResource.getByNameVersion, ~L293–304):

if (!accessCtrl.hasAccess(project, user, featureView)) {
  throw new FeaturestoreException(FEATURE_NOT_SHARED, Level.FINE,
      "Feature view '" + name + "' ... is not accessible: one or more of its"
      + " feature groups are not shared with the calling project or granted to the user.");
}

This keeps the degraded-owner intent (own-project short-circuits to true before the FG walk) while denying a cross-project or restricted caller who lacks any one constituent FG. The single-GET and the listing now agree; degraded own-project rendering is handled by FeatureViewBuilder.build wrapping query expansion in best-effort try/catch.

8. The indirect-leak threat model

Concrete scenario (pre-fix)
  1. Project A owns FG1 (public columns) and FG2 (contains salary).
  2. A builds feature view FV = FG1.* + FG2.salary.
  3. A shares only FG1 with project B (or grants restricted user U only FG1).
  4. B/U calls GET .../featureview/FV. The old check was own-project only — so FV metadata (and, via the query path, salary) leaked through the FV even though FG2 was never shared.

Direct access was already gated by FSTORE-1905/1940 (hasAccess(FG) / filterAvailableFeatures). The indirect leak was that derived objects (FV/TD) didn't look at their constituents. FSTORE-2026 closes it by making FV/TD access conjunctive over constituents; HWORKS-2744 plugs the reopened single-GET hole. Every read path — list, single GET, query construction (ConstructorController.construct calls verifyAccess), ArrowFlight offline read, online read, and embedding preview — now funnels through the same recursive logic that resolves to per-FG / per-column grant records.

10. What this means for the RonDB REST server (next step)

This document is the input to porting equivalent enforcement into RDRS2, which serves reads out of the online store. The load-bearing conclusions:

  • RDRS2 sits outside the enforcement perimeter today (§6.1). Hopsworks' column-level enforcement rides on per-user MySQL accounts; RDRS authenticates with API keys and reads via the NDB API under a service identity, so the GRANTs never apply. RDRS2 must read the five metadata tables (shared_* + restricted_*) — or a cache of them — and filter at the application layer.
  • Both routing legs must be reproduced (§5). Role check first (FEATURE_STORE_RESTRICTED?), then either the restricted allow-list (§4.3) or the shared cascade owner → store-entirely → FG-entirely → per-feature (§3.2/§3.4).
  • Recursive FV checks are mandatory (§7) for the feature-view endpoints RDRS2 serves: FV access = all constituent FGs/columns accessible, all-or-nothing deny at the FV level — otherwise the FSTORE-2026 indirect leak reopens at the REST layer. Column filtering, if implemented, belongs at the FG level.
  • PK + event-time columns are always granted alongside any column-level grant (§3.2/§4.1) — RDRS2 can rely on PK columns being readable whenever any column of the FG is.
  • Offline concerns don't apply. HopsFS ACLs and ArrowFlight signing (§6.2/§6.3) are out of scope; only the metadata model and the decision logic need porting.
  • Error surface: Hopsworks returns FEATURE_NOT_SHARED as HTTP 400 (code 268) — worth matching or consciously diverging.

Concrete RDRS2 design decisions are deferred to the implementation phase.
