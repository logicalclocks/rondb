RONDB-978: Project-User Rate-Limit Identity for RDRS

Design document — switching the REST server's rate-limit identity from API-key prefixes to Hopsworks project-user names, with a per-endpoint solution. Sources: Hopsworks (hops/hopsworks @ d7fe78bfab), the original upstream implementation (rondb2, commits 1d04f04ece9 / 32220b33624), current RDRS (rondb @ RONDB-978-Cont).

1. Executive summary

Today RDRS tags every NdbTransaction with the API-key prefix (rate_limit.hpp). That was the pragmatic stage-1 choice; its weakness is that an API key spans all of its owner's projects, so one bucket aggregates a user's traffic across projects, and REST buckets don't line up with anything else in the platform.

The proposal: make the identity the Hopsworks project-user, using the online feature store MySQL account convention:

identity = clip( project.projectname + "_" + users.username )
   where clip cuts to 31 chars ONLY when longer than 32 (a 32-char name stays 32)

Rationale: this is the exact string of the MySQL account each project member already has for online feature store access (OnlineFeaturestoreController.onlineDbUsername). The RONDB-978 MySQL-server path attributes usage by MySQL account name, so with this choice a project-user's REST traffic and MySQL traffic land in the same kernel rate-limit bucket, and Hopsworks can provision/drop USER entities in the exact place it creates/drops the MySQL accounts. One bucket per (project, member) — precisely the granularity Hopsworks already manages identities at.

The project half of the identity comes from the request (the target database / feature store), because the API key itself carries no project. The username half comes from hopsworks.users.username, cached alongside the API key. Requests whose identity has no provisioned USER entity run unmetered — which makes rollout safe and incremental.

2.2 Building blocks

ComponentFacts
users.username always exactly 8 chars, [a-z0-9]{8} (email local-part, stripped, zero-padded, numeric suffix on collision); column varchar(10), UNIQUE. UsersController.java:483
project.projectname ≤ 25 chars, starts with a letter, [a-zA-Z0-9_], may not contain __ or _featurestore, mixed case allowed. FolderNameValidator.java:54
Online DB name lowercase(projectname) — this is the database REST requests actually name. OnlineFeaturestoreController.java:575
Feature store name lowercase(projectname) — feature_store.name is set to the bare lowercased project name (FeaturestoreController.java:239), so feature-store requests and pk-read/scan URLs both resolve with the same key. (The Hive offline DB is lowercase(projectname) + "_featurestore", FeaturestoreController.java:331, but RDRS never bills by it.)
api_key → user prefix (16 chars, UNIQUE) → user_id → users.uid. No project dimension.
Membership project_team(project_id, team_member=users.email); one user ↔ many projects.
Gotchas the implementation must respect
  • Case: the request names the lowercased DB, but the identity uses the project name's original case. The mapping lowercase-db → ProjectName must come from a lookup of project.projectname (RDRS's API-key cache already reads these rows), never from string surgery on the request.
  • Clip >32 → 31 (a 32-char name survives). Max unclipped length is 25+1+8 = 34, so truncation is real for project names ≥ 24 chars, and exactly-32 names (23-char projects) stay whole. Reproduce Hopsworks' exact boundary or REST and MySQL buckets diverge for long project names.
  • Not parseable: project names may contain _, so the identity cannot be split back into (project, user). Treat it as an opaque bucket key; always build it from the pair.
  • Kernel storage: the data nodes store the entity as $<identity>; 31+1 chars is comfortably inside database-name limits.

3. What exists today (API-key prefix identity)

Identity is computed once per request in rate_limit.hpp:38 (get_rate_limit_identity), gated by REST.UserRateLimits; config RateLimitIdentity is validated to the single value "apikey". (Both keys were moved into a top-level .RateLimit section as built — see §5.4.) It is threaded as one const char* into pk_batch_read(...) / scan_read(...) and applied per transaction via NdbTransaction::setUserId (pkr_operation.cpp:386-397, rdrs_dal.cpp:1855).

Two load-bearing facts for this design:

  • The api-key cache entry (UserDBs, api_key.hpp:91-131) stores the owner's users.uid (m_user_id) but no username — and find_user_int currently reads only users.email. The word “username” does not exist in RDRS src today.
  • Every authenticate*() overload returns only RS_Status — there is no channel to hand an identity back to the controller. Adding one is the central API change.

4. Post-mortem: the original username implementation (rondb2)

The original code (Mikael, 1d04f04ece9, refactored in 32220b33624, later silently deleted by the RONDB-1088 squash merge) is a useful map of the plumbing, but it cannot be revived by cherry-pick:

#DefectEffect
1find_all_projects_int took HopsworksUsers by value; the username read from NDB never reached the caller. Identity built from an uninitialised struct.
2find_and_validate accepted username_ptr but never wrote to it; the cached m_user_ptr was assigned and never read. Controllers tagged transactions with uninitialised stack memory.
3feature_store_ctrl.cpp declared a shadowing char *username_ptr inside the auth block. Single feature-store endpoint always passed nullptr — untagged.
4set_user_id built the identity by memmove/memcpy in place in the shared request buffer. In per-op-transaction batches, op 2+ got a garbled, accumulating identity.
Naming surprise: the original concatenation was {database}{username} — request DB name, then username, no separator, username truncated at 10 chars. For feature-store requests the “project” half was actually {project}_featurestore. This matches no Hopsworks identity system, and nothing provisioned entities with those names. This design deliberately replaces it with the MySQL account convention (§2) instead of restoring it.

5. Core RDRS changes (shared by all endpoints)

5.1 Cache: carry the username and the project-name map

  • find_user_int (rdrs_hopsworks_dal.cpp:526): also read the username column (fixing upstream defect #1 — pass the struct by reference). USERS_USERNAME_SIZE = 10 + 1 added to rdrs_const.h, matching the varchar(10) latin1 column. AS BUILT this doc originally claimed such a constant already existed — it did not.
  • UserDBs (api_key.hpp): add char m_username[USERNAME_SIZE], filled on every cache load/refresh (update_cache, load_single_key, refresh_job all funnel through find_user_databases, so one write-site).
  • Add a per-entry map m_db_to_project: lowercase db → ProjectName (original case). The refresh path already fetches HopsworksProject.projectname with original case before lowercasing into userDBs (api_key.cpp:692-724); keep the pair instead of discarding it. Entries: member projects (grant source project_team) and, if shared-store metering is wanted (§10), shared stores' owning projects.

5.2 Authentication API: return an identity context

struct AuthCtx {           // filled by authenticate*() on success
  char username[USERNAME_SIZE];        // 8 chars in practice
  // accessor into the cache entry's db→ProjectName map, valid for the request
};

RS_Status authenticate(const std::string &apiKey, PKReadParams &, AuthCtx *ctx);
// ... same added parameter on the other three overloads

This is the fix for upstream defect #2 done properly: the out-parameter is written exactly once, under the cache entry's shared lock, by find_and_validate.

5.3 Identity computation: extend rate_limit.hpp

// .RateLimit.Identity: "apikey" (today's behaviour) | "username" (new)
// AS BUILT: the ctx parameter is a RateLimitIdentities (per-db map of
// precomputed identities), not the AuthCtx sketched in 5.2.
std::string get_rate_limit_identity(const std::string &api_key,
                                    const RateLimitIdentities &ctx,
                                    std::string_view target_db) {
  if (!globalConfigs.rateLimit.enable) return {};
  if (identity_mode == APIKEY) return prefix(api_key);          // unchanged
  // username mode:
  //   1. identity = ctx.identity_for(lowercase(target_db))   (map lookup;
  //      the key is the lowercased project name = online db name =
  //      feature store name, so no suffix handling is needed)
  //      - unknown db (not in map) -> return {} (unmetered)
  //   2. return it (already clip(ProjectName + "_" + username),
  //      built case-preserved from the project table at cache load)
}

Each call returns a fresh std::string owned by the controller — no shared mutable buffer (fixes upstream defect #4). The existing threading (const char*, len → setUserId per transaction) is unchanged, so the DAL and kernel plumbing this branch already validated keeps working.

5.4 Config (AS BUILT — differs from the original sketch)

The three flat .REST.* keys were moved into a top-level .RateLimit section and lost their now-redundant prefixes. Rate limiting is enforced by the data nodes and mysqld participates via its own --ndb-user-rate-limits, so it is a cluster participation policy rather than a REST server option; Rondis also issues NDB transactions from this same process (untagged today), so a REST-nested section would have needed moving again once Rondis is metered.

{
  "RateLimit": {
    "Enable": true,          // was .REST.UserRateLimits
    "Identity": "username",  // was .REST.RateLimitIdentity: "apikey" | "username"
    "FullAPIKey": false      // was .REST.RateLimitFullAPIKey
  },
  "REST":     { "ServerIP": "0.0.0.0", "ServerPort": 4406 },
  "RonDB":    { "Mgmds": [ { "IP": "localhost", "Port": 1186 } ] },
  "Security": { "APIKey": { "UseHopsworksAPIKeys": true } }
}
Earlier internal shape (flat)As built (section)
.REST.UserRateLimits.RateLimit.Enable
.REST.RateLimitIdentity.RateLimit.Identity
.REST.RateLimitFullAPIKey.RateLimit.FullAPIKey

No compatibility burden. The rate limit code is committed in the tree, but the plumbing to enable it has not been done — nothing provisions USER entities and no deployment turns it on — so no operator config sets these keys. The rename is therefore internal: the only consumers are this repo's MTR templates and the Go test harness, both updated alongside it. No aliases, deprecation window or upgrade note are needed.

Validation. Two rules live inside the section, two span sections and sit at AllConfigs level:

  • Identity must be "apikey" or "username". "apikey" remains the default — instant rollback path.
  • FullAPIKey is meaningful only in apikey mode; rejected in username mode.
  • Enable requires .Security.APIKey.UseHopsworksAPIKeys. Both identity modes derive from the request's API key (apikey from the key itself, username from its owner), and all six endpoints compute an identity only inside their useHopsworksAPIKeys branch — so without API keys nothing would ever be rate limited. This replaces the narrower username-only rule originally proposed here.
  • Enable requires .REST.Enable: only REST requests are tagged, so enabling it with REST off would meter nothing. Nesting under .REST gave this check for free; at top level it has to be explicit.

Stale keys fail loudly, not silently. Worth recording because it is the property that makes this whole feature safe to configure: the parser rejects any unrecognised key — DEFINE_STRUCT_PARSER throws ConfigParseError("Unexpected key") for anything that neither matches an element nor starts with #. A config using the old flat keys does not quietly fall back to defaults with rate limiting off; rdrs2 refuses to start and names the line:

Error while initializing configuration.
HTTP code 400
Unexpected key before/at line 5, column 22
rdrs2: Exit with code 1.

The same protection covers ordinary typos ("Identiy", a key at the wrong nesting level), which matters here because every other misconfiguration in this feature — an unprovisioned USER entity, a wrong-case project name, a clip-length mismatch — fails silently as "no rate limiting" (§7). Config-key typos are the one class of mistake the server can catch for you, and it does.

Note for any future rename: ALIAS() cannot bridge a change of nesting level. It maps an alternative key name within one class, so it could not lift .REST.UserRateLimits into the nested .RateLimit object; accepting both spellings would need new macro machinery.

6. Per-endpoint solutions

6.1 pk-read POST /0.1.0/{db}/{table}/pk-read

Today
Auth at pk_read_ctrl.cpp:119 with one TableAccessRequest; single DB from the URL; one transaction, tagged.
Solution
target_db = path.db. Identity clip(Proj(db) + "_" + username) computed right after auth; passed exactly as today. The URL DB is the online DB (= lowercased project name), so the map lookup always resolves for member projects. Simplest case; no structural change.
Edge
DB not in the project map (e.g. system db accessed by an admin key): empty identity → unmetered. Acceptable and explicit.

6.2 scan / index-scan POST /0.1.0/{db}/{table}/scan

Today
Auth at scan_read_ctrl.cpp:206; single DB from URL; exactly one transaction (rdrs_dal.cpp:1836), tagged; already maps 429 explicitly.
Solution
Identical to pk-read: target_db = path.db, one identity, one transaction. No structural change.

6.3 batch-pk-read POST /0.1.0/batch

Today
Sub-operations can name different databases in one request (batch_pk_read_ctrl.cpp:176-212). With UseSingleTransaction=true (default) the whole batch shares transactions, and one identity tags them all.
Problem
A transaction has exactly one userId. A mixed-project batch under a single identity either over-bills one project (upstream's "first op wins") or under-bills all.
Solution — group by database
Partition sub-operations by req->DB() before setup_transactions; start one transaction (chain) per database group; tag each group's transactions with that database's project identity. For the overwhelmingly common single-DB batch this degenerates to exactly today's behaviour (one group), so no performance change; mixed-DB batches gain one transaction per extra database — correct attribution at proportional cost. Per-group identities live in per-group std::strings (fixes upstream defect #4 structurally).
Fallback if grouping is deemed too invasive for v1
Tag all transactions with the identity of the first operation's DB and document it. Deterministic but mis-attributes mixed batches; grouping is the recommended end state.
AS BUILT
The fallback shipped, not the grouping: batch_pk_read_ctrl.cpp bills the whole batch to reqStructs[0].path.db. Mixed-project batches are therefore mis-attributed to the first operation's project. Per-database transaction groups remain the recommended end state and are tracked as a follow-up.

6.4 feature-store POST /0.1.0/feature_store

Today
Metadata is resolved before auth (feature_store_ctrl.cpp:634-641), so the feature view's own store (reqStruct.featureStoreName) is known early. Reads may touch feature groups in other projects' stores (shared FGs, metadata->featureStoreNames); auth deliberately validates those cross-project grants. One pk_batch_read over possibly several DBs; single identity today.
Solution — bill the entry project
target_db = reqStruct.featureStoreName — the feature store name equals the lowercased project name, so this is directly the feature view's own project. All transactions of the request (including sub-reads that land in shared stores) are tagged with clip(FVProject + "_" + username). Rationale: the caller is acting in that project — the same attribution MySQL gives when the client connects as that project's account and selects from a shared DB. Do not use per-FG store identities: shared-FG reads would then bill the owning project's project-user, which may not even exist for this caller (no membership → no MySQL account → no bucket).
Note
This is a single-identity request, so no transaction grouping is needed regardless of how many stores the FV spans.

6.5 batch-feature-store POST /0.1.0/batch_feature_store

Today
Same shape as feature-store — one feature view, N entry rows (batch_feature_store_ctrl.cpp:127-182).
Solution
Identical to 6.4: one identity from the FV's own store; entries multiply operations, not identities.

6.6 ronsql POST /0.1.0/ronsql

Today
Completely untagged — the controller computes no identity, and ronsql_dal (rdrs_dal.cpp:190) has no identity parameter; no setUserId under db_operations/ronsql/. (The original upstream code obtained a username here but also never forwarded it.)
Solution
The single database comes from the body (reqStruct.database, validated at ronsql_ctrl.cpp:102) and auth already happens after a parse-only pass discovers the table/columns. Wire the standard chain for the first time: compute the identity from that database, add an identity parameter to ronsql_dal(...) → ronsql_operation → setUserId on the execution transaction, and map queueing-abort NDB errors to 429 in the controller (copy the scan controller's mapping, scan_read_ctrl.cpp:236-240). Aggregation scans are the expensive queries — leaving RonSQL unmetered would leave the biggest per-query cost outside the quota system.
AS BUILT
Tagging landed via new RonSQLExecParams::rate_limit_identity fields applied at RonSQLPreparer::execute()'s transaction start, rather than by adding a parameter to ronsql_dal. The 429 mapping needed two fixes, because a RonSQL rejection reaches the caller as a thrown exception rather than a returned status:
  1. handle_ronsql_exception now classifies the quota codes (243/2203/247/248) into a new RonSQLRateLimitError carrying the NDB code, instead of folding them into the temporary/permanent verdict — which had cost 3×50 ms of pointless retries against an already-overflowing bucket. Classifying in the exception handler rather than at the setUserId call site covers both routes to a rejection: the client-side backoff window failing setUserId, and the data nodes rejecting the aggregation scan mid-flight.
  2. ronsql_ctrl.cpp hardcoded k500InternalServerError for every non-200, so even a correct TOO_MANY_REQUESTS status was flattened to 500. It now mirrors the scan controller.
The throw is guarded on rate_limit_identity != NULL, so the new exception type is structurally unreachable for embedders that never opted into tagging — ronsql_cli ends its handler chain with catch (...) { abort(); }. Covered by a new Go package, test_go/internal/integrationtests/ronsql/ratelimit_test.go, green in both identity modes.

6.7 batch write / delete 26.04+ only

Situation
Not present on 26.02; on 26.04+ they already take the downstream rate_limit_identity DAL signature (ported during the upmerge).
Solution
Same as batch-pk-read (6.3): group by database, per-group identity. Writes use the write-rate constants in the kernel; nothing endpoint-specific beyond that.

7. Provisioning USER entities from Hopsworks

The kernel only meters identities that exist as USER entities ($-prefixed records created via mgm USER SET). Unprovisioned identities run unmetered, so provisioning defines coverage. Hopsworks should own it, mirroring the MySQL account lifecycle:

OptionMechanismAssessment
A — co-locate with the MySQL account (recommended) Call mgm USER SET clip(proj_user) --rate-per-sec=<quota> next to OnlineFeaturestoreFacade.createOnlineFeaturestoreUser (OnlineFeaturestoreFacade.java:167) and USER DROP next to removeOnlineFeaturestoreUser (:187). Exact 1:1 with the accounts the identity mirrors; covers both the eager addMember path and the lazy setupOnlineFeatureStore path (MySQL users are created on first online-FS touch, not at project creation). Synchronous — needs a best-effort/retry wrapper so mgm unavailability doesn't fail membership changes.
B — operation_log async handler Implement OnlinefsOperationHandler (hopsworks-common/.../async/service/); the ONLINE_FS_DB_CREATE_USER / REMOVE_USER rows already carry online_fs_user — literally the identity string. Template: SupersetUserAccountHandler.java. Retries, per-service status, decoupled from the request path; slightly delayed (timer-driven). Excellent either as the primary mechanism or as the retry layer under A.
  • Idempotency: use SET-then-ALTER (as the Go test helper does) — Hopsworks re-runs provisioning defensively, and multi-region executes twice.
  • Service users (onlinefs, rondb_replication, serving keys): ordinary members, so they'd get buckets too. Exempt them (skip provisioning, or provision rate 0 = unlimited) using operation_log.is_service_user / OperationHandlerHelper.isServiceUser.
  • Quota source: a per-project (or cluster-default) setting in Hopsworks; role-differentiated limits (Data owner vs Data scientist) are possible later since the role is known at provisioning time.
  • Reconciliation: a periodic job comparing mgm USER LIST against the expected set heals missed events (mirror of RDRS's own 60s re-LIST philosophy).

8. Kernel considerations

  • Cardinality: entities = active (project, member) pairs — the same cardinality as online-FS MySQL accounts, which the platform already sustains. Each is one small DICT record distributed to TC/LQH.
  • Drop under traffic is now safe on this branch: the DBLQH stale m_user_ptr_i UAF (node crash on USER DROP with live scans) is fixed (5b32fa7783e), and in-flight operations are gated by DBTC's PREPARE_DROP refcount. The fix must be ported to 26.04/26.05 before this feature ships there.
  • Client cache: the authoritative user-id cache + CREATE/DROP push + 60s re-LIST (40dee85245d) means newly provisioned project-users start being enforced within push latency, without per-transaction DICT probes — validated by TestRateLimitUserCreatedAfterServerStart.
  • Kill switches (unchanged by this design): per-user USER ALTER --rate-per-sec=0 (live), .RateLimit.Enable=false + RDRS roll, ActivateRateLimits=0 + data-node roll. Making the last one runtime-SETable is a recommended companion change.

9. Rollout

  1. Ship the RDRS changes with .RateLimit.Identity: "apikey" (default) — zero behaviour change; the username plumbing is dormant but testable.
  2. Ship Hopsworks provisioning (entities appear; nothing meters them yet since RDRS still tags prefixes and MySQL-path buckets only bite if MySQL-path limits are set).
  3. Flip .RateLimit.Identity: "username" per cluster + rolling RDRS restart. Rollback = flip back.
  4. Test coverage per endpoint mirrors the existing per-endpoint ratelimit Go tests, plus: a mixed-database batch asserting per-group attribution, a shared-FG feature-store read asserting the entry project is billed, and a ronsql throttle test (new coverage entirely).
    AS BUILT The ronsql throttle test shipped (integrationtests/ronsql/ratelimit_test.go), plus a C++ unit test pinning the clip boundary at total lengths 31/32/33/34 against an independent restatement of the Java rule (test/api_key_test.cpp, RateLimitIdentity.*). The mixed-database batch test was not added, since first-op-wins shipped instead of grouping (6.3).

10. Open questions (need product/review decisions)

  1. Shared-store scans/pk-reads outside feature-store endpoints: a pk-read directly against a shared project's online DB resolves to a project the caller is not a member of. Options: (a) unmetered (map lookup fails — simplest, proposed default); (b) extend the map with shared stores so it bills {OwnerProject}_{username} — requires provisioning those extra buckets on share-grant events (ONLINE_FS_DB_GRANT_PRIVILEGES rows exist for this).
  2. Mixed-DB batch grouping (6.3): accept the per-group transaction cost in v1, or start with first-op-wins? Recommendation: group — the code motion is contained in setup_transactions.
  3. MySQL-path string — RESOLVED: ha_ndbcluster::set_user_id (ha_ndbcluster.cc:7756) tags with security_context()->user(), the plain account name without host suffix, so REST and MySQL buckets coincide byte-for-byte.
  4. JWT-authenticated RDRS requests (if/when enabled): the JWT subject is the bare username and the project comes from claims — same identity formula applies, different extraction point.
