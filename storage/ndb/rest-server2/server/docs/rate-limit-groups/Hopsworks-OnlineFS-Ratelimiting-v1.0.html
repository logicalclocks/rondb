Hopsworks · RonDB · Feature white paper · October 2026

Hopsworks OnlineFS Ratelimiting Version 1.0

Shared database budgets for teams. An administrator can say “this team may use 20% of the online feature store”, or “that team may use 5% when it reads our data”. RonDB then enforces each team’s budget, whether the team’s members connect through the REST server (RDRS) or through the MySQL server.

The online feature store is one RonDB cluster shared by every project, every user and every job in a Hopsworks installation. This feature introduces the rate limit group: a named budget shared by a set of users or whole projects, applied either to everything they read or to specific feature groups and feature stores. Rate limit group groups are created on one administration page. Work that falls under a rate limit group is slowed down and, if it keeps coming, rejected once the budget is used up; everyone outside the rate limit group is unaffected.

This paper describes the problem, the feature, how the limit is applied, a worked scenario, the administration page, what a limited team experiences, and how budgets are planned.

1. Summary

  • One budget per team, not per key. A rate limit group is a share of the cluster given to a set of users or projects. Every member’s work draws from the same budget, through both entry points for data: the REST server (RDRS) and the MySQL server.
  • Scoped to data when needed. A rate limit group can cover everything its members read, or only named feature groups and feature stores. That lets a data owner cap its own hot tables, or cap what a partner project may burn when reading shared data.
  • A ceiling, never a permission. Rate limit group groups do not grant or revoke access, and they do not reserve capacity. They stop one team from degrading the cluster for the others.
  • Managed in Hopsworks. One page lists the rate limit group groups, their budgets, who shares them, what they cover, and whether each is live on the cluster.
  • Enforced in RonDB. Work is metered in CPU time per data node. Over budget, requests are first queued, then rejected with a retryable error.

2. The problem: one shared cluster, many tenants

Data in the online feature store is reached through two entry points: the REST server (RDRS), for low-latency key lookups with an API key, and the MySQL server, for SQL with a database account. Every project and every user share one RonDB cluster behind both. All of their work competes for the CPU of the same data nodes, and when one user takes more than their share, every other user sees it as latency.

A limit per identity is the obvious tool, and RonDB can put a budget on a name. The question is which name. The natural identities are too fine:

  • A user has several API keys, and creates more at will. A budget per key multiplies with every key.
  • The same user also connects through the MySQL server with a database account, not a key. A budget per key never sees that traffic.
  • Splitting a team’s share evenly across its identities starves the busy one while the idle ones hold capacity nobody uses.

What an administrator wants to say is “this team, together, may use this much”, where a team is a set of people, and sometimes “this team may use this much of our data”. That is what a rate limit group expresses.

3. The feature: rate limit group groups

A rate limit group is a named budget with two lists attached: who shares it and what data it applies to.

PartWhat the administrator enters
NameA short name for the budget.
BudgetA percentage of the cluster’s capacity for database work. Section 4 explains what a given percentage means.
WhoLogin users and/or whole projects. A project means its current members: people who join later are covered automatically, people who leave drop out.
WhatEither all accessible data, or a list of feature groups and feature stores. A feature store entry covers every feature group in it, including ones created later.

Everyone in the rate limit group draws from the same budget, so one busy member can use it all. What the rate limit group guarantees is that the rest of the cluster is protected from that team. Two things a rate limit group is not:

  • Not a permission. Listing someone in a rate limit group does not let them read anything they could not read before, and removing a share still blocks them even if a rate limit group names them. Access is decided by project membership and sharing, as before.
  • Not a reservation. 20% is a ceiling, not capacity set aside for the team. On an idle cluster the team still gets at most 20%; on a busy one it is still allowed up to 20%.

Rate limit group groups are not tied to the organisation chart. A rate limit group whose members are a set of service accounts, another for a set of heavy users, and a small one for a free-tier project are the same mechanism with different lists.

4. What a budget of 20% means

Think of each data node as able to do a fixed amount of database work every second. A budget is a slice of that. A budget of 20% means the team may use up to one fifth of each data node’s work capacity, every second.

“Work” is what the database actually does, not how many requests arrive. Looking up one row is cheap. Writing one row costs about three times as much. Scanning through a table costs a little per row examined, so a query that reads one row is cheap and a query that scans a million rows is expensive. All of it is counted in the same unit and charged to the team’s budget.

For example, on a data node with 20 CPU cores, if the team did only one kind of work:

BudgetSimple lookupsor writesor rows scanned
20%about 3 million per secondabout 1 million per secondabout 5 million per second
5%about 800,000 per secondabout 250,000 per secondabout 1.3 million per second
2%about 320,000 per secondabout 100,000 per secondabout 500,000 per second

Figures are per data node and scale with its size: a node with 40 CPU cores gives twice as much, and more nodes give more in total. The administration page shows the exact figure for your cluster next to the percentage.

Three simple facts about a budget:

  • It is shared. Everyone in the rate limit group, through both entry points, draws from the same budget. One member running a big scan can use it all.
  • It is a ceiling. The team is never held below its budget and never allowed above it, whatever the rest of the cluster is doing. An idle cluster does not give the team more; a busy cluster does not give it less.
  • It is per data node. Work spread across the cluster can use the budget on every node; work that piles onto one node hits that node’s limit first.

5. How a limit is applied

When someone reads or writes a table, RonDB finds the rate limit group that contains both that person and that table, and charges the work to it. Four rules cover every case:

  1. Both entry points count. A request through the REST server (RDRS) with an API key and a query through the MySQL server with a database account are charged to the same rate limit group, because both identify the person doing the work. The platform’s own administrative queries are not charged.
  2. The more specific group wins. When a person and a table match more than one rate limit group, a group scoped to that feature group beats a group scoped to its feature store, which beats a group covering all data. The administration page refuses two rate limit group groups that would tie.
  3. One transaction, one rate limit group. A request that touches several tables, such as a feature-view read, is charged as a whole to one rate limit group.
  4. Not in a group, not limited. A person who is in no rate limit group, or a read of data that no group of theirs covers, is not limited.

Work is measured as CPU time on the data nodes: a small cost per row read, a larger one per row written, a cost per row scanned, plus a little per byte moved. Each data node lets a group’s total drain at the configured rate. Short bursts pass. Sustained excess is first slowed by queueing new transactions, then, if it continues, reads are rejected with a temporary error, and writes only under heavy, sustained overload (section 8).

When two rate limit group groups match, the more specific one wins. Suppose Marketing adds a fourth rate limit group, recommender2_clicks_rl: project Recommender2 on feature group marketing_clicks, 1%. Rosa reading marketing_clicks now matches both the group scoped to the store and the group scoped to the feature group; the feature-group scope is more specific, so she is charged to recommender2_clicks_rl. Her reads of marketing_campaigns still go to recommender2_marketing_rl. The two budgets are separate: the 5% is not a cap on her total.

The three rate limit group groups add up to 27% of the cluster. The cluster carries one budget per rate limit group, not one per person or per key, so a handful of rate limit group groups covers a whole organisation.

7. Administration

One page under Hopsworks administration: a list of rate limit group groups on the left, and a form for the selected rate limit group on the right. The list also shows whether each rate limit group is live on the cluster, so an administrator can see when a saved rate limit group has actually been installed.

Three details worth knowing:

  • The name is fixed after saving. It is the identity RonDB meters; renaming would mean dropping and recreating the limit.
  • The budget field shows the converted rate, so the administrator sees what the cluster will receive (section 9), and the sentence preview restates the rate limit group in words, which is the quickest check that Who and What were filled in as intended.
  • “All accessible data” is an explicit choice. This protects a team from suddenly being capped on everything because the one feature group in their rate limit group was deleted: such a rate limit group simply matches nothing and is shown as inert.
Cluster columnMeaning
● installedThe limit is live on the cluster.
● pendingSaved in Hopsworks; the cluster does not have it yet. Until it does, that traffic runs unlimited.
● refusedThe cluster rejected it because the total budget is already full (section 9). Lower another budget first.
○ inertA selected-data rate limit group whose data entries are gone (its feature group was deleted). It matches nothing.

The page refuses two rate limit group groups that would tie, that is, two rate limit group groups at the same level that cover the same person and the same data. Who may create rate limit group groups is a product decision; a natural split is that administrators create all-data rate limit group groups, while the data owner of a feature store or feature group may cap its own data or its consumers.

8. What a limited team experiences

RonDB adds up work under the group’s name and lets the total drain at the configured rate. Short bursts pass unnoticed. Sustained excess is handled in stages:

  1. Slower. New transactions from the rate limit group are queued for a short time before they start. Latency rises; nothing fails.
  2. Reads rejected. If the excess continues, reads get a temporary error: HTTP 429 from the REST server (RDRS), MySQL error 1297 with the RonDB reason from the MySQL server.
  3. Writes rejected only under heavy, sustained overload.

Rejections are temporary and carry no risk to data; callers back off and retry. Nobody outside the rate limit group is affected, which is the point.

9. Planning budgets

Budgets are percentages of each data node’s capacity for database work (section 4), and they add up across rate limit group groups.

All budgets together may not exceed 50% of a data node. The reason is simple: the meter only counts row operations, the reads, writes and scans a user causes. Redo logging, checkpoints, network threads, schema changes, backups and the platform’s own unmetered work also need CPU. Half the machine is kept for them, so that even when every rate limit group runs at its ceiling the node is not saturated and the limits still mean something. Three consequences for planning:

  • A rate limit group counts toward the 50% even while its members are idle. A handful of team-sized rate limit group groups fits comfortably.
  • If a new rate limit group would push the total over 50%, the cluster refuses it and the administration page shows refused. Lower another budget first.
  • Budgets are ceilings, not reservations.

10. Several clusters

Some installations give each big project its own RonDB cluster. The owner of a cluster then wants to say “that team may use 20% of my cluster, this other team 30%”. The same rate limit group groups express that, and nothing in a rate limit group names a cluster: a rate limit group on a project’s data is enforced wherever that project’s data lives, and its percentage is a percentage of that cluster. A rate limit group on all accessible data means that percentage on each cluster. The administration page shows the cluster state per cluster.

11. Questions we expect

Does a rate limit group restrict who can read what?
No. Access is decided by project membership and sharing exactly as before. A rate limit group only decides which budget pays for work that is already allowed.
Someone joins or leaves the team. Do I edit the rate limit group?
Not if the rate limit group names the project; membership is read live. If the rate limit group names people individually, you edit the list.
We created version 2 of a feature group that is in a rate limit group.
A feature-group entry in a rate limit group is one version. Add version 2, or put the feature store in the rate limit group instead; that covers every feature group and version in it, including future ones.
Can a person be in two rate limit group groups?
Yes, as long as they do not tie. A person can be capped on one feature group and belong to a team-wide rate limit group; for that table the group scoped to the feature group wins. Two all-data rate limit group groups that both contain the same person are refused.
A query touches several feature groups, such as a feature view.
The whole transaction is charged to one rate limit group.
Is 20% a guarantee?
No. It is the most the team may use.
We have several clusters. Does a rate limit group cover all of them?
An all-data rate limit group means that percentage on each cluster. A rate limit group on specific data is enforced on the cluster that holds the data.
