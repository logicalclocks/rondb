Rate Limit Groups: The Two Variants, Explained

A plain-words companion to the design document Hopsworks OnlineFS Ratelimiting: Design v1.0. It explains the two possible ways to decide which rate limit group a request belongs to: Variant A, where the REST server (RDRS) works it out, and Variant B, where RonDB works it out. All precise semantics, line references and edge cases live in the design document (sections 5 to 8); this page only explains the idea.

1. The problem in one minute

A rate limit group is a shared budget. An admin says: these people (or these whole projects), reading this data (or all data), may together use this much of the RonDB cluster. For example: Mary and Mike, on the feature group marketing_clicks version 1, get 2% of the cluster.

RonDB already knows how to enforce one budget per name: a kernel USER object holds a rate, and every transaction tagged with that name is charged against it. So one group simply becomes one USER on the cluster.

The hard part is the moment a request arrives. Something, somewhere, has to answer: which group does this request belong to? The answer depends on two things at once: who is asking, and what data they are touching. The two variants differ only in where that question is answered.

2. What both variants share

Most of the feature is the same in both variants:

  • The Hopsworks tables. Groups are stored in three new tables in the hopsworks database: the group itself, its people, its data.
  • The admin page. Where groups are created and edited.
  • The sync loop. A timer in RDRS that reads the group tables and turns them into objects on every RonDB cluster.
  • One kernel USER per group, holding the budget.

In other words, the whole pipeline from "admin saves a group" to "the cluster has a budget meter" is identical. The variants only disagree on the last step: at request time, who matches the request to the right meter.

3. Variant A: RDRS works out the group

In Variant A, RDRS answers the question itself, on every REST request, before the request reaches RonDB. From the group rows it builds two maps: person → groups and data → groups. For each request it looks the caller up in one map, the data up in the other, and takes the first level where the two agree (exact feature group first, then feature store, then ALL). It then tags the transaction with the group name directly.

  1. Alice's application sends a read with her API key.
  2. RDRS: who is this? The key belongs to Alice, of project Recommender.
  3. RDRS: what data? The URL names marketing.marketing_clicks_1.
  4. RDRS: which group contains both Alice and this data? recommender_team_rl.
  5. RDRS tags the transaction recommender_team_rl and sends it.
  6. The data node sees a tag that names an existing USER and charges it. Nothing new happens in RonDB at all.

Why Variant A is attractive

  • RonDB does not change at all. Only RDRS code is written.
  • The matching logic sits where the Hopsworks metadata already is.

Why Variant A is not enough

Its weakness is its location. Only traffic that passes through RDRS can be matched. SQL through the MySQL server goes straight to the data nodes, and the MySQL server cannot run this lookup itself: it tags a transaction once, before it knows which tables the statement will touch, and teaching it the lookup would mean rebuilding RDRS's whole Hopsworks-metadata cache inside mysqld (and a third copy in ClusterJ). So under Variant A, a user who connects with their database account bypasses the group budget entirely.

4. Variant B: RonDB works out the group

In Variant B, nobody at the edge needs to know about groups. Both entry points tag the transaction with the caller's account name, the same Project_username string the person uses to log in to MySQL. The MySQL server already does this today; RDRS tags the identical string. The data node then answers the group question itself, using small rule objects called aliases that the sync loop installed beforehand.

An alias is a dictionary object named after one account. It has no budget of its own, just an ordered list of rules: on this exact table, charge that group; on this database, charge that group; on everything, charge that group. When a tagged request arrives, the data node checks the rules in that order and the first match names the USER to charge. No match means the request runs unmetered, exactly as an unknown name does today.

  1. Alice reads marketing.marketing_clicks_1, through REST or through SQL. Either way the transaction is tagged Recommender_alice4f2.
  2. The data node sees the tag and the table together. The tag resolves to the alias Recommender_alice4f2, installed earlier by the sync loop.
  3. Rules in order: a rule for this exact table? none. A rule for this database? none. A rule for everything? yes, it points at recommender_team_rl.
  4. The transaction is charged to USER recommender_team_rl. Her REST reads and her SQL reads land on the same meter.

Why Variant B is the proposal

  • Every entry point is covered with one mechanism. SQL needs no change at all; the MySQL server keeps doing exactly what it does today.
  • The decision is made at the only place that always has both facts, the caller and the table, at the same time.
  • Per request the new cost is one rule walk, and only for names that are aliases.

What Variant B costs

  • RonDB gains a new dictionary object type (the alias), with its restart, backup and management-command plumbing.
  • One alias per member account: a big deployment can carry thousands of small objects. They hold no budget, so they cost the rate pool nothing, but the object count needs verifying (design doc 7.5).
  • A change becomes live at the next sync run plus, at worst, the clients' 60-second name-cache refresh.

5. Does RonDB read the Hopsworks tables? No.

"RonDB resolves" can sound as if the data nodes would query the hopsworks database to find out who Alice is and which project owns a feature group. They never do, in either variant. The work happens at two different times, done by two different components:

So "RonDB resolves" means: RonDB evaluates a few pre-installed rules. It does not mean RonDB understands projects, members, shares or feature groups. All of that is expanded away in RDRS before anything reaches the cluster, and what arrives is as plain as it gets: a name, a scope, and which budget to charge.

7. Which one the design proposes

The design proposes Variant B, because a budget that a user can step around by opening a SQL connection is not a budget. Variant A remains interesting for one reason: the Hopsworks tables, the admin page and the sync loop are the same work in both variants, so Variant A could ship first as a REST-only stepping stone while the kernel alias is built. Whether to ship that intermediate step at all was an open decision (design doc, section 14). Decided 2026-11-13: Variant B, with no REST-only intermediate step. The per-request matching of section 3 above is not built; RDRS tags the account name from the start.

For precise semantics see the design document: section 5 (Variant A's matching), 6.1 (why the MySQL server cannot do it), 6.2 to 6.4 (why the kernel can, and the full comparison), 7 (the alias object), 8 (the sync loop).
