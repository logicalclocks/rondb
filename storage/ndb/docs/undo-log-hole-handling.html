1. Why holes exist

LGMAN writes the UNDO log strictly sequentially, but with three properties that together make holes possible after a crash:

  • Up to MAX_UNDO_PAGES_OUTSTANDING = 512 pages (16 MByte) are written in a single FSWRITEREQ (write_log_pages()).
  • Only one write is outstanding per file at a time, and files are opened with OM_SYNC (or O_DIRECT with sync semantics), so each write chunk is durable before the next chunk is issued.
  • Within one chunk the file system may persist the pages in any order. A crash in the middle of a chunk can therefore leave any subset of that chunk's pages on disk.

Consequently the durable file after a crash is always a fully written prefix of completed chunks, followed by one partially persisted chunk in which holes can appear at arbitrary positions, followed by pages never reached this lap. The WAL protocol guarantees that no record in the partially persisted chunk was ever relied upon: m_last_synced_lsn only advances when a chunk completes, and PGMAN only flushes a data page after the UNDO log is synced up to that page's LSN.

2. What counts as a hole

A hole page below the log head takes one of two on-disk forms:

FormOn diskWhen it occurs
Unwritten All zeros, page type PT_Unallocated. When read during restart, LGMAN patches the in-memory copy to page LSN 0 with a synthetic UNDO_END record (execFSREADCONF). First lap of the log — the page was zero-initialized at file creation and the write that should have filled it never persisted.
Old-lap page A valid PT_Undopage whose page LSN is lower than the LSN of the first page of the file from the current lap. After the log has wrapped — the lost write should have overwritten data from a previous lap.

Both forms are recognized by a single rule, used consistently by the end-of-log search, the backward hole scan and UNDO log execution:

Hole rule. A page in file F is a hole if and only if page_lsn < F.m_start_lsn, where m_start_lsn is the page LSN of the file's first page as read during the file sort at restart. Unwritten pages (patched to LSN 0) and old-lap pages both satisfy this; every page written in the current lap has page_lsn ≥ m_start_lsn.

The rule depends on m_start_lsn > 0, i.e. on page 1 of the file being intact. Page 1 is written and fsynced at file creation (with an UNDO_END record) and rewritten as a single-page write at the start of every lap (write_log_pages() forces the first write in a file to one page), so m_start_lsn == 0 only occurs on a damaged file. See edge case E8.

3. The restart sequence

During a node or system restart, LGMAN processes each logfile group through the following phases before UNDO log execution begins:

1. Sort         read page 1 of every file, sort files by start LSN
                (FS_SORTING)
2. Binary search  locate a written→unwritten boundary in the newest file
                (FS_SEARCHING, find_log_head_in_file)
3. Forward end check  scan forward from the boundary, adopt any written page
                with a higher LSN as the new head
                (FS_SEARCHING_END, find_log_head_end_check)
4. Backward hole scan  scan up to 512 pages below the head, rewrite holes
                with filler pages
                (FS_SEARCHING_BACKWARD, start_backward_hole_scan)
5. Final read   reread the head page into the buffer
                (FS_SEARCHING_FINAL_READ, issue_final_head_read)
6. Execution    apply the UNDO log backwards down to the restored LCP
                (init_run_undo_log, get_next_undo_record)

4. Finding the end of the log

The binary search compares each probed page's LSN against the highest LSN found so far: higher means "move forward", lower or unwritten means "move backward". In a file with holes the written→unwritten boundary is not unique, so the search converges on some boundary — possibly below the true head.

The forward end check then reads pages one by one after the boundary. Whenever it finds a written page whose LSN is higher than the highest seen so far, it adopts that page as the new head. Two details are essential (both fixed in RONDB-1090 Phase 1):

  • The adopted page's LSN is recorded (m_online.m_lsn = last_lsn) so that m_next_lsn, m_last_read_lsn and m_last_synced_lsn are derived from the true head. A stale LSN here fails the page LSN validation when execution starts, and — worse — resumes logging with LSNs that already exist in the file, breaking the LSN monotonicity that the next restart's binary search depends on.
  • The scan window restarts at every adoption (scanned_pages = 0). If the binary search converged on a hole left behind by an earlier crash, the true head can be far more than 512 pages ahead; without the reset the scan would stop in the middle of a written region and adopt a false head, silently skipping synced UNDO records.

5. The backward hole scan

Holes below the head are harmless for the restart that finds them — but they are never rewritten during normal operation (the head only moves forward until the log wraps), so they would survive to hurt a later restart in two ways: its binary search can converge on the old hole, and its UNDO execution treats a hole encountered after records have been applied as a corrupt log (NDBD_EXIT_SR_UNDOLOG). The backward hole scan removes the problem at its source by making the log contiguous on disk again before execution starts.

read_backward_scan_page() walks one page at a time from the head downward, switching to the previous file in the group when it steps below page 1 (the same traversal as update_consumer_file_pos()). For each page read, find_log_head_backward_check() applies the hole rule:

  • Hole: remember the top of the current run (m_hole_top_idx) and keep scanning.
  • Written page, no run pending: keep scanning.
  • Written page directly below a run: the run is resolved. Its pages are rewritten with filler pages (section 6), then the scan resumes below the written page.

The scan limit is the UNDO log buffer size in pages (at least 512); the scan also terminates earlier when the next step would land on the head itself (possible only when the whole log is smaller than the window). The buffer-size limit, rather than the single-write limit of 512 pages, is needed because of file boundaries: the one-outstanding-write rule is per file, and buffer pages are only released by the in-file-order reply processing in execFSWRITECONF(). When the log head crosses a file boundary, the chunk is split — a large tail write into the old file, a solo page-1 write into the new file — and writes into the new file continue while the old file's tail write is still in flight. A crash in this state leaves the head in the new file with holes in the previous file's tail (this is the use case that requires the backward scan to cross file boundaries at all). In the extreme, one slow outstanding write per file leaves a partially persisted chunk at the tail of each of several consecutive files; the total is bounded by the number of buffer pages that existed at the crash, which is why the current buffer size is used as the scan limit.

6. Filler pages and LSN assignment

A resolved run of k holes above a written page with page LSN L is rewritten bottom-up with filler pages carrying page LSNs L+1, L+2, … L+k. Each filler is a valid PT_Undopage with m_words_used = 1 and a single record:

data[0] = ((UNDO_NOOP | UNDO_NEXT_LSN) << 16) | 1

i.e. a Type-1 record of length 1 whose LSN is implicitly "previous record's LSN minus one". UNDO_NOOP (= 18) is skipped without action by execute_undo_record().

Why ascending LSNs are always safe. Every written UNDO page contains at least one record (a record that does not fit in a page is placed entirely in the next page — records never span pages). The k lost pages of the run therefore contained at least k records, whose LSNs lay strictly between L and F, the LSN of the first record of the written page above the run. Hence F ≥ L+k+1, and the filler LSNs L+1 … L+k fit in the gap without colliding with any real LSN, keep the file strictly LSN-monotone for future binary searches, and form a contiguous chain with the page below. No duplicate LSNs are created, so the debug-build assertion in get_next_undo_record() (ndbassert(page_lsn < m_last_read_lsn - 1)) is never violated.

Fillers are written one page at a time through the shared restart buffer page, each write completing (including fsync, files are OM_SYNC) before the next is issued. Completions are routed by file state (FS_SEARCHING_BACKWARD) in execFSWRITECONF() to hole_filler_write_conf().

7. UNDO log execution across holes and fillers

Execution consumes pages backward from the head. On entering a new page, get_next_undo_record() validates the page LSN against the expected value m_last_read_lsn - 1:

  • Exact match: normal case, consume the page.
  • Lower, but ≥ the file's start LSN: pages were lost above this page (the LSN gap). Accept, log "Continue applying log records in written page", and resynchronize m_last_read_lsn = page_lsn + 1.
  • Lower than the file's start LSN: a hole. Allowed only while no record has been applied yet (m_applied == false) — by WAL, every record in the fuzzy region is a no-op in DBTUP, so real applications can only start below it. A hole after an applied record is a corrupt log: progError(NDBD_EXIT_SR_UNDOLOG).
  • Higher than expected: forbidden (ndbrequire at the page LSN validation) — this is what the Phase 1 fix prevents from triggering spuriously.

8. Edge cases

All edge cases handled by the new code, with the mechanism that covers each:

Edge caseHandling
E1 Binary search converges below the last written page (e.g. at the boundary before a hole). The forward end check adopts every written page with a new highest LSN, records its LSN, and restarts its 512-page window at each adoption, so the true head is always reached — even when the convergence point is a leftover hole from an earlier crash with more than 512 written pages beyond it.
E2 Binary search converges directly on the true head. The end check finds no higher page; the binary search branch already recorded the head LSN. Both convergence paths produce identical state before the backward scan starts.
E3 Multiple hole runs below the head (e.g. written–hole–written–hole–written). Each run is resolved independently by the written page directly below it and rewritten before the scan continues. Filler LSNs of different runs cannot collide since each run's fillers stay within its own LSN gap.
E4 A run of several adjacent holes. Rewritten bottom-up with ascending LSNs L+1 … L+k; the ≥-one-record-per-page argument guarantees the LSNs fit below the first record of the page above (see section 6).
E5 Run still pending when the scan crosses a file boundary. Impossible for a genuine partial-write hole: page 1 of every file is written and fsynced in a single-page write of its own before any other page of that file, so a hole at page 1 implies the head cannot be above it in that file. A pending run at a boundary is therefore never-written territory; it is dropped with a log message and nothing is rewritten.
E6 Run still pending when the scan limit is reached (buffer size in pages, minimum 512). Same reasoning: real holes always have a written page below them within the window (the durable prefix). The pending run is first-lap never-written territory (the log has not wrapped yet) and is left untouched. If the buffer size was reduced since the crash, a hole beyond the smaller window could be missed — benign: it is simply left unrewritten, i.e. the behaviour of versions without the backward scan.
E7 The whole log is smaller than the scan window (young log, or small wrapped single-file log). The scan stops when the next step would land on the head page itself. Without this guard the scan would continue circularly above the head and could rewrite pages in the forward region — where new logging resumes — with LSNs that collide with upcoming m_next_lsn values.
E8 m_start_lsn == 0 — the file's first page reads as unallocated (only possible on a damaged file; observed in the original RONDB-1090 incident as storage-level write loss). With start LSN 0 the hole rule cannot distinguish holes from written pages (every LSN is ≥ 0), so the scan classifies every page as indeterminate and rewrites nothing in that file. No run is ever started there. Recovery proceeds as before Phase 2.
E9 Scan crosses into the previous file of the group. Required use case: a crash while the log head crossed a file boundary — the split chunk leaves the head in the new file (page 1 is written in a solo write, and further writes into the new file proceed while the old file's large tail write is still in flight) with holes from that tail write in the previous file. The scan follows the same file traversal as execution (files.prev, wrapping to files.last). The left file's state is restored to FS_EXECUTING; the entered file is set to FS_SEARCHING_BACKWARD so read/write completions route correctly. Hole classification uses the entered file's own m_start_lsn, and hole runs still resolve within a single file (E5). The scan limit is sized by the buffer (section 5) so that the tails of several consecutive files are covered.
E10 Previous file was not written in the current lap (multi-file group, head early in the circular order). Its pages carry LSNs ≥ its own (old) m_start_lsn, so they are classified as written and nothing is rewritten — correct, since that file's content is internally consistent old data that execution never reaches.
E11 Head at page 1 of a file. The first backward step immediately switches to the previous file's last page. (Also handled downstream: find_log_head_complete() places the tail in the previous file.)
E12 Crash while filler pages are being written. Idempotent. Completed fillers are ordinary written pages for the next recovery; remaining holes are found and rewritten again. A torn filler is harmless: its single record and m_words_used = 1 live in the first sectors of the page, and the rest of the page is unused.
E13 Old hole crossed by execution after records were applied (crash–restart–crash with no LCP in between — the multi-restart false positive). Cannot occur anymore: the hole was rewritten during the earlier restart, so execution sees a written filler page and takes the tolerant LSN-gap branch, which is legal regardless of m_applied. This is why the gap branch must stay lenient for written pages.
E14 Hole directly below the head page. First scanned page starts a run immediately; the page above the run is the head itself, whose first-record LSN bounds the filler LSNs exactly as in the general case.
E15 End of log with no LCP ever completed. Unchanged from before: execution stops at the initialization-time UNDO_END record in page 1. Fillers never contain UNDO_END, so they can never terminate execution early.
E16 Downgrade. An UNDO log containing UNDO_NOOP filler records cannot be executed by binaries without RONDB-1090 Phase 2 — they hit the unknown-type ndbabort() in execute_undo_record(). A downgrade requires an initial node restart (or a log guaranteed free of fillers).

9. Testing

Error inserts (LGMAN range 15000–15999):

CodeEffect
15002 On the next fully-in-file UNDO log write of ≥ 3 pages: zero the second-to-last page of the chunk in the buffer before the write (creating a durable hole with a written, higher-LSN page after it) and arm 15003.
15003 Crash the node in execFSWRITECONF() once the tampered write (including fsync) has completed — guaranteeing the hole geometry is on disk.

Test cases in testSystemRestart (autotest suite daily-basic--04, disk table D2):

  • SR_DD_UndoHole — load disk data rows, arm 15002 on a random node, update until it crashes itself, restart it across the hole, verify the data, then perform a clean second restart to prove logging resumed with correct LSNs.
  • SR_DD_UndoHoleMulti — the same crash/restart cycle repeated back to back (default 3 cycles, property HoleCycles) on the same node, so later cycles recover over an UNDO log that already contains filler pages from earlier cycles, followed by a final clean restart.

Log signatures of the mechanisms in a node's out-log:

LGMAN: ERROR_INSERT 15002: zeroing page P in write of N pages ...   (crash setup)
LGMAN: Found written page after end found by binary search ...      (forward end check)
LGMAN: Rewriting UNDO log hole pages X to Y in file F with filler
       pages, first filler LSN L                                    (backward scan)
LGMAN: Rewrote N UNDO log hole pages with filler pages              (scan summary)
LGMAN: Backward scan dropping unresolved hole run up to page P ...  (E5/E6)
