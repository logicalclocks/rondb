## Observations (not defects)

- Run 2 (complete, unpushed MySQL, 1 and 8 threads): the collect RonSQL template is 1.3× faster than Hopsworks' ROW_NUMBER production twin; the snowflake production twins (nested PK joins, 126 / 144 µs) are 4× faster than the RonSQL templates (F13); at 8 threads point shapes still tie (~290 µs, ~26–27 k q/s), snowflake narrows to 2.2–2.9×, batch IN lists widen (F12: the table scans serialise on the data nodes, T8/T1 1.3–2× against 3× for MySQL).

- Point aggregates (S1, S2, S4, S5, S9-shaped, S10) and collect (S6b) are at parity with MySQL: 100–120 µs on both, ~70 µs data node + ~30 µs RDRS/HTTP/client.  RonSQL p99 130–160 µs.
- Interpreter vs JIT (`CompiledInterpreter OFF/ON`): no measurable difference on any fs_hw entry; the batch scans gain ≤ 3 %.
- RDRS schema cache: `load` 1–2 µs per request (warm); the ~400 µs `listIndexes` per request of `ronsql_bench_matrix.md` §"Findings" is not present in this run.
- MySQL pushdown aggregation is slower than unpushed on the batch IN lists (0.99 vs 0.25 ms at 10 keys, 169 vs 42 ms at 1000: one pushed scan per key range vs MRR reads) — the pushed path is not the right comparison baseline for S3.
- `collect5_cte` (S6 Hopsworks form) rejects with F0 as expected; MySQL runs it in ~120 µs.

## Run 4 observations (2026-09-22, benchmark computer; artifacts `bench_results/2026-09-22-benchbox-run4/`; reading `m3_plan.md` §6)

- Configuration caveat: the data nodes ran the suite's default `NumCPUs=4` thread configuration (2 LDM threads per node, 4 fragments per table) on 15-CPU binding sets; every scan-bound number is a 4-LDM number.
- F13 closed (above); F0's CTE collect form costs the same as the direct form (76 / 84 µs vs 77 / 78 µs).
- Every `fs_hw` point shape 76–93 µs (`firstbatch` 36–60 µs, `http+client` 28–29 µs), p99 123–150 µs outside the F25 set.
- The F25 stall inflates MySQL's side more than RonSQL's (its PK read 439 µs, point aggregate 210 µs, nested-join snowflakes ~1 ms, `snow1_batch100` 45 ms), so run-4 RonSQL/MySQL ratios are not comparable with the laptop's; run 4 is the box's baseline.
- `offline_fs`: RonSQL 1.1–2.0 s vs MySQL 2.1–82 s; `core_scan_agg` 428 ns per row per LDM over 6 M rows; AVG costs nothing extra; the client-side sort of `fs_history` adds ~200 ns/row over `core_pass_range`'s 274 ns/row drain.
- Compiled interpreter: the programs ran compiled (`core_scan_agg` 6 M rows executed per request through 4 reused programs, 0 fallbacks) and changed nothing on any entry (±10 %); programs with embedded constants recompile per request (`fs_hw_snow1_batch100` 1.97 compiles/req, 0.84×).
- Throughput reached only the `fs` category: `fs_point` 14.2 k vs 20.8 k q/s, `fs_floor` 42.8 k vs 56.1 k (the point-shape ceiling); the scan-heavy CTE shapes scale 1.7–2.7× from 1 to 8 clients on 4 LDM threads.
- `fs_hw_hash_point` failed for want of `--hash-twin` (driver fixed).
